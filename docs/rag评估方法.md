# 一、RAG系统评估整体设计
## 1.1 系统链路拆分
RAG效果由**检索正确性**与**生成正确性**共同决定，任何单一指标无法完整评价系统，因此按链路拆分评估：
```
用户Query → 检索模块（向量库/关键词检索/混合检索）→ 召回上下文Context → LLM生成回答 → 最终Answer
```
- 检索阶段问题：召回不相关、漏召回关键信息、排序靠后
- 生成阶段问题：幻觉、答非所问、信息缺失、格式错误
- 端到端问题：整体可用性、用户满意度

## 1.2 评估分层体系
| 评估层级 | 作用 | 适用阶段 |
|---------|------|---------|
| 细粒度单阶段指标 | 定位模块问题（检索/生成） | 开发迭代、模型调优 |
| 自动化综合指标 | 版本对比、回归测试 | 每日/每周构建验证 |
| 人工专家评估 | 校准自动指标、保证业务合规 | 上线前、重大版本 |
| 线上真实用户反馈 | 验证真实业务效果 | 上线后持续运营 |

# 二、检索模块详细评估方案
检索是RAG的核心瓶颈，**检索失败则生成必然失效**，本部分为项目可直接使用的检索评估细则。

## 2.1 检索评估核心指标（含业务定义）
### 2.1.1 基础召回与精确率
1. **召回率 Recall@k**
   - 定义：在前k条召回结果中，包含**标准答案对应原文片段**的比例
   - 项目常用：Recall@1、Recall@3、Recall@5、Recall@10
   - 业务意义：衡量是否“找得到”关键信息，避免漏召回
2. **精确率 Precision@k**
   - 定义：前k条召回结果中，与Query语义相关的文档占比
   - 业务意义：衡量上下文是否“干净”，减少冗余噪声

### 2.1.2 排序质量指标
1. **MRR（Mean Reciprocal Rank）**
   - 公式：`MRR = avg(1 / rank_i)`，rank_i为第i个Query首个相关文档位置
   - 意义：优先保证高价值内容排在最前，直接影响LLM读取效率
2. **NDCG@k**
   - 支持分级相关性标注（0无关/1弱相关/2强相关）
   - 意义：更贴合业务，对强相关文档赋予更高权重

### 2.1.3 RAG专用上下文指标
1. **上下文相关性 Context Relevance**
   - 定义：召回片段中**能直接用于回答问题**的有效信息占比
   - 判定标准：
     - 5分：所有内容均为关键信息，无冗余
     - 3分：部分冗余，但关键信息完整
     - 1分：大量无关内容，关键信息极少
2. **上下文覆盖率 Context Coverage**
   - 定义：检索结果覆盖问题所需**全部知识点**的比例
   - 意义：避免多跳问题、复合问题因信息不全导致生成错误

## 2.2 检索评估数据集构建（项目实操）
1. **数据集规模**
   - 测试集：≥200条Query（覆盖高频、低频、复杂、边缘问题）
   - 校验集：≥50条，用于快速验证
2. **标注规范**
   - 每条Query对应：标准问题+标准答案+关键原文chunk_id
   - 相关性分级：0（无关）、1（弱相关）、2（强相关）
3. **问题类型覆盖**
   - 事实查询：XX规则是什么？
   - 多条件查询：同时满足A和B的情况
   - 摘要类：总结某章节内容
   - 对比类：A与B的区别
   - 边缘/噪声query：无意义提问、错别字、口语化提问

## 2.3 检索评估执行步骤
1. 构建离线测试Query集与标注文档
2. 批量执行检索，记录top-k召回结果
3. 脚本自动计算Recall@k、MRR、NDCG@k
4. LLM自动打分Context Relevance/Coverage
5. 输出检索问题Top榜单：漏召回、排序靠后、无关召回

# 三、生成模块详细评估方案
生成评估核心目标：**无幻觉、忠于原文、回答完整、符合业务格式**。

## 3.1 生成核心评估指标
### 3.1.1 忠实度 Faithfulness
- 定义：生成内容**100%基于检索上下文**，无编造、无脑补、无外部知识引入
- 分级判定：
  - 完全忠实：无幻觉
  - 轻微偏差：表述略有出入，不影响理解
  - 严重幻觉：编造规则、数据、案例

### 3.1.2 回答相关性 Answer Relevance
- 定义：回答是否直接针对用户问题，不跑题、不冗余
- 典型负例：用户问A，回答大量讲B

### 3.1.3 回答完整性 Completeness
- 定义：是否覆盖问题**所有关键信息点**
- 例：问题包含3个疑问点，回答需全部覆盖

### 3.1.4 正确性 Correctness
- 定义：与业务标准答案一致，可用于直接决策
- 多用于合规、金融、法律、政务等高要求场景

### 3.1.5 可读性与格式
- 流畅度、无乱码、符合业务格式（表格/条目/编号）

## 3.2 LLM-as-Judge 自动评判规则（可直接写入Prompt）
```
你是RAG系统专业评估员，请根据【用户问题】、【检索上下文】、【模型回答】，按以下维度打分（1-5分）并给出理由：

1. 忠实度：是否完全基于上下文，无幻觉
2. 相关性：是否精准回答问题
3. 完整性：是否覆盖所有关键信息
4. 可读性：表达是否流畅规范

输出格式：
忠实度：x/5
相关性：x/5
完整性：x/5
可读性：x/5
问题说明：xxx
```

# 四、自动化评估工具落地（RAGAS / TruLens）
## 4.1 RAGAS 项目接入方案
RAGAS是目前工业界最通用的RAG自动化评估框架，支持全指标计算。

### 4.1.1 支持指标
- 检索：Context Precision、Context Recall、Context Relevance、Context Entailment
- 生成：Faithfulness、Answer Relevance、Answer Correctness、Answer Similarity

### 4.1.2 项目接入步骤
1. 环境安装
```bash
pip install ragas langchain chromadb
```
2. 构建评估数据集格式
```python
# 必需字段：question, answer, contexts, ground_truth
from datasets import Dataset
dataset = Dataset.from_list([
    {
        "question": "xxx",
        "ground_truth": "xxx",
        "contexts": ["chunk1","chunk2"],
        "answer": "llm生成结果"
    },
    # ...更多测试样本
])
```
3. 执行评估 & 输出报告
```python
from ragas import evaluate
from ragas.metrics import (
    faithfulness, answer_relevance, context_recall, context_precision
)
result = evaluate(
    dataset,
    metrics=[faithfulness, answer_relevance, context_recall, context_precision]
)
print(result.to_pandas())
```
4. 结果用途：版本迭代对比、构建质量门禁、失败样本筛选

## 4.2 TruLens 接入方案
适合需要**自定义评估规则、可视化看板、长期追踪**的项目：
- 支持自定义Prompt评判规则
- 内置Dashboard查看检索+生成链路
- 可记录每一轮调用的chunk、prompt、得分、耗时

# 五、人工评估方案（上线必做）
## 5.1 人工评估流程
1. 抽样规则：每日自动评估低分样本+随机抽样
2. 评估人员：业务专家+标注人员
3. 打分表：固定维度+权重
4. 仲裁机制：争议答案由业务负责人终审

## 5.2 人工评估打分表（可直接使用）
| 指标 | 权重 | 5分 | 3分 | 1分 |
|------|------|-----|-----|-----|
| 检索相关性 | 20% | 完全相关 | 部分冗余 | 大量无关 |
| 忠实度（无幻觉） | 30% | 完全无编造 | 轻微偏差 | 严重错误 |
| 回答完整性 | 20% | 信息全覆盖 | 缺次要信息 | 缺关键信息 |
| 可读性与格式 | 15% | 极佳 | 一般 | 混乱 |
| 业务可用性 | 15% | 可直接使用 | 需修改 | 不可用 |

## 5.3 质量门槛标准（可按业务调整）
- 企业通用标准：综合得分≥4.0
- 高合规场景：综合得分≥4.5，幻觉率=0
- 检索Recall@3 ≥90%

# 六、项目落地全流程（从0到1执行步骤）
## 阶段1：准备工作（1-2天）
1. 梳理业务场景，确定高频/核心/风险问题
2. 构建200+测试集，完成标准答案与chunk标注
3. 接入RAGAS/TruLens自动化评估环境

## 阶段2：基线评估（1天）
1. 跑通当前版本检索+生成全链路
2. 输出 baseline 指标报告
3. 定位短板：检索差 / 生成差 / 都差

## 阶段3：迭代优化（持续）
- 检索差：优化向量模型、chunk切分、检索策略（重排/混合检索）
- 生成差：优化prompt、增加格式约束、增强上下文筛选
- 每轮优化后执行自动化评估，对比指标提升

## 阶段4：上线验证（1天）
1. 人工全量复核测试集
2. 确认无重大幻觉、无业务错误
3. 设定线上监控指标

## 阶段5：线上持续评估
1. 日志埋点：记录query、召回chunk、生成answer、耗时
2. 定期抽样人工复核
3. 按月更新测试集，覆盖新业务问题

# 七、常见问题定位与指标对应
| 现象 | 对应异常指标 | 优化方向 |
|------|--------------|---------|
| 经常漏关键信息 | Recall@k 低、Context Coverage 低 | 优化向量模型、增大召回数、加入关键词检索 |
| 上下文噪声大 | Context Relevance 低、Precision 低 | 优化chunk切分、使用重排模型、过滤低相关片段 |
| 回答经常编造 | Faithfulness 低 | 加强prompt约束、增加事实校验、精简上下文 |
| 答非所问 | Answer Relevance 低 | 优化query理解、增强检索相关性 |
| 回答不完整 | Completeness 低 | 提升召回数量、补充多文档关联 |
