## ⚠️ 用户需求声明 (实施前必读)

> **以下需求来自用户直接反馈，实施方案必须严格遵守，不可偏离：**

### 🎯 用户画像
- **用户是懂技术的**（配置管理、提示词管理、回溯测试的使用者都有技术背景）
- **不是小白用户**，不需要"一键优化"式的傻瓜操作

### 🚫 禁止事项

1. **禁止替用户做决策** — 推荐只是参考，不能自动应用配置
2. **禁止隐藏决策依据** — 每个推荐必须解释"为什么改"
3. **禁止跳过对比环节** — 用户必须能看到改动前后的差异
4. **禁止省略影响分析** — 用户需要知道"改了会有什么后果"
5. **禁止兼容历史版本** — 项目未上线，不存在旧数据/旧接口/旧页面迁移需求，任何方案不得包含兼容性代码、迁移脚本、双版本并行逻辑

### ✅ 必须事项
1. **必须展示前后对比** — 配置值 diff、提示词内容 diff
2. **必须说明改动原因** — 触发条件、指标短板、Bad Case 分析
3. **必须预览改动影响** — 预期指标变化、风险警告、历史参考
4. **必须让用户手动确认** — 采纳 → 审查 → 保存为新版本，三步分离
5. **必须支持回溯** — 每次修改留版本记录，可回滚

### 💡 核心原则
```
系统角色：辅助决策者（提供信息、分析、建议）
用户角色：最终决策者（审查、判断、执行）

错误设计：检测到问题 → 自动应用推荐配置
正确设计：检测到问题 → 展示原因+对比+影响 → 用户决定是否采纳
```

## 1. 第一性原理分析

### 1.1 用户的核心任务是什么？

用户打开这个页面，本质上要完成 **3 个核心任务**：

| 任务 | 用户心智模型 | 当前页面问题 |
|------|-------------|-------------|
| **1. 诊断** | "我的 RAG 检索质量怎么样？哪里有问题？" | 指标全 0，无诊断能力 |
| **2. 调优** | "我调了参数，效果有没有变好？" | 无对比分析，无法验证 |
| **3. 数据** | "我要导入书籍生成测试用例" | 书籍导入失败，核心工作流中断 |

### 1.2 当前页面的本质问题

**不是"功能不够"，而是"工作流断裂"**：

```
期望工作流：
导入书籍 → 生成测试用例 → 运行诊断 → 查看问题 → 调参 → 验证效果 → 循环

当前工作流：
导入书籍 → ❌ 失败 → 无法生成用例 → 无法运行诊断 → 页面空白
```

### 1.3 书籍导入失败的根因（已定位）

| 失败点 | 严重程度 | 根因 |
|--------|---------|------|
| **EventSource 相对路径** | CRITICAL | 前端 dev server (5173) 和后端 (8000) 端口不同，SSE 请求 404 |
| **PDF/EPUB 二进制读取** | CRITICAL | 用文本模式读取二进制文件，产生乱码 |
| **DASHSCOPE_API_KEY 未配置** | CRITICAL | 环境变量缺失，LLM 调用失败 |
| **Redis 依赖问题** | HIGH | SSE 依赖 Redis Pub/Sub，Redis 未启动时消息丢失 |
| **asyncio.create_task 无引用** | HIGH | Task 可能被 GC，导致任务静默终止 |

### 1.4 批量测试失败的根因（已定位）

| 问题 | 严重程度 | 根因 |
|------|---------|------|
| **前端无 SSE 监听** | CRITICAL | 前端发 POST 后等待 HTTP 响应，但批量测试远超 30 秒超时 |
| **runSingleTest 调用 runAllTests** | CRITICAL | 代码 Bug：`_caseId` 参数被忽略，实际运行了所有测试 |
| **asyncio.create_task 无引用** | HIGH | 后台任务可能被 GC 回收 |
| **RetrievalService 重复初始化** | HIGH | 每个用例创建新实例，并发时耗尽连接池 |
| **分布式锁对唯一 run_id 无意义** | MEDIUM | 增加复杂度，Redis 故障时导致失败 |
| **complete_test_run 读到不完整数据** | MEDIUM | 聚合指标可能不准确 |
| **SSE 心跳队列内存泄漏** | LOW | 前端无消费，队列无限增长 |
| **前端 API 超时 30 秒** | HIGH | 批量测试通常远超 30 秒 |

## 2. 重构策略

### 2.0 Phase 0: 核心工作流修复 (实施前提)

> **需求来源**: 1.3 和 1.4 节已定位的 12 个根因，必须在 Phase 1 新功能实施前修复，否则核心工作流断裂。

#### 2.0.1 书籍导入修复需求

| 根因 | 修复需求 | 验收标准 |
|------|---------|---------|
| EventSource 相对路径 | 前端 SSE 连接必须使用绝对路径 (含协议、域名、端口) | 开发环境 (5173→8000) 和生产环境 SSE 连接均成功 |
| PDF/EPUB 二进制读取 | 系统必须使用专用解析器处理不同格式 (PDF→pypdf2, EPUB→ebooklib, TXT→文本读取) | 上传 PDF/EPUB/TXT 三类文件均能正确提取文本内容 |
| DASHSCOPE_API_KEY 未配置 | 系统启动时必须校验 LLM 环境变量，缺失时在前端展示明确错误提示 | 环境变量缺失时，前端显示"LLM 服务未配置，请联系管理员" |
| Redis 依赖问题 | 系统必须检测 Redis 可用性，不可用时降级到内存队列模式 | Redis 未启动时，SSE 推送仍可通过内存队列正常工作 |
| asyncio.create_task 无引用 | 后台任务必须保持强引用，防止被 GC 回收 | 长时间任务 (10min+) 不会静默终止 |

#### 2.0.2 批量测试修复需求

| 根因 | 修复需求 | 验收标准 |
|------|---------|---------|
| 前端无 SSE 监听 | 批量测试必须通过 SSE 推送进度，前端不得等待 HTTP 响应 | 前端能实时显示进度百分比和当前处理用例 |
| runSingleTest 调用 runAllTests | 单个用例测试必须严格只运行该用例，不得执行其他用例 | 传入 caseId 后，仅执行对应用例 |
| RetrievalService 重复初始化 | 批量测试必须复用同一个 RetrievalService 实例 | 128 用例测试不出现连接池耗尽 |
| 分布式锁对唯一 run_id 无意义 | 批量测试不得依赖分布式锁，应使用本地并发控制 | Redis 不可用时批量测试仍能执行 |
| complete_test_run 读到不完整数据 | 测试完成后必须等待所有用例结果聚合完毕再计算指标 | 报告指标与用例执行结果一致 |
| SSE 心跳队列内存泄漏 | 前端断开连接时，后端必须清理对应心跳队列 | 前端刷新页面后，后端队列内存释放 |
| 前端 API 超时 30 秒 | 前端发起批量测试后不得设置 HTTP 超时，改为依赖 SSE 进度事件 | 批量测试超过 30 秒不触发前端超时错误 |

### 2.1 核心原则

| 原则 | 说明 | 落地 |
|------|------|------|
| **零历史包袱** | 项目未上线，不存在旧数据/旧接口/旧页面 | 全新设计，不写兼容代码、不写迁移脚本、不做双版本并行 |
| **以测试集为核心** | 所有操作围绕测试集展开 | 测试集 → 用例 → 运行 → 报告 → 调优 → 复测 |
| **分层递进诊断** | 从快速规则到深度 LLM 诊断 | 规则引擎 → 历史对比 → LLM 诊断 |
| **报告驱动调优** | 报告页面直接集成配置/提示词编辑 | 推荐模式面板，一键应用 |
| **渐进式披露** | 从概览到详情，不一次性展示所有信息 | 推荐区 + 其他配置区分离 |

## 3. 核心功能需求

### 3.1 系统定位

这是一个**以测试集为核心的 RAG 评估平台**，核心工作流：

```
创建/选择测试集 → 运行测试集 → 生成评估报告 → 校验诊断 → 输出调优建议 → 应用建议 → 复测验证
```

### 3.2 分层递进架构

```
┌─────────────────────────────────────────────────────────┐
│                    评估报告 (Report)                      │
│  汇总所有校验结果，生成结构化诊断报告                        │
└──────────┬───────────────────────────────────────────────┘
           ▼
┌─────────────────────────────────────────────────────────┐
│              校验引擎编排层 (ValidationOrchestrator)       │
│  协调 6 层校验，支持异步/并行/降级执行                       │
└──┬────┬────┬────┬────┬──────────────────────────────────┘
   ▼    ▼    ▼    ▼    ▼
 Layer1 Layer2 Layer3 Layer4 Layer5 Layer6
 规则   历史   LLM   数据   检索   验证
 引擎   对比   诊断   质量   链路   保障
```

### 3.3 校验层定义 (6 层 / 13 种校验)

| 层级 | 名称 | 校验方式 | 执行时机 | 延迟 | 成本 | 可降级 |
|------|------|---------|---------|------|------|--------|
| **Layer 1** | 规则引擎 | 指标阈值触发 → 参数建议 | 测试完成后立即 | <50ms | 无 | ❌ 必须执行 |
| **Layer 2** | 历史对比 | 配置变更→指标变化关联 + 相似匹配 | 有≥1次历史运行时 | <100ms | 无 | ❌ 必须执行 (无历史时展示基准报告) |
| **Layer 3** | LLM 诊断 | Bad Case 语义分析 + 根因归类 | Bad Case≥5 时 | 1-3s | LLM 调用 | ✅ API 异常时跳过，显示"LLM 服务不可用" |
| **Layer 4** | 数据质量 | Golden覆盖度 + 分块质量 + 文档时效 | 测试完成后 | <500ms | 无 | ❌ 必须执行 |
| **Layer 5** | 检索链路 | Embedding质量 + 意图识别 + 错误模式聚类 | 测试完成后 | <1s | 无 | ⚠️ Embedding 校验可跳过，意图和聚类必须执行 |
| **Layer 6** | 验证保障 | 回归检测 + 交叉验证 + 成本效果 + A/B影子 | 按需触发 | 5-30s | 可选 LLM | ✅ 默认不执行，用户手动触发 |

### 3.4 核心数据模型

```python
class TestSet(Base):
    """测试集 - 测试用例的集合"""
    id, name, description
    source_type (book_generated / json_imported / manual)
    source_document_id (FK → Document, 可选)
    created_at, updated_at
    # total_cases 通过 COUNT(test_set_cases) 实时计算，不存储冗余字段

class TestSetCase(Base):
    """测试集-用例关联表 - 支持用例被多个测试集复用"""
    id, test_set_id (FK → TestSet), case_id (FK → TestCase)
    added_at, added_by

class TestCase(Base):
    """测试用例 - 单个测试条目"""
    id, query (str), age_months (int), domain (TestDomain enum)
    expected_document_ids (JSON)           # Golden Dataset: 期望命中的文档 ID 列表
    expected_key_points (JSON)             # 期望知识点列表
    source_draft_id (FK → TestCaseDraft, 可选)
    created_at
    # 注意: 不再包含 test_set_id，用例通过 TestSetCase 中间表与测试集关联

class ConfigVersion(Base):
    """配置版本 - 记录某时刻的完整 RAG 配置快照"""
    id, version_number (INT)               # 全局自增序号，用于展示和排序
    config_snapshot (JSON)                 # 完整配置快照，包含所有 RAG 参数
    created_at, created_by, change_summary
    # 注意: 不将参数拆为独立列，避免新增参数时 ALTER TABLE
    # config_snapshot 示例: {"bm25_top_k": 10, "vector_top_k": 10, "fusion_threshold": 0.25, ...}

class PromptVersion(Base):
    """提示词版本 - 记录某时刻的提示词内容"""
    id, prompt_key (str)                   # 如 query_rewrite, query_routing
    version (VARCHAR(64))                  # 版本号字符串，如 "v3", "v4-new-constraint"
    version_number (INT)                   # 该 prompt_key 下的自增序号，用于排序
    content (TEXT)                         # 提示词完整内容
    created_at, created_by, change_summary
    # 唯一约束: UNIQUE(prompt_key, version)

class ConfigChangeSet(Base):
    """配置变更集 - 原子保存配置+提示词的整体版本"""
    id, change_set_number (INT)            # 全局自增序号，格式 CS-{YYYYMMDD}-{seq}
    config_version_id (FK → ConfigVersion)
    prompt_version_ids (JSON)              # MySQL JSON 类型，存储 [1, 2, 3]
    created_at, status (committed / rolled_back)
    rollback_reason (str, 可选)

class TestReport(Base):
    """评估报告 - 每次运行生成一份报告"""
    id, run_id (FK → TestRun), test_set_id (FK → TestSet)
    config_version_id (FK → ConfigVersion)
    prompt_version_snapshot (JSON)         # {prompt_key: {version, version_number}, ...}
    overall_score, precision, recall, f1, mrr, ndcg
    layer1_results (JSON), layer2_results (JSON), layer3_results (JSON)
    layer4_results (JSON), layer5_results (JSON), layer6_results (JSON)
    validation_duration_ms (JSON)          # {layer1: 45, layer2: 89, ...}
    tuning_suggestions (JSON), created_at
    # 注意: TestReport 单向 FK → TestRun，TestRun 不持有 report_id，避免循环依赖

class TuningSuggestionRecord(Base):
    """调优建议记录"""
    id, report_id (FK → TestReport), param_name, current_value, suggested_value
    action, reason, expected_effect, priority
    source (rule_engine / history / llm)
    safe_range (JSON), applied (bool), applied_config_version_id
    ignored (bool), ignored_at, ignore_scope (report / test_set)  # 支持报告级/测试集级忽略

class PromptSuggestionRecord(Base):
    """提示词优化建议"""
    id, report_id (FK → TestReport), prompt_key
    current_version_id, suggested_version_id
    reason, expected_effect, priority, source
    suggestion_type (add_constraint / rewrite / parameter_tweak)
    applied (bool), applied_version_id
    ignored (bool), ignored_at, ignore_scope (report / test_set)

class TestRun(Base):
    """测试执行记录"""
    id, name, status, test_set_id (FK → TestSet)
    config_version_id (FK → ConfigVersion)
    overall_precision, overall_recall, overall_f1, overall_mrr, overall_ndcg
    total_test_cases, passed_test_cases, failed_at_case (可选)
    # 注意: 不持有 report_id FK，通过 TestReport.run_id 反向查询
    created_at, completed_at

class TestCaseDraft(Base):
    """测试用例草稿 - 书籍导入后生成的待审核用例"""
    id, source_document_id (FK → Document)
    query (str), age_months (int), domain (TestDomain enum)
    expected_key_points (JSON)
    status (draft / reviewed / rejected / imported)
    reviewed_by, reviewed_at, created_at

class IntentAnnotation(Base):
    """意图人工标注 - Layer 5b 意图识别准确率校验的数据来源"""
    id, case_id (FK → TestCase)
    intent_type (str)                      # 如: factual_query, how_to, comparison, definition
    annotated_by, annotated_at
```

**TestRun 状态枚举**:

| 状态 | 说明 | 触发时机 |
|------|------|---------|
| `pending` | 等待执行 | 创建 TestRun 后 |
| `running` | 正在执行 | SSE `run_started` 事件触发 |
| `completed` | 执行完成 | 所有用例执行完毕 |
| `failed` | 执行失败 | 异常中断，记录 `failed_at_case` |
| `cancelled` | 用户取消 | 用户主动取消运行 |

**TestCaseDraft 状态机**:

```
┌───────┐   通过    ┌─────────┐   归入    ┌─────────┐
│ draft ├──────────►│ reviewed├──────────►│ imported│
└───┬───┘           └─────────┘           └─────────┘
    │ 拒绝               │ 取消归入
    ▼                    ▼
┌──────────┐        ┌───────┐
│ rejected │        │ draft │ (重新编辑后)
└──────────┘        └───────┘
```

### 3.5 测试集运行工作流

```
用户操作                          后端处理
─────────                        ─────────
1. 选择测试集
   ↓
2. 点击"运行测试"              →  创建 TestRun (status=pending) → 执行每个用例 → 收集结果
3. 等待完成 (SSE 进度推送)      ←  SSE: progress/case_result/test_completed
   ↓
4. 查看报告                    →  触发 6 层校验 → 生成 TestReport → SSE: report_ready
5. 查看调优建议                →  报告内嵌
   ↓
6. 应用建议 (可选)             →  创建 ConfigChangeSet (原子事务) → 热更新
   ↓
7. 复测验证                    →  回到步骤 1，用新配置重新运行
```

**运行中取消**: 用户可在运行详情页点击 `[取消运行]`，后端设置 TestRun.status = `cancelled`，停止后续用例执行，已完成的用例结果保留。

### 3.5.1 SSE 事件定义

> **需求**: 前端依赖 SSE 事件实现进度条、实时状态和错误提示，必须定义完整的事件契约。

**事件类型**:

| 事件 | 触发时机 | 数据字段 |
|------|---------|---------|
| `run_started` | 测试开始 | `run_id`, `test_set_id`, `total_cases`, `config_version` |
| `progress` | 每完成一个用例 | `run_id`, `current_case`, `total_cases`, `current_query`, `elapsed_seconds` |
| `case_result` | 单个用例完成 | `run_id`, `case_id`, `query`, `hit_at_1`, `hit_at_3`, `hit_at_5`, `matched_doc_ids`, `status` |
| `test_completed` | 所有用例执行完毕 | `run_id`, `total_cases`, `passed_cases`, `overall_metrics` (precision/recall/f1/mrr/ndcg) |
| `validation_started` | 校验开始 | `run_id`, `layer` (1-6) |
| `validation_completed` | 单层校验完成 | `run_id`, `layer`, `duration_ms`, `suggestion_count` |
| `report_ready` | 校验全部完成且报告已生成 | `run_id`, `report_id`, `overall_metrics`, `total_duration_seconds`, `validation_summary` |
| `run_failed` | 测试异常中断 | `run_id`, `error_code`, `error_message`, `failed_at_case` |

**注意**: `case_result` 中单个用例无法计算 Precision/Recall/F1（集合指标），改为 `hit_at_k`（命中检测）。集合指标在 `test_completed` 事件中返回。

**前端展示映射**:

| SSE 事件 | 前端行为 |
|---------|---------|
| `run_started` | 显示进度条 (0%)，禁用"运行"按钮，显示 `[取消运行]` |
| `progress` | 更新进度条百分比，显示当前查询文本 |
| `case_result` | 更新用例列表状态 (✅/❌)，显示 hit@k |
| `test_completed` | 显示"用例执行完成，正在生成诊断报告..." |
| `validation_started` | 显示对应校验层状态为"处理中..." |
| `validation_completed` | 显示校验层状态为"完成"，展示建议数量 |
| `report_ready` | 跳转到报告页 `/rag-eval/reports/{report_id}`，启用"运行"按钮 |
| `run_failed` | 弹出错误提示，显示失败用例位置，启用"运行"按钮 |

**断线重连机制**:

| 场景 | 处理策略 |
|------|---------|
| 网络断开/页面刷新 | 前端重连后调用 `GET /api/runs/{run_id}/status` 查询当前运行状态 |
| 重连后状态恢复 | 根据 `status` 字段决定：`running` → 重新订阅 SSE 并请求最近进度；`completed` → 直接跳转报告页；`failed` → 显示错误 |
| 心跳机制 | 后端每 15 秒发送 `heartbeat` 事件 `{run_id, timestamp}`，前端 30 秒未收到心跳判定断线 |
| 后端清理 | 前端断开连接时，后端从心跳队列中移除对应 clientId，防止内存泄漏 |

### 4.2 推荐模式面板设计 (辅助决策，非自动执行)

> **用户需求**: 推荐只是参考，不替用户做决策。每个推荐必须回答：**为什么改？改了有什么影响？前后对比是什么？**

**核心原则**:
- 推荐只是**参考**，不替用户做决策
- 每个推荐必须回答：**为什么改？改了有什么影响？前后对比是什么？**
- 用户需要**预览影响**后再决定是否应用
- **禁止"一键应用"式设计**，用户需要审查后再保存

**三种模式**：

| 模式 | 定位 | 展示内容 | 触发场景 |
|------|------|---------|---------|
| **推荐模式** (默认) | 报告驱动，展示诊断发现 | 推荐修改区 + 影响预览 + 原因解释 | 报告页面默认进入 |
| **向导模式** | 按功能域浏览 | 按功能域分组（检索/重排序/年龄过滤/分块），关键参数优先 | 用户主动切换 |
| **专家模式** | 全量控制 | 全部 RAG 配置参数树 + 全部提示词列表 | 高级用户主动切换 |

**事务管理实现** (Service 层):
```python
async def save_config_change_set(config_data, prompt_data, session):
    """原子保存配置+提示词变更集"""
    async with session.begin():  # MySQL 事务边界
        # 1. 创建配置版本
        config_version = ConfigVersion(
            version_number=await next_version_number(session),
            config_snapshot=config_data,
            created_by=current_user,
            change_summary=generate_summary(config_data)
        )
        session.add(config_version)
        await session.flush()  # 获取 ID
        
        # 2. 创建提示词版本
        prompt_ids = []
        for prompt in prompt_data:
            pv = PromptVersion(
                prompt_key=prompt.key,
                version=prompt.version_string,
                version_number=await next_prompt_version_number(session, prompt.key),
                content=prompt.content,
                created_by=current_user,
                change_summary=prompt.summary
            )
            session.add(pv)
            await session.flush()
            prompt_ids.append(pv.id)
        
        # 3. 创建变更集
        change_set = ConfigChangeSet(
            change_set_number=await next_change_set_number(session),
            config_version_id=config_version.id,
            prompt_version_ids=prompt_ids,  # JSON 数组
            status='committed'
        )
        session.add(change_set)
    # 任何一步抛出异常，整个事务自动回滚
```

## 5. 校验定义

> **用户需求**: 校验结果不是最终答案，而是辅助用户决策的信息。每个校验必须提供：触发原因、影响分析、建议依据。

### 5.1 Layer 1: 规则引擎

**定位**: 根据指标短板快速定位问题方向，给出初步参数建议

**触发条件**: 任何指标低于阈值

**输入**:
- 测试运行指标 (Precision/Recall/F1/MRR/NDCG)
- 当前配置快照 (从 ConfigVersion.config_snapshot 解析)
- 功能开关状态

**输出**:
- 参数调整建议列表 (参数名、当前值、建议值、原因、优先级、安全范围)

**校验规则** (自适应步长 + 冲突检测):

| 规则 | 触发条件 | 建议动作 (自适应) | 冲突检测 |
|------|---------|-----------------|---------|
| P@5 不达标 | P@5 < 0.70 | `min(current + 5, safe_max)`，若 R@5 ≥ 0.95 则不推荐 (已饱和) | 与 R@5 规则合并，取较大 top_k |
| R@5 不达标 | R@5 < 0.85 | `min(current + 5, safe_max)`，若 P@5 ≥ 0.85 则优先增加 vector_top_k | 与 P@5 规则合并 |
| F1 不达标 | F1 < 0.75 | fusion_threshold ±0.05，P 低则减小，R 低则增大 | 独立调整 |
| MRR 不达标 | MRR < 0.70 | `min(current + 10, safe_max)` | 独立调整 |
| 短查询失败率高 | 短查询失败率 > 30% 且查询重写未开启 | 开启 query_rewrite_enabled | 独立 |
| 跨领域失败率高 | 跨领域失败率 > 20% 且同义词扩展未开启 | 开启 synonym_expansion_enabled | 独立 |
| PageIndex 未启用 | pageindex_enabled = false | 开启 pageindex_enabled | 独立 |
| 参数超出安全范围 | 参数值 < min 或 > max | 修正到边界值 | 优先级最高 |

**自适应步长规则**:
- 步长 = `max(1, min(5, int(当前值 × 0.3)))`，即当前值越大步长越大，但不超过 5
- 建议值 = `min(当前值 + 步长, safe_max)`，确保不超出安全上限
- 若当前值已在推荐范围内且指标差距 < 0.1，步长减半

**冲突检测与合并**:
- 当多个规则建议调整同一参数时，取最大值（如 P@5 和 R@5 都建议增加 bm25_top_k，取较大值）
- 当规则建议相反方向时（如 P 低建议减小 fusion_threshold，R 低建议增大），输出冲突警告，交由用户决策
- 最终建议列表按优先级排序：安全范围修正 > 功能开关 > 参数调优

**参数安全范围**:

| 参数 | 最小值 | 最大值 | 推荐范围 | 步长 |
|------|--------|--------|---------|------|
| bm25_top_k | 5 | 50 | [10, 20] | 5 |
| vector_top_k | 5 | 50 | [10, 20] | 5 |
| fusion_threshold | 0.1 | 0.5 | [0.2, 0.3] | 0.05 |
| reranker_initial_k | 10 | 100 | [20, 50] | 10 |
| reranker_final_k | 1 | 20 | [3, 10] | 2 |
| age_filter_strictness | 0.0 | 1.0 | [0.3, 0.7] | 0.1 |
| chunk_size | 256 | 2048 | [512, 1024] | 128 |

**参考指标阈值说明**:
- P@5 ≥ 0.70: RAG 检索系统 Precision 达标线，低于此值说明噪声文档过多
- R@5 ≥ 0.85: 召回率达标线，低于此值说明遗漏关键信息
- F1 ≥ 0.75: Precision 和 Recall 的调和平均，综合评估检索基础效果
- MRR ≥ 0.70: 平均倒数排名，衡量最相关结果的排序位置（注：原 0.80 偏严格，调整为 0.70）
- NDCG ≥ 0.70: 归一化折损累积增益，评估整个排序列表质量

### 5.2 Layer 2: 历史对比

**定位**: 从历史运行中匹配相似问题，展示"上次改了什么、效果如何"

**触发条件**: 存在 ≥1 次历史运行记录

**无历史时行为**: 展示"基准报告"概念，显示当前指标的绝对水平，提示"运行更多次后可获得历史对比分析"

**输入**:
- 当前运行指标
- 当前配置版本
- 历史运行列表 (TestRun)

**输出**:
- 历史参考列表 (历史运行 ID、配置变更、指标变化、关联分析)

**校验规则**:

| 规则 | 算法 | 说明 |
|------|------|------|
| 配置变更→指标变化关联 | 差分对比：提取相邻 ConfigVersion 的 config_snapshot diff，关联对应 TestRun 的指标变化。仅展示变更项和对应指标变化，不做因果推断（多参数变更时指标变化可能是多因素叠加） | 对比当前配置与历史配置，找出变更项，关联指标变化 |
| 相似问题匹配 | 基于失败模式标签匹配：提取当前 Bad Case 的失败类型（未召回/排序倒置/误杀/语义不匹配），在历史运行的 TuningSuggestionRecord 中搜索相同失败类型的已解决记录，按 source=rule_engine/history/llm 分组展示 | 从历史 Bad Case 中匹配相似模式，展示历史解决方案 |

### 5.3 Layer 3: LLM 诊断

**定位**: 对 Bad Case 进行语义分析，给出针对性深度建议

**触发条件**: Bad Case 数量 ≥ 5 且 ≤ 50 (超过 50 时抽样 50 个最具代表性的用例)

**降级策略**: LLM API 异常时跳过本层，前端展示"LLM 服务不可用，已跳过深度诊断"

**输入**:
- Bad Case 列表 (查询、期望文档、实际文档、指标)
- 当前配置摘要

**输出**:
- 诊断结果列表 (失败类型、根因、置信度、建议措施)
- 汇总统计 (最常见失败类型、最常见根因、Top 建议)

**失败类型分类**:

| 类型 | 说明 | 优先级 |
|------|------|--------|
| 未召回 | 期望文档未出现在 Top-K 结果中 | HIGH |
| 排序倒置 | 期望文档排名过低 (如 > K/2) | HIGH |
| 误杀 | 不相关文档排名过高 | HIGH |
| 语义不匹配 | 检索结果与查询语义不相关 | MEDIUM |
| 部分召回 | 期望文档部分命中 (如 2/3 个期望文档) | HIGH |
| 年龄过滤排除 | 文档相关但被年龄过滤拦截 | HIGH (本项目核心场景) |
| 重排序误判 | Cross-Encoder 给相关文档打低分 | HIGH |

**根因分类**:

| 根因 | 说明 | 关联失败类型 |
|------|------|-------------|
| Embedding 质量问题 | 语义向量未能捕捉关键词关联 | 未召回, 语义不匹配 |
| 分块不合理 | 内容被截断或切分不当 | 未召回, 部分召回 |
| 关键词缺失 | BM25 未能匹配到关键词 | 未召回, 排序倒置 |
| 同义词未覆盖 | 同义词扩展未覆盖关键术语 | 未召回, 部分召回 |
| 年龄过滤过严 | 年龄过滤排除了相关文档 | 年龄过滤排除 |
| 重排序模型不匹配 | BAAI/bge-reranker-v2-m3 对特定领域表现差 | 排序倒置, 重排序误判 |
| 查询路由错误 | 简单/复杂查询分类错误导致走了错误流水线 | 语义不匹配 |
| 分块粒度不当 | chunk_size 过大导致信息稀释，或过小导致上下文丢失 | 部分召回, 未召回 |

**抽样策略** (Bad Case > 50 时):
- 按失败类型分层抽样：未召回/排序倒置/误杀/部分召回/年龄过滤排除/重排序误判 各占比例与总体一致
- 每层至少抽取 3 条，确保各失败类型都有代表
- 若某层不足 3 条，全量抽取

**降级策略细化**:

| 异常类型 | 处理策略 |
|---------|---------|
| 超时 (> 30s) | 重试 1 次，仍超时则降级 |
| Rate Limit (429) | 等待 retry-after 后重试 1 次，仍失败则降级 |
| 返回格式错误 | 使用 `json-repair` 库修复 (CLAUDE.md 要求)，修复失败则降级 |
| 内容安全拦截 | 标记并跳过该 Bad Case，继续处理剩余 |
| API 完全不可用 | 跳过本层，前端展示"LLM 服务不可用，已跳过深度诊断" |

### 5.4 Layer 4: 数据质量 (3 种校验)

#### 5.4.1 校验 4a: Golden 覆盖度分析

**定位**: 检查测试用例是否覆盖了足够的源文档和章节

**触发条件**: 测试完成后

**输入**:
- 测试用例列表 (含 source_document_id)
- 源文档列表 (含 chapter_count)

**输出**:
- 覆盖度报告 (书籍覆盖率、章节覆盖率、各领域覆盖文档数)

**校验规则**:

| 规则 | 触发条件 | 警告级别 |
|------|---------|---------|
| 书籍覆盖率低 | 覆盖书籍数 / 总书籍数 < 60% | ⚠️ |
| 章节覆盖率低 | 覆盖章节数 / 总章节数 < 40% | ⚠️ |
| 某领域无覆盖 | 某发展领域无对应测试用例 | 🔴 |

---

#### 5.4.2 校验 4b: 分块质量评分

**定位**: 检查文档分块的信息密度、可读性、切分合理性

**触发条件**: 测试完成后

**输入**:
- 分块列表 (content, metadata)

**输出**:
- 分块质量报告 (平均质量分、低质量分块比例、低质量示例)

**校验规则**:

| 规则 | 触发条件 | 警告级别 |
|------|---------|---------|
| 低质量分块过多 | 低质量比例 > 10% | ⚠️ |
| 平均质量过低 | 平均质量分 < 0.6 | 🔴 |

**质量维度与验收标准** (修正后):

| 维度 | 计算方式 | 高质量 | 低质量 |
|------|---------|--------|--------|
| 信息密度 | 1 - (停用词数 / 总词数)。停用词列表使用中文通用停用词表 (的/了/是/在/有/和/或/但等) | > 0.6 (停用词占比 < 40%) | < 0.3 (停用词占比 > 70%) |
| 结构化程度 | (标题数 × 2 + 列表项数) / 段落数。反映文档的结构化程度，结构化越高可读性越好 | > 0.5 | < 0.1 |
| 切分合理性 | 以完整句子/段落结束的分块占比。检查 chunk 末尾是否为句号/问号/感叹号/段落结束标记 | > 90% | < 70% |

**综合质量分**: 三个维度加权平均 (信息密度 40% + 结构化程度 30% + 切分合理性 30%)

**专业术语密度** (辅助指标，不纳入综合分):
- 计算: 儿童发展领域专业术语数 / 总词数
- 专业术语列表来自领域知识库 (如: 感统训练/精细动作/粗大动作/前庭觉/本体觉等)
- 用于区分"专业内容"和"通用内容"，辅助判断分块的信息价值

#### 5.4.3 校验 4c: 文档时效性检查

**定位**: 检查源文档内容是否过期 (针对儿童发展领域特殊调整)

**触发条件**: 测试完成后

**输入**:
- 源文档列表 (含 content_summary, upload_date, document_type)

**输出**:
- 时效性报告 (过期文档数、过期比例、过期文档列表)

**文档类型分类与时效阈值**:

| 文档类型 | 时效阈值 | 说明 |
|---------|---------|------|
| 政策法规/指南 | 3 年 | 如教育部最新指南、地方政策，更新频繁 |

| 规则 | 触发条件 | 警告级别 |

### 5.5 Layer 5: 检索链路 (3 种校验)

#### 5.5.1 校验 5a: Embedding 质量校验

**定位**: 检查 Embedding 模型的语义区分能力（修正方法论）

**触发条件**: 测试完成后

**输入**:
- 测试用例查询列表
- Embedding 向量 (通过 DashScope API 获取，使用 SafeDashScopeEmbedding 包装器)

**输出**:
- Embedding 质量报告 (同义查询对相似度、区分度指标、异常向量检测)

**校验方法** (修正后):

| 方法 | 说明 | 阈值 |
|------|------|------|
| 同义查询对验证 | 人工构造或从历史日志提取语义等价的查询对 (如"什么是感统训练" vs "感统训练是什么")，检查其 embedding 余弦相似度 | 同义对相似度 ≥ 0.85 ⚠️ 低于则警告 |
| 区分度检查 (Silhouette Score) | 按领域分组计算 silhouette score，衡量同类查询聚拢、异类查询分离的程度 | silhouette ≥ 0.5 为良好，< 0.3 ⚠️ 警告 |
| 异常向量检测 | 检测零向量、NaN、维度异常、全相同向量 | 发现异常 🔴 严重警告 |

**注意**: 不再使用"同类查询组内平均相似度"方法，因为同一领域/年龄的不同查询语义本就不该相似。

#### 5.5.2 校验 5b: 意图识别准确率

**触发条件**: 测试完成后

**数据来源** (双轨制):

| 来源 | 说明 | 优先级 |

|------|---------|---------|

**定位**: 对 Bad Case 进行多维交叉分组，找出共性失败模式

**触发条件**: 测试完成后

**输入**:
- Bad Case 列表

- 错误模式分组报告 (各分组名称、数量、示例、建议修复方案)

**分组方法** (多维交叉，非 ML 聚类):

| 维度 | 取值 |
|------|------|
| 错误类型 | 未召回 / 排序倒置 / 误杀 / 部分召回 / 年龄过滤排除 / 重排序误判 |

**交叉分组输出**: 每个 (错误类型 × 领域 × 年龄组) 组合为一个分组，输出:
- 分组名称 (如"未召回-感统-3-6岁")

- 示例查询 (最多 3 条)

|------|---------|---------|

| 指标严重退化 | 某指标下降 > 15% | 🔴 |

#### 5.6.2 校验 6b: 交叉验证

**定位**: 检查各领域/年龄组的指标一致性

**触发条件**: 测试完成后

---

#### 5.6.3 校验 6c: 成本效果分析

**定位**: 分析配置变更带来的指标提升与额外成本的比例

**触发条件**: 存在配置变更

**输入**:
- 配置变更列表
- 指标变化
- LLM 调用成本 (token 消耗)

**输出**:
- 成本效果报告 (提升分数、额外成本、成本效果比、是否值得)

**成本效果比公式**:

```
成本效果比 = 指标提升归一化值 / 额外成本归一化值

其中:
  指标提升归一化值 = (ΔP@5 × 0.3 + ΔR@5 × 0.3 + ΔF1 × 0.2 + ΔMRR × 0.1 + ΔNDCG × 0.1) × 100
  # 将各指标变化加权后映射到 0-100 分范围

  额外成本归一化值 = log2(1 + 额外 token 数 / 10000)
  # 使用对数缩放，防止 token 数过大时成本效果比趋近于 0
  # 10000 token 约为一次中等规模测试的额外消耗
```

**校验规则**:

| 规则 | 触发条件 | 建议 |
|------|---------|------|
| 成本效果比低 | 成本效果比 < 0.1 | 不建议应用该变更 (成本高，提升小) |
| 成本效果比中等 | 0.1 ≤ 成本效果比 ≤ 0.5 | 可考虑应用 (权衡成本与效果) |
| 成本效果比高 | 成本效果比 > 0.5 | 强烈推荐应用 (成本低，提升大) |

**成本类型说明**:
- 检索参数调整 (top_k, fusion_threshold): 成本几乎为零，成本效果比通常很高
- 开启 LLM 功能 (查询重写, 同义词扩展): 成本为每次查询的 LLM token 消耗
- 分块参数调整 (chunk_size): 成本为重新分块和重新 Embedding 的一次性消耗

---

#### 5.6.4 校验 6d: A/B 影子测试

**定位**: 同时运行两个配置，逐条对比效果

**触发条件**: 用户主动触发

**输入**:
- 配置 A
- 配置 B
- 测试集

**输出**:
- A/B 对比报告 (胜出方、各用例对比、指标差异、统计显著性)

**展示内容**:
- 总体胜出方 (A 或 B)
- 各用例逐条对比 (hit@k 差异)
- 指标总差异 (precision_delta, recall_delta, f1_delta)
- 统计显著性 (p-value, 置信区间)

**成本提示需求**:
- 触发前必须展示预计耗时 (基于测试集用例数量和平均单用例耗时计算)
- 运行中显示 `[取消测试]` 按钮，点击后二次确认，已完成的用例结果保留
- 必须支持"抽样模式"：用户可选择抽样比例，系统按分层随机抽样选取用例

**抽样模式** (修正后):

| 测试集用例数 | 抽样策略 | 说明 |
|-------------|---------|------|
| ≤ 30 | 禁止抽样，强制全量 | 样本量过小，抽样结果无统计意义 |
| 31-100 | 50% 分层抽样 | 按领域×年龄组分层，每层至少抽取 3 条 |
| > 100 | 20% 或 50% 分层抽样 | 用户可选，按领域×年龄组分层 |

**分层随机抽样**:
- 按 (领域 × 年龄组) 交叉分层，确保各领域/年龄组按比例抽取
- 每层至少抽取 3 条，若某层不足 3 条则全量抽取
- 抽样模式需在报告中标注"抽样结果，仅供参考，建议全量验证"

**统计显著性检验**:
- 使用配对 t-test (paired t-test) 比较 A/B 配置的指标差异
- 输出 p-value: p < 0.05 表示差异显著，p ≥ 0.05 表示差异不显著
- 输出 95% 置信区间: 展示指标差异的可能范围
- 若 p ≥ 0.05，报告中标注"差异不显著，A/B 配置效果相当"

## 6. 数据流设计

### 6.1 6 层校验数据流

```
TestRun 完成 (SSE: test_completed)
    │
    ├──▶ Layer 1: 规则引擎
    │    输入: metrics + config_snapshot (JSON 解析)
    │    输出: List[TuningSuggestion] (参数调整建议，自适应步长 + 冲突检测)
    │
    ├──▶ Layer 2: 历史对比
    │    输入: metrics + current_run_id + test_set_id
    │    查询: 历史 TestRun + ConfigVersion (同一 test_set_id)
    │    输出: List[HistoryReference] (差分对比 + 失败模式匹配)
    │
    ├──▶ Layer 3: LLM 诊断
    │    输入: run_id (获取 Bad Case 列表)
    │    条件: Bad Case ≥ 5 且 ≤ 50 (超过 50 时按失败类型分层抽样)
    │    降级: API 异常时按类型处理 (超时重试/Rate Limit 等待/json-repair 修复)
    │    输出: LLMDiagnosis (语义诊断 + 建议，含 7 种失败类型 + 8 种根因)
    │
    ├──▶ Layer 4: 数据质量
    │    ├── 4a. Golden 覆盖度分析
    │    │    输入: test_cases + source_documents
    │    │    输出: coverage_report (书籍/章节/领域覆盖率)
    │    ├── 4b. 分块质量评分
    │    │    输入: chunks (content, metadata)
    │    │    输出: chunk_quality_scores (信息密度/结构化程度/切分合理性 + 专业术语密度)
    │    └── 4c. 文档时效性检查
    │         输入: source_documents (upload_date, document_type)
    │         输出: staleness_report (按文档类型分类的过期标记)
    │
    ├──▶ Layer 5: 检索链路
    │    ├── 5a. Embedding 质量校验
    │    │    输入: test_cases (查询列表)
    │    │    输出: embedding_quality_report (同义查询对相似度 + silhouette 区分度 + 异常检测)
    │    ├── 5b. 意图识别准确率
    │    │    输入: query_analysis_results + LLM 自动标注 + 人工标注
    │    │    输出: intent_accuracy_report (整体准确率 + 低置信度查询列表)
    │    └── 5c. 错误模式分组
    │         输入: failed_results (Bad Case 列表)
    │         输出: error_groups (多维交叉分组 + 修复方案规则映射)
    │
    └──▶ Layer 6: 验证保障
         ├── 6a. 回归检测
         │    输入: current_run + previous_run
         │    输出: regression_report (指标退化标记)
         ├── 6b. 交叉验证
         │    输入: test_cases (按领域/年龄分组)
         │    输出: cross_validation_report (各组指标一致性)
         ├── 6c. 成本效果分析
         │    输入: config_changes + metric_deltas + token_costs
         │    输出: cost_effectiveness_report (成本效果比 = 指标提升归一化 / 成本归一化)
         └── 6d. A/B 影子测试 (按需触发)
              输入: config_A + config_B + test_set
              输出: ab_comparison_report (分层抽样 + 配对 t-test + p-value)
```

**校验执行顺序**:
- Layer 1-2: 并行执行 (< 100ms)
- Layer 3: 依赖 Layer 1 识别的 Bad Case 列表，异步执行 (1-3s)
- Layer 4-5: 并行执行 (< 1s)
- Layer 6: 默认不执行，用户手动触发 (5-30s)

### 6.2 报告状态机

```
┌─────────┐    校验中     ┌───────────┐
│ pending ├──────────────►│ processing│
└─────────┘               └─────┬─────┘
                                │ 所有校验完成
                                ▼
                          ┌───────────┐
                          │ completed │
                          └─────┬─────┘
                                │ 应用建议 + 复测
                                ▼
                          ┌───────────┐
                          │ superseded│ (被新报告替代)
                          └───────────┘
```

## 7. 术语表

| 术语 | 定义 |
|------|------|
| **RAG** | Retrieval-Augmented Generation，检索增强生成 |
| **Golden Dataset** | 标准测试集，包含查询和期望答案 |
| **Precision@K** | 前 K 个检索结果中相关文档的比例 |
| **Recall@K** | 检索到的相关文档占所有相关文档的比例 |
| **F1 Score** | Precision 和 Recall 的调和平均数 |
| **MRR** | Mean Reciprocal Rank，平均倒数排名 |
| **NDCG** | Normalized Discounted Cumulative Gain，归一化折损累计增益 |
| **Bad Case** | 测试失败的用例，指标低于阈值 |
| **SSE** | Server-Sent Events，服务器推送事件 |
| **ConfigVersion** | 配置版本，记录某时刻的完整配置快照 (JSON 存储) |
| **PromptVersion** | 提示词版本，记录某时刻的提示词内容 |
| **ConfigChangeSet** | 配置变更集，原子保存配置+提示词的整体版本 |
| **TestReport** | 评估报告，每次运行生成一份，包含 6 层校验结果 |
| **TuningSuggestionRecord** | 调优建议记录，包含参数/提示词的当前值、建议值、原因 |
| **IntentAnnotation** | 意图人工标注，Layer 5b 校验的数据来源 |
| **TestSetCase** | 测试集-用例关联表，支持用例被多个测试集复用 |

## 8. 参考指标体系 (用户指定)

> **以下指标体系来自用户直接指定，系统必须支持这些指标的计算、展示和趋势追踪。这些指标是诊断和调优的核心依据，不可省略。**

### 8.1 检索阶段核心指标

| 指标 | 用途 | 达标阈值 | 说明 |
|------|------|---------|------|
| **精确率 (Precision)** | 衡量检索返回的文档片段中，与用户问题真正相关的内容占比，用于识别检索结果是否混入大量噪声文档 | P@5 ≥ 0.70 | 识别噪声文档过多问题 |
| **召回率 (Recall)** | 衡量知识库中所有与问题相关的文档片段里，被成功检索返回的内容占比，用于判断检索是否遗漏了关键信息 | R@5 ≥ 0.85 | 判断关键信息遗漏 |
| **F1 分数** | 精确率和召回率的调和平均值，用于平衡二者之间的天然张力，综合评估检索的基础效果，帮助找到检索 Top-K 的最优取值 | F1 ≥ 0.75 | 综合评估检索基础效果 |
| **平均倒数排名 (MRR)** | 衡量检索结果中第一个相关文档的排序位置，得分越高代表系统越能把最相关的结果排在前列，保障核心信息优先被大模型获取 | MRR ≥ 0.70 | 保障核心信息优先获取 |
| **归一化折损累积增益 (NDCG)** | 全面评估整个检索排序列表的质量，不仅考虑全量结果的相关性，还支持多级相关性标注，同时对排序靠后的文档做贡献度折损，更贴合 RAG 场景的排序需求 | NDCG ≥ 0.70 | 评估整个排序列表质量 |
| **上下文相关性 (Context Relevance)** | 由 RAGAS 框架提出，评估检索返回的整体上下文中，能真正用于回答用户问题的有效内容占比，可精准识别"检索内容多但有效信息少"的低效检索问题 | ≥ 0.75 | 识别低效检索 |

### 8.2 生成阶段核心指标

| 指标 | 用途 | 达标阈值 | 说明 |
|------|------|---------|------|
| **忠实度 (Faithfulness)** | RAG 生成评估的核心指标，衡量大模型生成的回答是否忠实于检索到的文档内容，是否编造了检索结果中不存在的信息，是保障 RAG 系统基于可靠外部知识回答的核心标尺 | ≥ 0.80 | 保障回答基于可靠知识 |
| **回答相关性 (Answer Relevance)** | 衡量生成的回答是否切题、是否真正回应了用户的问题，规避内容忠实但答非所问的低质量回答问题 | ≥ 0.80 | 规避答非所问 |
| **回答完整性 (Answer Completeness)** | 评估生成的回答是否覆盖了用户问题的所有核心要点，通常结合标注的参考答案对比关键信息点的覆盖情况，衡量回答的完整度 | ≥ 0.75 | 评估要点覆盖 |
| **回答正确性 (Answer Correctness)** | 衡量生成的回答的事实准确性，结合参考答案对比关键信息点的正确性 | ≥ 0.75 | 评估事实准确性 |

### 8.3 传统 NLP 辅助评估指标

| 指标 | 用途 | 定位 | 说明 |
|------|------|------|------|
| **BLEU** | 原本用于机器翻译评估，衡量生成文本与参考文本之间的 n-gram 重叠度，计算简单、无额外调用成本 | 辅助粗筛 | 仅可作为 RAG 评估的辅助参考，不能作为核心评估手段 |
| **ROUGE** | 原本用于文本摘要评估，侧重衡量参考文本中的关键 n-gram 是否被生成文本覆盖，计算成本极低 | 辅助粗筛 | 仅可作为 RAG 生成文本语义质量的辅助参考，无法衡量语义层面的匹配度 |
| **BERTScore** | 基于预训练语言模型的 Embedding 计算生成文本与参考文本的语义相似度，解决了传统指标"同义不同词"的缺陷 | 辅助参考 | 可作为 RAG 生成文本语义质量的辅助评估指标 |

### 8.4 端到端与整体闭环评估指标

| 指标 | 用途 | 说明 |
|------|------|------|
| **端到端回答正确性 (Answer Correctness)** | 端到端自动化评估核心指标，用于 RAG 系统版本间的效果对比与发布前的回归检测，整体衡量最终回答的综合质量 | 版本对比与回归检测 |
| **RAGAS 综合分数** | 基于 RAGAS 框架的综合自动化评估指标，用于版本间的整体效果对比，实现 RAG 系统迭代的快速效果验证 | 整体效果验证 |
| **人工评估 + 用户反馈** | RAG 评估体系的顶层校准环节，用于校准自动化评估指标的准确性，把握真实的用户体验，通常采用定期抽检的方式执行 | 顶层校准 |

**指标在系统中的落地**:
- 检索阶段指标 (Precision/Recall/F1/MRR/NDCG/Context Relevance): 由 Layer 1 规则引擎直接使用，作为阈值触发条件
- 生成阶段指标 (Faithfulness/Answer Relevance/Completeness/Correctness): 在评估报告中展示，用于端到端质量评估
- 传统 NLP 指标 (BLEU/ROUGE/BERTScore): 在报告详情页的"辅助指标"折叠区展示，标注"仅供参考"
- 端到端指标 (Answer Correctness/RAGAS Score): 在趋势追踪中展示，用于版本间对比
- 人工评估: 在报告页提供"标注反馈"入口，用户可标记报告中的指标是否与实际体验一致
