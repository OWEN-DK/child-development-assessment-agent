# 05 - 6 层校验引擎

> **本文档包含**: 分层架构、完整数据流、Layer 1-6 共 13 种校验的触发条件/输入/输出/规则/降级策略

## 3.2 分层递进架构

```
┌─────────────────────────────────────────────────────────┐
│                    评估报告 (Report)                      │
│  汇总所有校验结果，生成结构化诊断报告                        │
└──────────┬───────────────────────────────────────────────┘
           ▼
┌─────────────────────────────────────────────────────────┐
│              校验引擎编排层 (ValidationOrchestrator)       │
│  协调 6 层校验，支持异步/并行/降级执行                       │
└──┬────┬────┬────┬────┬──────────────────────────────────┘
   ▼    ▼    ▼    ▼    ▼
 Layer1 Layer2 Layer3 Layer4 Layer5 Layer6
 规则   历史   LLM   数据   检索   验证
 引擎   对比   诊断   质量   链路   保障
```

## 6.1 6 层校验数据流

```
TestRun 完成 (SSE: test_completed)
    │
    ├──▶ Layer 1: 规则引擎
    │    输入: metrics + config_snapshot (JSON 解析)
    │    输出: List[TuningSuggestion] (参数调整建议，自适应步长 + 冲突检测)
    │
    ├──▶ Layer 2: 历史对比
    │    输入: metrics + current_run_id + test_set_id
    │    查询: 历史 TestRun + ConfigVersion (同一 test_set_id)
    │    输出: List[HistoryReference] (差分对比 + 失败模式匹配)
    │
    ├──▶ Layer 3: LLM 诊断
    │    输入: Bad Case 列表 (hit_at_5 = 0 的用例)
    │           - 查询文本: 从 TestRunResult.query 获取
    │           - 期望文档: 从 TestCase.expected_document_ids 获取
    │           - 实际文档: 从 TestRunResult.matched_doc_ids 和 matched_doc_scores 获取
    │           - 指标: 从 TestRunResult.hit_at_1/3/5 获取
    │    条件: Bad Case ≥ 5 时触发；Bad Case > 50 时按失败类型分层抽样至 50 条
    │    降级: API 异常时按类型处理 (超时重试/Rate Limit 等待/json-repair 修复)
    │    输出: LLMDiagnosis (语义诊断 + 建议，含 7 种失败类型 + 8 种根因)
    │          + 生成质量指标 (Faithfulness/Answer Relevance/Completeness/Correctness)
    │          # 生成质量指标通过 LLM 对 Bad Case 的检索结果 + 期望答案进行评估
    │    # 注意: Layer 3 的"失败类型"（未召回/排序倒置/误杀等）是 LLM 语义分析的结果，
    │    #      不等于 Bad Case 的定义。Bad Case 仅指 hit_at_5=0 的用例，
    │    #      LLM 会进一步分析这些用例属于哪种失败类型。此外，Layer 3 也会对
    │    #      hit_at_5>0 但排名过低的"边缘用例"进行辅助分析，但建议权重低于 Bad Case。
    │
    ├──▶ Layer 4: 数据质量
    │    ├── 4a. Golden 覆盖度分析
    │    │    输入: test_cases + source_documents
    │    │    输出: coverage_report (书籍/章节/领域覆盖率)
    │    ├── 4b. 分块质量评分
    │    │    输入: chunks (content, metadata)
    │    │    输出: chunk_quality_scores (信息密度/结构化程度/切分合理性 + 专业术语密度)
    │    └── 4c. 文档时效性检查
    │         输入: source_documents (upload_date, document_type)
    │         输出: staleness_report (按文档类型分类的过期标记)
    │
    ├──▶ Layer 5: 检索链路
    │    ├── 5a. Embedding 质量校验
    │    │    输入: test_cases (查询列表)
    │    │    输出: embedding_quality_report (同义查询对相似度 + silhouette 区分度 + 异常检测)
    │    ├── 5b. 意图识别准确率
    │    │    输入: query_analysis_results + LLM 自动标注 + 人工标注
    │    │    输出: intent_accuracy_report (整体准确率 + 低置信度查询列表)
    │    └── 5c. 错误模式分组
    │         输入: failed_results (Bad Case 列表)
    │         输出: error_groups (多维交叉分组 + 修复方案规则映射)
    │
    └──▶ Layer 6: 验证保障
         ├── 6a. 回归检测
         │    输入: current_run + previous_run
         │    输出: regression_report (指标退化标记)
         ├── 6b. 交叉验证
         │    输入: test_cases (按领域/年龄分组)
         │    输出: cross_validation_report (各组指标一致性)
         ├── 6c. 成本效果分析
         │    输入: config_changes + metric_deltas + token_costs
         │    输出: cost_effectiveness_report (成本效果比 = 指标提升归一化 / 成本归一化)
         └── 6d. A/B 影子测试 (按需触发)
              输入: config_A + config_B + test_set
              输出: ab_comparison_report (分层抽样 + 配对 t-test + p-value)
```

## 3.3 校验层定义 (6 层 / 13 种校验)

| 层级 | 名称 | 校验方式 | 执行时机 | 延迟 | 成本 | 可降级 |
|------|------|---------|---------|------|------|--------|
| **Layer 1** | 规则引擎 | 指标阈值触发 → 参数建议 | 测试完成后立即 | <50ms | 无 | ❌ 必须执行 |
| **Layer 2** | 历史对比 | 配置变更→指标变化关联 + 相似匹配 | 有≥1次历史运行时 | <100ms | 无 | ❌ 必须执行 (无历史时展示基准报告) |
| **Layer 3** | LLM 诊断 | Bad Case 语义分析 + 根因归类 | Bad Case≥5 时 | 1-3s | LLM 调用 | ✅ API 异常时跳过，显示"LLM 服务不可用"；Bad Case>50 时按失败类型分层抽样至 50 条 |
| **Layer 4** | 数据质量 | Golden覆盖度 + 分块质量 + 文档时效 | 测试完成后 | <500ms | 无 | ❌ 必须执行 |
| **Layer 5** | 检索链路 | Embedding质量 + 意图识别 + 错误模式分组 | 测试完成后 | <1s | 无 | ⚠️ Embedding 校验可跳过，意图和聚类必须执行 |
| **Layer 6** | 验证保障 | 回归检测 + 交叉验证 + 成本效果 + A/B影子 | 按需触发 | 5-30s | 可选 LLM | ✅ 默认不执行，用户手动触发 |

**校验执行顺序**:
- Layer 1-2: 并行执行 (< 100ms)，两者互不依赖
- Layer 3: 从 TestRun 结果获取 Bad Case 列表，与 Layer 1-2 并行执行 (1-3s)
- Layer 4-5: 并行执行 (< 1s)，Layer 5c 错误模式分组直接使用 TestRun 的 Bad Case 列表
- Layer 6: 默认不执行，用户手动触发 (5-30s)，读取已完成的 TestReport 数据，不阻塞报告生成

**超时与资源限制**:
- **总体超时**: 6 层校验总耗时上限为 **5 分钟**。超时后，正在执行的校验层被取消，已完成的层保留，未完成的层标记 `status="timeout"`，报告仍标记为 `completed`（部分校验结果）
- **单层层超时**:
  - Layer 1/2/4/5: 单层层超时上限 30s，超时标记 `status="timeout"`
  - Layer 3 (LLM): 单层层超时上限 120s（含重试），超时降级为"LLM 服务不可用"
  - Layer 6: 单层层超时上限 60s，超时标记 `status="timeout"`
- **降级后的报告状态**: 任何校验层降级或超时，TestReport.status 仍为 `completed`，但 `validation_results` 中对应层的 `status` 字段标记为 `"degraded"` 或 `"timeout"`，`data` 字段记录降级原因。前端展示时，降级的校验层显示"⚠️ 部分结果不可用"
- **校验取消机制**: 用户可在报告页点击 `[取消校验]` 按钮，后端设置 TestReport.status = `completed`（已完成的层保留，未完成的层标记 `status="cancelled"`），并通过 SSE 推送 `report_ready` 事件
- **并发限制**: 同一时间最多允许 **3 个 TestReport 的校验引擎并行执行**，超出请求进入队列等待。队列上限 10，超出返回 503 错误

**依赖关系图**:
```
TestRun 结果 (Bad Case 列表) ──┐
                                ├──▶ Layer 3 (LLM 诊断)
Layer 1 (规则引擎) ─────────────┘  (Layer 1 提供参数建议，辅助 LLM 理解当前配置)

Layer 2 (历史对比) ──▶ 独立执行，读取历史 TestReport

Layer 4 (数据质量) ──┐
                      │
Layer 5a (Embedding) ─┤
                      ├──▶ 并行执行，互不依赖
Layer 5b (意图识别) ──┤
                      │
Layer 5c (错误分组) ──┘  直接使用 TestRun 的 Bad Case 列表，不等待 Layer 3

Layer 6 (验证保障) ──▶ 用户手动触发，读取已完成的 TestReport 数据
```

## 5.1 Layer 1: 规则引擎

**定位**: 根据指标短板快速定位问题方向，给出初步参数建议

**触发条件**: 任何指标低于阈值

**输入**:
- 测试运行指标 (Precision/Recall/F1/MRR/NDCG)
- 当前配置快照 (从 ConfigVersion.config_snapshot 解析)
- 功能开关状态

**输出**:
- 参数调整建议列表 (参数名、当前值、建议值、原因、优先级、安全范围)

**校验规则** (自适应步长 + 冲突检测):

| 规则 | 触发条件 | 建议动作 (自适应) | 冲突检测 |
|------|---------|-----------------|---------|
| P@5 不达标 | P@5 < 0.70 | `min(current + 5, safe_max)`，若 R@5 ≥ 0.95 则不推荐 (已饱和) | 与 R@5 规则合并，取较大 top_k |
| R@5 不达标 | R@5 < 0.85 | `min(current + 5, safe_max)`，若 P@5 ≥ 0.85 则优先增加 vector_top_k | 与 P@5 规则合并 |
| F1 不达标 | F1 < 0.75 | fusion_threshold ±0.05，P 低则减小，R 低则增大 | 独立调整 |
| MRR 不达标 | MRR < 0.70 | `min(current + 10, safe_max)` | 独立调整 |
| 短查询失败率高 | 短查询失败率 > 30% 且查询重写未开启 | 开启 query_rewrite_enabled | 独立 |
| 跨领域失败率高 | 跨领域失败率 > 20% 且同义词扩展未开启 | 开启 synonym_expansion_enabled | 独立 |
| PageIndex 未启用 | pageindex_enabled = false | 开启 pageindex_enabled | 独立 |
| 参数超出安全范围 | 参数值 < min 或 > max | 修正到边界值 | 优先级最高 |

**自适应步长规则**:
- 步长 = `max(1, min(5, int(当前值 × 0.3)))`，即当前值越大步长越大，但不超过 5
- 建议值 = `min(当前值 + 步长, safe_max)`，确保不超出安全上限
- 若当前值已在推荐范围内且指标差距 < 0.1，步长减半

**冲突检测与合并**:
- 当多个规则建议调整同一参数时，取最大值（如 P@5 和 R@5 都建议增加 bm25_top_k，取较大值）
- 当规则建议相反方向时（如 P 低建议减小 fusion_threshold，R 低建议增大），输出冲突警告，交由用户决策
- 最终建议列表按优先级排序：安全范围修正 > 功能开关 > 参数调优

**参数安全范围**:

| 参数 | 最小值 | 最大值 | 推荐范围 | 步长 |
|------|--------|--------|---------|------|
| bm25_top_k | 5 | 50 | [10, 20] | 5 |
| vector_top_k | 5 | 50 | [10, 20] | 5 |
| fusion_threshold | 0.1 | 0.5 | [0.2, 0.3] | 0.05 |
| reranker_initial_k | 10 | 100 | [20, 50] | 10 |
| reranker_final_k | 1 | 20 | [3, 10] | 2 |
| age_filter_strictness | 0.0 | 1.0 | [0.3, 0.7] | 0.1 |
| chunk_size | 256 | 2048 | [512, 1024] | 128 |

**参考指标阈值说明**:
- P@5 ≥ 0.70: RAG 检索系统 Precision 达标线，低于此值说明噪声文档过多
- R@5 ≥ 0.85: 召回率达标线，低于此值说明遗漏关键信息
- F1 ≥ 0.75: Precision 和 Recall 的调和平均，综合评估检索基础效果
- MRR ≥ 0.70: 平均倒数排名，衡量最相关结果的排序位置
- NDCG ≥ 0.70: 归一化折损累积增益，评估整个排序列表质量

## 5.2 Layer 2: 历史对比

**定位**: 从历史运行中匹配相似问题，展示"上次改了什么、效果如何"

**触发条件**: 存在 ≥1 次历史运行记录

**无历史时行为**: 展示"基准报告"概念，显示当前指标的绝对水平，提示"运行更多次后可获得历史对比分析"

**输入**:
- 当前运行指标
- 当前配置版本
- 历史运行列表 (TestRun)
- Bad Case 列表 (从 TestRun 结果获取，用于失败模式匹配)

**输出**:
- 历史参考列表 (历史运行 ID、配置变更、指标变化、关联分析)

**校验规则**:

| 规则 | 算法 | 说明 |
|------|------|------|
| 配置变更→指标变化关联 | 差分对比：提取相邻 ConfigVersion 的 config_snapshot diff。diff 策略：深度对比 JSON 对象，仅输出值发生变化的键值对（旧值 → 新值）。关联对应 TestRun 的指标变化。仅展示变更项和对应指标变化，不做因果推断（多参数变更时指标变化可能是多因素叠加） | 对比当前配置与历史配置，找出变更项，关联指标变化 |
| 相似问题匹配 | 基于失败模式标签匹配：提取当前 Bad Case 的失败类型（未召回/排序倒置/误杀/部分召回/语义不匹配），在历史运行的 TuningSuggestionRecord 中搜索相同失败类型的已解决记录，按 source=rule_engine/history/llm 分组展示 | 从历史 Bad Case 中匹配相似模式，展示历史解决方案 |

## 5.3 Layer 3: LLM 诊断

**定位**: 对 Bad Case 进行语义分析，给出针对性深度建议

**触发条件**: Bad Case 数量 ≥ 5 (超过 50 时按失败类型分层抽样至 50 条)

**降级策略**: 见下方降级策略细化表

**输入**:
- Bad Case 列表 (hit_at_5 = 0 的用例)，每条包含:
  - 查询文本: 从 TestRunResult.query 获取
  - 期望文档: 从 TestCase.expected_document_ids 获取
  - 实际文档: 从 TestRunResult.matched_doc_ids 和 matched_doc_scores 获取
  - 指标: 从 TestRunResult.hit_at_1/3/5 获取
- 当前配置摘要: 从 ConfigVersion.config_snapshot 解析

**输出**:
- 诊断结果列表 (失败类型、根因、置信度、建议措施)
- 汇总统计 (最常见失败类型、最常见根因、Top 建议)

**失败类型分类**:

| 类型 | 说明 | 优先级 |
|------|------|--------|
| 未召回 | 期望文档未出现在 Top-K 结果中 | HIGH |
| 排序倒置 | 期望文档排名过低 (如 > K/2) | HIGH |
| 误杀 | 不相关文档排名过高 | HIGH |
| 语义不匹配 | 检索结果与查询语义不相关 | MEDIUM |
| 部分召回 | 期望文档部分命中 (如 2/3 个期望文档) | HIGH |
| 年龄过滤排除 | 文档相关但被年龄过滤拦截 | HIGH (本项目核心场景) |
| 重排序误判 | Cross-Encoder 给相关文档打低分 | HIGH |

**根因分类**:

| 根因 | 说明 | 关联失败类型 |
|------|------|-------------|
| Embedding 质量问题 | 语义向量未能捕捉关键词关联 | 未召回, 语义不匹配 |
| 分块不合理 | 内容被截断或切分不当 | 未召回, 部分召回 |
| 关键词缺失 | BM25 未能匹配到关键词 | 未召回, 排序倒置 |
| 同义词未覆盖 | 同义词扩展未覆盖关键术语 | 未召回, 部分召回 |
| 年龄过滤过严 | 年龄过滤排除了相关文档 | 年龄过滤排除 |
| 重排序模型不匹配 | BAAI/bge-reranker-v2-m3 对特定领域表现差 | 排序倒置, 重排序误判 |
| 查询路由错误 | 简单/复杂查询分类错误导致走了错误流水线 | 语义不匹配 |
| 分块粒度不当 | chunk_size 过大导致信息稀释，或过小导致上下文丢失 | 部分召回, 未召回 |

**抽样策略** (Bad Case > 50 时):
- 按失败类型分层抽样：未召回/排序倒置/误杀/部分召回/年龄过滤排除/重排序误判 各占比例与总体一致
- 每层至少抽取 3 条，确保各失败类型都有代表
- 若某层不足 3 条，全量抽取

**降级策略细化**:

| 异常类型 | 处理策略 |
|---------|---------|
| 超时 (> 120s) | 重试 1 次，仍超时则降级 |
| Rate Limit (429) | 等待 retry-after 后重试 1 次，仍失败则降级 |
| 返回格式错误 | 使用 `json-repair` 库修复 (CLAUDE.md 要求)，修复失败则降级 |
| 内容安全拦截 | 标记并跳过该 Bad Case，继续处理剩余 |
| API 完全不可用 | 跳过本层，前端展示"LLM 服务不可用，已跳过深度诊断" |

## 5.4 Layer 4: 数据质量 (3 种校验)

### 5.4.1 校验 4a: Golden 覆盖度分析

**定位**: 检查测试用例是否覆盖了足够的源文档和章节

**触发条件**: 测试完成后

**输入**:
- 测试用例列表 (含 source_document_id)
- 源文档列表 (含 chapter_count)

**输出**:
- 覆盖度报告 (书籍覆盖率、章节覆盖率、各领域覆盖文档数)

**校验规则**:

| 规则 | 触发条件 | 警告级别 |
|------|---------|---------|
| 书籍覆盖率低 | 覆盖书籍数 / 总书籍数 < 60% | ⚠️ |
| 章节覆盖率低 | 覆盖章节数 / 总章节数 < 40% | ⚠️ |
| 某领域无覆盖 | 某发展领域无对应测试用例 | 🔴 |

### 5.4.2 校验 4b: 分块质量评分

**定位**: 检查文档分块的信息密度、可读性、切分合理性

**触发条件**: 测试完成后

**输入**:
- 分块列表 (content, metadata)

**输出**:
- 分块质量报告 (平均质量分、低质量分块比例、低质量示例)

**校验规则**:

| 规则 | 触发条件 | 警告级别 |
|------|---------|---------|
| 低质量分块过多 | 低质量比例 > 10% | ⚠️ |
| 平均质量过低 | 平均质量分 < 0.6 | 🔴 |

**质量维度与验收标准** (修正后):

| 维度 | 计算方式 | 高质量 | 低质量 |
|------|---------|--------|--------|
| 信息密度 | 1 - (停用词数 / 总词数)。停用词列表使用中文通用停用词表 (的/了/是/在/有/和/或/但等) | > 0.6 (停用词占比 < 40%) | < 0.3 (停用词占比 > 70%) |
| 结构化程度 | (标题数 × 2 + 列表项数) / 段落数。反映文档的结构化程度，结构化越高可读性越好 | > 0.5 | < 0.1 |
| 切分合理性 | 以完整句子/段落结束的分块占比。检查 chunk 末尾是否为句号/问号/感叹号/段落结束标记 | > 90% | < 70% |

**综合质量分**: 三个维度加权平均 (信息密度 40% + 结构化程度 30% + 切分合理性 30%)

**专业术语密度** (辅助指标，不纳入综合分):
- 计算: 儿童发展领域专业术语数 / 总词数
- 专业术语列表来自领域知识库 (如: 感统训练/精细动作/粗大动作/前庭觉/本体觉等)
- 用于区分"专业内容"和"通用内容"，辅助判断分块的信息价值

### 5.4.3 校验 4c: 文档时效性检查

**定位**: 检查源文档内容是否过期 (针对儿童发展领域特殊调整)

**触发条件**: 测试完成后

**输入**:
- 源文档列表 (含 content_summary, upload_date, document_type)

**输出**:
- 时效性报告 (过期文档数、过期比例、过期文档列表)

**文档类型分类与时效阈值**:

| 文档类型 | 时效阈值 | 说明 |
|---------|---------|------|
| 政策法规/指南 | 3 年 | 如教育部最新指南、地方政策，更新频繁 |
| 学术研究/实证 | 10 年 | 如实验研究、统计分析，有一定时效性 |
| 经典理论 | 不检查 | 如 Piaget 认知发展理论、Vygotsky 社会文化理论，长期有效 |
| 实操方法/训练方案 | 5 年 | 如感统训练方案、语言干预方法，可能随研究更新 |

**校验规则**:

| 规则 | 触发条件 | 警告级别 |
|------|---------|---------|
| 过期文档过多 | 过期比例 > 20% | ⚠️ |
| 存在严重过期文档 | 政策法规类 > 5 年前 | 🔴 |

**文档类型识别**: 通过文档元数据中的 `document_type` 字段识别，若未标注则默认为"学术研究"类

## 5.5 Layer 5: 检索链路 (3 种校验)

### 5.5.1 校验 5a: Embedding 质量校验

**定位**: 检查 Embedding 模型的语义区分能力（修正方法论）

**触发条件**: 测试完成后

**输入**:
- 测试用例查询列表
- Embedding 向量 (通过 DashScope API 获取，使用 SafeDashScopeEmbedding 包装器)

**输出**:
- Embedding 质量报告 (同义查询对相似度、区分度指标、异常向量检测)

**校验方法** (修正后):

| 方法 | 说明 | 阈值 |
|------|------|------|
| 同义查询对验证 | 人工构造或从历史日志提取语义等价的查询对 (如"什么是感统训练" vs "感统训练是什么")，检查其 embedding 余弦相似度 | 同义对相似度 ≥ 0.85 ⚠️ 低于则警告 |
| 区分度检查 (Silhouette Score) | 按领域分组计算 silhouette score，衡量同类查询聚拢、异类查询分离的程度 | silhouette ≥ 0.5 为良好，< 0.3 ⚠️ 警告 |
| 异常向量检测 | 检测零向量、NaN、维度异常、全相同向量 | 发现异常 🔴 严重警告 |

**同义查询对数据来源**:
- **首次运行**: 系统内置一批硬编码的同义查询对（约 20 对），覆盖 5 大发展领域（感统/语言/认知/社交/情绪），每领域 4 对。内置数据存储在 `backend/src/core/validation/synonym_query_pairs.json`，格式: `[{"query_a": "什么是感统训练", "query_b": "感统训练是什么", "domain": "感统"}, ...]`
- **后续运行**: 系统自动从历史 `QueryIntentLog` 中提取高置信度（confidence ≥ 0.9）且意图类型相同的查询对，若两个查询的编辑距离相似度 ≥ 0.7 但措辞不同，自动加入同义查询对池
- **用户维护**: 用户可在测试集详情页点击"管理同义查询对"，手动添加/删除/编辑同义查询对，数据存储在新增的 `SynonymQueryPair` 表中（字段: `id (UUID)`, `query_a (TEXT)`, `query_b (TEXT)`, `domain (VARCHAR)`, `created_by`, `created_at`, `source (ENUM: builtin / auto_extracted / manual)`）
- **优先级**: 用户手动添加的同义查询对 > 自动提取的同义查询对 > 内置同义查询对。校验时优先使用用户手动添加的对，若数量不足 10 对，补充自动提取的，仍不足则使用内置的
- **`SynonymQueryPair` 表定义**:
  ```python
  class SynonymQueryPair(Base):
      """同义查询对 - Layer 5a Embedding 质量校验的数据来源"""
      id (UUID)                                # 主键
      query_a (TEXT)                           # 查询 A
      query_b (TEXT)                           # 查询 B
      domain (VARCHAR(64))                     # 发展领域
      created_by (VARCHAR(64))                 # 创建者
      created_at (DATETIME)                    # 创建时间
      source (ENUM: builtin / auto_extracted / manual)  # 数据来源
      active (bool, default=True)              # 是否启用
      # 索引: INDEX(domain, active) 支持按领域查询启用的同义对
  ```

**注意**: 不再使用"同类查询组内平均相似度"方法，因为同一领域/年龄的不同查询语义本就不该相似。

### 5.5.2 校验 5b: 意图识别准确率

**定位**: 检查查询意图分类的准确性

**触发条件**: 测试完成后

**数据来源** (双轨制):

| 来源 | 说明 | 优先级 |
|------|------|--------|
| LLM 自动标注 (Baseline) | 使用 LLM 对查询意图分类，置信度 ≥ 0.8 的标记为"自动标注"，< 0.8 的标记为"待确认" | 默认启用 |
| 人工标注 (校准) | 用户在测试集详情页点击"标注意图"，抽样选择用例标注意图类型，用于校准 LLM 自动标注 | 可选 |

**意图类型分类**:
- `factual_query`: 事实查询 (如"什么是感统训练")
- `how_to`: 方法指导 (如"如何进行感统训练")
- `comparison`: 对比分析 (如"感统训练和物理治疗的区别")
- `definition`: 定义解释 (如"前庭觉是什么")
- `troubleshooting`: 问题诊断 (如"孩子注意力不集中怎么办")

**输入**:
- 查询分析结果 (系统运行测试时，对每个用例查询自动进行的意图分类结果，存储在测试执行日志中)
- 标注数据 (LLM 自动标注 + 人工标注)

**输出**:
- 意图准确率报告 (整体准确率、各意图类型准确率、低置信度查询列表)

**校验规则**:

| 规则 | 触发条件 | 警告级别 |
|------|---------|---------|
| 意图识别准确率低 | 整体准确率 < 80% (基于人工标注部分计算) | ⚠️ |
| 低置信度查询过多 | LLM 置信度 < 0.8 的查询占比 > 30% | ⚠️ |

### 5.5.3 校验 5c: 错误模式分组

**定位**: 对 Bad Case 进行多维交叉分组，找出共性失败模式

**触发条件**: 测试完成后

**输入**:
- Bad Case 列表

**输出**:
- 错误模式分组报告 (各分组名称、数量、示例、建议修复方案)

**分组方法** (多维交叉，非 ML 聚类):

| 维度 | 取值 |
|------|------|
| 错误类型 | 未召回 / 排序倒置 / 误杀 / 部分召回 / 年龄过滤排除 / 重排序误判 |
| 发展领域 | 感统 / 语言 / 认知 / 社交 / 情绪 |
| 年龄组 | 0-3岁 / 3-6岁 / 6-12岁 |

**交叉分组输出**: 每个 (错误类型 × 领域 × 年龄组) 组合为一个分组，输出:
- 分组名称 (如"未召回-感统-3-6岁")
- Bad Case 数量
- 占比 (该分组 Bad Case 数 / 总 Bad Case 数)
- 示例查询 (最多 3 条)
- 建议修复方案 (规则映射表，见下表)

**修复方案规则映射**:

| 错误模式 | 建议修复 |
|---------|---------|
| 未召回-任何-任何 | 增加 top_k，检查关键词覆盖 |
| 排序倒置-任何-任何 | 增加 reranker_initial_k，检查重排序模型 |
| 误杀-任何-任何 | 减小 fusion_threshold，检查同义词扩展 |
| 年龄过滤排除-任何-任何 | 降低 age_filter_strictness |
| 部分召回-任何-任何 | 检查分块粒度，调整 chunk_size |

## 5.6 Layer 6: 验证保障 (4 种校验)

### 5.6.1 校验 6a: 回归检测

**定位**: 对比当前运行与上一次运行，检测指标是否退化

**触发条件**: 存在上一次运行记录

**输入**:
- 当前运行指标
- 上一次运行指标

**输出**:
- 回归检测报告 (退化指标列表、退化幅度、严重程度)

**校验规则**:

| 规则 | 触发条件 | 警告级别 |
|------|---------|---------|
| 指标轻微退化 | 某指标下降 > 5% | ⚠️ |
| 指标严重退化 | 某指标下降 > 15% | 🔴 |

### 5.6.2 校验 6b: 交叉验证

**定位**: 检查各领域/年龄组的指标一致性

**触发条件**: 测试完成后

**输入**:
- 测试用例结果 (按领域/年龄分组)

**输出**:
- 交叉验证报告 (各组指标、一致性评分、表现差的领域列表)

**校验规则**:

| 规则 | 触发条件 | 警告级别 |
|------|---------|---------|
| 某领域表现显著低于平均 | 某领域 F1 < 平均 F1 - 0.1 | ⚠️ |
| 整体一致性差 | 一致性评分 < 0.7 | ⚠️ |

### 5.6.3 校验 6c: 成本效果分析

**定位**: 分析配置变更带来的指标提升与额外成本的比例

**触发条件**: 存在配置变更

**配置变更定义**: 当前运行的 config_version_id 与上一次运行的 config_version_id 不同

**输入**:
- 配置变更列表 (当前 ConfigVersion 与上一次 ConfigVersion 的 config_snapshot diff)
- 指标变化 (当前运行与上一次运行的指标差异)
- LLM 调用成本 (token 消耗)

**输出**:
- 成本效果报告 (提升分数、额外成本、成本效果比、是否值得)

**成本效果比公式**:

```
成本效果比 = 指标提升得分 / 额外成本得分

其中:
  指标提升得分 = ΔP@5 × 30 + ΔR@5 × 30 + ΔF1 × 20 + ΔMRR × 10 + ΔNDCG × 10
  # 各指标变化乘以其权重系数，满分 100（当所有指标从 0 提升到 1 时）
  # 实际场景中指标变化通常在 0.01~0.20 之间，得分通常在 0.3~15 之间

  额外成本得分 = log2(1 + 额外 token 数 / 1000)
  # 使用对数缩放，防止 token 数过大时成本效果比趋近于 0
  # 1000 token 约为单次查询的额外消耗基准
  # 典型值: 0 tokens→0, 1000 tokens→1, 10000 tokens→3.32, 100000 tokens→6.66

  特殊处理: 当额外 token 数 = 0 时 (纯参数调整)
    成本效果比 = 指标提升得分 × 10
    # 零成本优化给予固定权重放大，而非除以极小值导致比例失真
    # 示例: 指标提升得分 = 2.9 → 成本效果比 = 29 (仍显示"强烈推荐"，但数值合理)
```

**示例计算**:
```
场景 1: 开启查询重写功能
  ΔP@5 = +0.08, ΔR@5 = +0.03, ΔF1 = +0.05, ΔMRR = +0.02, ΔNDCG = +0.01
  额外 token = 50000 (128 用例 × 390 token/用例)

  指标提升得分 = 0.08×30 + 0.03×30 + 0.05×20 + 0.02×10 + 0.01×10 = 4.6
  额外成本得分 = log2(1 + 50000/1000) = log2(51) ≈ 5.67
  成本效果比 = 4.6 / 5.67 ≈ 0.81 → 强烈推荐

场景 2: 仅调整 bm25_top_k (无 LLM 调用)
  ΔP@5 = +0.05, ΔR@5 = +0.02, ΔF1 = +0.03, ΔMRR = +0.01, ΔNDCG = +0.01
  额外 token = 0

  指标提升得分 = 0.05×30 + 0.02×30 + 0.03×20 + 0.01×10 + 0.01×10 = 2.9
  零成本场景: 成本效果比 = 2.9 × 10 = 29 → 强烈推荐 (零成本优化，固定权重放大)
```

**校验规则**:

| 规则 | 触发条件 | 建议 |
|------|---------|------|
| 成本效果比低 | 成本效果比 < 0.1 | 不建议应用该变更 (成本高，提升小) |
| 成本效果比中等 | 0.1 ≤ 成本效果比 ≤ 0.5 | 可考虑应用 (权衡成本与效果) |
| 成本效果比高 | 成本效果比 > 0.5 | 强烈推荐应用 (成本低，提升大) |

**成本类型说明**:
- 检索参数调整 (top_k, fusion_threshold): 成本几乎为零，成本效果比通常很高
- 开启 LLM 功能 (查询重写, 同义词扩展): 成本为每次查询的 LLM token 消耗
- 分块参数调整 (chunk_size): 成本为重新分块和重新 Embedding 的一次性消耗

### 5.6.4 校验 6d: A/B 影子测试

**定位**: 同时运行两个配置，逐条对比效果

**触发条件**: 用户主动触发

**输入**:
- 配置 A
- 配置 B
- 测试集

**输出**:
- A/B 对比报告 (胜出方、各用例对比、指标差异、统计显著性)
- **报告生成策略**: A/B 测试生成 **3 份报告**：
  1. **配置 A 的常规报告** (TestReport): 包含 Layer 1-5 校验结果，`run_id` 指向配置 A 的 TestRun
  2. **配置 B 的常规报告** (TestReport): 包含 Layer 1-5 校验结果，`run_id` 指向配置 B 的 TestRun
  3. **A/B 对比报告** (独立 TestReport): 包含 Layer 6d 对比结果，`run_id` 为 NULL（不关联单个 TestRun，通过 `ab_test_id` 关联两个 TestRun）
- 前端展示：用户看到 3 个报告入口，A/B 对比报告有特殊标记"🔬 A/B 对比"
- 两个常规报告通过 `ab_test_id` + `ab_test_side` 关联到同一 A/B 测试

**展示内容**:
- 总体胜出方 (A 或 B)
- 各用例逐条对比 (hit@k 差异)
- 指标总差异 (precision_delta, recall_delta, f1_delta)
- 统计显著性 (p-value, 置信区间)

**成本提示需求**:
- 触发前必须展示预计耗时 (基于测试集用例数量和平均单用例耗时计算)
- 运行中显示 `[取消测试]` 按钮，点击后二次确认，已完成的用例结果保留
- 必须支持"抽样模式"：用户可选择抽样比例，系统按分层随机抽样选取用例

**并发控制与资源隔离**:
- A/B 测试采用**串行执行**策略：先执行配置 A 的全部用例，再执行配置 B 的全部用例，避免并发检索导致资源竞争
- 两次执行共用同一个 RetrievalService 实例，但使用不同的配置快照（配置 A 和配置 B 的 `config_snapshot`）
- 执行过程中，每个配置的运行结果独立存储，通过 `ab_test_id` + `ab_test_side` 关联同一 A/B 测试的两次运行
- 用户取消测试时，已完成的配置执行结果保留，未执行的配置跳过，报告中标注"测试已取消，结果基于部分配置"
- 单次 A/B 测试最大并发任务数为 1，同一时间只允许一个 A/B 测试运行

**抽样模式** (修正后):

| 测试集用例数 | 抽样策略 | 说明 |
|-------------|---------|------|
| ≤ 30 | 禁止抽样，强制全量 | 样本量过小，抽样结果无统计意义 |
| 31-100 | 50% 分层抽样 | 按领域×年龄组分层，每层至少抽取 3 条 |
| > 100 | 20% 或 50% 分层抽样 | 用户可选，按领域×年龄组分层 |

**分层随机抽样**:
- 按 (领域 × 年龄组) 交叉分层，确保各领域/年龄组按比例抽取
- 每层至少抽取 3 条，若某层不足 3 条则全量抽取
- 抽样模式需在报告中标注"抽样结果，仅供参考，建议全量验证"

**统计显著性检验**:
- 使用配对 t-test (paired t-test) 比较 A/B 配置的指标差异
- 输出 p-value: p < 0.05 表示差异显著，p ≥ 0.05 表示差异不显著
- 输出 95% 置信区间: 展示指标差异的可能范围
- 若 p ≥ 0.05，报告中标注"差异不显著，A/B 配置效果相当"
