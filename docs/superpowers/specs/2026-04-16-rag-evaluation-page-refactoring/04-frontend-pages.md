## 3.6 前端页面路由

```
/rag-eval                          # RAG 评估平台入口
├── /rag-eval/test-sets            # 测试集列表
├── /rag-eval/test-sets/{id}       # 测试集详情 + 用例管理
├── /rag-eval/test-sets/{id}/drafts  # 草稿审核页 (从测试集详情页弹窗或独立页面进入)
├── /rag-eval/runs                 # 运行历史列表
├── /rag-eval/runs/{id}            # 单次运行详情 + SSE 进度
└── /rag-eval/reports/{id}         # 评估报告 + 配置/提示词编辑 (核心页面)
```

**路由说明**:
- 当前前端**不存在** `/rag-eval` 相关路由，此为全新路由
- **旧路由 `/rag-evaluation` 处理**: 直接删除旧的 `/rag-evaluation` 路由和 `RagEvaluationPage` 组件，不保留兼容。旧路由的所有功能由新的 `/rag-eval/*` 子路由替代
- **`OneClickOptimize` 组件直接删除**: 该组件的"一键应用推荐配置"行为违反"禁止替用户做决策"原则，新功能由推荐模式面板的"采纳→审查→保存"三步流程替代
- 数据库表结构按新设计直接创建，不保留旧字段
- 草稿审核页入口：测试集详情页显示"待审核草稿 (N)"徽标，点击后进入审核页

## 4.2 推荐模式面板设计 (辅助决策，非自动执行)

> **用户需求**: 推荐只是参考，不替用户做决策。每个推荐必须回答：**为什么改？改了有什么影响？前后对比是什么？**

**核心原则**:
- 推荐只是**参考**，不替用户做决策
- 每个推荐必须回答：**为什么改？改了有什么影响？前后对比是什么？**
- 用户需要**预览影响**后再决定是否应用
- **禁止"一键应用"式设计**，用户需要审查后再保存

**三种模式**：

| 模式 | 定位 | 展示内容 | 触发场景 |
|------|------|---------|---------|
| **推荐模式** (默认) | 报告驱动，展示诊断发现 | 推荐修改区 + 影响预览 + 原因解释 | 报告页面默认进入 |
| **向导模式** | 按功能域浏览 | 按功能域分组（检索/重排序/年龄过滤/分块），关键参数优先 | 用户主动切换 |
| **专家模式** | 全量控制 | 全部 RAG 配置参数树 + 全部提示词列表 | 高级用户主动切换 |

**交互说明**:

> **用户需求**: 用户需要"采纳 → 审查 → 保存"三步分离，不能合并为一步。

| 操作 | 行为 | 用户需求 |
|------|------|---------|
| **复测** | 使用当前报告关联的测试集和配置版本，创建新的 TestRun 并跳转到运行详情页 | 验证当前配置在相同测试集上的效果是否一致 |

| 操作 | 行为 | 用户需求 |
|------|------|---------|
| **查看对比** | 弹出对比视图，展示修改前后的差异（配置值或提示词内容） | 必须看到前后差异 |
| **预览影响** | 展示预期指标变化、风险警告、历史参考案例（数据来自 `TuningSuggestionRecord.expected_effect` 结构化字段） | 必须知道改了有什么后果 |
| **采纳** | 将该修改加入"已采纳列表"，**不立即生效** | 推荐只是参考，不自动生效 |
| **忽略** | 隐藏该推荐，可后续在"已忽略"列表中恢复。支持选择忽略范围：`仅本次报告` 或 `该测试集的所有运行` | 用户有权拒绝推荐 |
| **审查已采纳项** | 展开审查面板（抽屉式），展示所有已采纳修改的完整 diff、影响预览、支持自定义调整建议值和移除单项 | 保存前必须总览审查 |
| **保存为新版本** | 将所有已采纳的修改保存为新的 ConfigVersion 和 PromptVersion，**必须原子执行** | 配置和提示词作为一个整体版本保存，部分失败时全部回滚 |
| **取消修改** | 清空已采纳列表 | 用户可随时撤销 |

**面板布局适配**:
- 默认使用右侧固定分栏，宽度 380px
- 13-14 寸屏幕（宽度 < 1440px）自动切换为 Drawer 抽屉式，从右侧滑出，覆盖 40% 屏幕宽度
- 用户可随时通过面板顶部的 `[固定] [抽屉]` 切换布局模式

**原子性需求**:
- 配置和提示词必须作为一个整体版本保存 (ConfigChangeSet)
- 如果配置保存成功但提示词保存失败，必须回滚配置保存操作
- 前端必须展示保存结果：成功时显示新版本号，失败时显示具体失败项和回滚状态

**事务管理实现** (Service 层):
```python
async def save_config_change_set(config_data, prompt_data, session):
    """原子保存配置+提示词变更集"""
    # 方式 1: 使用 async with session.begin()（自动 commit/rollback）
    async with session.begin():
        # 1. 创建配置版本
        config_version = ConfigVersion(
            version_label=await generate_version_label(session),
            config_snapshot=config_data,
            created_by=current_user,
            change_summary=generate_summary(config_data)
        )
        session.add(config_version)
        await session.flush()  # 获取 ID
        
        # 2. 创建变更集
        change_set = ConfigChangeSet(
            change_set_label=await generate_change_set_label(session),
            config_version_id=config_version.id,
            status='committed'
        )
        session.add(change_set)
        await session.flush()  # 获取 change_set.id
        
        # 3. 创建提示词版本并关联
        for prompt in prompt_data:
            pv = PromptVersion(
                prompt_key=prompt.key,
                version_label=prompt.version_string,
                version_number=await next_prompt_version_number(session, prompt.key),
                content=prompt.content,
                created_by=current_user,
                change_summary=prompt.summary
            )
            session.add(pv)
            await session.flush()  # 获取 pv.id
            
            csp = ConfigChangeSetPrompt(
                change_set_id=change_set.id,
                prompt_version_id=pv.id
            )
            session.add(csp)
        # async with session.begin() 块结束时自动 commit
        # 任何异常自动 rollback
    
    # 事务提交成功后才发布 Redis 事件
    await redis.publish("config_changed", json.dumps({
        "event": "config_changed",
        "change_set_id": change_set.id,
        "timestamp": datetime.utcnow().isoformat(),
        "changed_by": current_user
    }))
```

**注意**: `async with session.begin()` 会在块结束时自动调用 `commit()`，遇到异常自动 `rollback()`。**不需要**显式调用 `await session.commit()`。如果在块内显式调用 `commit()` 会导致重复提交异常。

**事务提交与热重载时序** (关键):
```
执行顺序（严格保证）:
  1. async with session.begin() 块结束 → 自动 commit    ← MySQL 事务提交，数据持久化
  2. 发布 Redis Pub/Sub 事件              ← 事务已提交，其他实例一定能读到新数据
  3. 返回前端成功响应

错误顺序（会导致不一致）:
  ❌ 先发布 Redis 事件 → 再 commit        ← 其他实例可能读到旧数据（事务未提交）
  ❌ commit 和发布事件并行                ← 竞态条件，无法保证顺序
```

**多实例配置生效延迟**:
- 事务提交后，Redis Pub/Sub 事件几乎瞬时到达（< 10ms）
- 各实例收到事件后刷新本地缓存，刷新耗时 < 50ms（单次数据库查询）
- **可接受延迟**: 配置变更后，所有实例在 **100ms 内** 生效
- **短暂窗口处理**: 在 100ms 窗口内，部分实例可能使用旧配置。由于 TestRun 创建时快照 `config_version_id`，运行中的测试不受影响，仅影响窗口内新创建的 TestRun

**配置热重载机制**:

> **需求**: 配置保存后，系统必须自动生效，无需手动重启服务。

| 机制 | 说明 | 实现方式 |
|------|------|---------|
| **生效时机** | 配置保存后立即生效，**下次 TestRun 使用新配置** | 当前正在运行的 TestRun 继续使用保存前的配置快照，不受影响 |
| **多实例同步** | 多实例部署时，所有实例必须同步更新 | 通过 Redis Pub/Sub 发布 `config_changed` 事件，各实例订阅后刷新本地配置缓存 |
| **配置缓存** | 配置数据缓存在内存，避免每次查询数据库 | 使用 `ConfigCache` 单例，结构: `{config_version_id: {config_snapshot, loaded_at}}`；订阅 Redis 事件后调用 `reload()` 刷新 |
| **缓存失效策略** | 配置变更后失效旧版本缓存，加载新版本 | `reload()` 查询最新 ConfigVersion，替换缓存字典；旧版本条目在 5 分钟 TTL 后自动清理 |
| **冲突处理** | 运行中的 TestRun 不受配置变更影响 | TestRun 创建时快照 `config_version_id`，运行时始终读取该版本的 `config_snapshot` |
| **回滚生效** | 配置回滚同样触发热重载 | 回滚操作创建新的 `ConfigChangeSet` (status=rolled_back)，同时发布 `config_changed` 事件 |

**Redis Pub/Sub 事件格式**:
```json
{
  "event": "config_changed",
  "change_set_id": "uuid",
  "timestamp": "2026-04-16T10:30:00Z",
  "changed_by": "user_id"
}
```

**实例端处理逻辑**:
```python
async def on_config_changed(message: str):
    """接收配置变更事件，刷新本地缓存"""
    event = json.loads(message)
    await ConfigCache.reload()  # 从数据库重新加载最新配置
    logger.info(f"配置已刷新: change_set_id={event['change_set_id']}")
```

**IgnoredSuggestion 数据模型**:
```python

    """忽略建议记录 - 独立表，支持高效跨报告查询"""
    id (UUID)                                # 主键
    test_set_id (UUID, FK → TestSet.id)      # 绑定测试集
    report_id (UUID, FK → TestReport.id, 可选)  # report 级别时填写

    suggestion_type (ENUM: config / prompt)  # 配置建议或提示词建议
    ignore_scope (ENUM: report / test_set)   # 忽略范围
    ignored_by (VARCHAR(64))                 # 操作用户

    restored (bool, default=False)           # 是否已恢复
    restored_at (DATETIME, 可选)             # 恢复时间
    # 索引: INDEX(test_set_id, ignore_scope, restored) 支持快速查询活跃忽略记录
    # 级联删除: test_set_id 删除时，自动清理关联的忽略记录
```

**查询逻辑**:
- 生成推荐列表时，先查询 `IgnoredSuggestion` 表，过滤 `restored=False` 且 `ignore_scope` 匹配的记录
- `test_set` 级别的忽略记录对该测试集的所有报告生效
- `report` 级别的忽略记录仅对当前报告生效

| **JSON** | 系统集成 | 前端生成：直接从报告 API 响应数据下载为 JSON 文件 | 完整报告数据 (含所有校验层原始结果) |

**API 端点**:
- `POST /api/reports/{report_id}/export` → 创建导出任务，返回 `{task_id, status: "pending"}`
- `GET /api/exports/{task_id}/status` → 查询任务状态 `{status: "pending|processing|completed|failed", progress?: number}`
- `GET /api/exports/{task_id}/download` → 返回 PDF 文件流（仅当 status=completed 时可用）
- CSV 和 JSON 导出由前端直接处理，无需后端端点

**PDF 导出技术方案**:
- **技术选型**: 使用 `weasyprint` 库（纯 Python，无需系统依赖如 wkhtmltopdf）
- **模板方式**: HTML 模板 + Jinja2 渲染 → weasyprint 转换为 PDF
- **模板位置**: `backend/src/templates/reports/` 目录，包含 `report_summary.html`（报告摘要模板）
- **依赖声明**: 在 `pyproject.toml` 中添加 `weasyprint` 依赖，使用 `uv add weasyprint`
- **字体处理**: 使用系统自带字体（macOS: PingFang SC, Windows: Microsoft YaHei），PDF 模板中通过 CSS `font-family` 指定中文字体回退链
- **样式处理**: 使用内联 CSS，避免外部样式表加载问题；图表使用 weasyprint 支持的 SVG 内联渲染
- **文件大小预估**: 不含用例明细的 PDF 约 200-500KB；含 128 条用例明细约 1-2MB

**导出任务存储**: 导出任务状态存储在 Redis 中（key: `export_task:{task_id}`，TTL: 24 小时），包含 `{task_id, report_id, status, progress, download_url, created_at, completed_at}`。任务完成后生成预签名下载 URL，存入 Redis。

**交互**:
- 点击 `[导出]` 按钮 → 弹出格式选择对话框
- 选择 PDF 格式后，后端创建异步任务，前端显示"正在生成 PDF..."加载状态
- 任务完成后，SSE 推送 `export_ready` 事件，前端自动触发下载
- 多用户并发导出时，后端通过任务队列限制**同时处理的 PDF 导出任务最多 2 个**，超出任务排队等待
- 单个 PDF 导出任务超时时间为 60 秒，超时标记为 failed 并通知前端
