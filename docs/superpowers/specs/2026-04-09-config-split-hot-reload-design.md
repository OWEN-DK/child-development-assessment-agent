# 配置文件拆分与热更新方案设计文档

## 一、方案概述
当前`settings.py`文件规模已达近700行，包含10多个类别的配置，维护成本高，修改风险大。本方案将配置文件按职责拆分，并实现配置热更新能力，在不破坏现有代码兼容性的前提下，提升配置可维护性和运行时灵活性。

## 二、配置拆分方案
### 2.1 拆分原则
- 按配置领域/功能类别拆分，每个配置文件职责单一
- 保持原有Pydantic配置定义方式不变
- 对外保持统一的`settings`实例接口，现有代码零修改兼容

### 2.2 拆分后文件结构
```
backend/src/config/
├── __init__.py                # 配置聚合入口，对外导出统一的settings实例
├── app_settings.py            # 应用基础配置
├── model_settings.py          # 模型相关配置
├── rag_settings.py            # 核心RAG配置
├── log_settings.py            # 日志配置
├── path_settings.py           # 路径配置
├── pageindex_settings.py      # PageIndex服务配置
├── query_fusion_settings.py   # 查询路由与结果融合配置
├── embedding_settings.py      # Embedding模型配置
├── vector_store_settings.py   # 向量存储配置
├── semantic_splitter_settings.py # 语义分块配置
└── ml_scoring_settings.py     # ML评分功能配置
```

### 2.3 各文件内容说明
| 文件名 | 包含配置内容 |
|--------|--------------|
| **app_settings.py** | 应用名称、版本、调试模式、服务IP、端口、代码热重载开关 |
| **model_settings.py** | 所有`model_`开头的配置、DashScope API密钥 |
| **rag_settings.py** | RAG混合检索、缓存、查询重写、相似度阈值、年龄过滤、分层内容生成、重排序器、自动持久化、性能、监控等所有RAG相关配置 |
| **log_settings.py** | 日志级别、日志文件路径 |
| **path_settings.py** | 数据目录、RAG存储目录、上传临时目录、模型文件路径等 |
| **pageindex_settings.py** | PageIndex服务开关、API地址、密钥、并发、超时、熔断、重试、降级等配置 |
| **query_fusion_settings.py** | 查询路由分类器、结果融合相关配置 |
| **embedding_settings.py** | 嵌入模型名称、最大长度、批处理大小等配置 |
| **vector_store_settings.py** | 向量存储类型、存储配置等 |
| **semantic_splitter_settings.py** | 语义分块相关的所有配置 |
| **ml_scoring_settings.py** | ML评分开关、模式、模型路径、权重等配置 |
| **__init__.py** | 聚合所有配置类，继承实现统一的Settings类，导出settings实例，实现热更新逻辑 |

> 优化说明：原计划中的`rule_metadata_settings.py`合并到现有的`rules.py`配置体系中，避免重复的配置管理体系，规则相关配置统一由`rules.py`管理。

## 三、热更新方案设计
### 3.1 设计目标
- 支持运行时配置变更自动生效，无需重启应用
- 区分可热更新配置与需重启配置，提供明确的变更指引
- 完全兼容现有代码接口，无侵入式实现

### 3.2 技术实现
#### 3.2.1 核心架构
```
┌─────────────────┐     ┌──────────────────┐     ┌─────────────────┐
│  配置文件变更   │────▶│  文件系统监控    │────▶│  配置重新加载   │
└─────────────────┘     └──────────────────┘     └─────────────────┘
                                                         │
                                                         ▼
┌─────────────────┐     ┌──────────────────┐     ┌─────────────────┐
│  组件同步更新   │◀────│  变更类型判断    │◀────│  配置变更对比   │
└─────────────────┘     └──────────────────┘     └─────────────────┘
         │
         ▼
┌─────────────────┐
│  变更日志记录   │
└─────────────────┘
```

#### 3.2.2 实现细节
1. **文件系统监控**：使用`watchdog`库监控以下路径变更：
   - .env环境变量文件
   - 配置文件所在目录（减少监听数量，提高性能）

2. **配置重载逻辑**：
   ```python
   def reload_settings():
       """重新加载配置并返回新的Settings实例
       
       实现失败回退机制：重载失败时返回原有配置实例
       """
       try:
           new_settings = Settings()
           # 执行Pydantic校验，确保配置合法
           new_settings.model_validate(new_settings.model_dump())
           return new_settings
       except Exception as e:
           logger.error(f"配置重载失败，保留原有配置: {e}")
           return settings
   ```

3. **原子性更新保证**：
   - 使用读写锁实现配置更新原子性，读操作无锁，写操作时阻塞新的读请求直到更新完成
   - 配置更新过程中所有请求获取到的配置始终是完整一致的版本，不会出现半更新状态

4. **变更对比与处理**：
   - 对比新旧配置差异，按字段判断是否支持热更新
   - 热更新字段：自动同步到所有依赖组件（检索引擎、重排序器、分块器等）
   - 需重启字段：记录警告日志，提示用户需要重启应用生效

4. **热更新字段范围**（根据原有`_is_hot_reloadable`方法定义）：
   - 支持热更新：RAG检索参数、缓存参数、分块参数、查询路由参数、融合参数、分层内容生成参数、规则相关参数等
   - 需重启：模型配置、API密钥、路径配置、存储配置、并发参数等

5. **组件更新机制**：
   - 复用现有的`event_bus`事件总线和`ConfigChangedEvent`事件，避免重复实现
   - 各组件可以订阅关心的配置变更事件
   - 当配置变更时，主动推送变更到订阅组件，实现实时更新

6. **与数据库动态配置协同**：
   - 配置优先级：数据库动态配置 > 文件配置 > 默认值
   - 文件变更热更新时，会保留数据库中的覆盖值，不会被文件配置覆盖
   - 两种热更新途径并行不悖：文件修改适合代码级配置变更，数据库修改适合运营级配置调整
   - 变更事件统一通过`event_bus`派发，组件无需关心配置变更来源

### 3.3 兼容性保证
- 对外导出的`settings`实例接口完全不变
- 所有原有属性、方法（如`get_all_config_metadata`、`llm_models`、`rag_config`等）保持不变
- 现有代码无需任何修改即可正常运行

## 四、实施步骤
1. 创建所有拆分后的配置文件，将对应配置字段迁移到各文件
2. 修改`__init__.py`实现配置聚合和热更新逻辑
3. 保留原有`settings.py`作为过渡，添加弃用提示，重定向到新的配置入口
   - 过渡期3个月，到期后删除原settings.py文件
   - 原有导入`from src.config.settings import settings`将自动重定向到新的配置实例
   - 日志中添加DeprecationWarning提示开发者迁移到新的导入路径`from src.config import settings`
4. 实现配置监控和热更新逻辑
5. 测试验证：
   - 验证所有配置项加载正确
   - 验证热更新功能正常工作
   - 验证现有业务代码无兼容性问题
6. 可选：迁移所有导入引用到新的`from src.config import settings`，删除原settings.py

## 五、测试策略
### 5.1 单元测试
- 验证每个拆分后的配置文件加载正确，字段默认值、类型、描述与原配置完全一致
- 验证聚合后的Settings类与原Settings类接口完全兼容，所有属性和方法都可以正常访问
- 测试配置重载逻辑：验证配置修改后可以正确加载，配置错误时能够回退到原有有效配置
- 测试原子性更新：验证并发读写时配置始终保持一致，不会出现半更新状态

### 5.2 集成测试
- 测试热更新功能：修改配置文件后验证新配置能够自动生效，相关组件能够正确接收到变更事件
- 测试与数据库动态配置的协同：验证数据库配置优先级高于文件配置，文件更新时不会覆盖数据库中的配置值
- 测试事件派发：验证配置变更后相关组件能够正确更新自身配置，功能正常运行

### 5.3 兼容性测试
- 全量回归测试现有业务功能，验证所有使用配置的代码无需修改即可正常运行
- 测试原有导入路径`from src.config.settings import settings`能够正常工作，并且正确输出弃用警告
- 测试所有配置的getter方法、工具函数与原实现完全一致，无破坏性变更

## 六、收益评估
1. **可维护性提升**：配置按类别拆分，单个文件规模大幅降低，便于定位和修改
2. **运维效率提升**：大部分配置变更无需重启服务，实时生效
3. **风险降低**：修改单一类别配置不会影响其他配置，减少误改风险
4. **兼容性好**：现有代码零修改即可享受新特性
