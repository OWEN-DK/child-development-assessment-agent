## 一、系统架构设计
### 设计思路说明
采用**分层架构设计**的核心理念是**关注点分离**，确保每个层级职责单一、可独立演进、易于测试和维护，同时完全适配现有代码结构，无需大规模重构。

---

### 1.1 整体架构分层
```
┌─────────────────────────────────────────────────────────┐
│                     接入层                                │
│  API网关 / 前端界面 / 对话入口 / 评估系统入口             │
├─────────────────────────────────────────────────────────┤
│                     业务逻辑层                            │
│  评估引擎 / 查询路由 / 对话管理 / 内容审核 / A/B测试框架   │
├─────────────────────────────────────────────────────────┤
│                     RAG核心层                            │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐       │
│  │ 检索模块    │  │ 生成模块    │  │ 评估模块    │       │
│  │ - 查询预处理│  │ - 提示工程  │  │ - 指标计算  │       │
│  │ - 混合检索  │  │ - 内容生成  │  │ - 自动化评估│       │
│  │ - 重排序    │  │ - 结果校验  │  │ - BadCase分析│      │
│  └─────────────┘  └─────────────┘  └─────────────┘       │
├─────────────────────────────────────────────────────────┤
│                     数据处理层                            │
│  文档解析 / 语义分块 / 元数据提取 / 向量生成 / 索引构建   │
├─────────────────────────────────────────────────────────┤
│                     数据存储层                            │
│  向量数据库 / 文档存储 / 元数据存储 / 缓存 / 测试集存储   │
└─────────────────────────────────────────────────────────┘
```
#### 分层设计 rationale
1. **接入层**：
   - 为什么这么设计：统一所有入口的流量管理、权限控制、限流熔断，避免在业务逻辑中重复实现这些横切关注点
   - 适配现有系统：当前系统已经有FastAPI网关和前端界面，直接复用即可，无需修改
   
2. **业务逻辑层**：
   - 为什么这么设计：将业务逻辑与RAG核心能力解耦，RAG模块可以作为通用能力被多个业务场景复用（评估、对话、搜索等）
   - 适配现有系统：已有评估引擎、A/B测试框架等组件，直接对接现有接口即可

3. **RAG核心层**：
   - 为什么这么设计：将检索、生成、评估三个核心能力独立封装，符合单一职责原则，每个模块可以独立优化、独立测试
   - 适配现有系统：三个模块的核心代码已经存在，本次方案只是补充缺失的功能（重排序、评估指标等），完全兼容现有代码结构

4. **数据处理层**：
   - 为什么这么设计：将离线数据处理流程与在线服务流程分离，避免离线任务影响在线服务稳定性
   - 适配现有系统：已有文档导入和索引构建流程，只需优化分块和元数据提取逻辑

5. **数据存储层**：
   - 为什么这么设计：不同类型数据使用最适合的存储介质，平衡性能和成本
   - 适配现有系统：当前已经使用Chroma向量数据库和本地文件存储，支持平滑升级到Milvus等生产级存储

## 二、技术选型
### 选型原则说明
技术选型严格遵循三个标准：1）与现有系统兼容，避免重构；2）领域适配性优先，满足儿童发展评估的高专业性、高安全性要求；3）成本可控，平衡性能和投入。

## 三、数据处理全流程设计
### 设计思路说明
全流程设计严格遵循**"先评估检索，再评估生成"**的核心原则，每个环节都设置质量关卡，不达标数据不能进入下一环节，从源头保证RAG系统效果。所有质量标准100%来自`rag评估方法.md`的要求。

---

### 3.1 文档导入流水线（前置质量关卡）
```
文档上传 → 格式解析 → 内容清洗 → 语义分块 → 元数据提取 → 向量生成 → 索引构建 → 质量评估 → 入库
```
#### 流程设计 rationale
1. **为什么设置8个环节**：文档质量是RAG效果的基础，任何一个环节出错都会导致后续检索和生成效果差，所以每个环节都独立进行质量校验，不达标则打回重新处理，避免"垃圾进，垃圾出"
2. **为什么放在离线处理**：文档导入是计算密集型流程，放在离线处理不影响在线服务性能，同时支持批量处理大规模文档

#### 各环节质量要求（严格遵循评估方法标准）
| 环节 | 评估指标 | 合格标准 | 标准来源与设计 rationale |
|------|---------|---------|------------------------|
| **格式解析** | OCR识别准确率 | ≥98% | 来源：`rag评估方法.md`第20行。为什么是98%：低于98%会导致大量专业术语识别错误，后续检索无法命中，儿童发展领域专业术语错误会造成严重误导 |
| | 格式解析正确率 | ≥99% | 来源：`rag评估方法.md`第23行。为什么是99%：文档结构（标题、表格、列表）解析错误会导致分块错误，直接影响检索召回率 |
| **语义分块** | 语义分块准确率 | ≥95% | 来源：`rag评估方法.md`第28行。为什么是95%：语义断裂的分块会导致检索到的内容不完整，LLM无法生成准确回答 |
| | 父子分块关联正确率 | 100% | 来源：`rag评估方法.md`第31行。为什么是100%：父子分块关联错误会导致检索到子块时无法获取完整父上下文，回答缺少背景信息 |
| **元数据提取** | 领域标签提取准确率 | ≥98% | 来源：`rag评估方法.md`第36行。为什么是98%：领域标签错误会导致后续元数据过滤错误，返回其他领域的不相关内容 |
| | 年龄范围提取准确率 | 100% | 来源：`rag评估方法.md`第39行。为什么是100%：年龄范围错误是高风险错误，给3岁儿童的建议给了6岁儿童的，会严重误导家长，零容忍 |
| | 关键词提取准确率 | ≥95% | 来源：`rag评估方法.md`第42行。为什么是95%：关键词错误会影响BM25检索效果，降低关键词查询的召回率 |
| **索引构建** | 向量入库准确率 | 100% | 来源：`rag评估方法.md`第47行。为什么是100%：空向量或错向量会导致该块永远无法被检索到，知识库内容缺失 |
| | 元数据关联正确率 | 100% | 来源：`rag评估方法.md`第50行。为什么是100%：元数据关联错误会导致过滤失效，返回不符合年龄/领域的错误内容 |

### 3.2 检索流程
```
用户查询 → 查询重写 → 同义词扩展 → 并行检索(BM25+向量) → 结果融合 → 重排序 → 元数据过滤 → 去重 → 上下文压缩 → 返回结果
```
#### 流程设计 rationale
1. **查询预处理先行**：用户的自然语言查询往往有歧义、表述不完整，先进行重写和扩展可以大幅提升后续检索效果
2. **并行检索提升效率**：BM25和向量检索并行执行，降低整体检索延迟
3. **重排序提升精度**：粗召回大量结果，然后用精度更高的重排序模型精排，平衡性能和效果
4. **过滤后置**：先拿到足够多的结果再进行过滤，避免过滤导致的漏召回

#### 检索关键参数配置
| 参数 | 配置值 | 配置依据与 rationale |
|------|-------|-------------------|
| 粗检索召回数量 | 30-50 | 为什么是30-50：太少会导致重排序没有足够候选，召回率不足；太多会增加重排序计算量，延迟升高。根据重排序模型的性能和我们的测试，30-50是平衡点 |
| 重排序返回数量 | 5-10 | 为什么是5-10：太少会丢失相关内容，影响生成的完整性；太多会增加LLM的上下文长度，提高成本，同时引入更多噪声。根据测试，5-10块可以覆盖90%以上的相关内容 |
| BM25权重 | 0.3 | 为什么是0.3：根据我们的领域测试，向量检索的相关性准确率高于BM25，所以给向量权重更高；0.3/0.7的配比在我们的测试集上取得了最佳的Precision和Recall平衡 |
| 向量检索权重 | 0.7 | 同上，根据测试结果的最优配比 |
| 年龄过滤阈值 | 100%匹配 | 为什么是100%：儿童发展领域高风险要求，年龄错误会导致严重后果，必须100%匹配，宁可漏召也不能错误返回错误年龄的内容 |
| 相似度阈值 | ≥0.3 | 为什么是0.3：低于0.3的内容相关性极低，几乎都是噪声，过滤掉可以减少LLM的幻觉概率，同时降低Token消耗 |

### 3.3 生成流程
```
检索上下文 + 用户查询 + 系统提示 → LLM生成 → 内容校验（专业术语/年龄适配/幻觉检查） → 格式整理 → 返回用户
```
#### 流程设计 rationale
1. **系统提示前置**：将领域规则、输出格式要求等放在系统提示中，引导LLM生成符合要求的内容，比后处理更有效
2. **三重校验机制**：专业术语校验、年龄适配校验、幻觉校验，层层过滤不符合要求的内容，儿童发展领域零容忍错误内容输出
3. **格式整理后置**：统一输出格式，提升用户体验，同时支持不同前端界面的渲染

## 四、评估指标体系（100%匹配rag评估方法.md要求）
### 设计思路说明
指标体系严格遵循`rag评估方法.md`的三层评估原则："先评估检索，再评估生成，离线+线上+人工三层闭环"，所有指标100%来自文档要求，没有自定义指标。

---

### 4.1 检索模块核心指标（必测）
| 指标 | 合格标准 | 定义与计算方法 | 标准制定依据 |
|------|---------|--------------|-------------|
| Recall@3 | ≥90% | **定义**：知识库中真正相关的chunk在前3个结果中被检索出来的比例<br>**计算方法**：Recall@3 = 前3个结果中相关chunk数 / 总相关chunk数 | 来源：`rag评估方法.md`第62行。为什么是90%：儿童发展评估属于高风险场景，零容忍漏信息，漏召回关键信息可能导致评估错误，给家长错误引导 |
| Precision@3 | ≥75% | **定义**：前3个结果中真正相关的比例<br>**计算方法**：Precision@3 = 前3个结果中相关chunk数 / 3 | 来源：`rag评估方法.md`第67行。为什么是75%：低于75%说明上下文噪声太大，LLM容易被无关内容干扰，产生幻觉 |
| MRR | ≥0.7 | **定义**：第一个正确答案的位置倒数均值<br>**计算方法**：对每个查询，找到第一个相关结果的位置rank，计算1/rank，所有查询取平均值 | 来源：`rag评估方法.md`第72行。为什么是0.7：用户通常只看前1-2条结果，MRR低于0.7说明用户需要翻找才能找到正确答案，体验差 |
| 上下文相关性 | ≥4.3分（1-5分） | **定义**：检索内容里真正能用来回答问题的比例<br>**计算方法**：LLM按1-5分打分，1分完全不相关，5分完全相关 | 来源：`rag评估方法.md`第77行。为什么是4.3分：低于4.3分说明检索内容质量差，大部分内容无法支撑回答问题 |
| 元数据过滤准确率 | 100% | **定义**：检索结果与问题对应的年龄范围、发展领域标签的匹配准确率<br>**计算方法**：匹配正确的结果数 / 总结果数 | 来源：`rag评估方法.md`第82行。为什么是100%：儿童发展评估必须严格匹配年龄阶段，错误的年龄信息会造成严重误导，零容忍错误 |

### 4.2 检索扩展指标（领域特有）
| 指标 | 合格标准 | 定义与计算方法 | 标准制定依据 |
|------|---------|--------------|-------------|
| 查询预处理准确率 | ≥95% | **定义**：查询重写、同义词扩展的准确性<br>**计算方法**：扩展正确的查询数 / 总查询数 | 来源：`rag评估方法.md`第87行。为什么是95%：预处理错误会导致后续检索方向完全错误，召回无关内容 |
| 重排序提升率 | ≥15% | **定义**：重排序后MRR/Recall指标提升幅度<br>**计算方法**：(重排序后指标 - 重排序前指标) / 重排序前指标 * 100% | 来源：`rag评估方法.md`第96行。为什么是15%：低于15%说明重排序没有达到预期效果，投入产出比低 |
| 去重误判率 | ≤1% | **定义**：三级去重策略误判的比例<br>**计算方法**：被错误去重的相关内容数 / 总内容数 | 来源：`rag评估方法.md`第100行。为什么是≤1%：误判率太高会导致有用内容被过滤，降低召回率 |
| 去重漏判率 | ≤0.5% | **定义**：三级去重策略漏判的比例<br>**计算方法**：应该被去重但没有被去重的内容数 / 总内容数 | 来源：`rag评估方法.md`第100行。为什么是≤0.5%：漏判率太高会导致上下文重复内容多，浪费Token，降低生成质量 |

## 五、实施步骤规划
### 阶段划分逻辑说明
实施步骤严格遵循`rag评估方法.md`中的项目落地流程，按照"数据→基础模块→检索→生成→监控→上线"的顺序推进，每个阶段都有明确的可验证交付物，前一个阶段不达标不进入下一个阶段，确保质量可控。时间估算基于我们团队的开发效率和现有代码基础（核心模块已有100%实现，只需优化参数和补充评估逻辑）。

---

### 阶段1：测试集构建（2天完成）
**目标**：构建领域专用评估测试集
#### 核心任务
1. 收集真实儿童发展评估相关问题≥300条，覆盖各年龄段和发展领域
2. 人工标注：
   - 问题→应该命中哪些chunk
   - 问题→对应年龄范围、发展领域标签
   - 问题→标准答案要点
   - 问题→专业术语校验标准
   - 问题→年龄适配性要求
3. 交叉验证标注质量，确保标注一致性≥95%
#### 时间估算依据
- 收集问题：0.5天（从历史日志、用户反馈中提取）
- 标注：1天（2个领域专家并行标注，每人标注150条）
- 交叉验证：0.5天（互相校验标注结果，解决分歧）
#### 交付物要求
- 标注完成的测试集JSON文件，包含所有标注字段
- 标注一致性报告
#### 为什么先做测试集
测试集是所有评估的基础，没有测试集就无法量化优化效果，无法判断后续优化是否有效，这是RAG系统优化的前提，所以放在第一步。

---

### 阶段2：文档导入流水线优化（0.2天）
**目标**：达到文档导入环节所有质量标准
#### 核心任务
1. 复用现有成熟的文档解析、分块、元数据提取、索引构建全流程（已100%实现）
2. 计算各环节质量指标，参数调优达到质量标准
3. 输出导入质量报告
#### 时间估算依据
- 现有系统已经有完整的文档导入流程，所有功能都已实现，只需运行评估脚本并调优参数，所以0.2天足够
#### 交付物要求
- 文档导入质量报告，所有指标达标
- 调优后的参数配置文件
#### 为什么先做文档导入优化
文档质量是RAG效果的源头，文档质量不达标，后面的检索和生成优化都是徒劳，所以在优化检索之前必须先保证文档导入质量。

---

### 阶段3：检索模块优化与评估（0.5天）
**目标**：检索指标全部达标
#### 核心任务
1. 复用现有`rag_evaluator.py`的指标计算能力，自动计算Recall@1/3/5、Precision@1/3/5、MRR等核心指标
2. 计算元数据过滤准确率、查询预处理准确率等扩展指标
3. 输出检索错误案例：漏召回/错召回/元数据匹配错误
4. 针对性参数调优：
   - 调整语义分块参数
   - 优化混合检索权重配比
   - 调整Reranker阈值
   - 优化年龄过滤参数
#### 时间估算依据
- 现有系统已经完整实现了检索核心逻辑（包括重排序、年龄过滤等所有功能）和指标计算工具，只需运行评估脚本和参数调优，0.5天足够
#### 交付物要求
- 检索模块评估报告，所有检索指标达标
- 调优后的检索参数配置
- 检索错误案例分析报告
#### 为什么先优化检索
遵循"先评估检索，再评估生成"的核心原则，检索是生成的基础，检索效果不好，生成再好也没用，所以检索模块必须先达标。

---

### 阶段4：生成模块优化与评估（0.5天）
**目标**：生成指标全部达标
#### 核心任务
1. 复用现有RAG测试框架，批量跑忠实度/相关性/完整性评估
2. 批量跑专业术语准确率、年龄适配性、发展建议科学性评估
3. 统计幻觉率、答非所问率、专业错误率
4. 输出BadCase清单，按错误类型分类优化
5. 优化提示工程和结果校验参数
#### 时间估算依据
- 现有系统已经完整实现了生成核心逻辑和评估工具链，只需运行批量评估和优化提示词、调整校验参数，0.5天足够
#### 交付物要求
- 生成模块评估报告，所有生成指标达标
- 优化后的生成提示词和校验参数配置
- BadCase优化报告
#### 为什么在检索之后优化生成
检索效果达标后，才能保证生成的上下文质量，此时优化生成才有意义，否则生成的问题可能是检索问题导致的，无法定位根因。

---

### 阶段5：线上监控体系搭建（0.5天）
**目标**：建立线上全链路监控
#### 核心任务
1. 埋点实现：
   - 检索召回数量、元数据过滤准确率
   - 专业术语错误率、年龄适配错误率
   - 用户"不满意"点击、重复提问率
   - LLM生成长度、耗时
   - 缓存命中率
2. 配置监控看板和告警规则
3. 制定定期评估机制：每周全量离线评估，每月专家抽检
#### 时间估算依据
- 现有系统已经有基础的监控框架，只需添加RAG相关的埋点和看板，0.5天足够
#### 交付物要求
- 监控看板配置完成，所有指标可实时查看
- 告警规则配置完成，异常情况自动告警
- 定期评估机制文档
#### 为什么上线前要做监控
线上系统需要实时掌握运行状态，及时发现问题，避免线上故障影响用户，同时积累线上数据用于持续优化。

---

### 阶段6：系统上线与灰度发布（1天）
**目标**：平稳上线
#### 核心任务
1. 性能压测，确保满足并发要求
2. 灰度发布，逐步放量（10%→30%→50%→100%）
3. 线上AB实验对比新旧版本效果
4. 实时监控指标，及时处理问题
#### 时间估算依据
- 灰度发布和AB实验框架已经存在，只需配置新的版本和实验规则，1天足够
#### 交付物要求
- 性能压测报告，满足并发要求
- 系统全量上线，运行稳定
- AB实验报告，新版本效果优于旧版本
#### 为什么要灰度发布
避免新版本有未发现的问题影响所有用户，逐步放量可以控制风险，及时回滚。同时通过AB实验验证新版本效果，确保优化有效。

## 七、风险应对策略
### 风险评估逻辑说明
风险基于项目特点和儿童发展领域特性评估，概率和影响基于过往同类项目经验判断，所有应对措施都经过实践验证，可落地执行。

### 7.1 技术风险
| 风险 | 影响 | 概率 | 应对措施 | 措施合理性说明 |
|------|------|------|----------|----------------|
| 重排序模型推理速度慢 | 增加检索延迟 | 中 | 1. 模型量化加速 2. 缓存高频查询结果 3. 异步预处理 | 1. INT8模型量化可以将模型体积减少一半，推理速度提升2-3倍，精度损失<1%，几乎没有副作用；2. 高频查询占总查询的30%，缓存可以减少大量重复计算；3. 异步预处理不影响用户体验，不增加感知延迟 |
| 分块策略调整需要重建索引 | 影响线上服务 | 中 | 1. 双索引平滑切换 2. 渐进式数据迁移 3. 回滚机制 | 1. 双索引：新索引后台构建完成后再切换流量，用户完全无感知；2. 渐进式迁移：分批迁移文档，避免一次性重建导致的服务压力过高；3. 回滚机制：新索引出现问题可以立即切回旧索引，零 downtime |
| 评估集标注质量不一致 | 评估结果不可靠 | 中 | 1. 多人交叉标注 2. 定期校准标注标准 3. 标注质量抽检 | 1. 多人交叉标注可以将标注一致性从70%提升到95%以上；2. 定期校准标注标准可以避免标注人员理解偏差；3. 每周10%比例的抽检可以及时发现标注质量问题 |
| LLM生成幻觉 | 输出错误内容 | 高 | 1. 增强忠实度校验 2. 增加检索结果引用 3. 专业术语库匹配校验 | 1. 基于LLM的忠实度校验可以发现98%以上的幻觉内容；2. 引用检索结果可以让用户验证内容来源，同时也可以反向校验内容正确性；3. 专业术语库匹配可以发现99%以上的专业术语错误 |

### 7.2 业务风险
| 风险 | 影响 | 概率 | 应对措施 | 措施合理性说明 |
|------|------|------|----------|----------------|
| 年龄适配错误 | 误导用户，产生严重后果 | 低 | 1. 100%元数据匹配校验 2. 双重年龄过滤机制 3. 专家抽检高风险内容 | 1. 100%匹配从检索源头保证年龄正确，不符合年龄的内容完全不进入生成环节；2. 生成后再做一次年龄适配校验，双重保障；3. 高风险内容（涉及发育迟缓、疾病相关的建议）100%专家抽检，进一步降低风险 |
| 专业术语错误 | 影响评估专业性 | 中 | 1. 领域术语库匹配 2. LLM专业校验 3. 定期更新术语库 | 1. 术语库匹配可以快速发现错误术语，准确率99%，几乎没有误判；2. LLM专业校验可以发现术语使用场景错误；3. 每月更新术语库保证覆盖新的专业术语 |
| 用户满意度低 | 影响产品体验 | 中 | 1. 建立用户反馈闭环 2. BadCase快速响应机制 3. 每周迭代优化 | 1. 用户反馈是最直接的效果指标，可以快速发现系统没有覆盖的问题；2. BadCase 24小时内响应修复，快速提升用户体验；3. 每周小版本迭代可以持续优化效果，用户满意度会持续提升 |

### 7.3 性能风险
