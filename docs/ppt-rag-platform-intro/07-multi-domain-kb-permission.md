# 07 · 多域聚合 + 多知识库 + 双层权限——跨域查询如何安全地得到完整答案？

> 目标受众：懂技术的产品经理
> 核心问题：一个查询可能涉及多个知识领域（"高血压合并糖尿病如何用药"涉及心血管、内分泌、药学三个域），但每个域的知识必须物理隔离，每个用户只能看到有权限的知识。这三个需求——多域并行检索、知识库独立管理、权限全局强制——深度耦合，必须统一设计。

---

## 为什么这三个问题必须统一设计

三个需求之间存在强耦合关系：

```
域路由（激活哪些域）
    │
    ├── 依赖 ──→ 知识库可见性（用户能看到哪些知识库？）
    │               │
    │               └── 依赖 ──→ 权限（用户的角色决定了可见的知识库）
    │
    └── 依赖 ──→ 域管道配置（每个域使用哪个知识库？什么检索策略？）
```

**无法独立设计**：如果先设计多域聚合再叠加权限，权限就会变成事后补丁（Post-filter）——信息已经泄漏。如果先设计权限再考虑多域，可能设计出"一个用户只能看一个域"的粗粒度模型，无法支持"不同角色看不同域"的灵活需求。

正确做法是将三者作为一个整体系统设计——域路由的决策依据包括用户权限，权限的注入点就在域分发和检索执行两个环节。

---

## Part A：多知识库管理——为什么必须物理隔离

### 物理隔离 vs 逻辑隔离——不只是标签的区别

```
逻辑隔离（同一向量库 + 标签过滤）：
─────────────────────────────────────────────
┌─────────────────────────────────────────────┐
│           单一 Chroma Collection              │
│  doc_1 (domain=心血管)  doc_2 (domain=药学)   │
│  doc_3 (domain=法律)    doc_4 (domain=教育)   │
│                                             │
│  搜"高血压用药" → 向量检索全库 → 按标签过滤    │
│  问题：语义相似的法律文档已经被检索到了          │
│        （Post-filter——检索后才过滤，已泄漏）     │
└─────────────────────────────────────────────┘

物理隔离（独立向量库）：
─────────────────────────────────────────────
┌──────────┐ ┌──────────┐ ┌──────────┐
│ 心血管库  │ │ 药学库    │ │ 法律库    │
│ Collection│ │ Collection│ │ Collection│
│ 独立索引  │ │ 独立索引  │ │ 独立索引  │
└──────────┘ └──────────┘ └──────────┘
  ↑              ↑
  搜"高血压用药"只在心血管库中检索
  药学、法律文档根本不在检索范围内（Pre-filter）
```

**为什么必须是物理隔离**：与权限控制同理——Post-filter（检索后按标签过滤）意味着文档已经被检索到了，只是不返回给用户。但检索过程本身会在日志、缓存、追踪数据中留下痕迹。物理隔离确保检索从一开始就在正确的范围内进行。

### 每个知识库的独立配置

不同领域对检索的需求不同，不应强制所有知识库使用相同配置：

| 配置项 | 心血管库（医疗） | 法律库 | 为什么不同 |
|--------|----------------|--------|-----------|
| chunk_size | 256 字 | 512 字 | 医疗文档信息密度高，小粒度检索更精准 |
| Embedding 模型 | DashScope v4（中文优化） | OpenAI text-embedding-3（法规中有大量英文引用） | 语言不同 |
| 相似度度量 | cosine | cosine | 两个 Embedding 模型都输出归一化向量 |
| 向量后端 | Milvus（千万级文档） | Chroma（千级文档） | 数据规模不同 |
| 权限可见性 | role_scoped（仅医生） | public（所有法律相关人员） | 敏感度不同 |

### 三种向量后端——规模决定选择

| 后端 | 适用规模 | 特点 | 成本 | 运维复杂度 |
|------|---------|------|------|-----------|
| **Chroma**（默认） | < 10 万文档 | 轻量、零依赖、本地持久化、Python 原生 | 免费（本地运行） | 低——无需单独部署 |
| **Elasticsearch** | 10 万-100 万文档 | 内置 BM25 + 向量检索、分布式、成熟生态 | 中——需要 ES 集群 | 中——需要管理 ES 集群 |
| **Milvus** | > 100 万文档 | 专用向量数据库、十亿级向量、GPU 加速、混合查询 | 中高——需要 Milvus 集群 | 高——需要管理专用向量数据库 |

**升级路径**：

```
Phase 2: Chroma（默认，开发和小规模使用）
    │ 满足 < 10 万文档的场景
    ▼
Phase 10: ES/Milvus 适配器验证
    │ 客户数据规模增长 → 平滑升级向量后端
    │
    ├── 中等规模（10万-100万文档）→ 切换到 ES
    └── 大规模（> 100万文档）→ 切换到 Milvus

升级方式：在知识库配置中切换 vector_backend 选项 → 触发数据迁移 → 验证后切换生效
```

### 知识库与管道的关系——多对多复用

```
知识库（独立存在）              管道（链接方式）
┌──────────────────┐
│ kb_cardiology     │ ──────┐
│ [公开—所有医生可见]│       ├──→ 综合问诊管道 → 跨域融合 → 统一答案
└──────────────────┘       │
                           │
┌──────────────────┐       ├──→ 心血管专科管道
│ kb_pharmacology   │ ─────┘
│ [角色:药师可见]    │
└──────────────────┘
```

**多对多关系的设计原则**：
- 知识库独立存在——不绑定于任何特定管道
- 一个管道可以链接多个知识库（如综合问诊管道链接心血管 + 内分泌 + 药学三个库）
- 一个知识库可以被多个管道复用（如心血管库同时被"综合问诊"和"心血管专科"两个管道使用）
- 权限注入点：管道链接知识库时，并非所有用户都能访问所有链接的库

### 知识库可见性模型

| 可见性 | 谁可以看到 | 典型场景 |
|--------|-----------|---------|
| `public` | 租户内所有角色 | 公开的医学指南、教科书 |
| `role_scoped` | 指定的角色列表 | 药学禁忌库——仅"药师"角色可见 |
| `private` | 仅创建者 | 个人研究笔记、未发表草案 |

**权限继承规则**：
- 文档默认 `inherit` 知识库的可见性
- 文档可设为 `restricted` 收紧权限（比知识库更严格）
- **禁止**文档权限比知识库更宽松（安全约束——文档不能覆盖知识库的权限限制）

## Part B：多业务域聚合——跨域查询的完整链路

### 为什么单路 RAG 做不到跨域查询

单路 RAG 把用户查询发给一个检索管道，从一个知识库检索，生成一个答案。这在一个问题只涉及一个领域时工作良好，但真实世界的查询经常跨越多个领域。

**三个典型跨域场景**：

| 场景 | 查询 | 涉及域 | 单路 RAG 怎么做 | 问题 |
|------|------|--------|--------------|------|
| 跨领域交叉 | "高血压合并糖尿病用药" | 心血管 + 内分泌 + 药学 | 从单一库检索，只得到部分答案 | 答案不完整——缺少药物相互作用信息 |
| 多角度看问题 | "前庭觉训练的神经科学基础" | 感统训练 + 神经科学 | 只能从训练方法角度回答 | 缺少神经科学视角 |
| 矛盾检测 | "低盐饮食 vs 某药需高盐环境" | 营养 + 药学 | 检索可能只返回一边的观点 | 用户收到矛盾信息而不知 |

### 域管道——独立的检索单元

每个业务域拥有独立配置的检索管道：

```
心血管域管道                    药学域管道
├── 链接知识库：kb_cardiology    ├── 链接知识库：kb_pharmacology
├── 同义词："高血压=血压升高"     ├── 同义词："禁忌=不宜=禁用"
├── 检索策略：BM25 权重 0.6     ├── 检索策略：向量权重 0.7
│   （医学术语精确匹配更重要）     │   （药物相互作用表述多样）
├── 安全节点：无特殊要求          ├── 安全节点：PII 脱敏
│   （不涉及患者数据）            │   （可能涉及患者用药记录）
└── 权限：所有医生可见            └── 权限：仅药师角色可见
```

**为什么不同域需要不同的检索策略**

心血管域以精确的医学术语为主——"ST 段抬高型心肌梗死"必须是"ST 段抬高型心肌梗死"，不能是"心脏 ST 段升高"。术语匹配的精确性优先 → BM25 权重更高。

药学域以药物相互作用描述为主——同一个药物相互作用可能有十几种不同的表述方式（"不宜联用""协同禁忌""合并使用风险""联用需监测"）。语义理解更重要 → 向量权重更高。

**同一个策略无法同时满足两个域的需求。**

### 聚合层 6 节点——跨域协调器

这 6 个节点位于域管道之上，负责查询分析、并行分发、结果融合：

#### 聚合节点 1：查询分析（Query Analysis）

**做什么**：识别用户查询涉及哪些业务域，决定激活哪些域。

**核心逻辑——规则 + LLM 两阶段**：

```
第 1 阶段（规则——快速、免费）：
  查询"高血压合并糖尿病用药"
  ├── 关键词匹配"高血压" → 命中心血管域的关键词列表 ✓
  ├── 关键词匹配"糖尿病" → 命中内分泌域的关键词列表 ✓
  ├── 关键词匹配"用药"   → 命中药学域的关键词列表 ✓
  └── 输出：初步激活 [心血管, 内分泌, 药学]

第 2 阶段（LLM——处理模糊情况）：
  规则未命中的情况：
  查询"这是一种需要长期管理的慢性病"
  → 规则无法匹配（没有关键词命中）
  → LLM 分析："长期管理的慢性病" → 通用描述 → 激活所有域（宽泛搜索）
```

**失败模式**：规则过度激活（激活了不相关的域）→ 域激活准确率下降；规则未激活相关域 → 跨域覆盖率下降。

#### 聚合节点 2：域分发（Domain Dispatch）

**做什么**：将查询并行分发到被激活的域管道，并在此注入权限过滤。

**权限注入点**：

```
管理员调用（对所有知识库有权限）：
  → 激活 [心血管, 内分泌, 药学]（全部）

普通医生调用（仅对心血管、内分泌有权限）：
  → 激活 [心血管, 内分泌]（药学域被跳过——因为用户无权限访问 kb_pharmacology）

实习生调用（仅对公开教材库有权限）：
  → 激活 [教材库]（只激活有权限的域）
```

**关键**：权限在域分发时就注入——无权限的域根本不会被激活，域管道不会执行，无权限的知识库不会被检索。

**并行执行策略**：

```
域分发并行执行：
  ├── 心血管域管道（独立执行，~180ms）
  ├── 内分泌域管道（独立执行，~160ms）  ← 并行，不互相等待
  └── 药学域管道（独立执行，~200ms）    ← 并行

总延迟 = max(180, 160, 200) = 200ms（取最慢的域）
而不是 180 + 160 + 200 = 540ms（串行）
```

#### 聚合节点 3：跨域融合（Cross-Domain Fusion）

**做什么**：将多个域管道的检索结果加权融合。

**融合逻辑**：每个域的结果在 RRF 融合时获得一个域权重。域权重由管道配置决定——"综合问诊"管道可能给三个域相等的权重（各 1/3），"心血管侧重"管道可能给心血管域 0.5，其他两个域各 0.25。

**输出**：融合后的统一结果列表（10-20 条），每条标注来源域。

#### 聚合节点 4：跨域去重（Cross-Domain Deduplication）

**做什么**：同一篇文档可能被多个域引用（如一篇关于"药物相互作用"的综述同时被心血管域和药学域检索到），MinHash 跨域检测去除重复。

#### 聚合节点 5：冲突检测（Conflict Detection）

**做什么**：用 LLM 检测跨域检索结果中存在的矛盾信息。

**为什么需要**：不同域的建议可能存在矛盾。例如——心血管域说"建议低盐饮食"，药学域说"某药物需要高盐环境吸收"。如果不检测，LLM 会生成自相矛盾的答案。

**检测原理**：

```
LLM 分析多域检索结果：

矛盾 1（已检测到 ✓）：
  心血管域："高血压患者应坚持低盐饮食（<5g/天）"
  药学域："呋塞米（利尿剂）在低钠环境下疗效下降"
  → 矛盾：低盐饮食可能导致利尿剂疗效下降
  → 标记：[冲突] 在答案中标注"低盐饮食建议与所用利尿剂存在潜在矛盾，请咨询医生"

矛盾 2（未检测到 ✗——需要领域知识判断上下文）：
  内分泌域："糖尿病患者应避免剧烈运动"
  康复域："建议糖尿病患者进行适量有氧运动"
  → LLM 判断："避免剧烈运动"和"适量有氧运动"不矛盾（一个讲"剧烈"，一个讲"适量"）
  → 但实际上是同一个建议的两种表述 → 不是矛盾
```

**输出**：`conflicts: [{domain_a, domain_b, description, suggestion}]`

**失败模式**：漏检（真矛盾未被检测 → 用户收到矛盾建议）> 误报（标记为矛盾但不矛盾 → 用户不必要地担心）相比，误报的代价更低——用户只会多确认一次，而漏检可能导致用户按矛盾建议行动。

**冲突检测的性能基准**（基于初步测试，待随平台集成测试更新）：
- 目标误报率：< 15%（标记为矛盾但实际不矛盾）
- 目标漏检率：< 10%（真矛盾未被检测到）
- 检测延迟：约 100ms（单次 LLM 调用判断跨域矛盾）
- 注意：漏检率的验证依赖高质量的人工标注测试集（标注所有跨域矛盾对），这是评估体系在平台阶段需要持续建设的资产

#### 聚合节点 6：统一答案合成（Unified Answer Synthesis）

**做什么**：综合多域检索结果和冲突检测结果，生成最终答案，标注每段信息的来源域。

**输出格式**：

```
📋 高血压合并糖尿病老年患者的用药建议

💊 药物治疗（来源：药学域）
├── 建议使用 ACEI 类降压药——对糖尿病肾病患者有保护作用
├── 避免使用噻嗪类利尿剂——可能升高血糖
└── 二甲双胍作为一线降糖药

❤️ 心血管注意事项（来源：心血管域）
├── 血压控制目标：<140/90 mmHg（老年患者可适当放宽至 <150/90）
└── 建议定期监测心电图——糖尿病患者心血管事件风险增加

⚠️ 检测到的潜在矛盾：
├── 心血管域建议"低盐饮食"，但药学域指出"呋塞米在低钠环境下疗效下降"
└── 建议：如正在服用呋塞米，请咨询医生调整饮食方案

🔬 内分泌视角（来源：内分泌域）
└── 糖化血红蛋白（HbA1c）控制目标：<7.5%（老年患者可适当放宽）
```

### 单域快捷路径——不浪费计算资源

当查询分析节点判断查询只涉及一个域时——如「高血压的诊断标准」只涉及心血管域——跳过全部 4 个聚合节点（跨域融合、跨域去重、冲突检测、统一答案合成），直接返回域管道结果。

```
多域查询：查询分析 → 域分发 → 域管道(并行) → 融合 → 去重 → 冲突检测 → 合成
单域查询：查询分析 → 域分发 → 域管道(单个) → 答案  （跳过 4 个聚合节点）
```

**节省**：单域查询端到端延迟减少约 130ms（跳过 4 个聚合节点的 LLM 调用和计算时间）。

## Part C：双层权限控制——为什么 Pre-filter 不是可选的

### RAG 场景下权限的特殊危险

传统应用权限控制：用户看不到的数据 → 不会返回。但在 RAG 语义检索中，**即使不精确匹配，语义相似的敏感文档也可能因为向量距离接近而被检索到**。

```
场景：A 公司的财务数据与 B 公司的普通查询
────────────────────────────────────────
A 公司文档："2024 年 Q4 营收增长 20%，得益于新产品线..."
B 公司查询："新产品营收增长趋势分析"

这两个文档在字面上没有相同的词（"2024Q4营收增长20%新产品线" vs "新产品营收增长趋势分析"）
但它们语义高度相似 → 向量距离很近 → 在 Post-filter 模式下，A 公司的文档已经被检索到了

如果权限是 Post-filter（检索→返回结果→过滤权限→返回给用户）：
  检索过程：A 公司文档被检索到 ✓（已经发生）
  结果：文档未被返回给用户 ✓（权限拦住了）
  但：缓存中有记录、日志中有记录、Trace 中有记录 ✗（发生了信息泄漏）

如果权限是 Pre-filter（注入权限条件→只检索有权限的文档→返回）：
  检索过程：A 公司文档根本不在检索范围内 ✗（从未被检索到）
  结果：只有 B 公司自己的文档被返回 ✓
```

### Pre-filter vs Post-filter——五个维度的本质区别

| 维度 | Post-filter（检索后过滤） | Pre-filter（检索前嵌入条件） |
|------|------------------------|--------------------------|
| **安全性** | 无权限文档已被检索到——日志、缓存、Trace 中有痕迹 | 无权限文档根本不在检索范围内 |
| **性能** | 先全库检索再丢弃——浪费算力检索了不该检索的文档 | 只检索有权限的范围——检索范围更小，更快 |
| **日志安全** | 日志中记录了对无权限文档的检索行为 | 日志中只记录了有权限范围内的检索 |
| **缓存隔离** | 不同权限的用户可能共享缓存——导致缓存污染 | 缓存 Key 包含权限上下文——不同用户不同缓存 |
| **可审计性** | 无法证明"没有检索过无权限文档" | 可以证明——检索从一开始就被限制 |

**核心结论**：权限不是"看到不该看的就删掉"（Post-filter）。权限是"不该看的永远不会被看到"（Pre-filter）。

### 第一层过滤：库级别——裁剪域激活计划

**时机**：域分发前

**做什么**：根据用户角色，过滤掉不可见的知识库。用户没有访问权限的知识库对应的域不被激活。

```
用户 JWT → 提取 roles: ["doctor"]
  → 查询：哪些知识库对 doctor 角色可见？
  → kb_cardiology: role_scoped → visible_roles=["doctor", "nurse"] → doctor 可见 ✓
  → kb_pharmacology: role_scoped → visible_roles=["pharmacist"] → doctor 不可见 ✗
  → 药学域不被激活
```

### 第二层过滤：文档级别——检索范围内的粒度控制

**时机**：检索执行时

**做什么**：即使在同一知识库内，不同文档也可能有不同的权限。在检索时注入文档级的 ACL 过滤条件。

**三种向量后端的注入方式**：

| 向量后端 | 注入方式 | 示例 |
|---------|---------|------|
| Chroma | `where` 条件 | `where={"doc_acl": {"$contains": "doctor"}}` |
| Elasticsearch | `filter` 上下文 | `filter: [{terms: {doc_acl: ["doctor"]}}]` |
| Milvus | `expr` 表达式 | `expr: "doc_acl like '%doctor%'"` |

### 文档 ACL 模型

| 属性 | 说明 | 默认值 |
|------|------|--------|
| `doc_acl` | 可访问此文档的角色列表 | 继承知识库的 `visible_roles` |
| `owner_id` | 文档上传者 ID | — |
| `access_level` | `inherit`（继承知识库可见性）/ `restricted`（独立收紧） | `inherit` |

**权限继承规则**：
1. 文档默认 `inherit`——自动获得所属知识库的 `visible_roles`
2. 仅当文档需要更严格权限时，设为 `restricted` 并指定 `doc_acl`
3. `restricted` 权限必须 ≤ 知识库权限（不能越权放宽）

### 多租户隔离——如何让不同客户共享平台

**一期：逻辑隔离（共享部署实例）**

| 维度 | 隔离方式 | 为什么这样隔离 |
|------|---------|-------------|
| 数据库 | `tenant_id` 行级过滤（所有 SQL 查询自动带 WHERE tenant_id=X） | 最简单——利用现有 RDBMS 的行级安全 |
| 向量库 | 命名约定 `{tenant_id}_{kb_id}` | Chroma 原生支持按 collection 名隔离 |
| 文件存储 | 目录 `storage/{tenant_slug}/` | 文件系统级别的物理隔离 |
| 缓存 | Redis Key 前缀 `{tenant_id}:` | 不同租户的缓存互不可见 |

**二期：物理隔离（按需升级）**

当某租户的数据规模或安全需求超出共享部署的承受范围时，支持：独立数据库实例 + 独立向量库集群 + 独立文件存储。升级过程不影响其他租户。

### 权限变更后的缓存失效

权限变更（如用户角色被修改、知识的可见性调整）后，语义缓存必须即时失效——否则用户可能通过缓存间接访问到已被撤销权限的数据。

**失效策略**：
1. 角色变更 → 清除该用户的所有缓存 Key（因为角色变了，应该重新计算权限）
2. 知识库可见性变更 → 清除引用该知识库的所有管道缓存
3. 缓存 Key 格式：`{tenant_id}:{role}:{query_hash}` → 角色在 Key 中，天然隔离

## 关键设计点

| 设计点 | 为什么 | 
|--------|--------|
| 三部分统一设计 | 域路由依赖 KB 可见性依赖权限——独立设计必然产生后补权限洞 |
| 物理隔离 KB | Post-filter 意味着文档已被检索到——已泄漏 |
| Pre-filter 不是可选的 | 5 个维度（安全/性能/日志/缓存/审计）Post-filter 都在 Pre-filter 之下 |
| 单域快捷路径 | 不浪费算力——单域查询跳过 4 个聚合节点 |
| 权限在域分发注入 | 域分发时裁剪不可见域——不可见域根本不被激活 |
| 一期逻辑隔离 | 成本低——共享部署，快速上线；二期按需升级物理隔离 |

## 一句话总结

> **多域聚合 = 查询分析 → 并行域管道 → 跨域融合。多知识库 = 独立 collection + 独立配置 + 多对多管道复用。双层权限 = 库级别裁剪域 + 文档级别 ACL 过滤——全部在检索前执行（Pre-filter），不可绕过。三者深度耦合，必须统一设计。**
