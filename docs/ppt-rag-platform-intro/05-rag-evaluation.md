# 05 · RAG 评估体系——检索管道好不好怎么判断？不好怎么知道改哪里？

> 目标受众：懂技术的产品经理
> 核心问题：BM25 的 k1 从 1.5 调到 2.0，向量 threshold 从 0.7 调到 0.6——这两个改动是好是坏？凭感觉说"好像好了点"不能作为上线依据。怎么用数据回答这个问题？

---

## 核心问题

RAG 系统有 14+ 个可调参数（详见 04-hybrid-search 参数速查表）。每次调参后必须回答三个问题：

1. **整体效果有没有变好？** — 用一个数字衡量，不能凭感觉
2. **如果变差了，是哪个环节的问题？** — 是检索不到（Recall 低）？检索到了但 LLM 没用上（Faithfulness 低）？还是答案偏题了（Relevancy 低）？
3. **知道了问题，改哪个参数？** — "Recall 偏低"不叫可操作的建议。"BM25 检索节点的 top_k 从 10 增大到 20"才是。

没有评估体系时，这三个问题都靠工程师直觉回答——上线前凭感觉调参 → 上线后用户投诉 → 紧急回滚 → 凭感觉再调 → 循环。有评估体系后，调参由数据驱动——每次调整有量化效果对照，上线前可验证，上线后可监控退化。

**RAG 评估体系 = 6 个引擎协作，7 项指标量化检索和生成质量，6 层诊断定位根因，调优建议指向具体节点参数。**

---

## 一、为什么需要 6 个引擎而非一个脚本

| 如果只有一个简单脚本 | 6 引擎协作 |
|-------------------|-----------|
| 手动编写测试用例——100 个用例需要几天，覆盖面有限 | DraftEngine 自动从源文档生成——几分钟，覆盖全面 |
| 跑完只看一个数字（如 Hit Rate=0.65）——不知道为什么低 | 7 项指标分 L1 检索/L2 生成/L3 综合——知道哪个层面差 |
| 知道哪个指标差但不知道为什么 | 6 层诊断从规则→历史→LLM→质量→效果→回归逐层定位根因 |
| 发现问题不知道改什么参数 | TuningEngine 指向具体节点的具体参数，可一键采纳 |
| 改了配置不知道效果如何 | 调优闭环：v1 → 评估 → 调优 → v2 → 再评估 → 发布 |

### 6 引擎全景

```
┌──────────────────────────────────────────────────────────────────────────┐
│                    RagEvalOrchestrator (评估编排器)                        │
│                    协调 6 个引擎的执行顺序和数据流转                          │
└──────────────────────────────────────────────────────────────────────────┘
    │        │        │        │        │        │
    ▼        ▼        ▼        ▼        ▼        ▼
DraftEngine  CaseEngine  RunEngine  MetricEngine  ReportEngine  TuningEngine
草稿引擎    用例引擎    运行引擎    指标引擎      报告引擎      调优引擎
────────────────────────────────────────────────────────────────────────────
生成测试    管理测试    执行测试    计算指标      生成报告      生成建议
草稿        用例库      运行任务    7项量化       结构化呈现    一键采纳
```

## 二、6 个引擎逐一详解

### 引擎 1：DraftEngine（草稿引擎）——测试题从哪来

**解决什么**

100 个手工编写的测试用例需要几天，且编写者的偏见会限制覆盖面——人倾向于写"容易想到"的问题。DraftEngine 自动从源文档中提取问答对。

**核心逻辑**

```
源文档（PDF/EPUB）
    │
    ▼
逐段分发给 LLM，提示词："基于以下文档片段，生成 2-3 个问答对：
  - 问题应该是用户可能搜索的自然语言问题
  - 答案应能从上下文中直接推导出来
  - 覆盖不同难度：简单（直接查找）、中等（需要综合）、困难（需要推理）"
    │
    ▼
LLM 输出问答对列表
    │
    ▼
忠实度验证（Faithfulness Check）：
  LLM 反问："这个答案能从给定的上下文中推导出来吗？"
  ├── 能 → 保留
  └── 不能 → 丢弃（LLM 编造的问答对）
    │
    ▼
MinHash 去重（threshold=0.85）→ 删除高度重复的问答对
    │
    ▼
输出：List[TestCaseDraft { question, expected_answer, context, source_document, difficulty }]
```

**关键设计决策**

| 决策 | 为什么 | 不这样的后果 |
|------|--------|------------|
| LLM 生成而非手工编写 | 200 页文档可能产生 200+ 个问答对，手工不可行 | 测试用例少 → 覆盖面窄 → 评估不全面 |
| 忠实度验证（Faithfulness Check） | LLM 可能编造看似合理但上下文无法推导的答案 | 测试用例的"正确答案"本身就是编造的 → 评估结果不可信 |
| 分三个难度级别 | 不同难度的失败原因不同——简单题失败 = 检索问题，困难题失败 = 生成问题 |

**成本**

200 个分块生成问答对：~0.24 元（qwen-plus，每块 ~1000 Token 输入 + ~500 Token 输出）。

### 引擎 2：CaseEngine（用例引擎）——管理考题库

**解决什么**

DraftEngine 生成的草稿需要人工审核、编辑后才能成为正式的测试用例。不同场景需要不同的测试集——如「前庭觉测试集」「本体觉测试集」「综合测试集」。CaseEngine 管理这些用例和测试集的生命周期。

**核心数据结构**

```
TestCase {
    id: UUID
    question: string            # "3岁儿童前庭觉训练方法有哪些？"
    expected_answer: string     # "游泳、平衡木、秋千等活动..."
    context: string             # 参考文档片段（用于验证检索是否命中）
    source_document: string     # "前庭觉训练指南.pdf"
    domain: string              # "感统训练"
    difficulty: enum            # easy | medium | hard
    tags: List[string]          # ["前庭觉", "训练方法", "3-6岁"]
    created_by: string          # "draft_engine" | "manual" | "csv_import"
}

TestSet {
    id: UUID
    name: string                # "前庭觉评估测试集"
    description: string         # "覆盖前庭觉训练相关的 50 个测试用例"
    case_ids: List[UUID]        # [1, 5, 12, ...]
    created_at: datetime
    last_updated: datetime
}
```

**操作支持**

| 操作 | 做什么 | 为什么需要 |
|------|--------|-----------|
| 从草稿批量创建 | 审核草稿 → 修改 → 创建正式用例 | DraftEngine 输出需要人工把关 |
| 手动创建 | 逐条编写测试用例 | 覆盖边缘情况和特殊场景 |
| CSV/JSON 导入 | 从外部分析工具导入用例 | 与已有测试资产对接 |
| 组织为测试集 | 将多个用例归入一个测试集 | 不同场景的评估需要不同的考试范围 |
| 导出 | 导出为 CSV/JSON | 与他人共享、存档、版本管理 |

### 引擎 3：RunEngine（运行引擎）——怎么公平地考试

**解决什么**

用测试集中的每个问题调用 RAG 检索管道，记录检索结果和 LLM 生成答案，为后续指标计算提供数据。

**核心设计：知识库快照**

测试运行可能需要 10-30 分钟（100 个用例 × 每个检索+生成）。测试运行期间，可能有用户上传新文档到知识库——这会让测试结果不可复现（前半段和后半段的检索条件不一致）。

**快照机制**：RunEngine 在测试开始前创建知识库快照——冻结当前文档集合和向量索引的状态。整个测试运行期间都使用这个快照，确保所有用例在相同的知识库状态下运行。

**执行流程**

```
1. 创建 TestRun
   ├── run_id: UUID
   ├── test_set_id: UUID
   ├── pipeline_config_id: UUID（被测试的管道配置版本）
   └── kb_snapshot_id: UUID（知识库快照）

2. 创建知识库快照 → 冻结当前状态

3. 按难度分批并发执行（避免一次性并发过多压垮系统）：
   ├── 先执行所有 easy 用例（并发 10 个）
   ├── 再执行 medium（并发 10 个）
   └── 最后 hard（并发 10 个）

4. 每个用例：
   question → RAG 检索管道 → 检索结果 + LLM 生成答案 + 记录延迟

5. 全部执行完成 → 触发 MetricEngine
```

**为什么按难度分批**

不同难度的用例延迟差异大。easy 用例可能几十毫秒就返回，hard 用例可能需要数秒。混在一起并发会导致 easy 用例被 hard 用例阻塞（因为并发槽位被占满）。

### 引擎 4：MetricEngine（指标引擎）——怎么量化效果

**分层指标体系**

三层指标分别评估三个不同层面的质量：

```
L1 检索质量（Retrieval Quality）：
  "检索到的文档对不对？全不全？排序好不好？"
  ├── Precision@K：返回结果中有多少是对的
  ├── Recall：所有应该被找到的文档中有多少被找到了
  ├── MRR：第一个有用结果排在第几位
  └── NDCG@K：相关文档有没有排在前面

L2 生成质量（Generation Quality）：
  "基于检索到的文档，LLM 生成的答案好不好？"
  ├── Faithfulness：答案中有多少有上下文依据
  ├── AnswerRelevancy：答案是否回答了用户的问题
  └── Groundedness：整体论点是否有上下文支撑

L3 综合评分（Overall Score）：
  L1 加权分 × 0.4 + L2 加权分 × 0.6 → 一个数字快速判断整体
```

**为什么分三层**：

- 检索到了垃圾 → LLM 再厉害也生成不出好答案 → L1 是 L2 的前提
- 检索完美但 LLM 编造答案 → 用户体验仍然差 → L2 是最终交付
- L3 给出一个数字让决策者快速判断，但定位问题需要 L1/L2 的分项

**L3 中 L2 权重更高（0.6）的原因**：最终用户关心的是"答案好不好"，不是"检索好不好"。检索完美但生成差 → 用户不满意；检索有瑕疵但生成好 → 用户可能接受。

### 7 项指标——逐一深度讲解

以下每项指标包含：公式、通俗解释、计算实例、什么分数算好、盲区、与他指标的关系。

#### L1-1：Precision@K（精确率@K）

**公式**

```
Precision@K = 前 K 个结果中相关文档的数量 / K
```

**通俗解释**：返回的结果中有多少是真正相关的？

**计算实例**

```
用户问："前庭觉训练方法"
K = 5，返回前 5 个结果：

  第 1 位：前庭觉训练方法大全 ✓（相关）
  第 2 位：前庭功能评估指南   ✓（相关）
  第 3 位：本体觉训练方案     ✗（不相关——领域错了）
  第 4 位：儿童前庭觉发展里程碑 ✓（相关）
  第 5 位：触觉训练游戏       ✗（不相关——完全不同的感统维度）

Precision@5 = 3/5 = 0.6
```

**直觉判断**

| 分数 | 用户体验 |
|------|---------|
| 0.9+ | 优秀——绝大多数返回结果都是相关的 |
| 0.6-0.9 | 可接受——部分噪音但不影响主要答案 |
| 0.3-0.6 | 差——近一半结果是噪音 |
| < 0.3 | 很差——用户看到的几乎都是无关内容 |

**盲区**：不关心相关文档是否被遗漏。如果知识库有 100 篇相关文档但只返回了 1 篇相关的 → Precision@5=0.2（看起来差），但实际问题是 top_k 太小而不是精确率低——只返回 1 个对的意味着 Recall 极低。

**与 Recall 的矛盾**：

```
想提高 Precision → 只返回最确定的文档（减少噪音，但遗漏更多）
想提高 Recall → 返回更多文档（提升覆盖面，但增加噪音）

F1 Score = 2 × P × R / (P + R)  ← 调和平均，综合权衡两者
```

---

#### L1-2：Recall（召回率）

**公式**

```
Recall = 被检索到的相关文档数 / 知识库中总相关文档数
```

**通俗解释**：知识库里所有应该被找到的文档，有多大比例被找到了？

**计算实例**

```
知识库中共有 10 篇关于"前庭觉训练"的文档
检索召回了 7 篇（其中 3 篇相关，4 篇不相关）

Recall = 7/10 = 0.7

被遗漏的 3 篇分别是：
  ├── 文档 X：标题"前庭刺激干预方案"（没包含"前庭觉训练"这个词 → BM25 没找到）
  ├── 文档 Y：内容在"平衡训练"小节中（语义检索分数不够高 → 被 threshold 过滤）
  └── 文档 Z：排在 top_k=10 之外（top_k 太小）
```

**盲区**：不关心返回了多少无关文档。返回 100 个文档、只有 10 个相关 → Recall=1.0（因为所有相关都被覆盖了），但 Precision 只有 0.1（90% 是噪音）。

**直觉判断**

| 分数 | 含义 |
|------|------|
| 0.8+ | 优秀——绝大部分相关文档被找到 |
| 0.5-0.8 | 可接受——有一半以上的相关信息可用 |
| < 0.4 | 差——超过一半的相关文档未被检索到，答案完整性严重不足 |

---

#### L1-3：MRR（Mean Reciprocal Rank，平均倒数排名）

**公式**

```
对单个查询：RR = 1 / (第一个相关结果的排名位置)
MRR = 所有查询的 RR 的平均值
```

**通俗解释**：用户平均需要翻多少个结果才能找到第一个有用的？翻得越少越好。

**计算实例**

```
用户问："前庭觉训练方法"
返回结果列表：
  第 1 位：本体觉训练 ✗（不相关）
  第 2 位：触觉训练   ✗（不相关）
  第 3 位：前庭觉训练方法 ✓（相关！第一个有用的在这）
  第 4 位：前庭觉有效训练 ✓（相关但排在后面）

MRR = 1/3 ≈ 0.33

理想情况：第 1 位就相关 → RR = 1/1 = 1.0 ⭐
糟糕情况：翻到第 20 位才找到 → RR = 1/20 = 0.05
```

**直觉判断**

| 分数 | 用户体验 |
|------|---------|
| 1.0 | 完美——第一个结果就是对的 |
| 0.5 | 平均第 2 位找到——可接受 |
| 0.2 | 平均第 5 位找到——用户已经开始不耐烦了 |
| 0.1 | 平均第 10 位找到——用户大概率已经放弃 |

**盲区**：只关心第一个相关结果的位置，不关心后面有多少相关结果。一个系统在 MRR=0.2（第一个对的在第 5 位），但第 5-10 位都是高度相关的 → MRR 低但用户仍然能找到答案（只是慢一点）。

**与 NDCG 的关系**：MRR 只关心第一个相关结果，NDCG 关心所有相关结果的排序质量。NDCG 更全面。

---

#### L1-4：NDCG@K（Normalized Discounted Cumulative Gain）

**公式**

```
DCG@K = rel₁ + Σ(k=2..K) rel_k / log₂(k)
NDCG@K = DCG@K / IDCG@K

其中：
  rel_k = 第 k 个结果的相关性分数（0=不相关, 1=有点相关, 2=相关, 3=非常相关）
  IDCG@K = 理想排序下的 DCG@K（所有结果按相关性从高到低排列时的 DCG）
```

**通俗解释**：不仅关心"有没有找到相关文档"，更关心"相关文档有没有排在前面"。

**计算实例**

```
返回前 5 个结果，相关性标注：[3, 2, 0, 3, 1]
（3=非常相关, 2=相关, 1=有点相关, 0=不相关）

实际排序的 DCG：
  DCG@5 = 3 + 2/log₂(2) + 0/log₂(3) + 3/log₂(4) + 1/log₂(5)
        = 3 + 2/1 + 0 + 3/2 + 1/2.32
        = 3 + 2 + 0 + 1.5 + 0.43 = 6.93

理想排序（相关性从高到低排列）：[3, 3, 2, 1, 0]
  IDCG@5 = 3 + 3/log₂(2) + 2/log₂(3) + 1/log₂(4) + 0
         = 3 + 3/1 + 2/1.58 + 1/2 + 0
         = 3 + 3 + 1.27 + 0.5 + 0 = 7.77

NDCG@5 = 6.93 / 7.77 = 0.89（排序质量很高，仅 11% 偏离理想排序）
```

**为什么用 log 折扣**：排第 2 位折扣 1/log₂(2)=1（不打折），排第 4 位折扣 1/log₂(4)=0.5（打 5 折）。排名越靠后，贡献折扣越大——因为用户越不可能翻到。

**盲区**：依赖相关性分数标注的质量。如果标注错误（把不相关的标成"非常相关"），NDCG 会虚高。标注成本高是 NDCG 在工业界使用受限的主要原因。

#### L2-1：Faithfulness（忠实度）——幻觉检测

**公式**

```
Faithfulness = 有上下文依据的声明数量 / LLM 答案中的总声明数量
```

**通俗解释**：LLM 生成的答案中，每一句话都能在检索到的文档中找到依据吗？

**检测原理——4 步**

```
步骤 1：拆解 LLM 答案为独立声明（原子事实）
  答案："游泳可改善前庭觉功能。建议每周 3 次，每次 30 分钟。"
  拆解为：
    声明 1："游泳可改善前庭觉功能"
    声明 2："建议每周 3 次"
    声明 3："每次 30 分钟"

步骤 2：对每个声明，用 LLM 判断能否从检索到的上下文中找到依据
  声明 1 → 上下文中有"游泳是前庭觉训练的有效方式" → ✓ 有依据
  声明 2 → 上下文中没有提到"每周 3 次" → ✗ 无依据（LLM 自己补充的）
  声明 3 → 上下文中没有提到具体的时长 → ✗ 无依据（LLM 自己补充的）

步骤 3：计算忠实度
  Faithfulness = 1/3 = 0.33（低——2/3 的声明是在编造）

步骤 4：有选择地标记/过滤无依据的声明
```

**为什么重要**

Faithfulness 是幻觉检测的核心指标。在医疗场景，LLM 补充的看似合理但无依据的细节（如"每周 3 次"）可能导致严重后果。与 Precision/Recall 不同——即使检索完美（L1 全高），生成仍可能不忠实（Faithfulness 低）。

**盲区**：只检查"答案是否忠于上下文"，不检查"上下文是否正确"。上下文错了但答案忠于上下文 → Faithfulness 高。这是检索的问题（L1 指标可以检测到），不是 Faithfulness 应该检测的。

**直觉判断**

| 分数 | 含义 |
|------|------|
| 0.9+ | 优秀——几乎所有声明都有来源 |
| 0.7-0.9 | 可接受——部分细节是 LLM 补充的（如常识性内容） |
| < 0.6 | 危险——近一半内容在编造，医疗场景不可上线 |

---

#### L2-2：AnswerRelevancy（答案相关性）——答非所问检测

**通俗解释**：答案有没有在回答问题？还是讲了一堆正确但不相关的内容？

**与 Faithfulness 的区别——关键对比**

```
场景 1：编造了不存在的训练方法
  Faithfulness 低（编造的内容没有依据）  AnswerRelevancy 高（虽然编造但确实在回答训练方法的问题）

场景 2：正确但偏题
  用户问"训练方法有哪些"，答案讲"本体觉的定义和历史"
  Faithfulness 高（内容在上下文中有依据）  AnswerRelevancy 低（没回答训练方法）

场景 3：完全编造且偏题
  两个都低 → 最差情况
```

**检测原理**：用 LLM 判断——"给定用户问题和生成的答案，这个答案在多大程度上回答了用户的问题？返回 0-1 的分数。"

**盲区**：LLM 的判断可能过于宽容（给出高分只是因为它"看起来相关"），也可能过于严格（把合理的扩展回答判定为不相关）。

#### L2-3：Groundedness（有依据性）——整体论点的可信度

**与 Faithfulness 的关键区别**

```
Faithfulness（逐句检查）：
  ├── 声明 "游泳改善前庭觉" → 有依据 ✓
  ├── 声明 "每周 3 次" → 无依据 ✗
  ├── 声明 "每次 30 分钟" → 无依据 ✗
  └── Faithfulness = 1/3 = 0.33（低——严格逐句检查）

Groundedness（整体判断）：
  ├── 核心论点 "游泳是有效的前庭觉训练方式" → 有支撑 ✓
  ├── 细节 "每周 3 次" → 虽无直接依据，但属于常识性训练建议
  └── Groundedness = 0.75（高——整体论点成立，细节有瑕疵但不影响主结论）
```

**为什么需要两个**：Faithfulness 太严格——每句话都要有依据，导致分数偏低。但有些无据细节可能是合理的常识补充（如训练时长建议）。Groundedness 提供了更宽松的视角——整体结论是否正确？两个指标互补判断。

---

### L3 综合评分的计算

```
L1 加权分 = Precision@K × 0.25 + Recall × 0.25 + MRR × 0.25 + NDCG@K × 0.25
L2 加权分 = Faithfulness × 0.4 + AnswerRelevancy × 0.3 + Groundedness × 0.3

Overall Score = L1 × 0.4 + L2 × 0.6
```

L1 四项等权（各 0.25），L2 三项 Faithfulness 最高权重（0.4）——幻觉是最高风险。L2 在 Overall 中权重 0.6——因为最终交付给用户的是答案，不是检索结果。

**权重可调**：法律场景可能提升 L1 权重（检索精确性更关键）、客服场景可能提升 L2 权重（答案友好性更关键）。

---

### 引擎 5：ReportEngine（报告引擎）——把数字变成洞察

**报告结构**

```
1. 执行摘要
   ├── 总体评分：78/100
   ├── 通过/失败：100 个用例，78 个通过，22 个不达标
   └── 关键发现：Recall 偏低（0.65），建议增大 BM25 top_k

2. 指标详情
   ├── L1 检索质量：Precision 0.72 | Recall 0.65 | MRR 0.81 | NDCG 0.78
   ├── L2 生成质量：Faithfulness 0.82 | Relevancy 0.85 | Groundedness 0.88
   └── L3 综合：L1=0.74, L2=0.84, Overall=0.80

3. 诊断分析
   ├── 6 层诊断结果（逐层输出）
   └── 根因分布：60% 检索问题（BM25 top_k 太小占 40%），25% 生成，15% 数据

4. Bad Cases（22 个）
   ├── 按失败类型分组
   └── 每组附代表性案例 + 失败原因

5. 调优建议（3 条）
   ├── 建议 1：BM25 top_k 10→20 → 预期 Recall +10%
   ├── 建议 2：向量 threshold 0.8→0.7 → 预期 Recall +8%
   └── 建议 3：启用重排序节点 → 预期 Precision +5%
```

---

### 引擎 6：TuningEngine（调优引擎）——从问题到行动

**三种建议类型**

| 类型 | 举例 | 产生条件 |
|------|------|---------|
| **配置调整** | "BM25 top_k 从 10 增大到 20" | 指标偏离方向明确，参数调优可解决 |
| **提示词优化** | "查询改写提示词缺少领域术语映射，补充分词表" | LLM 诊断发现查询理解偏差是根因 |
| **数据改进** | "触觉训练相关文档不足（仅 3 篇），补充文档" | 知识库本身缺少相关文档 |

**冲突检测**

多个建议之间可能存在矛盾：
- 建议 1：「增大 BM25 top_k 到 20」→ 预期 Recall +10%，延迟 +20ms
- 建议 2：「降低向量 threshold 到 0.6」→ 预期 Recall +15%，噪音 +30%
- 建议 3：「启用重排序」→ 预期 Precision +8%，延迟 +50ms

三条建议都在提升 Recall，但延迟的累计代价是 +70ms。TuningEngine 检测到这种"多个建议互相冲突或叠加影响过大"的情况时，标记冲突，要求人工决策。

**版本管理**：调优前自动保存配置快照，如调优后效果变差可一键回滚到调优前配置。

## 三、6 层诊断——从「知道指标差」到「知道为什么差」

### Layer 1：规则引擎（Rules Engine）——第一道过滤

**做什么**：用预定义阈值规则检查每项指标。纯数学判断，不调 LLM。60% 的评估在这一层就确认"一切正常"。

**规则示例表**

| 规则 | 阈值 | 命中后行为 |
|------|------|-----------|
| Recall 过低 | < 0.6 | 标记"检索覆盖面不足"，触发 Layer 2-3 |
| Faithfulness 过低 | < 0.7 | 标记"幻觉风险"，触发 Bad Case 分析 |
| Precision 和 Recall 差距过大 | > 0.3 | 标记"检索不平衡"——一边极端 |
| MRR 过低 | < 0.3 | 标记"排序质量差"——用户找不到第一个有用结果 |
| 端到端延迟过高 | > 2000ms | 标记"响应过慢"，建议检查缓存/节点并发 |
| 全部指标正常 | — | 直接输出"评估通过"，跳过 Layer 2-6 |

---

### Layer 2：历史对比（History Comparison）——发现退化

**做什么**：将当前运行的指标与历史基线对比。

| 对比 | 计算 | 判断标准 |
|------|------|---------|
| vs 基线 | 当前分数 - 基线分数 | 下降 > 5% → 回归警告 |
| vs 上一次 | 当前分数 - 上次分数 | 下降 > 3% → 趋势警告 |
| vs 历史最佳 | 当前分数 - 历史最佳 | 差距 > 10% → 触发诊断 |

**为什么需要**：单次运行的指标看不出趋势。Recall=0.65 不算高，但如果上次是 0.75 → 说明最近的变更导致了退化；如果上次是 0.60 → 说明在进步。只看绝对数值会误判。

---

### Layer 3：LLM 诊断（LLM Diagnosis）——分析失败根因

**做什么**：用 LLM 分析所有 Bad Cases，归类失败模式，识别根因。

**工作过程**

```
输入：
├── 所有 Bad Cases（指标低于阈值的用例）
└── 每个用例的完整数据：用户问题 + 期望答案 + 检索结果 + LLM 生成答案

LLM 分析一个具体 Bad Case：
────────────────────────────────────────
Bad Case #23：
  问题："触觉训练方法有哪些？"
  检索到了：本体觉训练相关文档（3 篇）
  LLM 回答：基于检索结果生成，但全在讲本体觉

  LLM 诊断结论：
  ├── 失败类型：检索问题（检索到了错误领域的文档——语义混淆）
  ├── 根因：向量检索将"触觉训练"和"本体觉训练"语义混淆
  │         这两个概念在向量空间中接近（都是"感统训练"的子领域）
  │         但它们是不同的维度，混淆导致检索到错误领域的文档
  └── 建议：① 提升向量 similarity_threshold 到 0.75 减少边缘混淆
            ② 在检索查询中增加领域限定词（如"触觉 感觉统合 训练"）
            ③ 增强同义词库中"触觉"的领域限定
────────────────────────────────────────
```

**输出（聚合分析）**：

```
根因分布报告（100 个用例，22 个失败）：
├── 60% 检索问题（13 个）
│   ├── BM25 top_k 太小（遗漏相关文档）：5 个（占失败的 23%）
│   ├── 语义混淆（领域间向量距离太近）：5 个（占失败的 23%）
│   └── 检索查询生成不佳（缺少关键术语）：3 个（占失败的 14%）
├── 25% 生成问题（6 个）
│   ├── 细节编造（Faithfulness 低）：4 个
│   └── 偏题（AnswerRelevancy 低）：2 个
└── 15% 数据问题（3 个）
    └── 知识库缺少相关文档：3 个
```

---

### Layer 4：质量校验（Quality Check）——系统性问题还是随机失败

**做什么**：检查跨用例的一致性、分数分布、失败聚类，判断失败是系统性的还是随机的。

| 检查项 | 方法 | 什么情况下触发警报 |
|--------|------|-----------------|
| 跨用例一致性 | 找语义相似的查询对比结果 | "3 岁前庭觉训练" 和 "3 岁儿童前庭觉训练方法" 答案差异巨大 → 检索不稳定 |
| 分数分布 | 分析指标的最小/最大/标准差 | 标准差过大 → 极端用例存在；全接近 1.0 → 测试用例太简单 |
| 失败聚类 | 按主题/难度/查询类型分组 | 某类查询集中失败（如所有"触觉"相关）→ 系统性缺陷 |
| 重复模式 | 检查多个 Bad Case 是否有相同错误 | 10 个用例都是"检索正确但答案不对"→ 生成提示词有问题 |

**为什么需要**：3 个失败可能是随机噪音，30 个失败集中在同一主题就是系统性缺陷。不区分这两者会导致：过度反应随机波动，或忽视真正的系统性问题。

---

### Layer 5：效果校验（Effect Validation）——调优真的有效吗

**做什么**：对比调优前后的指标，验证建议的实际效果。

```
调优建议："增大 BM25 top_k 从 10 到 20"（预期 Recall +10%）

调优前：Recall = 0.65
调优后：Recall = 0.75 → +15% → 超过预期阈值（+10%） → 效果验证 ✓ 通过

调优建议："启用重排序节点"（预期 Precision +5%）

调优前：Precision = 0.72
调优后：Precision = 0.71 → -1% → 未达到预期 → 标记"无效建议"
→ 触发重新分析：为什么重排序没有提升 Precision？
  可能原因：初始检索结果的精度已经较高，重排序能做的提升空间小
```

---

### Layer 6：回归校验（Regression Check）——没拆东墙补西墙

**做什么**：确保调优 A 指标时不劣化 B 指标。

**退化阈值矩阵**

| 指标 | 退化阈值 | 超过后 |
|------|---------|--------|
| 任何 L1/L2 指标 | > 3% 下降 | 标记为回归，警告 |
| 端到端延迟 | > 20% 增加 | 标记为回归，警告 |
| 任何指标 | > 10% 下降 | **阻止发布**（硬性约束） |

> **注意**：Layer 6 的退化阈值（3%）比 Layer 2 的基线退化阈值（5%）更严格——因为 Layer 6 检测的是"调优操作导致的直接退化"，调优应该提升效果而非劣化它，对退化的容忍度更低。Layer 2 检测的是"随时间漂移"，5% 的波动可能由知识库变化、模型版本更新等自然因素引起。

**完整校验实例**

```
调优：增大 BM25 top_k 从 10 到 20

| 指标 | 调优前 | 调优后 | 变化 | 判断 |
|------|--------|--------|------|------|
| Recall | 0.65 | 0.75 | +15% ✓ | 达到预期 |
| Precision | 0.72 | 0.71 | -1% | 可接受（< 3%） |
| MRR | 0.81 | 0.80 | -1% | 可接受 |
| Faithfulness | 0.82 | 0.82 | 0% | 不变 |
| 端到端延迟 | 120ms | 180ms | +50% ✗ | **超出退化阈值（20%）** |

结论：Recall 提升了 15%，但延迟从 120ms 暴涨到 180ms（超过 20% 退化阈值）。
→ 阻止发布！需要评估——这个延迟增长是否可接受？如果不可接受，是否有补偿措施（如引入缓存）？
```

**为什么这是上线前的最后一道安全网**

调优通常是为了提升 A 指标，但可能无意中劣化 B 指标。在医疗场景，为提升 Recall 而暴涨的延迟可能意味着用户等待时间从"可接受"变成"可能放弃"——这本身就是一种退化，即使所有质量指标都提升了。

## 四、调优闭环——完整案例

以下是一个完整的「配置 → 评估 → 调优 → 再评估」闭环实例：

```
─────────────────────────────────────────────────────────────────
第 0 步：当前配置 v1
─────────────────────────────────────────────────────────────────
BM25 top_k=10, 向量 top_k=10, RRF k=60, similarity_threshold=0.8, 无重排序

─────────────────────────────────────────────────────────────────
第 1 步：运行评估（100 个用例）
─────────────────────────────────────────────────────────────────
L1：Precision=0.72, Recall=0.65（偏低！）, MRR=0.81, NDCG=0.78
L2：Faithfulness=0.82, Relevancy=0.85, Groundedness=0.88
整体：78/100

Layer 1 规则引擎命中：Recall 0.65 < 0.7 → 触发诊断
Layer 2 历史对比：上次 Recall 0.70 → 下降了 5% → 退化警告
Layer 3 LLM 诊断：
  ├── 5 个 Bad Case 因 BM25 top_k=10 太小遗漏了相关文档
  ├── 4 个 Bad Case 因 similarity_threshold=0.8 太高过滤了语义相关但分数略低的文档
  └── 3 个 Bad Case 因未启用重排序导致排序质量不足

─────────────────────────────────────────────────────────────────
第 2 步：TuningEngine 生成建议
─────────────────────────────────────────────────────────────────
建议 1：BM25 top_k 10→20 → 预期 Recall +10%
建议 2：向量 similarity_threshold 0.8→0.7 → 预期 Recall +8%
建议 3：启用重排序节点 → 预期 Precision +5%

冲突检测：建议 1 和 2 叠加可能导致延迟增长 → 建议先单独试试建议 1

─────────────────────────────────────────────────────────────────
第 3 步：一键采纳 → 配置自动变更为 v2
─────────────────────────────────────────────────────────────────
BM25 top_k=20, 其他不变

─────────────────────────────────────────────────────────────────
第 4 步：再次评估
─────────────────────────────────────────────────────────────────
L1：Precision=0.71, Recall=0.75（+15% ✓）, MRR=0.80, NDCG=0.77
L2：无变化（Faithfulness=0.82, Relevancy=0.85, Groundedness=0.88）
整体：81/100（+3 分）

Layer 5 效果校验：Recall 提升 15% > 预期 10% → ✓ 通过
Layer 6 回归校验：
  ├── Precision -1%（< 5% 退化阈值）→ ✓ 可接受
  ├── 延迟 +10ms（< 20% 退化阈值）→ ✓ 可接受
  └── 其他指标无明显变化 → ✓ 全部通过

─────────────────────────────────────────────────────────────────
第 5 步：发布 v2
─────────────────────────────────────────────────────────────────
```

## 五、平台评估升级——跨域扩展 + 节点指向 + 一键采纳

以上评估体系是为单管道、单知识库设计的（MVP 场景）。平台化后需要增量扩展三层能力（详见 09-pipeline-publish-eval-upgrade 的评估升级部分）：

1. **跨域扩展指标**：4 项新指标评估多域聚合效果——域激活准确率、跨域覆盖率、冲突检测率、端到端延迟
2. **评估结果指向具体节点**：从「Recall 低」到「BM25 检索节点 top_k=10 导致 Recall 低」
3. **自动化调优闭环**：一键采纳 → 自动修改配置 → 版本对比 → 回滚保护

本章覆盖的是评估体系的基础架构（单管道场景），平台增量部分见 09-pipeline-publish-eval-upgrade。

## 关键设计点

| 设计点 | 为什么 | 量化收益 |
|--------|--------|---------|
| 6 引擎分工 | 生成→管理→运行→计算→报告→调优，各自独立 | 测试用例生成效率：从"几天"到"几分钟" |
| 分层指标（L1/L2/L3） | 不同层面独立评估，定位问题更快 | 问题定位精确到"检索"还是"生成" |
| 双指标互补（Faithfulness + Groundedness） | 严格逐句 + 宽松整体，避免单一视角误判 | 幻觉检测覆盖率提升 |
| 6 层诊断递进 | 从规则快速过滤到 LLM 深度分析到回归校验 | 60% 评估在 Layer 1 就完成，节省算力 |
| 回归校验 | 调优 A 时不劣化 B | 防止"拆东墙补西墙"的退化上线 |
| 调优闭环 | 配置→评估→诊断→建议→采纳→再评估 | 调优效率从"手动试错"到"一键采纳" |

## 一句话总结

> **RAG 评估 = 6 引擎协作 × 7 项三层指标 × 6 层递进诊断 × 调优闭环。从"凭感觉调参"到"数据驱动调优"，从"知道差"到"知道改哪个参数"。**
