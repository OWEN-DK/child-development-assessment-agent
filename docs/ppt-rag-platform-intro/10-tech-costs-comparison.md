# 10 · 成本分析 + 技术选型 + MVP vs 平台总结——花多少钱？怎么做？值不值？

> 核心问题：整个系统花多少钱？技术架构怎么选才不会成为瓶颈？平台比 MVP 到底好在哪里——为什么不能修补 MVP 而是必须重建？

## Part A：全链路成本分析

### 成本全景——为什么 LLM 成本不是瓶颈

```
MVP 各场景单次成本对比（对数尺度）：

  上传一本书 (200页)  ██████████████████████████░░  0.27 元
  跑一轮 RAG 评估     ██████████████████████████░░  1.15 元
  (100用例)
  跑一轮 Agent 评估   █████░░░░░░░░░░░░░░░░░░░░░░  0.05 元
  查一次 RAG          █░░░░░░░░░░░░░░░░░░░░░░░░░░  0.006 元
```

**关键发现**：LLM 调用成本极低——一次评估 5 分钱，一次查询不到 1 分钱。**真正的成本不在模型调用，而在开发效率和规模化交付。** 平台化的价值不是"省模型费"，而是"让新客户接入从 3-5 天变成 30 分钟"。

### 模型选型深度对比

| 模型 | 输入价格（元/百万Token） | 输出价格（元/百万Token） | 为什么用它 | 对应的场景 |
|------|----------------------|------------------------|-----------|-----------|
| **qwen-plus** | 0.8 | 2.0 | 性价比之王——精度接近 qwen-max（约 90%），价格只有 1/5 | Agent 评估、评分、报告、查询改写、元数据提取 |
| **qwen-turbo** | 0.3 | 0.6 | 最快最便宜——比 plus 便宜 60%，速度快 2-3 倍 | 分层摘要、记忆提取、查询分解（快速操作） |
| **qwen3-omni-flash** | 0.2 | 2.0 | 能看图的模型里最便宜——识别扫描版 PDF 中的文字 | VL 解析（仅降级兜底，约 15-20% 的文档才用） |
| **text-embedding-v4** | 0.5 | — | 中文优化最好——比 OpenAI embedding 便宜，中文效果更好 | 所有向量化场景（上传、搜索） |
| **qwen3-rerank** | 0.5 | — | 极低价格，显著提升检索精度 | 检索后重排序 |

**为什么用多个模型而不是一个模型包办**：不同任务对模型的要求不同——元数据提取需要精度（用 plus），查询分解需要速度（用 turbo），图片识别需要视觉能力（用 omni-flash）。一个模型包办一切 → 为简单任务付出不必要的成本，或为复杂任务牺牲了精度。

### 各场景成本拆解

**一次 Agent 评估 ≈ 0.048 元（约 5 分钱）**：

```
NodePre（预处理）： 0 元     — 纯统计计算，不调 LLM
Node1（校验）：     0.004 元 — qwen-plus，输入 3000 + 输出 800 Token
Node2（评估）：     0.007 元 — qwen-plus，输入 5000 + 输出 1500 Token
Node3（检索）：     0.005 元 — Embedding（可忽略）+ Rerank（10条候选）
Node4（评分）：     0.014 元 — qwen-plus × 2 次（AHP + ML 融合各一次）
Node5（报告）：     0.018 元 — qwen-plus，输入 12000 + 输出 4000 Token（最大单项开销，占 37%）
─────────────────────────────────────────────
总计 ≈ 0.048 元
```

**上传一本书（200 页，700 分块）≈ 0.27 元**：

```
文档解析：       0 元    — PyMuPDF（首选，免费）；如为扫描版 → Qwen-VL = 0.04 元
文档清洗：       0 元    — 纯规则
语义分块：       0 元    — 纯计算
元数据提取：     0.22 元 — 700 分块 × qwen-plus（每块 ~1000 Token 输入 + ~200 Token 输出）← 占 81%
向量化：         0.05 元 — 10.5 万 Token × 0.5 元/百万 Token
写入向量库：     0 元    — 本地 ChromaDB
刷新检索器：     0 元    — 本地操作
─────────────────────────────────────────────
总计 ≈ 0.27 元
```

**一次 RAG 搜索 ≈ 0.006 元**：

```
同义词扩展：     0 元      — 本地词库查表
查询向量化：     ~0.00003 元 — 可忽略
[可选] 查询重写： 0.0006 元 — qwen-plus（仅在启用查询重写节点时）
混合检索：       0 元      — 纯计算
[可选] 重排序：   0.005 元  — qwen3-rerank（10 条候选）← 最大开销
─────────────────────────────────────────────
总计 ≈ 0.006 元（含重排序）/ 0.0006 元（不含重排序）
```

**一轮 RAG 评估（100 用例）≈ 1.15 元**：

```
草稿生成：       0.24 元 — qwen-plus，200 分块提取问答对
测试运行：       0.76 元 — 100 用例 × 每个检索（0.006）+ 生成（0.001-0.002）
Faithfulness 检查：0.14 元 — 100 用例验证答案是否有据可查
LLM 诊断：       0.008 元 — 分析 Bad Cases
─────────────────────────────────────────────
总计 ≈ 1.15 元
```

**一次评估只需 1 块钱**——用不到一杯咖啡的成本，完成 100 个用例的检索质量全链路评估。

### 成本大头分析与优化方向

| 最大开销 | 占比 | 优化方向 | 预期效果 |
|---------|------|---------|---------|
| 元数据提取（上传） | 占上传总成本的 81% | 简单标签（age_range）用正则替代 LLM | 元数据成本降低 40-50% |
| 报告生成（Agent 评估） | 占评估总成本的 37% | 分级生成（先摘要再详情）+ 减少报告模板长度 | 报告成本降低 30% |
| 重排序（搜索） | 占搜索总成本的 83% | 用本地 CrossEncoder 模型替代 API 调用 | 重排序成本降为 0（但需要 GPU 推理） |
| 测试运行（评估） | 占评估总成本的 66% | 用 qwen-turbo 替代 qwen-plus 做初筛 | 测试运行成本降低 40% |

### 平台规模化后的边际成本递减

平台的多租户共享部署模型产生显著的成本摊薄效应：

```
10 个客户独立部署（MVP 模式）：
  10 × (服务器 + 数据库 + 向量库 + 监控 + 备份) = 10 套运维成本

10 个客户共享平台（平台模式）：
  1 套基础设施 + 10 × tenant_id 逻辑隔离 = 1 套运维成本（90% 成本节约）
```

**但真正的规模优势不在基础设施成本，而在配置效率**：客户 B 接入时，不需要开发重新搭建一套检索管道——客户管理员在编辑器中复制客户 A 的管道模板，修改参数，30 分钟上线。

## Part B：技术选型——Python + Rust 混合架构

### 选型第一原则：最低延迟 + 最佳体验

不做语言绑定，做性能绑定。不同任务用最合适的语言——不因偏好限制性能上限。

### 四个关键决策的深度对比

#### 决策 1：Python 主体 + Rust 热点（而非纯 Python 或纯 Rust）

```
PipelineCompiler 分工：
├── 编排框架：Python（LangChain 生态）
├── 23 个 I/O 密集型节点：Python
│   └── 瓶颈在网络等待（LLM API、向量库查询），Python 足够
└── 5 个 CPU 密集型热点：Rust + PyO3
    ├── MinHash 去重（纯数学计算）
    ├── RRF 融合（纯数学计算）
    ├── BM25 评分（纯数学计算）
    ├── PII 脱敏（密集正则匹配）
    └── 文档分块（大量文本处理）
```

| 如果走纯 Python | 如果走纯 Rust | Python + Rust 混合 |
|---------------|-------------|-----------------|
| 5 个 CPU 热点慢 10-100 倍 | 无 LLM SDK 生态（LangChain/LlamaIndex/DashScope 全 Python） | 取两者之长 |
| 但 LLM 生态完整 | GPU 推理支持不成熟 | Python 的生态 + Rust 的性能 |

**PyO3 的关键优势**：PyO3 是进程内调用（同一进程，直接函数调用），不像 gRPC/HTTP 需要跨进程通信。每次跨语言调用延迟 = 0（零额外开销），vs gRPC 的 1-5ms/次。在 RRF 融合这种高频调用场景，5ms × 10000 次调用的差距是巨大的。

#### 决策 2：不引入 K8s/Kafka/RabbitMQ（一期）

| 不引入 | 具体原因 | 当前替代方案 | 何时引入 |
|--------|---------|------------|---------|
| **Kafka/RabbitMQ** | 当前唯一的消息场景是异步任务状态推送，Redis Pub/Sub 已满足 | Redis Pub/Sub（已继承） | 需要事件溯源、多消费者组、消息持久化时 |
| **Kubernetes** | 一期单实例部署，K8s 的编排/扩缩容/服务发现能力用不上 | Docker Compose | 需要自动扩缩容、滚动更新、多实例负载均衡时 |
| **服务网格（Istio/Linkerd）** | 单体部署不需要微服务间的流量管理和 mTLS | Nginx 反向代理 + Docker 内部网络 | 拆分为微服务群时 |

**核心原则**：新增组件必须有"不用它就无法解决的明确问题"作为理由。每增加一个组件，运维复杂度指数增长。

#### 决策 3：渐进式优化——先用 Python 全通，再 profile 热点

不预先优化。Phase 8 之前全部用纯 Python 实现 28 种节点。Phase 8 后运行 profiling，识别真实的 CPU 热点（不是猜测的热点），只对真正的热点用 Rust 重写。

**为什么**：「过早优化是万恶之源」。最终可能只有 3-5 个节点真正需要 Rust，如果一开始就计划全部重写，80% 的工作量是浪费在不需要优化的节点上。

#### 决策 4：PipelineCompiler 自研（而非用 LangGraph）

| 如果选 LangGraph | 为什么不够 |
|----------------|-----------|
| LangGraph 提供通用的图编排 | 无原生的降级路径机制（一个节点失败 → 整个图失败） |
| 支持条件路由 | 无原生的域并行分发机制（多域并行是平台核心创新，LangGraph 无内置支持） |
| LangChain 生态兼容 | PipelineCompiler 需要特殊的编译优化——28 种节点的 JSON 配置 → 可执行 DAG——这个编译器逻辑是平台的核心壁垒 |

### 渐进式优化策略

```
Phase 0-7：纯 Python 跑通全部 28 种节点
    │
Phase 8：profiling 识别真实热点
    │  预期结果：绝大部分节点的瓶颈在 I/O（网络等待），CPU 占比 < 5%
    │  真正的热点只集中在 5 个纯计算节点
    ▼
Phase 8+：仅对 5 个 CPU 热点 → Rust + PyO3
    │  每个节点独立实现和验证
    │  性能提升预期：10-100 倍（对热点节点本身）
    │  对端到端延迟的影响：热点节点占端到端延迟的 5-15%
    │  → 端到端延迟提升 5-10%
    ▼
Phase 10：验证 ES/Milvus 适配器（规模驱动的升级，非语言驱动）
```

### 三种向量后端的升级路径

```
Chroma (默认，Phase 0-2)
  ├── 适用：< 10 万文档
  ├── 优点：轻量、零依赖、本地持久化
  └── 升级触发条件：文档量接近 10 万 → 检索延迟开始退化
        │
        ▼
Elasticsearch (中等规模，Phase 10)
  ├── 适用：10 万-100 万文档
  ├── 优点：内置 BM25 + 向量检索、分布式、成熟生态
  └── 升级触发条件：文档量接近 100 万 → ES 的向量检索（非专用）开始退化
        │
        ▼
Milvus (大规模，Phase 10)
  ├── 适用：> 100 万文档
  └── 优点：专用向量数据库、十亿级向量、GPU 加速
```

**升级方式**：在知识库配置中切换 `vector_backend` → 自动触发数据迁移流程（向量化数据从旧后端导出 → 导入新后端 → 验证一致性 → 切换生效）。一次知识库升级不影响其他知识库（各自独立后端选择）。

### 技术降级路径——每个决策有备选

| 组件 | 主选择 | 备选 | 切换到备选的触发条件 |
|------|--------|------|-----------------|
| 向量存储 | Chroma | ES（中等）/ Milvus（大规模） | Chroma 单机检索延迟 > 目标值 |
| 编排引擎 | PipelineCompiler（自研） | — | 自研是核心壁垒，无备选 |
| 前端画布 | React Flow | 自研 Canvas | React Flow 不支持关键的自定义交互类型 |
| BM25 索引 | 独立索引（Chroma 后端时）/ ES 内置（ES 后端时） | — | 跟随向量后端选择 |

## Part C：MVP vs 平台全景对比

### 12 维度对比表

| 维度 | MVP | 平台 | 改进价值 |
|------|-----|------|---------|
| **知识库** | 单库，所有领域知识混在一起 | 多库独立，物理隔离（独立 collection/index） | 检索不再被跨域文档污染 |
| **检索策略** | 硬编码在 Python 代码中 | 可视化管道编辑器，拖拽配置 28 种节点 | 从"开发改代码"到"客户自助" |
| **权限控制** | 无 | 双层 Pre-filter——库级别裁剪域 + 文档级别 ACL 过滤 | 安全合规，从根源防止信息泄漏 |
| **多租户** | 不支持——每个客户一套独立部署 | 逻辑隔离（一期）→ 物理隔离（二期） | 从"运维成本线性增长"到"边际成本递减" |
| **评估系统** | 有 6 引擎 + 7 指标，但与配置脱节 | 评估指向具体节点 → 一键采纳 → 调优闭环 | 从"知道差"到"知道改哪个参数 → 一键改好" |
| **搜索 API** | 单一端点 | 三种——发布 URL + 通用端点 + SSE 流式 | 从"内部专用"到"外部集成只需一个 URL" |
| **域聚合** | 不支持——单域单路检索 | 多域并行聚合——跨域融合 + 冲突检测 | 跨知识领域的完整答案 |
| **节点体系** | 固定 6 节点（Agent 评估专用） | 28 种可选节点（22 域内 + 6 聚合），全部可配 | 灵活组合——按需启用，不启用不付费（延迟） |
| **版本管理** | 不支持——无配置快照 | 管道版本管理——快照 → 对比 → 回滚 | 平滑升级，效果退化可一键回滚 |
| **降级路径** | 不支持——节点失败 → 管道崩溃 | 任意节点可配降级——主失败走备 → 备失败跳过 | 高可用——单个节点失败不影响整体 |
| **配置方式** | 开发改代码 | 客户管理员拖拽 UI | 新客户接入：从 3-5 天到 30 分钟 |
| **运维成本** | 随客户数线性增长 | 多租户共享部署 → 边际递减 | 10 个客户从"10 套运维"到"1 套运维" |

### 核心价值——按受益方划分

| 受益方 | MVP 能提供什么 | 平台能提供什么 | 核心变化 |
|--------|-------------|-------------|---------|
| **产品经理/客户管理员** | 提需求 → 排期 → 等开发 | 打开编辑器 → 拖拽配置 → 即时生效 | 从"需求方"到"操作者" |
| **安全/合规团队** | 没有权限控制——文档全员可见 | 双层 Pre-filter——按角色裁剪，不可绕过 | 从"无法合规"到"安全内建" |
| **算法工程师** | 知道指标差但不知道改哪 | 诊断指向具体节点参数 → 一键采纳 | 从"猜着调"到"数据驱动调优" |
| **最终用户** | 单域检索——跨域查询回答不完整 | 多域并行聚合——跨域完整答案 + 矛盾提示 | 从"部分信息"到"完整答案" |
| **运维/DevOps** | 每客户独立部署一套 | 多租户共享部署 → 一套运维 | 从"线性增长"到"边际递减" |
| **管理层/决策者** | 能力验证（POC 通过） | 规模化能力（可交付多客户） | 从"是否可行"到"是否可规模化" |

### 为什么不能修补 MVP——5 个根本性架构差异

| MVP 架构假设 | 平台架构要求 | 为什么不能修补 |
|------------|------------|-------------|
| 只有 1 个知识库 | N 个独立知识库，物理隔离 | 需要重建整个知识库管理层——从单库到多库不是加参数，是换架构 |
| 只有 1 个租户 | N 个租户，逻辑隔离 | 需要在所有数据层（DB/向量库/文件存储/缓存）注入 tenant_id |
| 管道硬编码在代码中 | 管道是 JSON 配置，由编译器执行 | 需要开发整个 PipelineCompiler——这是平台最核心的引擎 |
| 无权限概念 | 双层 Pre-filter，全局强制 | 需要在检索执行前注入权限条件——对 MVP 而言是从 0 到 1 的设计 |
| 评估结果不指向配置 | 评估指向具体节点参数 | 需要在 6 引擎基础上增加节点追踪和参数关联 |

### 修补 vs 重建——时间与风险对比

如果尝试在旧 MVP 架构上修补出平台的 5 项核心能力（多知识库、多租户、管道可配置、权限、评估闭环），与重建平台的对比：

| 对比维度 | 修补 MVP | 重建平台 |
|---------|---------|---------|
| **多知识库物理隔离** | 改造现有单库 CRUD → 多库管理 + 独立 collection。约 3-4 周，高风险——数据迁移可能损坏现有知识库 | 从 Phase 2 开始就是多库原生支持。已作为独立模块完成，3 周 |
| **多租户隔离** | 在所有 SQL 查询、Redis Key、文件路径中注入 tenant_id。约 2 周，高风险——遗漏一处即造成数据泄漏 | Phase 1 原生设计，所有数据层自带租户隔离。1 周 |
| **管道可视化 + 编译器** | 从硬编码管道反向提取为配置格式，再实现编译器。约 5-6 周，高风险——反向工程的配置格式可能不完整 | Phase 3 正向设计——28 种节点 + Compiler。已完成（含测试），4 周 |
| **双层 Pre-filter 权限** | 从"零权限"叠加到"检索前过滤"。约 3 周，高风险——安全模型打补丁容易出漏洞 | Phase 1-2 从第一天嵌入权限。已作为基础设施完成，2 周 |
| **评估→节点指向→一键采纳** | 评估结果与配置参数的关联需要反向工程。约 3-4 周 | Phase 7 正向设计，评估引擎原生感知管道节点结构 |
| **总计** | **约 16-19 周（4-5 个月）**，高风险——每步都是逆向手术 | **约 13-15 周（3-4 个月，Phase 0-7）**，低风险——正向设计 + 完整测试 |

**核心结论**：修补 MVP 不仅不会更快（时间相当甚至更长），而且每步都在逆向工程——先在旧代码中理解"为什么写死了这个参数"，再解开它，再测试确保没引入回归。累积风险远超重建。加上修补过程中旧系统需要停服或降级——而重建的新平台可以与旧系统并行运行，零停机切换（见 06 "现有 MVP 客户如何迁移"）。

**核心结论**：MVP 的 5 个局限不是"功能缺失"（加几个功能就能解决），而是"架构假设"（MVP 建在单租户/单库/硬编码的假设上）。要打破这些假设，必须在正确的架构上重建——这就是平台化的根本原因。

## 关键设计点

| 设计点 | 为什么 |
|--------|--------|
| LLM 成本不是瓶颈 | 一次查询不到 1 分——真正成本在开发效率和规模化交付 |
| 多模型分工 | 不同任务对精度/速度/能力的要求不同——一个模型包办一切既不经济也不最优 |
| Python+Rust 混合 | 不做语言绑定，做性能绑定——I/O 节点 Python，CPU 热点 Rust |
| 渐进式优化 | profiling 后再决定优化范围——避免 80% 的优化工作在不需要优化的节点上 |
| 不引入重型基础设施 | 每个新增组件必须有明确的"不用它解决不了的问题" |
| 平台价值不在技术本身 | 在"让客户自助配置"——开发效率 > 模型成本节省 |

## 一句话总结

> **全链路 LLM 成本极低（一次查询不到 1 分钱），瓶颈在开发效率和规模化交付。Python+Rust 混合架构兼顾生态和性能，渐进式优化不预先浪费。平台相比 MVP 的 12 维度提升不是功能叠加，而是架构重建——打破了单租户/单库/硬编码/无权限的 MVP 架构假设。**
