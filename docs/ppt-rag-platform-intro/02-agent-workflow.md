# 02 · Agent 评估工作流——如何自动评估运动计划并生成家长友好的报告？

> 目标受众：懂技术的产品经理
> 核心问题：用户输入儿童画像和运动计划，系统如何经过 6 个步骤，输出一份有科学依据、家长能看懂、可以指导行动的评估报告？

---

## 核心问题

家长输入：「3 岁男孩，平衡能力差，走路容易摔倒，对声音敏感。计划安排游泳和平衡木训练，每天 30 分钟。这个计划安全吗？适合孩子吗？」

如果把这个输入直接丢给一个巨大的函数处理——从数据清洗到评估到检索到报告一步完成——会发生什么？

1. **出问题不知道哪个环节错**。如果最终评分偏低，是输入校验有问题？是评估维度选错了？是检索到的文献不对？还是报告模板有偏差？
2. **改一个环节可能影响全局**。想优化预处理逻辑 → 改了可能影响校验 → 校验改了可能影响评估 → 牵一发而动全身。
3. **无法独立测试和替换**。想换个评分算法？必须连着报告生成一起改。
4. **成本失控**。每个环节都调 LLM？预处理 5000 Token，校验 3000 Token，评估 5000 Token……一次评估可能要 2 万 Token。

**解决方案**：把评估流程拆成 6 个独立节点，每个节点只做一件事。节点之间通过共享状态传递数据。这就是 **6 节点 DAG（有向无环图）架构**。

---

## 一、什么是 6 节点 DAG 架构

```
┌─────────────┐    ┌─────────────┐    ┌─────────────┐    ┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│  用户输入    │ →  │  NodePre     │ →  │  Node1       │ →  │  Node2       │ →  │  Node3       │ →  │  Node4       │
│  儿童画像    │    │  预处理      │    │  校验       │    │  评估       │    │  检索       │    │  评分       │
│  运动计划    │    │  上下文压缩  │    │  数据标准化  │    │  发展评估   │    │  知识检索   │    │  AHP+ML    │
└─────────────┘    └─────────────┘    └─────────────┘    └─────────────┘    └─────────────┘    └─────────────┘
                                                                                                    │
                                                                                                    ▼
                                                                                            ┌─────────────┐
                                                                                            │  Node5       │
                                                                                            │  报告生成   │
                                                                                            │  Markdown   │
                                                                                            │  家长友好   │
                                                                                            └─────────────┘
```

**每个节点是一个黑盒**：接收输入 → 执行自己的逻辑 → 写入输出。节点不知道也不关心其他节点内部怎么工作，只知道从共享状态读取什么、写入什么。

### 状态管理——节点间的共享内存

整个评估过程的状态存在一个叫 `AgentState` 的结构中。每个节点从它读取前序节点的输出，把自己的输出写回去：

| 字段 | 类型 | 谁写入 | 谁读取 | 含义 |
|------|------|--------|--------|------|
| `child_profile` | ChildProfile | 用户输入 | NodePre, Node1, Node2, Node3, Node4, Node5 | 儿童画像（年龄、性别、发展史） |
| `proposed_plan` | ProposedPlan | 用户输入 | Node1, Node2, Node3, Node4, Node5 | 拟定的运动计划（活动列表、频率、时长） |
| `condensed_context` | CondensedContext | NodePre | Node2, Node3, Node5 | 压缩后的历史上下文（统计特征） |
| `child_state` | ChildState | Node1 | Node2, Node4, Node5 | 标准化后的儿童发展状态 |
| `evaluation_result` | EvaluationResult | Node2 | Node4, Node5 | 发展评估结果（各维度对标里程碑） |
| `retrieved_docs` | List[KnowledgeItem] | Node3 | Node4, Node5 | 检索到的科学依据文档 |
| `final_score` | FinalScore | Node4 | Node5 | 多维度评分结果 |
| `final_report` | FinalReport | Node5 | 用户 | 最终 Markdown 评估报告 |

**为什么用共享状态而非节点间直接传参**：
- 节点可以按需读取，不需要的字段不污染输入
- 新增节点时不需要修改已有节点的接口（只增加新字段）
- 调试时可以检查任一时刻的完整状态快照

## 二、六个节点逐一详解

### NodePre · 预处理——上下文窗口优化器

**它解决什么问题**

用户的评估历史可能包含几十条记录：每次评估的时间、计划内容、评分结果、建议。如果把这些原始记录全部喂给 LLM，5000+ Token 的上下文会让后续每个节点的 LLM 调用成本暴涨，而且长上下文会稀释 LLM 对关键信息的注意力——这就是「迷失在中间」（Lost in the Middle）问题：LLM 对长文本中间部分的信息关注度显著下降。

**如果不做预处理**

直接把 5000 Token 原始历史传给下游节点 → 每个下游节点都多花 4500 Token → 5 个节点多花 22500 Token → 一次评估的 LLM 成本可能翻倍。更糟的是，LLM 可能会被历史中的噪音信息误导。

**输入输出**

```
输入：
├── child_profile（用户输入，~200 Token）
└── 历史评估记录（30 条，~5000 Token）

输出：
└── condensed_context（~500 Token）
    ├── 平均训练时长：每次 45 分钟
    ├── 频率一致性：每周 3 次（标准差 0.5，很规律）
    ├── 趋势分析：过去 3 个月能力评分上升 15%
    ├── 常用训练项目：前庭觉训练（出现 20 次）、本体觉训练（出现 12 次）
    ├── 异常记录：2 次训练后出现疲劳反应
    └── 最近一次评估结果摘要
```

**核心逻辑**

不调 LLM——纯统计计算。提取以下几个维度：
1. 时间维度：平均训练频率、时长趋势
2. 内容维度：高频活动、新增活动、停止的活动
3. 效果维度：能力评分的移动平均、最近变化幅度
4. 异常维度：标记异常的记录（疲劳、疼痛、中断）

**为什么不用 LLM**：压缩历史记录是结构化数据的统计聚合，用规则完成比 LLM 更快（0ms vs 200ms+）、更稳定（不会随机遗漏）、且免费。

**关键设计决策**

| 决策 | 为什么 | 如果不这样 |
|------|--------|-----------|
| 纯规则计算，不调 LLM | 压缩结构化数据不需要语言理解能力 | 增加不必要的延迟和成本，且结果可能不准确 |
| 保留异常记录而非丢弃 | 异常记录对评估很重要（如「2 次训练后疲劳」） | 评估可能忽略重要的安全隐患 |
| 压缩率 90%（5000→500 Token） | 既保留关键信息又不让上下文溢出 | 压缩太多→丢失关键信息；压缩太少→成本没降多少 |

**成本拆解**

0 元——完全使用统计计算，不调用任何 LLM API。

### Node1 · 校验——输入守卫

**它解决什么问题**

用户输入可能不标准甚至错误：「3 岁半」不是标准化的年龄数值；活动「游泳」可能缺时长和频率字段；运动强度用「中等」「还行」等模糊描述。直接把脏数据传给 LLM 会导致：LLM 猜测缺失字段 → 猜错 → 整个评估结果不可靠。这就是 GIGO 原则（Garbage In, Garbage Out）。

**如果不做校验**

LLM 自己推断缺失字段时，可能把「每天 30 分钟」推断为「高强度」（实际对 3 岁儿童是中等），导致评分偏离真实情况。更糟的是，数据缺失本身就是一个信号——家长可能对运动计划了解不足——这个信号在校验后会被传递给评估节点。

**输入输出**

```
输入：
├── child_profile（用户原始输入）
│   { "age": "3岁半", "gender": "男", "concerns": ["平衡不好", "对声音敏感"] }
└── proposed_plan（用户原始输入）
    { "activities": [{"name": "游泳", "duration": "30分钟"}], "frequency": "每天" }

输出：
├── child_state（标准化后）
│   { "age": 3.5, "gender": "male", "concerns": ["前庭觉-平衡", "听觉处理-敏感"] }
└── proposed_plan（补全和标准化后）
    { "activities": [
        { "name": "游泳", "duration": 30, "frequency": 7, "intensity": "medium",
          "completeness": 0.67, "missing_fields": ["训练强度来源", "教练资质"] }
    ]}
```

**核心逻辑**

1. **类型标准化**：「3岁半」→ 3.5（浮点数）；「每天」→ 7（次/周）
2. **字段补全**：根据活动名称，从活动数据库中查询默认值 → 补全时长、频率、强度
3. **术语映射**：将日常表述映射到专业维度——「平衡不好」→ 前庭觉维度；「对声音敏感」→ 听觉处理维度
4. **完整性评分**：每个字段标记是用户提供还是系统补全的，计算 `completeness` 分数

**为什么用规则 + 数据库而非 LLM**

活动名称的补全（"游泳"的默认时长、频率）是确定性操作——查询数据库即可，不需要语言理解。术语映射（"平衡不好"→ 前庭觉）需要领域知识但不需要上下文理解——用内置映射表完成。只在映射表未命中时才考虑 LLM。

**边界条件与异常处理**

| 情况 | 处理 | 为什么 |
|------|------|--------|
| 年龄超出范围（< 0 或 > 18） | 拒绝输入，返回错误提示 | 系统仅支持 0-18 岁儿童 |
| 活动名称为空 | 标记 `completeness = 0`，但不拒绝 | 允许用户只输入基本信息 |
| 活动名称不在数据库中 | LLM 推理补全（万不得已） | 规则优先，LLM 兜底 |
| 频率数值异常（如"每天 10 次"） | 标记异常，传递给评估节点 | 可能是输入错误，也可能是真实情况 |

**成本拆解**

约 **0.004 元**。仅在活动名称不在数据库、需要 LLM 推理补全时才调 LLM（~3000 Token 输入 + 800 Token 输出，qwen-plus）。

### Node2 · 评估——画像师

**它解决什么问题**

家长用日常语言描述孩子（「平衡不好」「对声音敏感」），但专业评估需要在感统维度（前庭觉、本体觉、触觉等）上对标年龄发展里程碑。这个节点就是把日常描述「翻译」成专业评估，并回答：「这个孩子在各个维度上处于同龄人的什么水平？」

**如果不做评估**

直接跳过评估去检索，检索查询就只能是用户原话——「平衡不好怎么训练」——而不是经过专业维度转换后的精确查询——「3 岁儿童前庭觉功能低于里程碑的前庭刺激训练方案」。

**输入输出**

```
输入：
├── child_state（Node1 输出，标准化后的儿童数据）
├── proposed_plan（Node1 输出，补全后的运动计划）
└── condensed_context（NodePre 输出，压缩后的历史趋势）

输出：
└── evaluation_result
    ├── 前庭觉（平衡）：15 百分位，低于年龄里程碑
    │   └── 依据：家长描述"走路容易摔倒"，历史趋势显示平衡能力持续低于同龄
    ├── 听觉处理：25 百分位，需关注
    │   └── 依据：家长描述"对声音敏感"，符合听觉防御特征
    ├── 本体觉：60 百分位，正常范围
    │   └── 依据：未提及相关问题，历史记录中也无异常
    ├── 触觉：55 百分位，正常范围
    └── 总体发展评估：前庭觉和听觉处理需要重点关注
```

**核心逻辑**

1. **维度分解**：将日常描述中的每个关注点映射到一个或多个感统维度
2. **严重度评估**：根据描述中的关键词判断严重程度——「容易摔倒」→ 频率高，严重度较高；「对声音敏感」→ 需进一步判断是防御还是过敏
3. **里程碑对标**：根据年龄（3.5 岁）查找对应的感统发展里程碑，判断每个维度是"达标""接近达标"还是"需要干预"
4. **历史趋势叠加**：如果有历史数据（来自 NodePre），判断是"持续落后""近期退化"还是"稳定进步"
5. **LLM 综合判断**：将以上结构化分析输入 LLM，生成自然语言评估结果

**为什么需要 LLM 而非纯规则**

维度分解和严重度评估有一定模糊性——「走路容易摔倒」可能是前庭觉问题，也可能涉及本体觉（身体感知）。LLM 的语言理解能力可以在模糊情况下做出合理判断，而纯规则只能做关键词匹配（"摔倒"→ 前庭觉），容易误判。

**关键设计决策**

| 决策 | 为什么 | 如果不这样 |
|------|--------|-----------|
| 规则做维度映射，LLM 做综合判断 | 分工明确——规则处理确定性部分，LLM 处理模糊性 | 全 LLM → 成本高且可能误判明显情况；全规则 → 模糊情况判断不准 |
| 与历史趋势叠加 | 一个孤立的数据点信息量有限 | 只看当前不看趋势 → 可能把"近期退化"误判为"一直有问题" |

**成本拆解**

约 **0.007 元**。LLM 输入 ~5000 Token（包含 child_state + proposed_plan + condensed_context），输出 ~1500 Token，使用 qwen-plus。

### Node3 · 检索——知识专家

**它解决什么问题**

评估不能凭空判断。说「游泳对前庭觉训练有效」，这句话必须有科学文献支撑。检索节点从知识库中找到与儿童画像和运动计划相关的科学依据，为后续的评分和报告生成提供事实基础。

**如果不做检索**

评分节点只能基于 LLM 的内置知识（可能过时、可能幻觉）打分；报告节点生成的建议没有出处，家长无法验证每一条建议是否可靠。

**输入输出**

```
输入：
├── child_state（Node1 输出）
├── proposed_plan（Node1 输出）
├── evaluation_result（Node2 输出）
└── condensed_context（NodePre 输出）

检索查询生成：
"3岁儿童前庭觉训练 游泳 平衡训练 听觉敏感干预 训练安全性 训练量建议"

输出：
└── retrieved_docs（5-10 条）
    ├── 文档1：《前庭觉训练指南》- "游泳是前庭觉训练的有效方式，水的浮力减少关节压力..."
    ├── 文档2：《儿童运动发展里程碑》- "3 岁儿童前庭觉发展标准：能单脚站立 3 秒..."
    ├── 文档3：《听觉防御干预策略》- "对声音敏感的儿童建议逐步适应而非完全隔离..."
    ├── 文档4：《儿童运动训练安全指南》- "3 岁儿童单次训练时长建议 20-30 分钟..."
    └── 文档5：《感统训练有效性研究》- "每周 3-4 次感统训练在 12 周内可改善平衡能力..."
```

**核心逻辑**

1. **检索查询生成**：根据儿童画像 + 评估结果 + 运动计划，合成一个自然语言检索查询（可选：LLM 查询重写优化）
2. **混合检索**：BM25 关键词 + 向量语义双路检索，RRF 融合（详见 04-hybrid-search）
3. **重排序**：用更精细的 Reranker 模型对候选结果重新排序
4. **去重**：MinHash 去掉高度重复的文档片段
5. **最终选取**：取 Top-5 到 Top-10，保证多样性（不全是同一篇文档的不同片段）

**关键设计决策**

| 决策 | 为什么 | 如果不这样 |
|------|--------|-----------|
| 检索查询基于评估结果而非用户原话 | 评估结果已经将日常描述转化为专业维度 | 用原话"平衡不好"检索 → 漏掉"前庭觉障碍干预"等专业文档 |
| 取 5-10 条而非 1-2 条 | 评分节点需要多角度信息（安全性、有效性、可行性） | 只取 1-2 条 → 可能缺少关键角度的证据 |

**为什么检索原理不在本章展开**

检索节点内部使用的 BM25、向量检索、RRF 融合、MinHash 去重的完整原理、公式推导和参数调优指南，详见 04-hybrid-search.md。本章只关注检索节点在 Agent 评估流程中的角色和接口。

**成本拆解**

约 **0.005 元**。查询向量化 ~0.00003 元（可忽略）+ 重排序 ~0.005 元（qwen3-rerank，10 条候选）。

### Node4 · 评分——裁判

**它解决什么问题**

前面的节点已经给出了评估结果和科学依据，但还没有一个量化的分数来回答最核心的问题：「这个运动计划对孩子来说，综合评分是多少？」

单一的评分方式各有缺陷：纯 LLM 评分不稳定（同一个计划两次评分可能差 1-2 分）；纯规则评分（如 AHP 层次分析法）可解释但无法捕捉复杂数据中的非线性模式；纯 ML 评分准确但可解释性差（用户不知道分从哪来）。

**解决方案**：AHP + ML 融合评分——AHP 基于专家知识建立评分框架并给出基准分，ML 模型从历史数据中学习非线性模式进行修正。两者结合 = 可解释 + 高准确。

**输入输出**

```
输入：
├── child_state（Node1）、proposed_plan（Node1）
├── evaluation_result（Node2：各维度评估）
└── retrieved_docs（Node3：科学依据）

输出：
└── final_score
    ├── 安全性：9/10（AHP 基准 8.5 + ML 修正 +0.5）
    ├── 有效性：8/10（AHP 基准 7.0 + ML 修正 +1.0）
    ├── 可行性：8/10（AHP 基准 8.0 + ML 修正 0）
    ├── 总体：8.1/10
    └── SHAP 解释：
        ├── 游泳作为训练活动：+1.2（贡献最大的正向因素）
        ├── 每天训练频率：-0.3（偏高，但仍安全）
        ├── 年龄 3.5 岁：+0.1
        └── 前庭觉功能较低：+0.5（计划针对性好，加分）
```

**核心逻辑——两步评分**

**第一步：AHP 基准评分（层次分析法）**

层次结构：
```
运动计划综合评分
├── 安全性（权重 0.4）
│   ├── 活动危险性评估
│   ├── 训练量是否超龄
│   └── 是否有禁忌症
├── 有效性（权重 0.4）
│   ├── 活动是否针对薄弱维度
│   ├── 训练频率是否足够
│   └── 活动多样性
└── 可行性（权重 0.2）
    ├── 器材要求
    ├── 家长执行难度
    └── 时间投入
```

权重的含义：安全和有效性同等重要（各 0.4），可行性略低（0.2）因为大部分计划调整后都能执行。

AHP 基准分 = 0.4 × 安全子分 + 0.4 × 有效子分 + 0.2 × 可行子分

**第二步：ML 模型融合（QwenScorer）**

将 AHP 基准分 + 儿童画像特征 + 运动计划特征 + 检索结果特征输入 QwenScorer，让模型捕捉数据中的非线性模式。然后用 SHAP 解释每个特征对最终分数的贡献——哪个特征加分最多，哪个特征在扣分，为什么。

**为什么用 AHP + ML 融合**

| 纯 AHP | 纯 ML | AHP + ML |
|--------|-------|---------|
| 可解释——每个子分有据可查 | 准确——可捕捉非线性模式 | 既可解释又准确 |
| 但权重固定——无法适应数据中的复杂关系 | 但不可解释——用户不知道分从哪来 | SHAP 给出逐特征解释 |
| 不能从历史数据中学习 | 能从历史数据中学习 | AHP 提供先验知识，ML 从数据中学修正 |

**关键设计决策**

| 决策 | 为什么 | 如果不这样 |
|------|--------|-----------|
| 两次 LLM 调用（AHP + ML 各一次） | AHP 确定方向（安全有效），ML 做精细修正 | 一次 LLM 同时做两件事 → 可能混淆基准和修正 |
| 安全权重 0.4，有效权重 0.4 | 安全和有效同等重要——不安全但有效 = 危险；安全但无效 = 浪费 | 偏向一边 → 计划评估失真 |

**边界条件**

| 情况 | 处理 |
|------|------|
| 检索结果为空（0 条文档） | 降级为纯 AHP评分（无 ML 修正，因为缺少科学依据特征） |
| 历史数据不足（新用户） | ML 模型置信度降低，更多依赖 AHP 基准 |
| 评分两极分化（安全和有效差距 > 3 分） | 标记异常，在报告中特别说明 |

**成本拆解**

约 **0.014 元**。qwen-plus × 2 次调用（AHP 评分 + ML 融合），每次 ~3000 Token 输入 + ~1000 Token 输出。

### Node5 · 报告生成——撰稿人

**它解决什么问题**

前面的节点产生的是结构化数据和专业术语——`前庭觉：15 百分位`、`安全性 9/10`。最终用户是家长，他们不懂「百分位」「前庭觉」「AHP 融合评分」是什么意思。报告节点的任务是把专业评估结果"翻译"成通俗易懂、可操作的建议。

**如果不做报告生成**

直接把 Node4 的输出给家长 → 家长看不懂 → 不被采纳 → 整个评估流程失去意义。评估的最终价值不在分数，在于家长能否根据报告采取行动。

**输入输出**

```
输入：
├── child_state, proposed_plan（Node1）
├── evaluation_result（Node2）
├── retrieved_docs（Node3）
├── final_score（Node4）
└── condensed_context（NodePre）

输出：
└── final_report（Markdown）
```

**报告内容结构**

```
📋 小明的运动计划评估报告

📊 整体评分：8.1/10（良好）

✅ 优势领域：
├── 本体觉（身体感知）：60 百分位，表现正常
└── 计划安全性：9/10，非常安全
    └── 游泳是低冲击运动，适合 3 岁儿童；训练量在安全范围内

⚠️ 需要关注：
├── 前庭觉（平衡能力）：15 百分位，低于同龄标准
│   ├── 这解释了为什么小明走路容易摔倒——平衡系统需要加强
│   └── 建议：增加平衡类训练，如走平衡木、单脚站立游戏、秋千
├── 听觉处理：25 百分位，对声音较敏感
│   ├── "对声音敏感"可能是听觉防御的表现
│   └── 建议：避免嘈杂环境，逐步适应不同声音，可咨询听觉治疗师

📝 计划可行性分析：
├── 游泳：✅ 强烈推荐——对前庭觉训练非常有效且安全（[来源] 前庭觉训练指南）
├── 平衡木训练：✅ 推荐——直接针对薄弱维度，建议每天 10-15 分钟
├── 训练频率：⚠️ 每天训练可能偏多，建议调整为每周 5 次，每次 30 分钟
│   └── 依据：3 岁儿童建议每周 3-5 次感统训练（[来源] 儿童运动训练安全指南）
└── 总体：计划方向正确，核心问题（前庭觉）被很好地覆盖

🔬 科学依据：
├── [1] 前庭觉训练指南 — 游泳对前庭觉的改善作用
├── [2] 儿童运动发展里程碑 — 3 岁儿童前庭觉发展标准
└── [3] 儿童运动训练安全指南 — 训练量建议
```

**核心逻辑**

1. **分层生成**：先写摘要（1-2 句，给只扫一眼的家长），再写分项（优势/关注/建议），最后附科学依据
2. **专业术语翻译**：「15 百分位」→「低于 85% 的同龄儿童」；「前庭觉」→「平衡系统」
3. **可操作建议**：不给「建议加强平衡训练」这种空话，而是给「每天走平衡木 10-15 分钟」这样的具体方案
4. **来源标注**：每条建议后标记出处——「[来源] 前庭觉训练指南」——让家长知道这不是 AI 编的

**关键设计决策**

| 决策 | 为什么 | 如果不这样 |
|------|--------|-----------|
| 分层生成（摘要→分项→依据） | 不同家长需要不同深度——忙的只看摘要，用心的看完整 | 全堆在一起 → 信息过载，家长不读 |
| 每条建议附来源 | 建立信任——让家长知道建议有科学依据 | 没有来源 → 看起来像 AI 编的 |
| 可操作而非空泛 | 「每天走平衡木 10 分钟」比「加强平衡训练」更有用 | 空泛建议 → 家长不知道具体怎么做 |

**成本拆解**

约 **0.018 元**。LLM 输入 ~12000 Token（所有前序节点的输出 + 报告模板），输出 ~4000 Token，使用 qwen-plus。这是整个评估中成本最高的单个节点，占每次评估总成本的 ~37%。

## 设计理念总结

| 设计点 | 为什么 | 量化收益 |
|--------|--------|---------|
| 6 节点 DAG | 每个节点职责单一，可独立测试和替换 | 调试时间减少（出问题定位到一个节点而非一个巨大的函数） |
| 预处理压缩 | 降低下游节点的 Token 消耗 | LLM 成本降低 ~40%（5000→500 Token 的节省在下游节点复用） |
| 校验层 | 防止脏数据进入系统 | 评估结果可靠性提升（Garbage In 的数量 → 0） |
| RAG 检索 | 评估有科学依据支撑 | 每项建议可追溯来源，幻觉风险可控 |
| AHP+ML 融合 | 结合专家知识和数据驱动 | 既可比对专家规则（可解释），又能从数据中学习（准确） |
| 家长友好报告 | 最终用户是家长而非医生 | 建议采纳率提升（具体可操作 vs 专业术语堆砌） |

## 一句话总结

> **6 节点 DAG 将评估流程拆成独立步骤——预处理压缩、校验补全、评估画像、检索证据、评分量化、报告翻译——每个节点只做一件事，节点间通过共享状态传递数据。一次评估 5 分钱、2.5 秒。**
