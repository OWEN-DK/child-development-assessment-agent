# 04 · 混合检索——用户日常语言怎么匹配专业文档？

> 目标受众：懂技术的产品经理
> 核心问题：用户搜「孩子平衡不好怎么训练」，但知识库里的文档写的是「前庭觉功能障碍的干预策略」。两种表述没有一个词相同，怎么让计算机理解它们说的是同一件事？

---

## 核心问题

这是 RAG 系统最核心的技术挑战——**表述鸿沟**（Terminology Gap）。用户用日常语言提问，知识库用专业术语写作。两者在字面上完全不同，但语义高度相关。

如果只用关键词匹配（BM25）：搜「平衡不好」→ 找不到「前庭觉功能障碍」→ 召回率极低，用户必须用专业术语搜索。

如果只用语义搜索（向量检索）：搜「前庭觉」→ 可能返回「前庭神经」「前庭性偏头痛」等语义相近但不精确的结果 → 精确度比关键词差。

这个问题没有一个单一检索方法能解决。答案是用两种检索方法，然后融合它们的结果——这就是**混合检索**。

---

## 一、为什么单一检索不够——各自的致命盲区

| 检索方式 | 擅长 | 致命盲区 | 盲区导致的后果 |
|---------|------|---------|-------------|
| **BM25（关键词匹配）** | 精确术语匹配——搜「前庭觉」精确找到含「前庭觉」的文档 | 不懂语义——搜「孩子平衡不好」找不到「前庭觉训练」文档（因为没有相同的词） | 用户必须学会用专业术语搜索，普通用户不会 |
| **向量检索（语义相似）** | 语义理解——搜「孩子平衡不好」能找到「前庭觉训练」文档 | 精确度不如关键词——搜「前庭觉」可能返回「前庭神经炎」（不相关但在向量空间中接近） | 专业术语精确搜索时噪音多 |

两者盲区恰好互补：BM25 不懂但向量懂（语义），向量不精确但 BM25 精确（术语）。两者结合 → 既有覆盖面又有精确度。

### 具体对比实例

```
用户搜"前庭觉训练方法"

纯 BM25 检索结果：
├── 文档A："前庭觉训练方法包括平衡木、秋千..." ✓（含"前庭觉训练方法"）
├── 文档B："前庭觉障碍的评估方法" ✗（含"前庭觉"但不相关）
├── 文档C："本体觉训练方法" ✗（含"训练方法"但领域不同）
└── 文档D："前庭觉训练指南" ✓
→ BM25 找到了 2 个相关文档，但遗漏了"平衡能力训练"等不同表述的相关文档

纯向量检索结果：
├── 文档A："前庭觉训练方法..." ✓（语义最接近）
├── 文档E："平衡能力训练对前庭功能的影响" ✓（语义相关但用词不同）
├── 文档F："儿童前庭刺激方案设计" ✓（语义相关）
├── 文档G："前庭神经炎的药物治疗" ✗（语义接近"前庭"+训练但内容不相关）
└── 文档H："前庭性偏头痛的康复训练" ✗
→ 向量检索召回了 3 个相关文档，但引入了 2 个噪音（前庭神经炎、偏头痛）

混合检索（RRF 融合后）：
├── 文档A：两个检索都找到 → 分数最高 ✓
├── 文档E：向量检索找到 → 补充了 BM25 遗漏的 ✓
├── 文档F：向量检索找到 → 分数中等 ✓
├── 文档D：BM25 找到 → 分数中等 ✓
├── 文档B：只被 BM25 找到 → 分数较低
├── 文档G：只被向量检索找到 → 分数较低
→ 混合检索兼顾了精确（A/D）和覆盖（E/F），压制了噪音（B/G）
```

## 二、BM25 检索——关键词匹配的数学原理

### BM25 公式拆解

BM25(D,Q) = Σ IDF(qi) × TF(qi,D) × (k1+1) / (TF(qi,D) + k1 × (1 - b + b × |D|/avgdl))

看起来复杂，但只有三个核心部件：

### 部件 1：IDF（逆文档频率）——什么是"稀有词"

```
IDF(qi) = log((N - df(qi) + 0.5) / (df(qi) + 0.5) + 1)

N = 文档库中的总文档数
df(qi) = 包含词 qi 的文档数
```

**通俗解释**：一个词在越少的文档中出现，它就越有区分度，权重越高。

```
库中共有 10000 篇文档：

"的"出现在 9800 篇文档 → IDF ≈ log(200/9800.5) ≈ log(0.02) ≈ 很低
  → 几乎所有文档都有"的"，无法用它区分文档 → 权重极低

"前庭觉"出现在 50 篇文档 → IDF ≈ log(9950.5/50.5) ≈ log(197) ≈ 5.3
  → 只有少量文档有这个词 → 它是区分相关文档的有效信号 → 权重高

"本体觉"出现在 30 篇文档 → IDF ≈ log(9970.5/30.5) ≈ log(327) ≈ 5.8
  → 比"前庭觉"更稀有 → 权重更高
```

**为什么 IDF 需要**：不过滤常见词的话，搜「前庭觉的训练方法有哪些」，其中「的」「有哪些」会干扰结果——这些词几乎所有文档都有。

### 部件 2：TF 词频饱和度——为什么一个词出现 100 次和 5 次不是 20 倍差距

```
TF 饱和度 = (k1 + 1) × TF / (TF + k1 × 归一化因子)

TF(qi,D) = 词 qi 在文档 D 中出现的次数
```

**为什么需要饱和度**：如果一个词在同一文档中反复出现 100 次，这个文档不应该是出现 1 次的 100 倍重要。k1 控制这个饱和曲线的形状。

```
k1 = 1.5（默认值）时：
────────────────────
TF=1  →  分数 = (2.5×1)/(1+1.5×1) = 2.5/2.5 = 1.0
TF=2  →  分数 = (2.5×2)/(2+1.5×1) = 5.0/3.5 = 1.43  （+43%）
TF=5  →  分数 = (2.5×5)/(5+1.5×1) = 12.5/6.5 = 1.92  （+92%）
TF=20 →  分数 = (2.5×20)/(20+1.5×1) = 50/21.5 = 2.33  （+133%，但增速明显放缓）
TF=100→  分数 ≈ (2.5×100)/(100+1.5) = 250/101.5 = 2.46 （几乎没有再增长）

曲线特征：前几次出现贡献大，第 5 次以后贡献急剧减小 → 防止"一个词重复 100 次的文档"碾压胜出
```

**k1 参数的行为差异**：

```
k1 = 0.5（低）：
────────────────
TF=1 → 1.0   TF=5 → 1.36   TF=100 → 1.49
词频的影响非常平缓 → 适合"一个词出现一次就够了"的场景（如法条检索）

k1 = 1.5（默认）：
────────────────
TF=1 → 1.0   TF=5 → 1.92   TF=100 → 2.46
词频影响适中 → 平衡"提及"和"重点讨论"

k1 = 3.0（高）：
────────────────
TF=1 → 1.0   TF=5 → 2.86   TF=100 → 3.91
词频高的文档被强烈偏好 → 适合"核心主题"检索（如综述性文献检索）

默认值 1.5 的依据：数学上使得词频曲线最接近现实中「同一个词出现两次，重要性大约是 1.3 倍」的经验关系
```

### 部件 3：文档长度归一化——为什么 100 页的文档不能仅因为"长"而一直排第一

```
归一化因子 = 1 - b + b × (|D| / avgdl)

|D| = 当前文档长度
avgdl = 库中所有文档的平均长度
b = 长度惩罚强度（0-1）
```

**为什么需要归一化**：长文档天然包含更多词——100 页的教材中"前庭觉"可能出现 50 次，1 页的摘要中可能出现 3 次。如果不归一化，100 页教材的 BM25 分数会因为词频高而碾压 1 页摘要——即使摘要更相关。

```
b = 1.0（完全惩罚）：
───────────────────
长文档被按比例惩罚 → 100 页文档中的 1 次"前庭觉"权重 = 1 页文档中的 1 次"前庭觉"
适合"精确短语"场景——文档长度与相关性无关

b = 0.75（默认）：
───────────────────
长文档仍有一定优势（因为确实可能包含更全面的信息）
但不会仅因为"长"就碾压性胜出
绝大部分搜索引擎（Elasticsearch、Lucene）都使用这个值

b = 0（不惩罚）：
───────────────────
长文档天然占优 → 适合"综合文献"场景——长篇综述天然比短篇更全面

默认值 0.75 的依据：数学上使文档长度的影响曲线最接近实际检索场景中「文档长度与相关性的关系」
```

### BM25 其他参数

| 参数 | 默认值 | 作用 | 调高后果 | 调低后果 |
|------|--------|------|---------|---------|
| top_k | 10 | 返回关键词结果数 | 召回率↑，但 RRF 融合算力↑ | 延迟↓，但可能遗漏相关文档 |
| score_threshold | 0 | 最低 BM25 分数阈值 | 精确度↑，召回↓ | 噪音↑，但覆盖面↑ |
| 字段权重 | title:2.0, body:1.0 | 标题和正文分别加权 | 标题匹配的文档排序更高 | 标题匹配不再有优势 |

## 三、向量检索——语义相似度的数学原理

### 向量检索的完整流程

```
用户查询："孩子平衡不好怎么训练"

步骤 1：查询向量化
  → DashScope text-embedding-v4 → [0.023, -0.156, 0.089, ..., 0.234]（1536 维向量）

步骤 2：在向量库中搜索最近的向量
  向量库中有 10000 个文档向量，每个也是 1536 维
  → 计算查询向量与每个文档向量的距离
  → 返回距离最近的 top_k 个

步骤 3：返回满足 similarity_threshold 的结果
  只返回距离 < threshold（即相似度 > threshold）的文档
```

### 三种距离度量——cosine、euclidean、dot_product 何时用哪个

| 度量 | 公式 | 关心什么 | 何时用 | 何时不用 |
|------|------|---------|--------|---------|
| **cosine（余弦）** | `cos(θ) = A·B / (|A| × |B|)` | 只关心方向，不关心向量长度 | Embedding 模型输出已归一化向量时（默认选择） | 向量未归一化时——不同文档的向量长度差异大，只关心方向会失真 |
| **euclidean（欧氏）** | `√(Σ(Ai - Bi)²)` | 关心向量在空间中的绝对距离 | 向量未归一化时，或关心"绝对位置"时 | 向量已归一化时——退化为 cosine 的单调变换，但计算更慢 |
| **dot_product（点积）** | `A·B = Σ(Ai × Bi)` | 同时关心方向和大小 | Embedding 模型输出向量的大小代表"置信度"时 | 向量大小不代表有用信息时 |

**默认用 cosine**：DashScope Embedding 输出已归一化的向量（长度为 1），此时 cosine 等价于 dot_product，且数值更稳定。

### similarity_threshold 调优——0.5 / 0.7 / 0.95 的行为差异

```
threshold = 0.95（极高）：
────────────────────────
只返回和查询"几乎一模一样"的文档
  ├── 精确度极高（Precision ↑↑）
  ├── 覆盖面极窄（Recall ↓↓）
  └── 适合："法条精确引用"场景——必须逐字匹配

threshold = 0.7（默认）：
────────────────────────
返回语义上"相关但不要求完全相同"的文档
  ├── 平衡精度和覆盖面
  └── 适合：绝大多数知识检索场景

threshold = 0.5（低）：
────────────────────────
返回"稍微有点关系"的文档
  ├── 覆盖面广（Recall ↑↑）
  ├── 噪音多（Precision ↓↓）
  └── 适合："灵感发散"场景——从宽泛主题中寻找灵感

默认 0.7 的依据：DashScope Embedding + cosine 的经验最优值。
0.8+ = 高度相似（同一主题），0.7 = 包含相关但不完全相同，
0.6- = 开始出现明显不相关内容
```

### 向量检索参数速查

| 参数 | 默认值 | 作用 | 调高后果 | 调低后果 |
|------|--------|------|---------|---------|
| top_k | 10 | 返回语义结果数 | 召回↑，延迟↑ | 延迟↓，可能遗漏 |
| similarity_threshold | 0.7 | 最低语义相似度 | 精确度↑，召回↓ | 召回↑，噪音↑ |
| similarity_metric | cosine | 距离度量方法 | — | — |

## 四、查询处理——同义词扩展和查询重写

### 同义词扩展

**为什么需要**

用户说「血压高」，知识库写的是「高血压」——这两个表述在 BM25 看来是不同的词，向量相似度也只有 0.7-0.8。同义词扩展将查询中的关键词展开为同义词列表，同时用多个词搜索。

```
用户输入："血压高怎么治疗"
    ↓ 同义词扩展
扩展查询："高血压 血压升高 血压偏高 怎么治疗 用药 处理"

搜索时：同时包含"高血压""血压升高""血压偏高"的文档都会被检索到
```

**三种词库来源**

| 来源 | 内容 | 示例 | 维护方 |
|------|------|------|--------|
| 内置通用词库 | 中文常见同义词 | "孩子"→"儿童""患儿" | 系统自带 |
| 域专用词库 | 领域特定的术语映射 | "平衡不好"→"前庭觉障碍""平衡功能障碍" | 客户管理员 |
| 自定义上传 | 客户特有的术语 | 某医院的内部缩写、科室名称缩写 | 客户管理员 |

**扩展策略选择**

| 模式 | 做法 | 适用场景 | 风险 |
|------|------|---------|------|
| 全量扩展 | 所有词都扩展 | 短查询（3-5 个词） | 引入噪音（常见词被扩展为无关词） |
| 仅名词扩展 | 只扩展名词 | 有大量动词/形容词的查询 | 可能漏掉专业的动词/形容词 |
| 仅关键术语扩展 | 只扩展专业术语 | 查询中已有专业术语 | 日常用语不被扩展 |

**什么时候同义词扩展会引入噪音**

"训练"的同义词包括"锻炼""练习"，但也包括"培训"——搜「前庭觉训练」被扩展到「前庭觉培训」→ 返回员工培训手册 → 完全不相关。因此扩展数量不宜过多，一般 max_synonyms=5。

### 查询重写（可选节点）

同义词扩展做的是"词的替换"，查询重写做的是"句子的改写"——用 LLM 将口语化查询改写为更适合检索的专业表述。

```
用户输入："孩子平衡不好咋办"
查询重写："3岁儿童前庭觉平衡能力训练方法与干预策略"
```

**成本与效果权衡**：查询重写增加一次 LLM 调用（~0.0006 元），但显著提升检索质量——尤其是对口语化严重或表述模糊的查询。在管道编辑器中它是可选节点——不需要的客户不拖入即可。

## 五、RRF 融合——怎么把两种分数合在一起

### 为什么不能用加权求和

BM25 分数范围 0-10+（取决于查询），向量分数范围 0-1（归一化后）。直接把 BM25 分数 × 0.4 + 向量分数 × 0.6 → BM25 端因为数值范围大而主导融合结果 → 向量检索几乎不起作用。

归一化？Min-Max 归一化需要知道分数的 min 和 max，但这取决于每次查询——这次查询 BM25 分数 0.5-8.0，下次可能是 0.1-12.0。无法预先知道。

### RRF（Reciprocal Rank Fusion）的解决方案

不关心具体分数，只关心排名。

```
公式：RRF_score(d) = Σ 1 / (k + rank_i(d))

其中：
  k = 60（常数，控制排名差距的敏感度）
  rank_i(d) = 文档 d 在第 i 个检索器中的排名（从 1 开始）

如果一个文档在多个检索器中都排第一：
  → RRF_score = 1/(60+1) + 1/(60+1) = 0.0164 + 0.0164 = 0.0328 → 分数最高

如果一个文档只在 BM25 中排第 5，在向量检索中没出现：
  → RRF_score = 1/(60+5) = 1/65 = 0.0154 → 分数较低
```

### k 值的行为差异——RRF 最关键的参数

```
k = 1（极小）：
────────────────
rank 1：1/(1+1) = 0.500
rank 2：1/(1+2) = 0.333（差距 0.167）
rank 10：1/(1+10) = 0.091
排名靠前的文档碾压性胜出，几乎忽略靠后的结果
  → 适合："唯一正确答案"的场景（如百科问答）

k = 60（默认）：
────────────────
rank 1：1/(60+1) = 0.0164
rank 2：1/(60+2) = 0.0161（差距 0.0003，几乎无差异）
rank 10：1/(60+10) = 0.0143
所有排名的影响被大幅平滑，但仍有细微差异
  → 适合：绝大多数检索场景（平衡排名贡献和差异度）

k = 1000（极大）：
────────────────
rank 1：1/(1001+1) ≈ 0.00100
rank 10：1/(1001+10) ≈ 0.00099
所有排名差异几乎被抹平 → 排名无意义
  → 几乎不使用

默认值 60 的依据：业界标准值（源于 RRF 原始论文的实证研究），在大多数数据集上表现最优
```

### 为什么向量权重更高（0.6 vs 0.4）

在 RRF 融合后，如果使用加权 RRF（`weight / (k + rank_i)`）：

- 用户习惯用自然语言提问（"孩子平衡不好怎么训练"），更依赖语义理解 → 向量权重 0.6
- 但精确术语的匹配也需要保留 → BM25 权重 0.4

两种典型场景的调整建议：

| 场景 | 建议 BM25 权重 | 建议向量权重 | 理由 |
|------|-------------|------------|------|
| 专业医学检索 | 0.6 | 0.4 | 医学术语精确匹配更重要（"前庭觉"不可替代） |
| 科普教育检索 | 0.2 | 0.8 | 用户使用日常语言，需更强的语义理解 |
| 默认场景 | 0.4 | 0.6 | 平衡——多数用户用日常语言搜索 |

### 分数校准：RRF → 前端展示分数

RRF 分数范围约 0.001-0.033，不适合在前端显示（"你的搜索得分 0.015" → 用户困惑）。

使用 **Per-Query Min-Max 归一化**将每次查询的 RRF 分数映射到 0-100：

```
对当前查询的所有结果（假设 20 个文档）：

RRF 分数 = [0.005, 0.015, 0.012, ..., 0.003]

min = 0.003, max = 0.033（本次查询的最小和最大 RRF 分）

归一化后分数 = (RRF_score - min) / (max - min) × 100

文档 A（RRF = 0.033）：(0.033 - 0.003) / (0.033 - 0.003) × 100 = 100
文档 B（RRF = 0.015）：(0.015 - 0.003) / (0.033 - 0.003) × 100 = 40
文档 C（RRF = 0.003）：(0.003 - 0.003) / (0.033 - 0.003) × 100 = 0

前端显示：文档 A 得分 100，文档 B 得分 40，文档 C 得分 0
```

**注意**：归一化是 per-query 的——不同查询间的 100 分不可直接比较（一次简单查询的 100 分和一次困难查询的 100 分不是同一等级的匹配质量）。这个分数仅用于同一查询内部的结果排序展示。

## 六、MinHash 去重——如何快速判断两段文字"几乎一样"

### 问题

多篇文档可能引用同一段指南。返回 10 条结果中可能有 5 条内容几乎一样——用户看到的是重复信息，体验差，且浪费 LLM 的上下文窗口。

### MinHash 算法原理——4 步

**步骤 1：分词并生成 n-gram（连续词组）**

```
文档 A："前庭觉训练可改善平衡能力"
  → n-gram 集合（n=1,2,3）：
  {"前庭觉", "训练", "可", "改善", "平衡能力",
   "前庭觉训练", "训练可", "可改善", "改善平衡能力",
   "前庭觉训练可", "训练可改善", "可改善平衡能力"}
```

**步骤 2：对每个 n-gram 计算多个哈希值**

```
"前庭觉" → hash1("前庭觉") = 23456, hash2("前庭觉") = 78901, hash3("前庭觉") = 34567, ...
"训练"   → hash1("训练") = 56789, hash2("训练") = 12345, hash3("训练") = 89012, ...
...（对每个 n-gram 重复）
```

**步骤 3：取每个哈希函数的最小值，组成 MinHash 指纹**

```
MinHash 指纹（通常取 128 或 256 个最小值）：

从所有 n-gram 的 hash1 值中取最小值 → 12
从所有 n-gram 的 hash2 值中取最小值 → 345
从所有 n-gram 的 hash3 值中取最小值 → 678
...

文档 A 的指纹：[12, 345, 678, 901, 234, ...]（128 个整数）
```

**步骤 4：比较两个文档的 MinHash 指纹**

```
文档 A 指纹：[12, 345, 678, 901, 234, 567, ...]  ← 128 个整数
文档 B 指纹：[12, 345, 678, 901, 235, 567, ...]  ← 128 个整数

相同的哈希值：128 个中有 125 个相同 → 125/128 = 97.7% 相同
  → 判定为近似重复（> 85% 阈值）→ 删除其中一个
```

### 为什么用 MinHash 而非逐字比较

| 方法 | 时间复杂度 | 问题 |
|------|-----------|------|
| 逐字比较 | O(n²) —— 10 万个文档两两比较需要 50 亿次 | 不可行，太慢 |
| MinHash | O(n) —— 每个文档压缩为固定长度指纹（128 个整数） | 两个指纹的比较是 O(1)（固定 128 个整数比较） |

另外，MinHash 对微小修改不敏感——改几个字，指纹几乎不变——而逐字比较会把"改了 5 个字"的文档当成新文档。

### 关键数学性质

**MinHash 相似度 ≈ Jaccard 相似度**（由大数定律保证）：

```
Jaccard(A,B) = |A ∩ B| / |A ∪ B|  （两个集合的交集大小除以并集大小）

MinHash 签名中相同哈希的比例 ≈ Jaccard 相似度

证明思路（非严格）：对于随机哈希函数 h，h(A_min) = h(B_min) 的概率 = Jaccard(A,B)
取足够多的哈希函数（128/256），大数定律保证这个近似足够精确
```

### threshold=0.85 的选择依据

```
threshold = 0.95（极高）：只有完全相同的文档才去重
  → 几乎无效——稍作修改的同一篇文档不会被去重

threshold = 0.85（默认）：约 85% 的 Jaccard 相似度
  → 对于 n-gram 级别的文本重复，这是"几乎是同一段话"的水平

threshold = 0.5（低）：相关但不重复的文档也被去重
  → 误杀率极高——不同但相关的信息被丢弃

默认 0.85 的依据：在信息检索领域，"85% Jaccard 相似度"是近似重复检测的标准阈值
```

## 八、场景化调优指南

不同应用场景需要不同的参数组合。以下是两个典型场景：

### 场景 A：专业医学检索

```
用户画像：医生、药师，使用专业术语搜索
特点：精确术语匹配至关重要（"前庭觉""本体觉""BM25"的术语不可替代）

建议参数组合：
├── BM25 权重：0.6（术语精确匹配更重要）
├── 向量权重：0.4（语义理解辅助）
├── BM25 k1：1.5（默认）
├── BM25 b：0.75（默认）
├── similarity_threshold：0.75（稍高，减少"不太相关"的语义噪音）
└── 同义词扩展：仅关键术语扩展（避免"前庭觉"被扩展为"前庭神经"）
```

### 场景 B：科普教育检索

```
用户画像：家长、学生，使用日常语言搜索
特点：表述多样，需要强语义理解来桥接日常语言与专业术语的差距

建议参数组合：
├── BM25 权重：0.2（弱化精确匹配——用户不用术语）
├── 向量权重：0.8（强语义理解——用户用日常语言）
├── similarity_threshold：0.65（降低阈值，扩大覆盖面）
├── 同义词扩展：全量扩展（尽可能桥接表述差距）
└── 查询重写：启用（将口语化查询改写为专业表述）
```

### 场景 C：法律/合规检索

```
用户画像：律师、合规官，使用精确术语和条文编号搜索
特点：精确匹配和语义理解同等重要——漏一条法条可能造成法律风险；
      法律条文之间存在大量交叉引用，需要精确的条文编号匹配

建议参数组合：
├── BM25 权重：0.5（精确匹配条文编号、案例号、法条引用格式）
├── 向量权重：0.5（语义理解——"违约"也需要匹配"不履行合同义务"）
├── similarity_threshold：0.60（降低阈值——宁可多找不少找；遗漏法条的代价 > 多筛几条噪音）
├── BM25 k1：1.0（降低词频饱和度——法条中同一术语重复多次不意味着更相关）
├── 同义词扩展：仅关键术语扩展（精确术语不能被扩展为泛化表述——"善意取得"不能被扩展为"合法获得"）
├── 查询重写：禁用（律师使用精确法律术语，改写可能改变法律含义）
└── MinHash threshold：0.80（稍低——同一法条的不同司法解释版本可能只有部分重叠，过高阈值可能漏掉判例变体）
```

**法律场景的特殊性**：在医学场景中，"宁可精确也不要噪音"（Precision 优先于 Recall）。在法律场景中，"宁可多找也不要漏"（Recall 优先于 Precision）——漏掉一条相关的判例可能导致错误的法律建议。因此法律场景的向量 threshold 比医学低 0.1-0.15，确保覆盖面。同时 BM25 权重与向量等权——精确条文编号匹配和语义理解同样重要。

## 关键设计点

| 设计点 | 为什么 | 量化收益 |
|--------|--------|---------|
| 混合检索而非单一检索 | BM25 和向量检索各有致命盲区，互补 | Recall 提升 30-50%（相比纯 BM25） |
| RRF 而非加权求和 | 分数范围不同无法直接求和 | 融合公平——不受分数范围差异影响 |
| 同义词扩展 | 用户的日常表述 ≠ 文档的专业术语 | 填补表述鸿沟 |
| MinHash 去重 | 多文档引用同一段指南 | 去重后的结果多样性提升 |
| 分数校准（Min-Max 归一化） | RRF 分数不可读 | 前端展示 0-100 分，用户可理解 |
| 参数可调 | 不同场景需要不同策略（医学 vs 科普） | 场景自适应 |

## 一句话总结

> **混合检索 = BM25 关键词精确匹配 + 向量语义相似度 + RRF 排名融合 + 同义词桥接表述鸿沟 + MinHash 去重。14 个可调参数支持从专业医学到科普教育全场景自适应。**
