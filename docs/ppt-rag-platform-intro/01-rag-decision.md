# 01 · 为什么需要 RAG——LLM 能聊天，但能做专业评估吗？

> 目标受众：懂技术的产品经理
> 核心问题：LLM 能聊天、写文章、写代码，为什么不能直接用它做儿童发展评估？

---

## 核心问题

一个家长输入：「3 岁男孩，平衡能力差，走路容易摔倒，对声音敏感。计划安排游泳和平衡木训练，每天 30 分钟。」然后问：「这个计划安全吗？适合孩子吗？」

如果你把这段话直接发给 ChatGPT，它会给出一个听起来很专业的回答——引经据典、条理清晰、语气自信。但问题在于：**你不知道它说的是真的还是编的。** 你可能得到 2022 年已经被更新的旧指南建议，可能得到纯属虚构的「某某研究表明」，甚至可能得到危险的训练量建议。

这就是**纯 LLM 的幻觉问题（Hallucination）**——模型不确定时会编造看似合理的答案，且编造得极其自信。在医疗、法律、教育等专业场景，这种幻觉可能造成严重后果。

**RAG（Retrieval-Augmented Generation，检索增强生成）** 要解决的就是这个问题：在 LLM 回答之前，先让它「查资料」，确保答案有据可依。

---

## 一、RAG 是什么——开卷考试 vs 闭卷考试

最直观的类比：

```
闭卷考试（纯 LLM）
─────────────────
问题 → LLM 凭记忆回答 → 可能编造答案
       ↑
       记忆可能过时、错误、或完全不存在

开卷考试（RAG）
─────────────────
问题 → 先翻书找相关内容 → 基于找到的内容回答 → 每句话有出处可查
       ↑                    ↑
       知识库               检索+LLM生成
```

RAG 三个步骤对应的动作：

| 步骤 | 做什么 | 为什么不可省略 |
|------|--------|--------------|
| **Retrieval（检索）** | 根据用户问题，从知识库中找到最相关的文档片段 | 确定 LLM 的「参考资料范围」 |
| **Augmented（增强）** | 把检索到的内容作为上下文，注入 LLM 的提示词 | 让 LLM 在「有据可依」的约束下回答 |
| **Generation（生成）** | LLM 基于检索到的内容生成答案 | 用 LLM 的语言能力将资料转化为可读答案 |

**关键理解**：知识存储（知识库）和答案生成（LLM）是解耦的。知识库可以独立更新而不影响 LLM；LLM 可以独立升级而不影响知识库。这种解耦是 RAG 相比微调最根本的架构优势。

---

## 二、为什么要选择 RAG 而不是模型微调

这是最常被问到的问题。两者的本质区别在于**知识存储的位置和方式**。

### 两种方案的底层逻辑

```
微调（Fine-tuning）
─────────────────
训练数据 → 改变模型参数 → 模型"学会"了新知识 → 凭记忆回答
类比：让学生背诵整本教材，然后闭卷考试
核心问题：模型"记住了"但不知道从哪记住的，也无法精确删除某条记忆
每次更新：重新训练（数小时到数天，$10-$100+）

RAG（检索增强生成）
─────────────────
文档存储 → 查询时检索 → 把相关内容放入提示词 → 基于资料回答
类比：开卷考试，学生不需要背诵，但能精确翻到正确答案所在页
核心优势：知识存储和答案生成解耦，各自独立优化
每次更新：上传文档（秒级生效，向量化一本书约 ¥0.3）
```

### 十四维度逐一对比

以下对比覆盖了决策 RAG vs 微调时需要评估的全部维度。每个维度附具体场景，说明两个方案的差异究竟意味着什么。

| 维度 | 微调 | RAG | 结论 | 场景说明 |
|------|------|-----|------|---------|
| **知识更新速度** | 重新训练，数小时到数天 | 上传文档，秒级生效 | RAG 优 | 医学指南每年更新 → 微调需要每年重新训练；RAG 上传新指南即生效 |
| **答案溯源** | 无法追溯——模型"知道"但不"记得"从哪知道 | 每个答案指向具体文档片段 | RAG 优 | 家长问"为什么游泳对这孩子的训练量是安全的？"→ RAG 可给出"依据《前庭觉训练指南》第3章" |
| **幻觉控制** | 模型仍会编造，且更隐蔽（编造得更"专业"） | 答案受限于检索到的文档，幻觉范围可控 | RAG 优 | 微调过的模型可能编造不存在的"某某研究"；RAG 只基于检索到的文档回答，没检索到就说不知道 |
| **单次更新成本** | $10-$100+/次 | 向量化一本书约 ¥0.3 | RAG 优 | 新增一本训练指南：微调需 GPU 集群重训练；RAG 只需一次 Embedding 调用 |
| **操作门槛** | 需准备训练数据、调参、防过拟合 | 上传文档即可 | RAG 优 | 产品经理可以直接上传新文档到知识库；微调需要算法工程师介入 |
| **知识删除** | 无法精确删除——只能重新训练整个模型 | 删除文档立即生效 | RAG 优 | GDPR"被遗忘权"要求删除某用户的训练数据 → 微调无法做到；RAG 删除对应文档即可 |
| **权限控制** | 无法做到"不同人看到不同知识" | 双层 Pre-filter，按角色裁剪可见范围 | RAG 优 | 药师能查药学禁忌，普通医生不能 → RAG 按角色过滤检索范围 |
| **数据安全** | 训练数据需上传 GPU 集群，有泄漏风险 | 文档存本地向量库，不出企业网络 | RAG 优 | 医院患者数据不能上传到公有云 GPU 集群 → RAG 本地部署，数据不出网 |
| **多领域复用** | 一个微调模型绑定一个领域 | 多知识库 + 多域管道，一平台多领域 | RAG 优 | 心血管和药学是两个领域 → 微调需要两个模型；RAG 两个知识库 + 两条管道即可 |
| **基座模型升级** | 基座升级后微调模型需重新训练 | 基座升级直接受益，知识库无需改动 | RAG 优 | GPT-4 → GPT-5：微调模型需重新训练；RAG 只需切换 API 端点 |
| **长尾知识** | 罕见知识容易"灾难性遗忘" | 只要文档在库中就能检索到 | RAG 优 | 一种罕见病的治疗方案：微调可能因训练数据不足而遗忘；RAG 只要上传了相关文献就能检索到 |
| **监管合规** | 难以审计——无法证明某个回答基于什么训练数据 | 可审计——每个回答可追溯到具体文档 | RAG 优 | FDA/CE 认证要求医疗器械的 AI 建议可审计 → RAG 可输出完整溯源链 |
| **灾难性遗忘** | 新知识训练可能冲淡模型已有的旧知识 | 知识库中每条知识独立存储，不存在此问题 | RAG 优 | 新增前庭觉训练文献不会影响已有的本体觉训练知识 |
| **响应延迟** | 无需检索，毫秒级响应 | 检索步骤增加 50-200ms 延迟 | 微调优 | 对延迟极敏感的场景（如实时对话中的打字建议），微调有优势 |

**关键结论**：14 个维度中 RAG 在 13 个维度更优。微调的唯一优势在延迟，但 50-200ms 的检索延迟在绝大多数专业评估场景中不可感知——用户等待 LLM 生成答案本身就需要数秒。

### 微调并非无用——它在什么情况下更合适？

| 场景 | 为什么微调更好 | 但与 RAG 的关系 |
|------|---------------|----------------|
| **风格/语调统一** | 想让 AI 始终用特定口吻回答，微调比提示词更稳定 | 不是"二选一"——可以在 RAG 基础上对 LLM 微调风格 |
| **格式严格遵循** | 需要 AI 严格按特定 JSON Schema 输出 | RAG 的结构化输出节点也能做到，只是微调更稳定 |
| **极低延迟要求** | 不需要检索步骤，响应更快（< 100ms） | RAG 的语义缓存节点命中时也能达到类似延迟 |

**最佳实践**：RAG 为主，微调为辅。先解决"知识准确"的核心矛盾（用 RAG），再考虑"风格统一"的锦上添花（用微调）。两者的关系不是排他的。

## 三、RAG 带来的五个核心价值

| 价值 | 说明 | 量化依据 |
|------|------|---------|
| **准确性** | 答案有据可查，可追溯到具体文档 | 检索结果作为上下文注入 LLM——每个声明可追溯到检索到的文档片段；平台阶段引用验证节点进一步自动校验每句话的出处 |
| **时效性** | 更新知识库即可，不需要重新训练 LLM | 新文档上传即生效，分钟级；微调需要数小时到数天 |
| **私有性** | 企业数据留在自己的知识库中，不上传给 LLM 厂商 | 本地部署数据不出网；平台阶段 Pre-filter 权限控制进一步确保数据隔离 |
| **可控性** | 可以控制 LLM 参考哪些知识，过滤敏感信息 | 知识库范围可控——只检索被授权的文档；平台阶段升级为双层权限 + 敏感词过滤 + PII 脱敏 |
| **成本效益** | 比微调便宜得多，更新也更方便 | 一次查询不到 1 分钱（详见 10-tech-costs-comparison） |

### 不用的后果

- 医疗场景：LLM 可能推荐过时的治疗方案，造成医疗事故
- 法律场景：LLM 可能引用已废止的法条，导致法律风险
- 企业场景：内部机密数据如果用于微调，会泄漏给模型厂商
- 合规场景：监管机构要求 AI 决策可审计，纯 LLM 无法提供决策依据

## 四、RAG 不适用的场景——诚实说明边界

RAG 不是银弹。以下场景不适合或需要额外方案：

| 场景 | 为什么不适用 | 替代/补充方案 |
|------|------------|-------------|
| **纯创意写作** | 不需要事实核查——写小说、写诗不需要检索知识库 | 纯 LLM 更合适，无需 RAG 开销 |
| **实时数据查询** | 需要天气、股价、体育比分等实时数据 | 需要 API 调用节点而非知识库检索 |
| **知识库为空** | 如果没有任何文档上传，RAG 退化为纯 LLM | 先上传至少一批基础文档 |
| **多轮对话中的指代消解** | 用户说"那前一个方案呢"，RAG 检索无法理解"前一个"指什么 | 需要对话历史管理节点（管道编辑器支持） |
| **知识库本身质量差** | 如果上传的文档充满错误（过时的指南、劣质翻译），RAG 会忠实地检索错误信息并让 LLM 基于错误信息回答 | RAG 不能修复知识库的质量——它是"忠实检索者"而非"事实审核者"。预防方案：上传前的人工审核；检测方案：评估体系的 Faithfulness 指标能检测答案与上下文的矛盾，但无法检测"上下文本身就错了"的情况（需要领域专家审查源文档） |

## 五、怎么做——RAG 基本工作流程

### 整体架构

```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│  1. 文档入库   │ →  │  2. 向量化    │ →  │  3. 用户查询  │ →  │  4. 生成答案  │
│  上传PDF/EPUB │    │  文本→向量    │    │  检索相关文档  │    │  LLM基于文档  │
│  解析+分块    │    │  存入向量库   │    │  混合检索     │    │  生成答案     │
└──────────────┘    └──────────────┘    └──────────────┘    └──────────────┘
```

### 核心技术组件速览

| 组件 | 做什么 | 为什么需要它 | 详见 |
|------|--------|------------|------|
| 文档解析 | 把 PDF/EPUB 转成可处理的文本 | 原始文档是二进制格式，计算机无法直接读取 | 03-knowledge-ingestion |
| 语义分块 | 按语义边界切分文档，保持内容完整 | 太长→检索不准，太短→上下文缺失 | 03-knowledge-ingestion |
| 向量化 | 把文本转成数字向量，使计算机能计算语义相似度 | 计算机不懂"前庭觉"和"平衡训练"是相关的 | 03-knowledge-ingestion |
| 向量存储 | 存储和检索向量 | 需要专门优化向量相似度搜索的数据结构 | 03-knowledge-ingestion |
| 混合检索 | 关键词 + 语义双路检索，RRF 融合 | 单一检索各有盲区：BM25 不懂语义，向量不擅精确匹配 | 04-hybrid-search |
| 重排序 | 用更精细的模型对检索结果重新排序 | 初始检索速度快但精度有限 | 04-hybrid-search |
| 答案生成 | 基于检索到的文档生成答案 | LLM 的语言能力将检索结果转化为可读答案 | 02-agent-workflow |
| 评估体系 | 用指标量化检索和生成效果 | 凭感觉调参不可靠，需要数据驱动 | 05-rag-evaluation |

### 三大业务流程及其数据依赖

整个系统包含三条互相依赖的业务流：

```
Agent 评估（面向用户的业务流程）
    │
    │ 依赖 RAG 检索来获取科学依据
    ▼
RAG 检索 ←── 依赖 ── RAG 上传（知识库是检索的前提）
    │                    ↑
    │                    │ 反馈优化
    └── 质量保障 ────→ RAG 评估（测试检索效果，驱动调优）
```

- **Agent 评估**：面向最终用户。输入儿童画像和运动计划，输出评估报告。依赖 RAG 检索获取科学依据。
- **RAG 上传**：面向管理员。把文档变成可搜索的知识。是 Agent 评估的前提——没有知识库就没有可检索的内容。
- **RAG 评估**：面向运维/算法。测试检索管道效果，驱动调优。是质量保障——不能等用户投诉了才发现检索效果差。

三者缺一不可。只做 Agent 评估而不做评估体系 → 检索效果无法保证 → 评估结果不可靠。

## 关键设计点

| 设计点 | 为什么 | 好处 |
|--------|--------|------|
| 知识存储与生成解耦 | 各自独立演进——更新知识不触及 LLM，升级 LLM 不触及知识 | 灵活、低成本更新 |
| RAG 为主、微调为辅 | 核心矛盾是「知识准确」，微调研「风格统一」是次要矛盾 | 先解决主要矛盾 |
| 三流程解耦 | 每个流程独立开发、测试、部署 | 互不阻塞 |
| 本地部署 | 数据不出企业网络 | 安全合规 |

## 一句话总结

> **RAG = 让 LLM 在回答问题之前先「查资料」。14 个维度中在 13 个维度优于微调。知识存储和答案生成解耦，是 RAG 最根本的架构优势。**
