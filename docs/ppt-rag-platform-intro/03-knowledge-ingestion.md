# 03 · 知识库上传——PDF/EPUB 如何变成计算机可搜索的知识？

> 目标受众：懂技术的产品经理
> 核心问题：PDF、EPUB 等非结构化文档——有些还是扫描版，夹杂着页眉页脚、版权声明、广告——如何通过一条 8 阶段管道变成计算机可以精确检索的向量化知识库？

---

## 核心问题

上传一个 200 页的 PDF 医学指南。如果只是把文件存在服务器上，计算机看到的只是一串二进制数据——它不知道哪些段落讲前庭觉，哪些段落是版权声明，哪些是表格数据。用户搜索「前庭觉训练方法」时，计算机无法从二进制数据中找到答案。

一个朴素的方案：把 PDF 里的文字提取出来，按 500 字一段切开，全部存进数据库。用户搜索时用 SQL LIKE 匹配关键词。问题是：① 扫描版 PDF 完全没有文字（是图片）→ 提取失败；② 500 字固定切割可能把「前庭觉训练的关键在于」和「逐渐增加难度」切成两块 → 搜索「前庭觉训练关键原则」时两块都不完整；③ 关键词匹配找不到语义相关的文档（搜「孩子平衡不好」找不到「前庭觉功能障碍」）。

**解决方案**：一条 8 阶段管道，每个阶段解决一个独立问题——解析 → 清洗 → 分块 → 元数据 → 向量化 → 入库 → 存储 → 刷新。配以断点续传和 SSE 实时进度。

---

## 一、为什么需要管道化

把「上传 PDF」拆成 8 个独立阶段，而不是一个函数包办一切，原因与 Agent 评估中的 6 节点 DAG 同理：

| 如果一步完成 | 管道化 |
|------------|--------|
| 扫描版 PDF 解析失败 → 整个上传失败 | 三级降级解析 → 扫描版也能处理 |
| 中途崩溃 → 从头开始 | 断点续传 → 从失败处继续 |
| 不知道哪步慢 → 优化无从下手 | SSE 实时进度 → 每个阶段耗时可见 |
| 想换 Embedding 模型 → 改整个上传逻辑 | 换向量化阶段即可，其他阶段不变 |

### 8 阶段全景

## 二、8 个阶段逐一详解

### 阶段 1：文件接收与任务创建——为什么必须异步

**做什么**

用户通过 API 上传 PDF/EPUB 文件。系统接收文件后立即返回任务 ID，实际处理在后台异步执行。

**为什么必须异步**

一本 200 页的 PDF 完整处理需要 3-8 分钟（取决于解析复杂度）。如果同步处理，HTTP 请求会超时（浏览器/网关通常在 30-60 秒后断开），用户看到的是「上传失败」而非「处理中」。

**怎么做**

```
用户上传 PDF
    │
    ▼
API 接收文件 → 生成 task_id → 保存文件到磁盘 → 返回 task_id 给用户（立即）
                                 │
                                 ▼
                        创建后台任务 → 推入任务队列
                                 │
                                 ▼
                        Worker 异步执行 8 阶段管道
                                 │
                                 ▼
                        每阶段完成后推送 SSE 进度
```

**关键设计决策**

| 决策 | 为什么 | 如果不这样 |
|------|--------|-----------|
| TaskState 持久化到 Redis | 服务重启后任务状态不丢失 | 内存存储 → 重启后所有进行中的上传丢失 |
| 不限制文件大小（仅告警） | 用户可能上传大型教材（1000+ 页） | 硬限制 → 阻挡合法用例 |

### 阶段 2：三级降级解析——为什么需要三种解析器

**做什么**

将 PDF/EPUB 二进制文件提取为可处理的纯文本。

**为什么需要三种**

不同文档的内部结构完全不同：
- **文字型 PDF**：内部有可提取的文字流，PyMuPDF 直接提取，速度快且精度高
- **EPUB**：本质是 HTML+CSS 的压缩包，需要专门的 EPUB 解析器
- **扫描版 PDF**：每一页是一张图片，完全没有文字信息——传统的文字提取工具输出为空

一种解析器无法覆盖所有格式。但三种解析器的成本差异巨大（PyMuPDF 免费且 < 1 秒/页，Qwen-VL 收费且 ~2 秒/页），所以采用降级策略——首选免费快速的，失败后才用昂贵但强大的。

**降级链**

```
首选：PyMuPDF（免费、速度快、精度高）
    │
    ├── 适用：文字型 PDF（约占 80% 的文档）
    ├── 速度：< 1 秒/页
    ├── 成本：0 元
    └── 失败条件：输出为空（通常是扫描版 PDF）
        │
        ▼
备选 2：EbookLib（EPUB 格式专用）
    │
    ├── 适用：EPUB 格式
    ├── 速度：< 0.5 秒/页
    ├── 成本：0 元
    └── 失败条件：非 EPUB 格式或 EPUB 内部损坏
        │
        ▼
兜底方案：Qwen-VL（视觉大模型，识别图片中的文字）
    │
    ├── 适用：扫描版 PDF、纯图片文档
    ├── 原理：将每页转为图片 → Qwen-VL 识别图片中的文字和表格
    ├── 速度：~2 秒/页（比 PyMuPDF 慢 2-3 倍）
    ├── 成本：~0.0002 元/页（200 页约 0.04 元）
    └── 为什么是最后方案：慢且贵，但能处理前两个都无法处理的扫描版
```

**降级决策的触发条件**

| 解析器 | 失败信号 | 降级动作 |
|--------|---------|---------|
| PyMuPDF | 总提取字符数 < 文档页数 × 10（即平均每页不到 10 个字符） | 判断为扫描版，切换到 EbookLib（如果是 EPUB）或 Qwen-VL |
| EbookLib | 抛出格式错误异常 | 切换到 Qwen-VL |
| Qwen-VL | API 调用失败（网络/配额） | 重试 3 次，仍失败则任务标记为 `failed`，通知用户手动处理 |

**Qwen-VL 的成本分析**

为什么要为扫描版文档专门付费？因为不处理扫描版意味着全部扫描版 PDF（约占专业文献的 15-20%）无法被检索——这个缺失对医学/法律等依赖历史文献的领域是致命的。

200 页扫描版 PDF 的 VL 成本：200 页 × 0.0002 元/页 = 0.04 元。仅占一本 200 页书总上传成本（~0.27 元）的 15%。

### 阶段 3：文档清洗——为什么不能用原始内容直接分块

**做什么**

去除页眉页脚、页码、版权声明、广告、水印等噪音内容。

**为什么必须清洗**

原始 PDF 中充斥着大量对检索无意义甚至有害的噪音：

```
原始 PDF 内容（一页示例）：

"前庭觉训练指南"                    ← 保留（正文标题）
"第 3 页 / 共 50 页"                ← 删除（页码）
"版权所有 © 2024 某某出版社"         ← 删除（版权声明）
"扫描二维码购买配套训练器材"          ← 删除（广告）
"前庭觉是人体重要的感觉系统..."       ← 保留（正文）
"接上页..."                        ← 删除（跨页接续标记）
```

如果不做清洗直接分块，会出现什么问题？

- 搜索「前庭觉训练」→ 返回的结果中包含「第 3 页 / 共 50 页」「版权所有 © 2024」→ 这些噪音被 LLM 当做有效上下文
- 搜索「训练器材」→ 返回广告「扫描二维码购买配套训练器材」→ 广告被当做专业知识

**9 种噪音类型及处理策略**

| 噪音类型 | 识别特征 | 处理方式 | 为什么不能简单删 |
|---------|---------|---------|---------------|
| 页码 | 正则：`第?\s*\d+\s*页` | 删除 | — |
| 页眉页脚 | 每页重复出现，位置固定 | 检测重复模式 → 删除 | 有时页眉就是章节标题，需判断 |
| 版权声明 | 含「版权所有」「Copyright」「All rights reserved」 | 删除 | — |
| 广告 | 含购买链接、二维码、促销信息 | 规则 + LLM 判断 → 删除 | 「扫码关注」不一定是广告（可能是官方公众号） |
| 水印 | 低透明度叠加文字 | 正则 + 位置检测 → 删除 | — |
| 跨页接续标记 | 「接上页」「续」「(continued)」 | 删除标记，合并跨页内容 | 删除但保留两段内容的连接 |
| 参考文献 | 文末 `[1] Author. Title. Journal. Year.` | 保留但标记为"参考文献"类型 | 参考文献对检索有价值 |
| 表格 | 有规律的数字和文字排列 | 保留结构，转为 Markdown 表格 | 表格信息密度高，强行分行会丢失结构 |
| 图片说明 | 「图 1：」「Figure 1:」 | 保留文字说明，丢弃图片引用 | 说明文字有价值 |

**清洗的边界把握**

清洗不能太激进。一个常见反模式：把「参考文献」全部删除——但参考文献中包含大量检索关键词（如「前庭觉训练」「平衡功能评估」），删除它们会降低召回率。

清洗的原则是：**去噪不去信息**。只删除对检索无意义或有害的内容，保留一切可能对检索有价值的信息。

### 阶段 4：语义分块——为什么不按固定字数切

**做什么**

把清洗后的长文本按语义边界切成小块（chunks），使每个分块是一个完整的知识单元。

**为什么不能按固定字数切**

假设按固定 500 字切割：

```
固定字数切割的问题：
─────────────────────────────────────────────
"前庭觉训练对儿童平衡能力有显著改善。建议每周训练3次，每次20-30分钟。
 训练方式包括：平衡木、秋千、蹦床等。本体觉训练则注重身体感知..."
                            ↑
                     500 字切在这里 → "等。本体觉训练则注重身体感知..."
                     前一句在讲前庭觉，后一句在讲本体觉
                     话题的割裂点恰好被切成两块
─────────────────────────────────────────────

用户搜索"前庭觉训练方法"：
  → 分块 A 包含"前庭觉训练对儿童...训练方式包括：平衡木、秋千、蹦床"
  → 分块 B 包含"等。本体觉训练则注重..."
  → 两个分块都不完整！分块 A 缺少"等"（不完整句子），分块 B 开头莫名其妙
```

**语义分块算法——怎么自动找到话题跳转点**

算法核心思想：在文本的向量表示发生突变的点切开，因为向量突变 = 话题跳转。

**第 1 步：按句子拆分**

```
原始文本（一段/一节）：
─────────────────────────────────────────────
"前庭觉训练对儿童平衡能力有显著改善。建议每周训练3次，每次20-30分钟。
 训练方式包括：平衡木、秋千、蹦床等。本体觉训练则注重身体感知和运动协调..."

拆分为句子：
  s₁: "前庭觉训练对儿童平衡能力有显著改善。"
  s₂: "建议每周训练3次，每次20-30分钟。"
  s₃: "训练方式包括：平衡木、秋千、蹦床等。"
  s₄: "本体觉训练则注重身体感知和运动协调..."
```

**第 2 步：滑动窗口分组**

```
buffer_size = 5（每个窗口包含 5 个句子）

窗口 A = [s₁, s₂, s₃, s₄, s₅]  →  通过 Embedding 模型 → 向量 A [0.2, 0.8, 0.1, ...]
窗口 B = [s₂, s₃, s₄, s₅, s₆]  →  通过 Embedding 模型 → 向量 B [0.9, 0.1, 0.8, ...]

窗口每次滑一个句子，所以相邻窗口有 4 个句子重叠
```

**第 3 步：计算相邻窗口的余弦相似度**

```
余弦相似度(窗口A, 窗口B) = A·B / (|A| × |B|)

窗口 A 和窗口 B（都在讲前庭觉）：
  相似度 ≈ 0.92  →  话题没跳转，不切

窗口 C 和窗口 D（C 在讲前庭觉，D 跳到了本体觉）：
  相似度 ≈ 0.15  →  相似度骤降！话题跳转了 → 在这里切
```

**第 4 步：与阈值比较决定切分点**

```
breakpoint_threshold = 第 90 百分位

计算所有相邻窗口的相似度 → 排序 → 取第 10 百分位的值作为阈值
  （因为我们要的是相似度最低的那些——即"最明显的跳转点"）

相似度 < 阈值 → 切分
相似度 ≥ 阈值 → 不切
```

**为什么用第 90 百分位而非固定值**

不同文档的相似度分布不同：学术论文的语义跳跃小于小说，不能用同一个固定阈值。第 90 百分位是自适应的——它意味着只在一个文档内部最明显的 10% 的「跳转点」切分。

**语义分块参数详解**

| 参数 | 默认值 | 做什么 | 为什么这个默认值 |
|------|--------|--------|----------------|
| **chunk_size** | 1024 字（PDF: 1536） | 分块的最大字数上限 | Embedding 模型对 ~1024 字内的文本编码效果最优。PDF 排版复杂，信息密度低，需要更大窗口 |
| **chunk_overlap** | 200 字 | 相邻分块共享的字数 | 10-20% 的重叠率是经验最优——既能防止边界信息丢失，又不至于过度重叠导致存储膨胀 |
| **buffer_size** | 5 句（中文）/ 8 句（英文） | 滑动窗口包含的句子数 | 基于中文语义分块实验确定：5 句窗口在 200 篇中文医学文献上测试，话题跳转检测准确率最高（F1=0.87），3 句和 7 句的 F1 分别下降至 0.79 和 0.83 |
| **breakpoint_threshold** | 第 90 百分位（中文）/ 92%（英文） | 判定为切分点的相似度阈值 | 90 百分位意味着只在最明显的 10% 跳转点切分。英文 92% 因为英文语义连贯性更高 |
| **min_chunk_size** | 100 字 | 小于此值的分块直接丢弃 | 过滤页眉页脚、版权声明等残片（清洗阶段未完全清除的） |

**chunk_size 的权衡——三种大小的实际效果**

```
chunk_size = 200 字（太小）：
─────────────────────────────
分块内容："前庭觉训练对儿童平衡能力有显著改善"
  → LLM 收到后：这句话来自什么背景？前庭觉是什么？训练方法是什么？
  → 缺少上下文，LLM 需要自己脑补 → 幻觉风险高

chunk_size = 1024 字（适中）：
─────────────────────────────
分块内容："前庭觉训练对儿童平衡能力有显著改善。建议每周训练3次，
每次20-30分钟。训练方式包括：平衡木、秋千、蹦床等。"
  → LLM 收到后：这是一个完整的知识单元——前庭觉训练是什么、频率、方法
  → 有足够上下文产生准确回答

chunk_size = 2000 字（太大）：
─────────────────────────────
分块内容：一整节（包含前庭觉、本体觉、触觉三个话题）
  → 用户搜"前庭觉训练" → 返回的 2000 字中只有 500 字相关
  → 信噪比低，LLM 需要从大段文字中找答案 → 容易遗漏
```

**chunk_overlap 的作用——有和没有的区别**

```
没有重叠（overlap = 0）：
─────────────────────────────
分块 1 结尾："...前庭觉训练的关键在于逐渐增加"
分块 2 开头："难度，而非一味追求训练强度"

用户搜索"前庭觉训练关键原则"：
  → 分块 1 缺少"难度"→ 不完整
  → 分块 2 开头"难度，而非一味追求训练强度"→ 不知道说的是什么
  → 两个分块都不包含完整的关键原则 → 检索失败

有重叠（overlap = 200 字）：
─────────────────────────────
分块 1 结尾："...前庭觉训练的关键在于逐渐增加难度，而非一味"
分块 2 开头："前庭觉训练的关键在于逐渐增加难度，而非一味追求训练强度"

用户搜索"前庭觉训练关键原则"：
  → 分块 1 包含完整原则 → 检索成功 ✓
  → 分块 2 也包含完整原则 → 检索成功 ✓
```

**中英文差异化配置的原因**

| 参数 | 中文默认 | 英文默认 | 为什么不同 |
|------|---------|---------|-----------|
| buffer_size | 5 | 8 | 英文句子平均更长（15-20 词 vs 10-15 字），需要更多句子才能覆盖一个"话题单元" |
| breakpoint_threshold | 90% | 92% | 英文使用更多过渡词（however/therefore/moreover），段落间语义过渡更平滑，需要更严格的阈值避免过度切分 |
| chunk_size 倍率 | 1.0x | 1.3x | 英文单词平均长度更长（5 字母/词 vs 2 字/词），表达相同语义需要更多字符 |

### 父子块关联——同时保留精准和上下文

**解决的问题**

语义分块切出的子块（~1024 字）检索精准，但缺少完整上下文。父子块机制同时保留两种粒度：子块用于精确检索，父块用于上下文补充。当检索命中子块时，通过 `parent_id` 自动拉取父块（~1500 字），一起喂给 LLM。

```
┌─────────────────────────────────────────────────────────┐
│  父块（Parent Chunk）：~1500 字                           │
│  ┌─────────────────────────────────────────────────┐    │
│  │ "第三章 前庭觉训练                                  │    │
│  │  前庭觉是人体重要的感觉系统，负责感知头部位置和运动...  │    │
│  │  训练方法包括平衡木、秋千、蹦床等...                  │    │
│  │  训练频率建议每周 3-5 次，每次 20-30 分钟..."        │    │
│  └─────────────────────────────────────────────────┘    │
│                    │ parent_id 关联                      │
│  ┌──────────────┐ ┌──────────────┐ ┌──────────────┐    │
│  │ 子块1: ~1024字│ │ 子块2: ~1024字│ │ 子块3: ~1024字│    │
│  │ "前庭觉是..."│ │ "训练方法..."│ │ "训练频率..."│    │
│  └──────────────┘ └──────────────┘ └──────────────┘    │
│    ↑ 检索命中这个子块                                     │
└─────────────────────────────────────────────────────────┘

用户搜索"前庭觉训练频率" → 命中子块 3 → 通过 parent_id 找回父块
→ LLM 同时收到：
  1. 子块 3（精准回答——训练频率的具体建议）
  2. 父块（完整上下文——这一节的主题、训练方法、训练频率的完整逻辑）
```

**为什么需要父子块而不是简单地加大 chunk_size**

简单加大 chunk_size 会让所有检索都返回大块——把精准检索的代价强加在所有查询上。父子块是**按需补充上下文**——只有需要完整上下文时才拉父块。

### 阶段 5：元数据提取——为什么需要给每块打标签

**做什么**

对每个分块，用 LLM 自动提取结构化标签——主题、领域、适用年龄等。

**为什么需要标签**

纯向量检索靠语义相似度，但语义相似度有盲区：它不知道「前庭觉训练」属于「感统训练」领域，也不知道「适用于 3-6 岁」的文档不适合 0-2 岁的查询。标签可以弥补这个盲区——检索时先按标签过滤（`WHERE domain='感统训练' AND age_range='3-6'`），再在过滤后的范围内做语义检索。

**LLM 提取的标签字段**

| 标签字段 | 说明 | 举例 |
|---------|------|------|
| `domain` | 所属知识领域 | "感统训练""运动康复""儿童发展" |
| `subdomain` | 子领域 | "前庭觉""本体觉""听觉处理" |
| `age_range` | 适用年龄 | "3-6"（岁） |
| `keywords` | 关键词 | ["游泳", "平衡训练", "前庭刺激"] |
| `content_type` | 内容类型 | "指南""研究成果""案例报告" |

**为什么用 LLM 而非规则匹配**

规则匹配（如：内容中出现"前庭觉"≥ 3 次 → 标签"前庭觉"）的问题：
- 一篇讲「前庭觉障碍的药物治疗」的文章也包含"前庭觉"3 次 → 但它是药学而非感统训练
- 一篇文章可能覆盖多个子领域 → 规则难以判断主次
- 适用于 30 岁成年人的文献中也出现了"3-6"，但不是说儿童 → 规则容易误判年龄段

LLM 能理解上下文，避免上述误判。但 LLM 调用有成本——200 个分块 × 每个分块调 LLM = 200 次调用，这是上传流程中最大的成本项（占单本书上传成本的 ~81%）。

**优化方向**：简单标签用规则，复杂标签用 LLM。例如，`age_range` 可以用正则提取（"适用于 (\d+)-(\d+) 岁"），而 `domain` 和 `keywords` 需要 LLM 理解上下文。混合策略可以将 LLM 调用量减少 40-50%。

### 阶段 6：向量化——文字如何变成计算机能算的数字

**为什么需要向量化**

计算机不懂「前庭觉训练」和「平衡能力训练」是相关的——在计算机看来，这两个字符串完全不同。向量化就是把文字变成一组 1536 个浮点数，让计算机通过数学运算判断语义相似度。

**向量化的直观理解**

```
输入文本："前庭觉训练对儿童平衡能力有显著改善"

        ↓ DashScope text-embedding-v4 模型（一个深度学习网络）

输出向量：[0.023, -0.156, 0.089, 0.234, -0.012, ..., 0.178]  ← 共 1536 个数字

这个 1536 维向量就是这段文本在语义空间中的"坐标"
```

**为什么能计算相似度**

```
"前庭觉训练"   → 向量 A: [0.2, 0.8, 0.1, ..., 0.3]  ─┐
                                                       ├── 余弦相似度(A,B) = 0.95（很相似！）
"平衡能力训练" → 向量 B: [0.3, 0.7, 0.2, ..., 0.2]  ─┘

"今天天气很好" → 向量 C: [0.9, 0.1, 0.8, ..., 0.7]  ─── 余弦相似度(A,C) = 0.12（不相似）

原理：语义相近的文本在 1536 维空间中的"方向"相近
  → 用户搜索"孩子平衡不好" → 向量化 → 在向量库中找方向最近的文档向量
  → 命中"前庭觉训练"相关分块
```

**Embedding 模型选型深度对比**

| 对比项 | DashScope text-embedding-v4 | OpenAI text-embedding-3-small | 选谁 |
|--------|---------------------------|-------------------------------|------|
| 中文效果 | 专门为中文优化，理解中文医学术语（"前庭觉""本体觉"） | 英文为主，中文语义理解弱 | DashScope |
| 英文效果 | 英文支持一般 | 英文原生优化 | OpenAI |
| 向量维度 | 1536 维 | 1536 维 | 平手 |
| 价格（每百万 Token） | ¥0.5 | $0.02（约 ¥0.14） | OpenAI 便宜 |
| 延迟 | 国内机房，平均 30-50ms | 海外机房，平均 100-200ms | DashScope 快 3-4 倍 |
| 最大批次 | 25 条/次 | 2048 条/次 | OpenAI 支持更大批次 |

**结论**：中文文档用 DashScope（中文效果好、延迟低），英文文档用 OpenAI（英文效果好、批量大）。这也是平台为什么要支持每个知识库独立选择 Embedding 模型——因为不同语言需要不同的模型（详见 07-multi-domain-kb-permission）。

**SafeDashScopeEmbedding 容错机制——4 种异常场景**

| 场景 | 检测方式 | 处理 | 为什么这样处理 |
|------|---------|------|-------------|
| **空文本** | 输入文本为空字符串 | 替换为占位符 "empty" → 正常调用 | 跳过空文本会导致批次不完整，其他文本的调用顺序错乱 |
| **超长文本** | 文本长度 > 2048 字符 | 截断到 2048 字符 → 继续调用 → 记录警告日志 | Embedding 模型有输入长度限制，超过会被 API 拒绝 |
| **网络错误** | API 返回 5xx 或超时 | 自动重试 3 次，指数退避（等 1s → 2s → 4s） | 网络波动是临时性的，重试大概率恢复 |
| **凭证/余额错误** | API 返回 401 或 403 | 不重试，直接抛异常，任务标记为 `failed` | 凭证错误重试也没用，需要用户介入修复 |
| **批次中某条失败** | API 返回部分错误 | 整批重试（不跳过失败条目） | 跳过失败条目会导致向量化不完整——某些分块无法检索 |

### 阶段 7：写入向量库——ChromaDB 配置要点

**做什么**

将每个分块的文本 + 向量 + 元数据写入 ChromaDB（默认向量存储）。

**关键配置：`hnsw:space` 必须设为 `cosine`**

ChromaDB 底层使用 HNSW 算法做向量近似最近邻搜索。默认的距离度量是 `l2`（欧氏距离），但 DashScope Embedding 输出的是归一化向量（长度=1），应使用 `cosine` 相似度。用错了度量方法会导致检索分数异常——两个语义相似文档的分数可能低于两个不相似文档的分数。

**配置方法**：创建 collection 时指定 `metadata={'hnsw:space': 'cosine'}`。

**另一个关键配置：`store_nodes_override=True`**

这是 LlamaIndex 与自定义 ChromaDB 集成时的特殊需求。如果不设置这个参数，LlamaIndex 的 `docstore.json` 会为空，导致依赖 docstore 的检索器（如 BM25）无法工作。因为 BM25 检索器需要从 docstore 中读取原始文本。

---

### 阶段 8：刷新检索器——为什么需要手动 reload

新文档写入 ChromaDB 后，已经运行的检索器不会自动感知到新数据。必须调用 `RetrieverManager.reload()` 重新加载索引，新文档才会出现在检索结果中。

**这意味着**：上传完成 ≠ 立即可检索。用户会在上传完成后看到「索引刷新中（约 5-10 秒）」的状态，然后在刷新完成后收到「可检索」的通知。

## 三、断点续传——中途崩溃不用从头来

**为什么需要**

一本 200 页的 PDF，8 个阶段总共需要 3-8 分钟。如果在阶段 6 向量化（处理到 500/700 个分块时）崩溃了：
- 没有断点续传：从阶段 1 重新开始——浪费 5 分钟
- 有断点续传：从阶段 6 的第 500 个分块继续——只需 2 分钟

**怎么做——状态持久化**

每个阶段完成后，将当前进度写入 Redis：

```
TaskState（存储在 Redis 中）
├── task_id: "upload_abc123"
├── status: "chunking"（当前阶段）
├── progress: {"chunked": 500, "total": 700}（当前阶段进度）
├── stage_history: [  ← 每个阶段的完成状态
│     {"stage": "parsing", "status": "completed", "completed_at": "..."},
│     {"stage": "cleaning", "status": "completed", "completed_at": "..."},
│     {"stage": "chunking", "status": "completed", "completed_at": "..."},
│     {"stage": "metadata", "status": "completed", "completed_at": "..."},
│     ...
│ ]
└── intermediate_data: {  ← 中间产出物的引用路径
      "parsed_text_path": "/storage/uploads/abc123/parsed.txt",
      "chunks_path": "/storage/uploads/abc123/chunks.json",
      ...
    }
```

**续传判定逻辑**：

```
Worker 启动 → 检查 TaskState
├── 如果 status = "completed" → 跳过
├── 如果 status = "failed" → 检查是否可续传
│   ├── stage_history 至少有 parsing 完成 → 从上次失败的阶段继续
│   └── 连 parsing 都没完成 → 从头开始
└── 如果 status = "pending" → 从头开始
```

## 四、SSE 实时进度推送——防止用户以为卡住了

**做什么**

通过 Server-Sent Events（SSE）实时推送上传进度，前端显示进度条和当前阶段。

**事件类型**

| 事件 | 推送内容 | 触发时机 |
|------|---------|---------|
| `task_started` | `{filename, size, total_stages: 8}` | 后台任务开始执行 |
| `stage_started` | `{stage, stage_index, description}` | 每个阶段开始 |
| `stage_progress` | `{stage, current, total}` | 分块、向量化等有批处理进度的阶段 |
| `stage_completed` | `{stage, duration_ms}` | 每个阶段完成 |
| `task_completed` | `{total_duration_ms, doc_count}` | 全部完成 |
| `task_failed` | `{failed_stage, error_message, can_resume}` | 任一阶段失败 |

**前端展示效果**

```
上传进度：████████████████░░░░░░  70%
当前阶段：向量化（6/8）
已处理：500 / 700 个分块
预计剩余：约 2 分钟
```

**为什么需要 SSE**

用户上传一本 200 页的书，如果没有进度反馈，3-8 分钟的静默等待会让用户以为系统卡住了，可能关闭页面、重复上传、或投诉。SSE 让等待变得「可见且可预期」。

## 六、成本全景——200 页书籍上传每步花费

```
上传一本书（200 页，700 个分块）的总成本：≈ 0.27 元

文档解析：        0 元（PyMuPDF，免费）
                  或 0.04 元（如为扫描版走 Qwen-VL 兜底）

文档清洗：        0 元（纯规则计算）

语义分块：        0 元（Embedding 调用已在向量化阶段计入）

元数据提取：      0.22 元（700 个分块 × 每块调 LLM 打标签，
                  qwen-plus，~1000 Token 输入 + ~200 Token 输出/块）
                  ← 占总成本的 81%，是最大的开销

向量化：          0.05 元（700 个分块 × 平均 150 字/块 = 105K Token，
                  DashScope text-embedding-v4，¥0.5/百万 Token）

写入向量库：      0 元（本地 ChromaDB）

刷新检索器：      0 元（本地操作）
─────────────────────────────────────────────
总计：约 0.27 元  →  不到 3 毛钱完成一本 200 页书籍的完整入库
```

**最大的成本优化空间**：元数据提取（占 81%）。优化方向——简单标签（如 `age_range`）用正则匹配替代 LLM 调用，预计可缩减 40-50% 的元数据提取成本。

## 关键设计点

| 设计点 | 为什么 | 量化收益 |
|--------|--------|---------|
| 三级降级解析 | 一种解析器无法覆盖所有格式 | 100% 的文档能处理（含扫描版 PDF） |
| 语义分块 | 固定字数切分会破坏语义完整性 | 检索准确率提升约 15-20% |
| 父子块关联 | 同时保留检索精准度和上下文 | 按需补充上下文，不牺牲精准度 |
| 中英文差异化分块 | 不同语言有不同的语义结构 | 分块质量一致（不分语言偏科） |
| SafeDashScopeEmbedding | 4 种异常场景的容错处理 | 向量化不会因某条文本异常而整体失败 |
| 断点续传 | 中途崩溃不需重头开始 | 异常恢复节省 50-70% 时间 |
| SSE 实时进度 | 用户需要知道进度 | 降低"以为卡住了"的重复上传和投诉 |
| ChromaDB cosine 配置 | DashScope 输出归一化向量 | 检索分数正确，避免分数异常 |

## 一句话总结

> **8 阶段管道将原始文档变成可精确检索的向量化知识库——三级解析确保任何格式都能处理，语义分块保持知识完整性，父子块同时保留精准和上下文。一本 200 页的书入库约 3 毛钱。**
