# 09 · 管道发布 + 评估升级——配置好的管道如何被调用？效果如何持续验证？

> 目标受众：懂技术的产品经理
> 核心问题：在编辑器里配置好的管道，外部业务系统怎么调用？多域场景下，评估体系如何从单管道升级到覆盖多域聚合效果？

---

## Part A：管道发布——URL 即服务

### 核心问题

管道在编辑器里配置好了——混合检索 + 重排序 + 敏感词过滤，6 个节点。外部业务系统（如医院的电子病历系统、律所的文档管理系统）需要调用它。但它们不应该知道管道内部的结构——不知道有多少个节点、用什么检索策略、权重如何分配。

**解决方案**：每条管道发布为一个自定义 URL 端点。调用方只做一件事——向 URL 发送查询文本，接收答案。

### 发布为 URL 的理念

```
管道编辑器（配置端）                  发布后的 URL（调用端）
───────────────────                 ─────────────────────
跨学科综合问诊管道 v3   ──→ 发布 ──→  POST /search/medical-consultation
                                      ↑
                                    调用方只需要：
                                    1. 向这个 URL 发 POST
                                    2. body: {"query": "高血压合并糖尿病用药"}
                                    3. 接收 JSON 答案

法律尽调查询管道 v1     ──→ 发布 ──→  POST /search/legal-due-diligence
金融合规审查管道 v2     ──→ 发布 ──→  POST /search/finance-compliance
```

**调用方不知道也不需要知道**：
- 管道内部有多少个节点
- 用了 BM25 还是向量检索
- RRF 融合时的权重
- 是否启用了敏感词过滤
- 检索了多少个域

**管道内部变更对调用方透明**：把"医学综合问诊 v3"的 BM25 权重从 0.4 调到 0.6 → URL `POST /search/medical-consultation` 保持不变 → 调用方零感知。

### 三种搜索方式的应用场景矩阵

| 方式 | URL | 适用场景 | 为什么需要 |
|------|-----|---------|-----------|
| **发布 URL** | `POST /search/{custom-path}` | 生产环境对外暴露 | 简洁——隐藏内部细节，外部系统集成只需 URL |
| **通用端点** | `POST /api/v1/search` + `{pipeline_id}` | 测试、内部调试 | 灵活——可动态切换管道 ID，调试时不用发布多个 URL |
| **SSE 流式** | `POST /api/v1/search/stream` | 大模型生成时实时推送 | 体验——生成答案需要时间，流式推送让用户实时看到进度 |

### 发布 URL 的独立配置

每个发布 URL 可独立配置安全和性能参数：

| 配置项 | 说明 | 为什么需要独立配置 |
|--------|------|-----------------|
| **启用/停用** | 临时关闭某个 URL | 紧急下线某管道，不影响其他管道 |
| **认证要求** | API Key / JWT / 无认证 | 不同管道安全要求不同——公开 FAQ 不需要认证，内部医学咨询需要 JWT |
| **速率限制** | max_qps | 保护系统不被单一客户端压垮 |
| **参数白名单** | 只允许特定参数传入 | 防止调用方传入未预期的参数干扰管道执行 |

### 权限过滤全局强制

同一 URL 被不同角色调用时，返回结果自动受该用户权限约束：

```
POST /search/medical-consultation
Authorization: Bearer <JWT>

管理员调用（roles: ["admin"]）：
  → 域分析激活全部 3 个域 → 跨域融合全部结果 → 返回完整答案

普通医生调用（roles: ["doctor"]）：
  → 域分发时检测到 doctor 无药学库权限 → 药学域不被激活
  → 返回心血管 + 内分泌的结果（药学域被跳过）

实习生调用（roles: ["intern"]）：
  → 仅激活公开教材库 → 返回教材库的结果（心血管和临床库因权限被裁剪）
```

**关键**：调用方不需要传权限参数——权限从 JWT 自动提取。权限过滤是全局强制行为，所有搜索 API 不可绕过。任何试图越权访问的行为在检索发生前就被拦截。

### 管道版本管理——URL 不变，内部切换

```
管道 v1（评估 78 分）→ 发布 URL: /search/medical-consultation（在线）
管道 v2（评估 81 分）→ 发布 URL: /search/medical-consultation（发布者将 URL 指向 v2）
  → 调用方零感知升级——URL 不变，但背后管道版本已切换

管道 v3（评估 79 分）→ 发布 URL: /search/medical-consultation
  → 效果不如 v2 → 一键回滚到 v2
```

**灰度发布策略**：

```
第 1 步：新版本 v2 发布到灰度 URL：POST /search/medical-consultation-gray
         v1 仍由正式 URL 提供服务：POST /search/medical-consultation

第 2 步：通过 Nginx/应用层路由分流 5-10% 流量到灰度 URL（按 tenant_id 哈希，同一租户始终走同一版本）

第 3 步：灰度监控期（建议 24-48 小时）
         监控指标：
         ├── 评估指标：在灰度 URL 上运行评估测试集 → 对比 v1 的 7+4 项指标
         ├── 延迟分布：P50/P95/P99 端到端延迟 → 与 v1 对比
         ├── 错误率：5xx 比例 → 不应超过 v1 的 2 倍
         └── 业务指标：答案采纳率（如有点赞/踩机制）→ 不应显著低于 v1

第 4 步：决策
         ├── 全部达标且无回归 → 渐进提升灰度比例 5%→25%→50%→100%
         ├── 指标有退化但 < 阈值 → 延长观察期，调参后再评
         └── 指标退化 > 阈值 → 立即回滚——灰度 URL 下线，全部流量回 v1

第 5 步：全量切换 — 正式 URL 指向 v2，灰度 URL 保留 v1 一周作为紧急回滚备份
```

**回滚触发条件**（任一触发即回滚）：
- 任何 L1/L2 指标下降 > 5%（比 Layer 6 的 3% 宽松——因为灰度环境与评估环境可能存在差异）
- 端到端延迟 P95 增加 > 30%
- 5xx 错误率 > v1 的 3 倍
- 发现安全漏洞或权限绕过

### SSE 流式——实时推送

传统方式：等待 5 秒 → 返回完整答案。SSE 流式：实时推送事件流。

```
POST /search/stream
Headers: Authorization: Bearer <JWT>
Body: {"query": "高血压合并糖尿病老年患者如何用药"}

─────────────────────────────────────────────
event: domain_activated
data: {"domains": ["心血管", "内分泌", "药学"], "total": 3}

event: retrieval_progress
data: {"domain": "心血管", "found": 10, "status": "completed"}

event: retrieval_progress
data: {"domain": "内分泌", "found": 8, "status": "completed"}

event: retrieval_progress
data: {"domain": "药学", "found": 6, "status": "completed"}

event: fusion_complete
data: {"total_candidates": 15, "after_dedup": 12}

event: answer_chunk
data: {"text": "根据心血管指南，高血压老年患者建议..."}

event: answer_chunk
data: {"text": "合并糖尿病患者需注意药物相互作用..."}

event: conflict_detected
data: {"description": "低盐饮食建议与呋塞米存在潜在矛盾", "severity": "medium"}

event: complete
data: {"final_answer": "...", "sources": [...], "conflicts": [...]}
─────────────────────────────────────────────
```

事件序列让前端可以渐进式渲染——先展示检索进度，再逐字渲染答案，最后展示冲突提示。

## Part B：评估升级——从单管道到多域平台

### MVP 评估 vs 平台评估

基础评估体系（6 引擎 + 7 指标 + 6 层诊断 + 调优闭环）的完整架构见 05-rag-evaluation.md。本章聚焦"相对于 MVP，平台新增了什么"。

| 维度 | MVP 评估 | 平台评估 | 增量价值 |
|------|---------|---------|---------|
| 评估范围 | 单知识库、单管道 | 多知识库、多域 | 可以评估跨域聚合效果 |
| 指标数量 | 7 项（L1 4项 + L2 3项） | 11 项（+ 跨域 4 项） | 从"检索+生成"扩展到"路由+融合+冲突检测" |
| 诊断深度 | 6 层诊断，不指向具体节点 | 指向具体节点和参数 | 从"Recall 低"到"BM25 节点 top_k=10 导致 Recall 低" |
| 调优方式 | 手动调参 | 一键采纳 + 配置版本管理 | 从"看懂报告"到"点击采纳" |
| 权限感知 | 无 | 按角色评估——不同角色看到的结果不同 | 评估反映真实场景 |

### 跨域扩展指标——4 项新指标详解

#### 跨域指标 1：域激活准确率（Domain Activation Precision）

**公式**：`DAP = 正确激活的域数 / 实际激活的域总数`

**通俗解释**：激活的域中有多少是真正相关的？（激活的对不对？）

```
查询："高血压合并糖尿病如何用药"
查询分析节点激活了 4 个域：
  ├── 心血管域 ✓（相关——高血压涉及）
  ├── 内分泌域 ✓（相关——糖尿病涉及）
  ├── 药学域   ✓（相关——用药涉及）
  └── 神经域   ✗（误激活——查询中未提及神经系统）

DAP = 3/4 = 0.75（25% 的域不该激活）
```

**盲区**：只关心激活的对不对，不关心该激活的是否被遗漏（那是跨域覆盖率的职责）。

#### 跨域指标 2：跨域覆盖率（Domain Coverage）

**公式**：`DC = 被激活的相关域数 / 应该被激活的总相关域数`

**通俗解释**：所有应该激活的域中，有多少被成功激活了？（有没有漏掉？）

```
查询："高血压合并糖尿病如何用药"
应该激活：心血管 + 内分泌 + 药学 = 3 个
实际激活：心血管 + 内分泌 = 2 个

DC = 2/3 = 0.67 → 漏掉了药学域，答案不完整
```

**与 DAP 的矛盾**：想提高 DAP → 只激活最确定的域 → DC 下降（遗漏增多）。想提高 DC → 降低激活门槛 → DAP 下降（噪音增多）。两者需平衡。

#### 跨域指标 3：冲突检测率（Conflict Detection Rate）

**公式**：`CDR = 正确检测到的跨域矛盾数 / 实际存在的跨域矛盾总数`

**通俗解释**：跨域的矛盾信息有多少被成功发现了？

```
实际存在 3 个矛盾：
  ├── 矛盾 1：低盐饮食 vs 某药需高盐 → 检测到 ✓
  ├── 矛盾 2：避免剧烈运动 vs 建议适量运动 → 检测到 ✓
  └── 矛盾 3：控制碳水 vs 某药需搭配碳水 → 未检测到 ✗

CDR = 2/3 = 0.67
```

**关键权衡**：误报（标记不矛盾的内容为矛盾）的代价 < 漏检（真矛盾未被发现）的代价。因为误报只会让用户多确认一次，而漏检可能导致用户按矛盾建议行动。

#### 跨域指标 4：端到端延迟（End-to-End Latency）

**公式**：

```
端到端延迟 = 查询分析 + max(各域管道并行延迟) + 跨域融合 + 冲突检测 + 答案合成
```

**计算实例**：

```
查询分析：        50ms
域管道（并行）：   心血管 180ms, 内分泌 160ms, 药学 200ms → max = 200ms
跨域融合：        30ms
冲突检测：        100ms（调 LLM 检测矛盾）
答案合成：        500ms（LLM 生成答案）
────────────────────────────────
端到端延迟 = 50 + 200 + 30 + 100 + 500 = 880ms
```

**优化线索**：答案合成占 57%——最大优化空间（换更快模型/减少 max_tokens）。域管道占 23%——启用缓存减少。冲突检测占 11%——仅在多域且有潜在矛盾的场景启用。

### 11 项指标全景权重表

| 层次 | 指标 | 层内权重 | 在 Overall 中的占比 | 目的 |
|------|------|---------|------------------|------|
| L1 检索 | Precision@K | 25% | 10% | 评估检索精准度 |
| L1 检索 | Recall | 25% | 10% | 评估检索覆盖面 |
| L1 检索 | MRR | 25% | 10% | 评估排序质量（第一个对的在哪） |
| L1 检索 | NDCG@K | 25% | 10% | 评估排序质量（所有对的位置） |
| L2 生成 | Faithfulness | 40% | 24% | 幻觉检测——最高权重，最高风险 |
| L2 生成 | AnswerRelevancy | 30% | 18% | 答非所问检测 |
| L2 生成 | Groundedness | 30% | 18% | 整体论点可信度 |
| **跨域** | 域激活准确率 | — | 独立呈现 | 域路由是否精准（不混入 L1/L2） |
| **跨域** | 跨域覆盖率 | — | 独立呈现 | 域路由是否完整 |
| **跨域** | 冲突检测率 | — | 独立呈现 | 跨域矛盾检测质量 |
| **跨域** | 端到端延迟 | — | 独立呈现 | 性能监控 |

**为什么跨域指标不混入 Overall Score**：跨域指标评估的是多域聚合的"路由和合成"质量，与 L1 检索、L2 生成是不同维度的独立问题。混在一起会掩盖具体哪个环节出问题——检索差？生成差？还是路由差？

### 评估结果指向具体节点——从现象到根因

MVP 的评估报告说「Recall=0.65，偏低」。平台评估报告说「BM25 检索节点的 top_k=10 导致 Recall 低，证据：增大到 20 后 Recall 提升到 0.75」。

```
评估报告（平台）：
─────────────────────────────────────────────
总体 Recall: 0.65（偏低，触发 Layer 1 规则引擎）

根因分析（Layer 3 LLM 诊断）：

  ├── BM25 检索节点 (node_id: bm25_main)
  │   ├── 当前参数：top_k=10
  │   ├── 问题：top_k 太小，遗漏了 5 个相关文档
  │   ├── 证据：top_k=10 时 RR 召回排名中，相关文档平均排在第 13 位
  │   │         → 它们存在但被 top_k=10 截断了
  │   └── 建议：增大 top_k 到 20（预期 Recall +10%）

  ├── 向量检索节点 (node_id: vector_main)
  │   ├── 当前参数：similarity_threshold=0.8
  │   ├── 问题：阈值太高，过滤了语义相关但分数稍低的文档
  │   ├── 证据：在 0.7-0.8 区间有 3 个相关文档被过滤
  │   └── 建议：降低阈值到 0.7（预期 Recall +8%）

  └── 重排序节点 (node_id: reranker_01)
      ├── 状态：未启用
      ├── 问题：没有精细排序，排序质量依赖初始检索的原始分数
      ├── 证据：启用重排序后，Precision@5 提升 8%
      └── 建议：启用重排序（预期 Precision +5%）

一键采纳 → 自动应用全部 3 条建议 → 保存为管道 v2
```

### 调优闭环完整链路

```
配置管道 v1
    │
    ▼
运行评估（100 用例）
    ├── 总体 78/100
    ├── Recall 0.65（偏低）
    └── MRR 0.81（良好）
    │
    ▼
Layer 1-6 诊断分析
    ├── 根因 1：BM25 top_k=10 太小
    ├── 根因 2：向量 threshold=0.8 太高
    └── 根因 3：未启用重排序
    │
    ▼
TuningEngine 生成 3 条建议 + 冲突检测（无冲突）
    │
    ▼
一键采纳 → 自动修改配置 → 保存为管道 v2
    │
    ▼
再次评估（100 用例）
    ├── 总体 85/100（+7分 ✓）
    ├── Recall 0.75（+15% ✓）
    ├── Precision 0.71（-1%，< 5% 退化阈值 ✓）
    └── 延迟 130ms（+10ms，< 20% 退化阈值 ✓）
    │
    ▼
Layer 5 效果校验：所有建议效果达到预期
Layer 6 回归校验：无指标退化为不可接受水平
    │
    ▼
发布 v2（URL 不变，内部切换到 v2）
```

### 一键采纳后的冲突检测与版本管理

多条调优建议可能相互冲突：

- 建议 1：增大 BM25 top_k 到 20 → Recall +10%，预期延迟 +20ms
- 建议 2：降低向量 threshold 到 0.6 → Recall +15%，预期噪音 +30%
- 建议 3：启用重排序 → Precision +8%，预期延迟 +50ms

TuningEngine 检测到：三条建议都在提升 Recall，但累计延迟 +70ms（可能超过退化阈值）。标记冲突，要求人工决策。

**版本保护**：一键采纳前自动保存当前配置为版本快照。采纳后的配置作为新版本。如效果退化 → 一键回滚到上一版本（配置回滚 + 检索器自动 reload）。

## 关键设计点

| 设计点 | 为什么 |
|--------|--------|
| 发布为 URL | 调用方不感知管道内部结构——管道变更对调用方透明 |
| 三种搜索方式 | 生产（URL）、测试（通用端点）、体验（SSE）各有场景 |
| 权限全局强制 | 同一 URL 不同角色不同结果——JWT 自动提取，不可绕过 |
| 跨域指标独立呈现 | 不混入 L1/L2——保持不同维度评估的清晰性 |
| 评估指向节点 | 从"某指标差"到"某节点的某参数"--调优可操作 |
| 一键采纳 | 消除"看懂报告"到"执行调优"之间的手动断层 |
| 回归校验 | 调优 A 指标前先检查 B 指标是否退化——上线前的安全网 |

## 一句话总结

> **管道发布 = 配置完成的管道暴露为 URL，调用方只发查询不收内部细节，权限全局强制。评估升级 = 跨域 4 项指标 + 评估指向具体节点 + 一键采纳 + 版本回滚，从"知道差"到"一键改好"。**
