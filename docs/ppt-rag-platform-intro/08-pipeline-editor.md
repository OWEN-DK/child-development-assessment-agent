# 08 · 可视化管道编辑器——如何让客户自助配置检索策略？

> 目标受众：懂技术的产品经理
> 核心问题：不同客户需要不同的检索策略——医学客户需要精确术语匹配，教育客户需要强语义理解，法律客户需要敏感词过滤。每接一个客户就改一次代码是不可持续的。怎么让客户自己配置，而不是让开发替客户改代码？

---

## 核心问题

在 MVP 中，检索管道是硬编码的——节点的类型、顺序、参数都写在 Python 代码中。客户想调整 BM25 权重？改代码。想加个重排序节点？改代码。想换 Embedding 模型？改代码。

接一个客户 = 改一次代码。接 10 个客户 = 10 套不同的代码分支？不可行。

**解决方案**：可视化管道编辑器——客户管理员像搭积木一样拖拽节点、连线、调参，保存为 JSON 配置。后端 PipelineCompiler 读取 JSON，编译为可执行的管道 DAG。全程不改一行代码。

**核心理念**：所有节点都是可选的，不拖入即跳过。每个节点的每个参数在属性面板中可调。配置完成 → 评估效果 → 一键发布 → 外部系统调用。

---

## 一、硬编码 vs 可视化——四个维度的对比

| 维度 | 硬编码方式（MVP） | 可视化方式（平台） |
|------|----------------|----------------|
| **新客户接入** | 开发改代码 → 测试 → 部署（3-5 天） | 客户管理员拖拽配置（30 分钟） |
| **策略调整** | 提需求 → 排期 → 开发 → 发布（1-2 周） | 改参数即时生效 |
| **实验对比** | 改代码 → 部署两套 → 对比（复杂） | 管道版本管理 → 一键对比评估结果 |
| **操作门槛** | 需要开发人员 | 产品经理/客户管理员即可 |

**可视化管道编辑器的本质**：将"开发改代码"变成"客户改配置"。平台的核心价值不是提供了多少种节点，而是**让客户拥有自主配置能力**。

## 三、28 种节点分类体系

为什么分 5 类？每类解决管道执行的不同层次问题：

```
查询理解（7 种）  →  理解用户真正想问什么（查询进入管道的第一道处理）
    │
    ▼
检索策略（5 种）  →  决定如何搜索文档（管道的核心——检索）
    │
    ├── 同时进行 ──→  安全合规（3 种）→ 保护敏感信息（检索时并行过滤）
    │
    ▼
质量增强（4 种）  →  提升检索和生成质量（检索后的精细化处理）
    │
    ▼
性能优化（2 种）  →  提升响应速度和系统稳定性（贯穿全管道的横切关注点）

答案合成（1 种）  →  格式化最终输出
```

加上聚合层的 6 种跨域协调节点（详见 07-multi-domain-kb-permission），共 28 种（22 种域内 + 6 种聚合）。

## 四、节点详解

> **约定的阅读方式**：每个节点包含——解决什么问题 / 核心逻辑 / 可配置参数及调优后果 / 适用场景 / 反模式（什么时候不该用）/ 与其他节点的交互。

> **关于检索参数**：BM25 的 k1/b、向量的 similarity_threshold/metric、RRF 的 k 值等检索参数的完整原理推导见 04-hybrid-search.md。本节的检索策略类节点仅列出参数项和交互效应，不重复原理。

### 4.1 查询理解类（7 种）

#### 节点 1：查询改写（Query Rewrite）

**解决什么**：用户输入可能口语化、不规范。改写为更适合检索的专业表述。

```
用户输入："孩子平衡不好咋办"
查询改写："3岁儿童前庭觉平衡能力训练方法与干预策略"
```

**可配参数**：

| 参数 | 默认值 | 含义 | 调高后果 | 调低后果 |
|------|--------|------|---------|---------|
| model | qwen-plus | 用于改写的 LLM | 改写质量更好，但延迟和成本增加 | 改写可能不够好 |
| prompt_template | 内置模板 | 改写的提示词 | — | — |
| max_retries | 3 | 改写失败重试次数 | 花费更多时间恢复临时错误 | 网络波动可能导致改写失败 |

**适用场景**：用户使用日常语言、口语化表述的场景（如科普教育检索）。

**反模式**：用户已经在使用专业术语（如医生直接搜"前庭觉障碍诊断标准"）——查询改写可能把精确术语"翻译"成泛化表述，反而降低精确度。

**与其他节点的交互**：通常放在查询理解流水线的第一个位置。改写后触发同义词扩展和术语标准化。

---

#### 节点 2：同义词扩展（Synonym Expansion）

**解决什么**：用户的表述与文档的表述不同。用同义词扩展查询词，提升召回率。

**可配参数**：

| 参数 | 默认值 | 含义 |
|------|--------|------|
| synonym_source | 内置+域专用+自定义 | 同义词库来源 |
| max_synonyms | 5 | 每个词最大扩展数 |
| expansion_mode | 全量扩展 | 全量 / 仅名词 / 仅关键术语 |

**expansion_mode 的选择指南**：

| 模式 | 何时用 | 风险 |
|------|--------|------|
| 全量扩展 | 短查询（3-5 词），表述多样的科普场景 | 可能引入噪音（"训练"→"培训"→ 返回员工培训手册） |
| 仅名词扩展 | 查询中有大量动词/形容词 | 可能漏掉专业的动词/形容词术语 |
| 仅关键术语扩展 | 查询中已有专业术语，只需扩展核心概念 | 日常用语不被扩展 |

**适用场景**：用户的用词习惯与知识库的术语体系有差异的场景（几乎所有 RAG 场景都需要）。

**反模式**：知识库的文档用词与用户查询用词完全一致时——同义词扩展只会增加噪音。但在实践中这种情况极少。

**与其他节点的交互**：通常在查询改写之后、术语标准化之前。

---

#### 节点 3：查询分解（Query Decomposition）

**解决什么**：复杂查询包含多个独立子问题。一次性检索效果差——因为每个子问题的相关文档不同。

```
输入："前庭觉训练和本体觉训练有什么区别，各自的方法是什么"

拆解为：
├── 子查询 1："前庭觉训练方法"
├── 子查询 2："本体觉训练方法"
└── 子查询 3："前庭觉和本体觉训练的区别"
```

每个子查询独立检索，最后合并结果。

**可配参数**：

| 参数 | 默认值 | 含义 |
|------|--------|------|
| model | qwen-plus | 分解用的 LLM |
| max_subqueries | 5 | 最大子查询数 |
| decomposition_strategy | auto | 按并列关系 / 按层级关系 / 自动判断 |

**decomposition_strategy 选择指南**：

| 策略 | 何时用 | 举例 |
|------|--------|------|
| 按并列关系 | 查询包含"和""与""以及"连接的独立问题 | "XX、YY 和 ZZ 的方法是什么" |
| 按层级关系 | 查询有嵌套结构——先问大类再问子类 | "感统训练有哪些类型，其中前庭觉训练的具体方法是什么" |
| 自动判断（auto） | 不确定查询的结构 | LLM 自行判断 |

**适用场景**：查询明显包含多个独立子问题。

**反模式**：简单查询不需要分解——「前庭觉训练方法」只是一个问题，分解不会改善效果且增加延迟和成本。

**与其他节点的交互**：分解后的每个子查询各自走完整的后续流水线（同义词扩展→混合检索→重排序→...），结果在节点内部合并。

---

#### 节点 4：术语标准化（Term Standardization）

**解决什么**：同一个概念有多种表述。将用户表述统一为标准术语——「血压高」→「高血压」、「肾衰」→「肾功能衰竭」。

**两种标准化模式**：

| 模式 | 做法 | 速度 | 覆盖面 | 何时用 |
|------|------|------|--------|--------|
| 精确匹配（查表） | 在术语映射表中查找 → 替换 | 快（< 1ms） | 仅覆盖表中已有的映射 | 领域术语明确且稳定 |
| LLM 动态标准化 | LLM 判断是否需要标准化 → 标准化 | 慢（~100ms） | 覆盖未在表中的新术语 | 领域术语多变或客户频繁更新 |
| 两者（默认） | 先查表，未命中再用 LLM | 兼顾 | 全覆盖 | 绝大多数场景 |

**适用场景**：领域内有明确的术语标准，但用户日常表述多样的场景（医疗、法律、金融等所有专业领域）。

**反模式**：创意写作场景——术语标准化会把作者独特的表达风格统一掉。

---

#### 节点 5：意图分类（Intent Classification）

**解决什么**：不同意图的查询需要不同的处理路径——知识查询走 RAG 检索，服务请求走业务系统。

```
查询"前庭觉训练方法" → 意图"知识查询" → 走检索管道
查询"预约下周的评估" → 意图"服务请求" → 走业务系统
查询"上次评估的结果" → 意图"历史记录查询" → 走数据库查询
```

**可配参数**：

| 参数 | 默认值 | 含义 |
|------|--------|------|
| model | qwen-plus | 分类用的 LLM |
| categories | 客户自定义 | 分类体系（可增删） |
| routing_rules | 每类对应路由 | 各类别的处理路径 |

**适用场景**：系统的使用场景不止一种（知识查询 + 服务请求 + 历史查询）。

**反模式**：系统只做知识检索一种事——意图分类的额外延迟和成本没有对应价值。

---

#### 节点 6：禁用词过滤（Stop Word Filtering）

**解决什么**：查询中的无意义词（"请问一下""的""有哪些"）会干扰检索——这些词几乎所有文档都有，不能区分相关性。

```
输入："请问一下前庭觉训练的方法有哪些"
过滤后："前庭觉 训练 方法"
```

**可配参数**：

| 参数 | 默认值 | 含义 |
|------|--------|------|
| stop_words | 内置常用词表 | 禁用词列表（支持在线编辑/导入/正则） |
| enabled | true | 是否启用 |
| case_sensitive | false | 是否区分大小写 |

**适用场景**：用户输入包含大量口语化填充词的场景。

**反模式**：过度过滤——把有检索价值的短词也过滤掉了。例如在医学场景中"心""肺""肝"等单字可能是关键术语，不应被过滤。

---

#### 节点 7：查询扩展（Query Expansion）

**解决什么**：单一查询可能遗漏相关文档。生成多个扩展查询，从不同角度检索，合并结果。

```
输入："前庭觉训练方法"
扩展：
├── 改写版："3岁儿童前庭觉训练指南"
├── 限定版："前庭觉训练 安全注意事项"
└── 换角度："如何在家做前庭觉训练"
```

**与同义词扩展的区别**：同义词扩展是词级别的替换，查询扩展是句子级别的生成——改变查询的结构和角度，而不只是替换词。

**可配参数**：

| 参数 | 默认值 | 含义 |
|------|--------|------|
| model | qwen-plus | 扩展用的 LLM |
| expansion_count | 3 | 生成的扩展查询数 |
| expansion_method | 多选 | 改写/加限定/换角度 |

**适用场景**：查询较短（3-5 词），单次检索可能覆盖面不足。

**反模式**：查询已经很长且具体（50+ 字）——扩展可能偏离原意。

### 4.2 检索策略类（5 种）

> 以下节点的参数原理（BM25 k1/b、向量 similarity_threshold/metric、RRF k 值）的完整公式推导和调优指南见 04-hybrid-search.md。

#### 节点 8：BM25 检索（关键词匹配）

**解决什么**：精确匹配包含查询词的文档。

**可配参数**：

| 参数 | 默认值 | 调高后果 | 调低后果 |
|------|--------|---------|---------|
| top_k | 10 | 召回↑，延迟↑ | 延迟↓，可能遗漏 |
| k1 | 1.5 | 高频词文档更占优 | 词频影响更平缓 |
| b | 0.75 | 长文档更受压制 | 长文档更有优势 |
| 字段权重 | title:2.0, body:1.0 | — | — |
| score_threshold | 0 | 精确↑，召回↓ | 噪音↑ |

**适用场景**：精确术语匹配重要的场景——医疗诊断标准、法律条文。

**反模式**：用户使用日常语言提问（非术语）→ BM25 找不到任何匹配。

**与其他节点的交互**：BM25 的 top_k 和向量检索的 top_k 联合决定了 RRF 融合的候选数量。两者差距过大（如 BM25 top_k=5, 向量 top_k=50）会导致 RRF 融合向向量端严重倾斜。（详见 04-hybrid-search 参数交互效应）

---

#### 节点 9：向量检索（语义相似度）

**解决什么**：基于语义相似度检索，找到"意思相近但不一定包含相同词"的文档。

**可配参数**：

| 参数 | 默认值 | 调高后果 | 调低后果 |
|------|--------|---------|---------|
| embedding_model | DashScope v4 | — | — |
| top_k | 10 | 召回↑，延迟↑ | 延迟↓，可能遗漏 |
| similarity_threshold | 0.7 | 精确↑，召回↓ | 召回↑，噪音↑ |
| similarity_metric | cosine | — | — |
| collection_name | 对应知识库 | — | — |

**适用场景**：用户使用日常语言、表述多样的场景。

**反模式**：需要精确术语匹配的场景（法条引用）——向量检索可能返回"语义相似但不精确"的文档。

---

#### 节点 10：混合检索（BM25 + 向量 + RRF）

**解决什么**：同时执行 BM25 和向量检索，用 RRF 融合两者的结果。兼顾精确和覆盖面。

**可配参数**：

| 参数 | 默认值 | 调高后果 | 调低后果 |
|------|--------|---------|---------|
| vector_weight | 0.6 | 语义理解更重要 | BM25 精确匹配更重要 |
| keyword_weight | 0.4 | BM25 精确匹配更重要 | 语义理解更重要 |
| top_k | 10 | — | — |
| fusion_method | RRF | 见 04-hybrid-search RRF k 值 | — |
| rrf_k | 60 | 排名贡献趋于匀化 | 排名靠前者碾压胜出 |

**适用场景**：几乎所有 RAG 场景——这是默认推荐的主检索节点。

**反模式**：知识库极小时（< 100 篇文档）→ 单一检索足够，混合检索的开销不值得。

---

#### 节点 11：多模态检索（文本 + 图片 + 表格）

**解决什么**：有些文档包含图片（扫描版 PDF 的图片、插图）和表格——纯文本检索会漏掉这些内容。

**可配参数**：各模态的权重分配和 top_k。

**适用场景**：知识库包含图表、扫描版文献的场景。在医学和法律领域尤为常见（医学影像、法条表格）。

---

#### 节点 12：结果融合（多路检索结果合并）

**解决什么**：当管道中有多路独立的检索分支时（如同时使用 BM25、向量检索、多模态检索三路），需要融合它们的结果。

**与混合检索节点的区别**：混合检索节点是内置的 BM25+向量两路融合。结果融合节点是更通用的多路融合——可以接入任意数量的检索分支。

---

### 4.3 安全合规类（3 种）

#### 节点 13：敏感词过滤

**解决什么**：过滤包含敏感词的文档或查询。

**可配参数**：

| 参数 | 默认值 | 含义 |
|------|--------|------|
| word_list | 内置列表 | 敏感词列表（支持在线编辑/导入/正则） |
| filter_mode | 删除 | 删除（移除文档）/ 脱敏（替换为 ***）/ 标记（仅标记） |
| apply_to | 两者 | 应用于查询文本 / 检索结果 / 两者 |

**适用场景**：内容合规要求严格的行业——医疗、金融、政府。

**反模式**：敏感词列表过大 → 过滤掉大量实际上不敏感的文档 → 召回率严重下降。

---

#### 节点 14：PII 脱敏（个人信息隐藏）

**解决什么**：隐藏个人信息——手机号、身份证、姓名、地址等。

**可配参数**：

| 参数 | 默认值 | 含义 |
|------|--------|------|
| target_types | [手机号, 身份证, 姓名, 邮箱, 地址, 银行卡] | 脱敏目标（可多选） |
| mask_char | * | 替换字符 |
| preserve_pattern | 按类型预设 | 保留格式（如手机号前 3 后 4 → 138****1234） |

**保留格式的含义**：不是把所有字符都替换成 *，而是保留部分信息以保持数据可读性——`138****1234` 比 `***********` 对用户更有意义。

**适用场景**：检索结果可能包含患者/客户个人信息的场景。

---

#### 节点 15：内容审核

**解决什么**：审核查询和文档内容是否合规——色情、暴力、政治敏感等。

**可配参数**：

| 参数 | 默认值 | 含义 |
|------|--------|------|
| model | qwen-plus | 审核 LLM（可设为 none 走纯规则模式） |
| audit_rules | 多选 | 色情/暴力/政治/违法/歧视/广告 |
| action | 过滤文档 | 命中后：过滤文档 / 标记警告 / 直接拒绝查询 |
| threshold | 0.7 | 审核敏感度（0-1，越高越严格） |

**threshold 的权衡**：
- 过高（> 0.9）→ 大量正常内容被误标 → 用户体验差
- 过低（< 0.5）→ 违规内容漏过 → 合规风险
- 默认 0.7 是平衡点

---

### 4.4 质量增强类（4 种）

#### 节点 16：重排序（Reranking）

**解决什么**：初始检索速度快但精度有限。用更精细的 Reranker 模型对候选结果重新排序。

**必要性**：初始检索（BM25/向量）需要在秒级内从海量文档中找到候选。Reranker 模型更精细但更慢——只对前 initial_k 个候选重排。两阶段检索策略（粗排→精排）是业界标准。

**可配参数**：

| 参数 | 默认值 | 含义 | 调高后果 | 调低后果 |
|------|--------|------|---------|---------|
| model | bge-reranker-v2-m3 | 重排序模型 | — | — |
| initial_k | 50 | 送入重排的候选数 | 重排更全面但延迟↑ | 重排更快但可能遗漏 |
| final_k | 10 | 输出保留数 | 返回更多但可能含噪音 | 返回更精准但可能遗漏 |

**initial_k vs final_k 的权衡**：initial_k 决定了"重排的候选池"有多大——池子越大，好的文档进入重排的概率越高，但重排耗时越长。final_k 决定最终返回给下游节点的结果数。

**适用场景**：大多数场景建议启用。只有在延迟要求极严格（< 200ms）且初始检索精度足够时可以考虑跳过。

**与其他节点的交互**：通常放在检索节点之后、答案生成之前。initial_k 受到前面检索节点 top_k 的总和制约。

---

#### 节点 17：去重（Deduplication）

**解决什么**：多路检索可能返回高度相似或完全相同的结果。

**两种去重方法**：

| 方法 | 原理 | 速度 | 准确度 | 何时用 |
|------|------|------|--------|--------|
| MinHash | 文本指纹 | 快 | 对近似重复敏感，对改写不敏感 | 默认选择 |
| Embedding | 向量相似度 | 慢 | 对改写也敏感 | 需要检测"同义改写"时 |

**可配参数**：去重方法、threshold（默认 0.85）、去重范围（域内/跨文档/两者）。

**MinHash 的完整原理**：见 04-hybrid-search.md MinHash 章节。

---

#### 节点 18：幻觉检测（Hallucination Detection）

**解决什么**：LLM 生成的答案可能包含上下文无法支撑的内容。

**检测原理**：将 LLM 答案拆解为独立声明 → 对每个声明检查能否从上下文中找到依据 → 标记无依据的声明。

**可配参数**：

| 参数 | 默认值 | 含义 |
|------|--------|------|
| model | qwen-plus | 检测 LLM |
| threshold | 0.7 | Faithfulness 低于此值触发告警 |
| action | 标记 | 过滤（移除幻觉答案）/ 标记（标记"可能含幻觉"）/ 两者 |

**适用场景**：高风险领域——医疗诊断、法律建议、金融分析。

**反模式**：低风险场景（如娱乐问答）——幻觉检测的额外延迟和成本不值得。

---

#### 节点 19：引用验证（Citation Verification）

**解决什么**：验证 LLM 答案中的引用是否准确——引用的文档片段实际存在且内容一致。

**两种验证模式**：

| 模式 | 做法 | 何时用 |
|------|------|--------|
| strict | 验证每句声明的引用 | 学术/医学——每个说法都要有出处 |
| lax | 仅验证关键论点的引用 | 一般知识问答——大体正确即可 |

---

### 4.5 性能优化类（2 种）

#### 节点 20：语义缓存（Semantic Cache）

**解决什么**：相似查询反复检索浪费算力。缓存相似查询的结果，语义相似度 > threshold 命中时直接返回缓存。

```
用户 A 问："前庭觉训练方法" → 检索（500ms）→ 缓存
用户 B 问："前庭觉怎么训练" → 语义相似度 0.92 → 命中缓存 → 直接返回（10ms）
```

**可配参数**：

| 参数 | 默认值 | 含义 |
|------|--------|------|
| cache_backend | Redis | 缓存后端 |
| similarity_threshold | 0.95 | 命中阈值（0-1） |
| ttl | 3600 秒 | 缓存过期时间 |
| cache_key_strategy | 语义相似匹配 | 精确匹配 / 语义相似匹配 |
| cache_key_scope | 包含角色信息 | 防止不同权限用户互相污染缓存 |

**缓存键设计的关键——防止跨角色污染**：

```
错误设计：cache_key = hash(query)
  用户 A（管理员）搜"高血压用药" → 缓存答案（含药学库的所有信息）
  用户 B（实习生）搜"高血压用药" → 命中缓存 → 获得管理员才能看到的信息 → 信息泄漏！

正确设计：cache_key = hash(query + role + tenant_id)
  用户 A（管理员）→ 缓存
  用户 B（实习生）→ 不同缓存键 → 不会命中 A 的缓存 → 安全
```

**适用场景**：查询量大、重复/相似查询多的场景。典型的 FAQ 场景中缓存命中率可达 40-60%。

**反模式**：知识库频繁更新的场景——缓存可能返回过时结果，TTL 需调短，缓存价值降低。

---

#### 节点 21：速率限制（Rate Limiting）

**解决什么**：限制请求频率，防止系统过载或被单一客户端压垮。

**三种限流算法**：

| 算法 | 做法 | 是否允许突发 | 何时用 |
|------|------|------------|--------|
| 滑动窗口 | 统计最近 N 秒内的请求数 | 否——超过 qps 就拒绝 | 简单场景 |
| 令牌桶 | 以固定速率生成令牌，请求消耗令牌。桶有上限 | 是——可以消耗积累的令牌处理突发 | 允许正常业务突发的场景 |
| 漏桶 | 请求入桶，以固定速率处理。桶满则溢出 | 否——流量被强制平滑 | 需要严格平滑流量的场景 |

**可配参数**：max_qps、算法、限流范围（按域/管道/用户）、超限行为（排队等待/直接拒绝 429/降级返回缓存）。

**适用场景**：所有生产环境。不限流的 API 在流量高峰时会被压垮。

---

### 4.6 答案合成类（1 种）

#### 节点 22：结构化输出（Structured Output）

**解决什么**：将 LLM 生成的自然语言答案格式化为指定结构（JSON/Table/Markdown），便于外部系统解析。

```
自然语言："游泳可改善前庭觉，建议每周3次，每次30分钟"

结构化输出（JSON）：
{
  "activity": "游泳",
  "effect": "改善前庭觉",
  "frequency": "每周3次",
  "duration": "每次30分钟",
  "source": "前庭觉训练指南"
}
```

**可配参数**：

| 参数 | 默认值 | 含义 |
|------|--------|------|
| output_format | Markdown | JSON / Table / Markdown / 自定义 Schema |
| schema_definition | — | 自定义输出结构定义（JSON Schema） |
| model | qwen-plus | LLM 模型 |
| strict_mode | true | 严格校验（失败重试）/ 宽松容错（失败降级为自然语言） |

### 4.7 聚合层节点（6 种）

这 6 个节点负责跨域协调。完整运作机制和权限注入点见 07-multi-domain-kb-permission。此处摘要：

| 节点 | 做什么 | 关键触发条件 |
|------|--------|------------|
| 查询分析 | 识别涉及的业务域 | 规则匹配 + LLM 分析两阶段 |
| 域分发 | 并行分发到各域管道 + 注入权限 | 根据 JWT 角色裁剪不可见域 |
| 跨域融合 | 加权 RRF 融合多域结果 | 每个域的权重由管道配置决定 |
| 跨域去重 | MinHash 跨域检测重复 | 同文档可能被多个域引用 |
| 冲突检测 | LLM 检测跨域矛盾 | 逐对检查域间是否存在矛盾表述 |
| 统一答案合成 | 综合多域结果 + 标注来源 + 冲突提示 | 单域查询跳过此节点 |

## 五、条件路由——根据运行结果动态选路

条件路由让管道不再是一条固定的线性流水线，而是一棵根据实时条件分支的执行树。

```
                    ┌──────────┐
                    │ 语义缓存  │
                    └────┬─────┘
                         │
              ┌──────────┴──────────┐
              │ 缓存命中？           │
              ├─────────────────────┤
              ▼ YES                 ▼ NO
        ┌──────────┐         ┌──────────┐
        │ 答案合成  │         │ 意图分类  │
        └──────────┘         └────┬─────┘
                                 │
                    ┌────────────┴────────────┐
                    │ 意图 = "知识查询"？      │
                    ├─────────────────────────┤
                    ▼ YES                     ▼ NO
            ┌──────────┐               ┌──────────┐
            │ 混合检索  │               │ 业务路由  │
            └──────────┘               └──────────┘
```

### 四种路由条件

| 条件类型 | 触发逻辑 | 举例 |
|---------|---------|------|
| **缓存命中** | 语义缓存节点输出 hit=true | 跳过检索链，直接走答案合成 |
| **意图分类** | 分类结果决定路径 | "知识查询"→ 检索，"服务请求"→ 业务系统 |
| **用户角色** | JWT 中的角色决定可见域 | 管理员激活全域 → 普通医生跳过药学域 |
| **查询复杂度** | 单域 vs 多域 | 单域跳过聚合层 4 节点 |

## 六、降级路径——节点失败时怎么办

管道中的任意节点都可能失败——API 超时、配额耗尽、输入异常。降级路径定义失败时的备选方案。

### 逐节点降级策略

| 节点 | 失败时的降级 |
|------|------------|
| 查询改写 | 跳过改写，用原始查询继续 |
| 同义词扩展 | 跳过扩展，用原始查询词检索 |
| 混合检索 → BM25 | BM25 超时 → 只用向量检索 |
| 混合检索 → 向量 | 向量检索超时 → 只用 BM25 |
| 重排序 | 主 Reranker 失败 → 切换备选 Reranker → 跳过重排序 |
| 幻觉检测 | 失败 → 标记答案"幻觉检测不可用"而非丢弃答案 |
| 任何 LLM 调用 | 3 次重试后失败 → 任务标记失败，告知用户 |

### 全管道降级

当整个管道因异常而无法完成时（如检索全部超时），降级到语义缓存结果（如有）。如果缓存也没有，返回"服务暂时不可用"而非静默失败。

**降级设计原则**：尽可能返回部分结果（即使不完美），而不是返回空结果或报错。在医疗场景，宁可说"无法提供完整答案"也不要给出编造的答案。

## 七、复合节点——常用组合一键复用

某些节点组合是常用的最佳实践——如"术语标准化 + 混合检索 + 重排序"是标准医学检索组的标配。将这些组合封装为复合节点。

```
复合节点："标准医学检索组"
┌──────────────────────────┐
│  术语标准化 → 混合检索 → 重排序  │  ← 内部包含 3 个节点
└──────────────────────────┘

拖入管道后：
  → 展开态：显示内部 3 个节点，可独立调整参数
  → 折叠态：显示为一个节点块，方便画布管理
```

**价值**：降低配置门槛——新手不需要理解每个节点的作用，直接拖入"标准医学检索组"即可获得经过验证的最优配置。

### 预设复合节点库

平台内置以下经过验证的复合节点，客户管理员可以直接拖入管道使用：

| 复合节点 | 内部节点 | 适用场景 | 默认参数要点 |
|---------|---------|---------|------------|
| **标准医学检索组** | 术语标准化 → 混合检索 → 重排序 | 医学诊断、药学查询、临床指南检索 | BM25 权重 0.6，向量 threshold 0.75，术语标准化 = 精确匹配 + LLM 双模式 |
| **快速 FAQ 组** | 语义缓存 → 禁用词过滤 → 同义词扩展 → 向量检索 | 客服 FAQ、常见问题自助查询 | 缓存 TTL 3600s、缓存 threshold 0.95、向量 threshold 0.65（覆盖面优先） |
| **合规审查组** | 敏感词过滤 → PII 脱敏 → 内容审核 → 幻觉检测 → 引用验证 | 法律合规审查、合同审核、隐私数据检索 | 敏感词过滤 = 标记模式，PII 脱敏保留格式，幻觉检测 = 严格模式（citation strict） |
| **口语搜索桥接组** | 查询改写 → 同义词扩展（全量）→ 术语标准化 → 混合检索 | 用户用日常语言搜索，知识库为专业术语 | 向量权重 0.8（语义优先），查询改写启用，同义词扩展 = 全量扩展 |
| **极速问答组** | 语义缓存 → 禁用词过滤 → 向量检索 | 对延迟极敏感的场景（实时对话中的知识辅助） | 缓存 TTL 7200s，跳过重排序，向量 top_k=5，禁用 BM25（减少融合延迟） |

## 八、管道版本管理——快照 → 对比 → 回滚

每次保存管道配置时自动创建版本快照：

```
管道"综合问诊 v1" → 评估得分 78
    │ 调整 BM25 top_k 10→20
    ▼
管道"综合问诊 v2" → 评估得分 81 ✓
    │ 启用重排序
    ▼
管道"综合问诊 v3" → 评估得分 79 ✗（重排序引入了噪音）
    │ 一键回滚到 v2
    ▼
回滚到 v2（得分 81）
```

**版本对比**：选中两个版本，并列展示配置差异 + 评估结果差异 → 数据驱动决策。

## 九、编辑器与评估的集成

从编辑器画布可直接启动评估——选中管道版本 → 选择测试集 → 点击"评估"→ 系统后台运行 RunEngine + MetricEngine → 评估结果返回后，在画布节点上叠加指标：

```
┌──────────┐
│ 混合检索  │  Hit Rate: 0.72  ← 偏低
│          │  [评估详情 →]
└──────────┘
```

点击节点 → 跳转到该节点在评估报告中的详细分析 → 如在评估中发现该节点的 top_k=10 导致 Recall 低 → 建议 top_k=20 → 一键采纳 → 自动更新节点参数。

## 关键设计点

| 设计点 | 为什么 |
|--------|--------|
| 28 种节点全部可选 | 不拖入即跳过——不为不需要的功能付出延迟和算力 |
| 参数全部可调 | 同一节点不同场景需要不同参数（医学 vs 教育） |
| 条件路由 | 根据实时条件动态选路——缓存命中直接走答案 |
| 降级路径 | 单个节点失败不影响整体——降级而非崩溃 |
| 复合节点 | 降低配置门槛——新手可直接使用经过验证的组合 |
| 版本管理 | 数据驱动决策——版本对比 + 评估结果 → 科学选版 |
| 评估集成 | 编辑器 → 评估 → 一键采纳 → 闭环全程在 UI 内完成 |

## 不要这样做的典型反模式

1. **把所有节点都拖入管道** → 延迟叠加，一条简单查询经过 20 个节点 → 延迟 2 秒+
2. **所有场景用同一套参数** → 医学和教育的检索策略差异大，统一参数 = 两边都不最优
3. **忽略降级配置** → 一个 Reranker 挂了整个管道就挂了
4. **缓存键不含角色信息** → 不同权限用户互相污染缓存 = 信息泄漏

## 一句话总结

> **管道编辑器 = 28 种节点搭积木，条件路由动态选路，降级路径保可用，复合节点降门槛，版本管理可回滚，评估集成闭环。客户自主配置，不改代码。**
