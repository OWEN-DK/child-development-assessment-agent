## 1. 设计方向

### 1.1 设计概念: "Research Laboratory"

```
学术研究实验室的严谨 × 现代编辑工具的流畅 × 数据可视化的清晰
```

| 维度 | 选择 | 理由 |
|------|------|------|
| **风格** | Editorial / Research Dashboard | 知识审核是严肃学术工作，需要高信息密度但不压迫的界面 |
| **色调** | 暖灰底色 + 靛蓝主色 + 语义色点缀 | 长时间阅读不疲劳，颜色仅用于传达状态而非装饰 |
| **字体** | 宋体/衬线（正文MD） + 系统等宽（UI） | MD 正文用衬线体唤起"纸质学术出版"的信任感 |
| **空间** | 宽裕留白 + 严格网格 | 三栏编辑器需要清晰的信息分区 |
| **动效** | 仅在状态转换时使用（150-200ms ease-out） | 减少认知负荷，不抢内容焦点 |
| **差异化记忆点** | 左侧实体导航的"确认勾选"交互 + 图谱的冲突虚线动画 | 用户记住的不是颜色而是交互节奏 |

### 1.2 竞品参照

| 参照 | 借鉴点 |
|------|--------|
| **Notion** | 侧边栏导航、slash command 快速操作 |
| **Obsidian** | 双向链接展示、图谱可视化 |
| **Figma** | 左侧图层面板 ↔ 右侧属性面板的布局逻辑 |
| **Arxiv / PubMed** | 学术内容的排版节奏和信息密度 |

### 1.3 与现有知识库的关系：强前置约束

```
                      ┌─────────────────────┐
                      │   Step 1 (必须)       │
                      │   知识库上传 EPUB     │
                      │   /knowledge-base     │
                      │   → 分块 → Chroma    │
                      │   → 分配 kb_book_id  │
                      └──────────┬──────────┘
                                 │
                                 │  kb_book_id
                                 ▼
                      ┌─────────────────────┐
                      │   Step 2 (必须)       │
                      │   绑定页 BindBookPage │
                      │   /admin/curation     │
                      │   按 kb_book_id 绑定  │
                      │   重新读取 EPUB       │
│   按章节重新解析       │
                      └──────────┬──────────┘
                                 │
                                 ▼
                      ┌─────────────────────┐
                      │   Step 3 (自动)       │
                      │   AI 生成 → 审核     │
                      │   → Neo4j 入库       │
                      └─────────────────────┘
```

**硬约束**:

| # | 规则 |
|---|------|
| 1 | **知识库上传是唯一入口** — 书籍必须先上传到知识库并获得 `kb_book_id`，不存在"直接上传到策管"的路径 |
| 2 | **`kb_book_id` 是登记凭据** — 策管不依赖知识库的 chunks。绑定后重新读取原始 EPUB，独立做章节解析和 AI 生成。chunks 仅用于知识库的 RAG 检索，与策管无关 |
| 3 | **非 EPUB 不可策管** — PDF 等其他格式可以在知识库中使用，但绑定页会拒绝（结构化提取需要 EPUB 章节结构） |
| 4 | **知识库侧不变** — 策管不修改知识库中的 chunks/索引/元数据，仅读取 |
| 5 | **策管独立生命周期** — 绑定后，策管侧独立管理 draft/reviewed/published 状态，知识库侧的删除不影响已入库的 KG 节点（但会阻止重新生成） |

### 绑定后的行为

| 步骤 | 行为 |
|------|------|
| 1. 确认绑定 | 在策管系统中创建书籍记录，`source = "knowledge_base"`, `kb_id = "kb_001"` |
| 2. 章节解析 | 重新解析 EPUB 获取章节结构（不从 chunks 反推） |
| 3. AI 生成 | 从原始 EPUB 重新读取完整章节文本，每章独立调用 LLM |
| 4. 后续流程 | 与直接上传完全一致：审核 → 入库 → KG |

### 为什么需要重新解析 EPUB 但不重新分块

| 操作 | 理由 |
|------|------|
| **重新解析 EPUB** | 知识库的分块策略（语义分块）丢失了原始章节边界，AI 生成需要章节上下文 |
| **独立读取原始 EPUB** | 不依赖知识库的 chunks。策管从原始文件重新读取完整章节文本，保证 AI 看到的是完整的章节上下文 |
| **不重新写入知识库** | 策管流程不修改知识库，两者完全解耦 |

## 10. 无障碍与响应式

### 10.1 无障碍检查清单

| 检查项 | 实现方式 |
|--------|---------|
| 色板对比度 ≥ 4.5:1 | 所有文本/背景组合通过 WCAG AA |
| 键盘导航 | 所有交互元素支持 Tab / Enter / Escape |
| 焦点环可见 | 2px solid `var(--border-focus)`, offset 2px |
| 屏幕阅读器 | `aria-label` 在图标按钮，`aria-expanded` 在折叠面板 |
| 表单标签 | 所有 input 有可见 label 或 `aria-label` |
| 动态内容 | 进度更新用 `aria-live="polite"` |
| 减少动效 | `prefers-reduced-motion` 关闭动画 |

### 10.2 响应式断点

```
≥ 1440px: 标准桌面 — 三栏全宽
1024-1439px: 紧凑桌面 — 实体导航可折叠，信息面板可收起
768-1023px: 平板 — 单栏，侧边栏变抽屉
< 768px: 手机 — 仅支持查看 MD，不支持编辑（提示切换桌面端）
```
