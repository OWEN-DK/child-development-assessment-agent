## 1. 问题诊断

### 1.1 v1 方案的四个致命缺陷

| # | 缺陷 | 根因 | 后果 |
|---|------|------|------|
| 1 | **逐章独立提取，丢失跨章上下文** | 每个章节单独发给 LLM，LLM 不知道全书在讲什么 | 同一概念在不同章节被重复提取但无法关联；全书主旨、论证线索完全丢失 |
| 2 | **单 LLM 单次调用，信息必然遗漏** | 每章仅 1 次 LLM 调用，输出 token 有上限，注意力有衰减 | 案例细节、嵌套数据、引言等被跳过；输出越长丢失越多 |
| 3 | **输出 YAML 格式，人看不懂** | LLM 输出原始 YAML，不是给人看的 | 审核者无法判断提取质量；MD 草稿本身没有阅读价值 |
| 4 | **MD 中间产物成为瓶颈** | 图谱质量受制于 MD 解析质量，MD→图谱的转换环节是信息丢失的高风险区 | YAML 解析错误、格式变异、字段遗漏直接影响图谱完整性 |

### 1.2 信息丢失链路

```
v1: 书 → 章节 → 单次 LLM → YAML → 解析 → 图谱    (信息丢失 50-70%)
v2: 书 → 章节 → 14 次 LLM → MD → 解析 → 图谱      (改进但 MD 中间层仍是瓶颈)
D2G: 书 → 章节 → 3 次 LLM → Pydantic → 图谱        (直接到图，无中间损耗)
```

**结论**: 问题不在"调用几次"，而在**提取到图谱的路径长度**。路径越短，信息损耗越少。

## 2. 业内方案调研

| 方案 | 核心思路 | 对本项目的启示 |
|------|---------|--------------|
| **Microsoft GraphRAG** | chunk 提取实体→建图→社区检测→层级摘要 | 跨章关联通过图社区结构内生解决，不需要单独的"跨章综合"阶段 |
| **Instructor / 约束生成** | Pydantic schema 约束 LLM 输出，强制结构化 | 消除格式解析错误，输出 100% 可解析 |
| **Chunk-Grounded Extraction** | 每条提取标注 `[source: para_id]`，覆盖率 = 程序化检查未引用段落 | 用源段落引用追踪替代 LLM 判断覆盖率，零误差零额外成本 |
| **DSPy 程序化优化** | 把 LLM 流程抽象为可优化的程序，自动调优 prompt | 可测量、可迭代的提取质量 |
| **Hierarchical Map-Reduce** | 叶节点=段落提取→自底向上合并→根节点=全书 | 长章节分段处理的理论基础 |
| **LangChain `with_structured_output()`** | BaseChatModel 内置方法，通过 tool calling 实现 | 已有依赖，DashScope/qwen 原生支持，零成本引入 |

### 核心洞察

| v2 的假设 | 业内更好的做法 |
|-----------|--------------|
| "LLM 提取不可靠，需要双盲冗余" | **Schema 约束 + 源段落引用**让提取更可靠，不需要冗余 |
| "覆盖率需要 LLM 逐段判断" | **源段落引用追踪**让覆盖率变成程序化检查 |
| "8 个 Agent 各管一类" | **3 轮聚焦提取**每轮 task 明确、输入输出小 |
| "跨章综合需要单独 Phase" | **图社区检测**天然产生跨章关联 |
| "MD 是主要产物" | **图是真相源，MD 是图的视图** |

## 3. D2G 方案总览

### 3.1 核心设计原则

| 原则 | 说明 |
|------|------|
| **图优先** | 图是真相源，MD 仅作为审核视图从图反向生成（不是反过来） |
| **Schema 约束** | 用 Pydantic model 定义输出结构，LLM 通过 tool calling 强制按 schema 输出 |
| **源段落追踪** | 每条提取标注 `source_para_ids`，覆盖率 = 程序化检查未引用段落 |
| **3 轮聚焦提取** | 实体→关系→细节，每轮 task 明确、输入输出小、可独立优化 |
| **逐章审核** | 每章提取完生成审核 MD，审核通过后合入主图 |
| **程序化质量** | 图质量指标（孤立节点率、连通分量、段落覆盖率）全部程序化计算 |
| **零新依赖** | 完全在现有技术栈（LangChain + DashScope + NetworkX + Redis）内实现 |
| **幂等可重试** | 每个阶段的输出可持久化（Redis + 本地文件，详见 §14.1），失败后从断点恢复而非从头重跑；单章提取失败不阻塞其余章节；每个 Redis key 带 TTL（默认 7 天），避免残留数据堆积 |

### 3.2 五阶段流水线

```
书 (EPUB)
  │
  ▼
Phase 0: 全书深度阅读 ───────────────────────────────────────────────────
  输入: 全书原文（分段，每段 5 章）
  输出: BookContext（全书主旨、术语表、章节脉络）
  模型: qwen-turbo │ 调用: ~9-10 次（含自校验） │ token 预算: ~260K input + ~50K output
  │
  ▼
Phase 1: 逐章 3 轮聚焦提取 ─────────────────────────────────────────────
  输入: 章节原文 + 全书背景 + 已审核章节实体列表
  Round 1: 实体提取 → list[ExtractedEntity]
  Round 2: 关系提取 → list[ExtractedRelationship]
  Round 3: 细节提取 → ChapterDetails
  模型: qwen-turbo │ 调用: 3 次/章 │ 长章节: 3N+1 次（N=段数）
  │
  ▼
Phase 2: 逐章审核 + 增量入图 ───────────────────────────────────────────
  输入: 单章提取结果
  步骤: 生成审核 MD → 人工审核 → 实体消歧 → 合入主图
  模型: qwen-turbo（消歧） │ 调用: ~3 次/章
  │
  ▼
Phase 3: 全书图质量检查 ─────────────────────────────────────────────────
  输入: 完整主图
  步骤: 程序化指标计算 → 异常章节标记
  模型: 无（纯程序化） │ 调用: 0 次
  │
  ▼
Phase 4: 入库 Neo4j ─────────────────────────────────────────────────────
  输入: 完整主图
  步骤: 生成 Cypher → dry_run 预检 → 执行写入
  模型: 无 │ 调用: 0 次
```

### 3.3 与 v2 的关键差异

| 维度 | v2 方案 | D2G 方案 |
|------|---------|---------|
| 提取输出 | 自由文本 MD | **Pydantic 结构化数据** |
| 覆盖率验证 | LLM 逐段判断 | **程序化段落引用检查** |
| Agent 架构 | 8 个 Agent 并行分拣 | **3 轮聚焦提取** |
| 信息冗余 | 双盲（同一任务跑 2 次） | **Schema 约束**（单次即可） |
| 跨章关联 | 单独 Phase 2 LLM 综合 | **增量实体消歧**（embedding + LLM） |
| 真相源 | MD 文档 | **内存图（NetworkX）** |
| 审核产物 | MD 是提取目标 | **MD 是图的视图** |

### 4.3 提取结果数据结构

每条提取结果必须包含：

- **实体**: name, entity_type, description（≥20字）, source_para_ids
- **关系**: source, target, relation_type, evidence（原文引用）, source_para_ids
- **案例**: title, background, process, result, insight, related_entities, source_para_ids
- **数据**: metric, value, context, source_attribution, source_para_ids
- **引言**: text, speaker, context, source_para_ids

`source_para_ids` 是段落级引用，用于：
1. 程序化覆盖率检查（哪些段落没有被任何提取引用）
2. 审核时的来源追溯
3. 质量指标计算

### 4.4 主图模型

内存中的有向图（NetworkX DiGraph），每个节点包含：

```
节点属性:
  name: str              # 实体名称（主键）
  entity_type: str       # 实体类型
  description: str       # 描述（合并策略见下方说明）
  source_chapters: list  # 来源章节列表
  source_para_ids: dict  # {chapter_id: [para_ids]}

边属性:
  relation_type: str     # 关系类型
  evidence: str          # 支撑证据
  source_chapters: list  # 来源章节列表
```

**description 合并策略**（同一实体出现在多章时）：
- 若两段描述长度差异 > 50%，保留更长版本（信息更完整）
- 若长度相近（差异 ≤ 50%），用分隔符 `---` 拼接两段描述，保留不同章节视角
- 示例：BDNF 在运动章节描述为"运动诱发分泌的神经营养因子"，在学习章节描述为"促进突触可塑性的关键蛋白"，合并后两段都保留
- `source_chapters` 和 `source_para_ids` 始终取并集

### 4.5 实体消歧详细实现

#### 4.5.1 消歧 Prompt 模板

LLM 精判阶段使用的 prompt：

```
你是知识图谱实体消歧专家。给定两个实体，判断它们是否指代同一概念。

## 实体 A（新提取）
名称: {entity_a.name}
类型: {entity_a.entity_type}
描述: {entity_a.description}
来源章节: {entity_a.source_chapters}

## 实体 B（图中已有）
名称: {entity_b.name}
类型: {entity_b.entity_type}
描述: {entity_b.description}
来源章节: {entity_b.source_chapters}

## 判断规则
1. 名称相同或互为别名（如"BDNF"和"脑源性神经营养因子"）→ same=true
2. 描述高度重叠但名称不同 → same=true
3. 类型不同 → same=false（不同类型通常不是同一实体）
4. 名称相似但语义不同（如"注意力"和"注意力缺陷"）→ same=false

请只回答 JSON: {"same": true/false, "reason": "一句话理由"}
```

#### 4.5.2 阈值校准策略

embedding 粗筛阈值 `0.85` 是初始值，需通过实际数据校准：

1. **PoC 阶段**（§16.2 Step 1）：对第一本书的提取结果，用 0.70/0.75/0.80/0.85/0.90 五个阈值分别跑消歧，人工标注正确/错误合并
2. **计算 precision/recall**：阈值过高 → 漏合并（recall 低）；阈值过低 → 误合并（precision 低）
3. **选择 F1 最高的阈值**作为正式值，写入配置文件 `d2g_config.yaml`
4. **后续每本书**：审核者反馈的合并/拆分操作会记录到日志，定期（每 10 本书）重新校准

#### 4.5.3 消歧失败兜底

| 失败场景 | 处理策略 |
|---------|---------|
| embedding 计算超时 | 降级为名称精确匹配（name == name → 合并，否则新增） |
| LLM 精判超时（>30s） | 跳过合并，将该实体标记为"待人工消歧"，在审核 MD 中高亮提示 |
| LLM 返回格式异常 | 用 `json_repair.loads()` 修复；若仍失败，视为 same=false（保守策略，宁可多一个孤立节点也不误合并） |
| LLM 返回 same=true 但类型不同 | 强制覆盖为 same=false（类型不同不允许合并） |

### 4.6 Pydantic 模型定义

以下为 D2G 核心 Pydantic 模型，存放于 `models.py`：

```python
from pydantic import BaseModel, Field
from typing import Optional

class ExtractedEntity(BaseModel):
    name: str = Field(description="实体名称，如 BDNF、有氧运动")
    entity_type: str = Field(description="实体类型，必须是 §4.1 枚举之一")
    description: str = Field(min_length=20, description="实体描述，不少于 20 字")
    aliases: list[str] = Field(default_factory=list, description="别名列表")
    source_para_ids: list[str] = Field(description="来源段落号，如 [P1, P3, P5]")

class ExtractedRelationship(BaseModel):
    source: str = Field(description="起点实体名称，必须与 Round 1 输出一致")
    target: str = Field(description="终点实体名称")
    relation_type: str = Field(description="关系类型，必须是 §4.2 枚举之一")
    evidence: str = Field(description="原文直接引用作为证据")
    source_para_ids: list[str] = Field(description="来源段落号")

class CaseStudy(BaseModel):
    title: str = Field(description="案例标题")
    background: str = Field(description="背景")
    process: str = Field(description="过程")
    result: str = Field(description="结果")
    insight: str = Field(description="启示")
    related_entities: list[str] = Field(description="关联实体名称列表")
    source_para_ids: list[str] = Field(description="来源段落号")

class DataPoint(BaseModel):
    metric: str = Field(description="指标名称")
    value: str = Field(description="数值")
    context: str = Field(description="上下文说明")
    source_attribution: str = Field(description="数据来源/出处")
    source_para_ids: list[str] = Field(description="来源段落号")

class Quote(BaseModel):
    text: str = Field(description="原文措辞")
    speaker: Optional[str] = Field(default=None, description="说话人")
    context: str = Field(description="引言上下文")
    source_para_ids: list[str] = Field(description="来源段落号")

class ChapterDetails(BaseModel):
    cases: list[CaseStudy] = Field(default_factory=list)
    data_points: list[DataPoint] = Field(default_factory=list)
    quotes: list[Quote] = Field(default_factory=list)

class BookContext(BaseModel):
    summary: str = Field(description="全书主旨，2-3 句话")
    core_arguments: list[str] = Field(description="3-5 个核心论点")
    glossary: dict[str, str] = Field(description="术语表 {术语: 定义}")
    chapter_outline: str = Field(description="各章逻辑关系描述")
```

## 5. Phase 0: 全书深度阅读

### 5.1 目的

为后续逐章提取提供全书级上下文：作者在整本书中想论证什么、用了什么术语、各章之间是什么逻辑关系。

### 5.2 方法

将全书分为若干段（每段 ~5 章），每段做一次深度阅读，最后综合所有段的结果。

### 5.3 输出

`BookContext`:
- **全书主旨**: 2-3 句话概括作者最核心的主张
- **核心论点**: 3-5 个关键论点 + 简要论证
- **术语表**: 10-20 个专业术语 + 完整定义
- **章节脉络**: 各章之间的逻辑关系描述

### 5.4 模型与调用

- 模型: qwen-turbo
- 分段阅读: ~5 次调用（每段输入全文原文）
- 全书综合: 1 次调用
- 总计: ~6 次（不含自校验）
- 自校验: +3-4 次（详见 §5.5）
- **总计含自校验: ~9-10 次**
- **token 预算**: 分段阅读 ~200K input + ~40K output；综合 ~30K input + ~8K output；自校验 ~30K input + ~2K output

### 5.4.1 Context Window 处理

Phase 0 的分段阅读每段输入约 5 章原文（~50-80K tokens）。若单段超出模型 context window（qwen-turbo 128K）：

| 场景 | 处理策略 |
|------|----------|
| 单段 ≤ 100K tokens | 直接输入，无需额外处理 |
| 单段 100-128K tokens | 截断尾部结构段落（目录、参考文献等），保留正文 |
| 单段 > 128K tokens | 该段进一步拆分为 2 个子段，分别阅读后在全书综合阶段合并 |
| 单章 > 50K tokens | 该章独立成段，不与其他章合并（详见 §7 长章节处理） |

> **设计约束**: Phase 0 的输入是"全书原文"而非"章节摘要"，因此 token 消耗较大。这是 D2G 相比 v2 的额外成本，但换来的是后续 Phase 1 提取时有全书上下文支撑，显著减少跨章重复提取和概念遗漏。

### 5.5 质量校验（Phase 0 自校验）

Phase 0 的 `BookContext` 是后续所有提取的上下文基础，如果全书主旨或术语表有偏差，后续所有章节的提取都会受影响。因此增加一次自校验：

**校验流程**:
1. 从全书中随机抽取 3 章（首章、中间章、末章），用独立 prompt 让 LLM 提取这 3 章的核心术语和主旨
2. 与 Phase 0 输出的术语表做交叉对比：术语重叠率（embedding cosine ≥ 0.8 的视为匹配）
3. 若重叠率 < 60%，说明 Phase 0 的术语表可能遗漏了重要术语，触发一次修正调用（将遗漏术语追加到术语表）
4. 若全书主旨与 3 章独立推断的主旨存在明显矛盾（由 LLM 判断），触发全书重新阅读

**校验模型**: qwen-turbo（与 Phase 0 一致）
**额外调用**: 3 次（抽样章节）+ 0-1 次（修正），已计入 §11 成本估算

## 6. Phase 1: 逐章 3 轮聚焦提取

### 6.1 上下文构造

每个章节的输入包含：
1. **全书背景**（Phase 0 输出的 BookContext）
2. **本章原文**（完整，不压缩，带 `[P{n}]` 段落标记）
3. **已审核章节的实体列表**（供关系提取参考，不发全文）
   - 截断策略: 当已审核实体超过 200 个时，按与本章的语义相关度（embedding cosine similarity）取 Top 100，避免输入 token 超限
   - **相关度下限**: cosine similarity < 0.3 的实体直接丢弃（即使 Top 100 不足 100 个也不纳入低相关实体，避免干扰 LLM）
   - **batch 计算**: 所有已审核实体的 embedding 预先缓存（Phase 2 消歧时已计算），每章提取时只需一次 batch cosine 计算，无需重复调用 embedding API

不发送相邻章节全文——Phase 0 的全书背景已包含章节脉络信息。

### 6.2 Round 1: 实体提取

- **目标**: 逐段扫描，提取所有实体
- **输入**: 章节原文 + 全书背景
- **输出**: `list[ExtractedEntity]`（Pydantic 约束）
- **关键规则**:
  - 宁多勿漏，不确定时也提取
  - description 不少于 20 字，保留原文关键信息
  - 标注来源段落号 `[P{n}]`

### 6.2.1 Round 1 覆盖率校验（Gate）

Round 1 输出后、进入 Round 2 前，执行一次轻量级程序化校验：

**校验逻辑**:
1. 统计本章总段落数 `total_paras`
2. 统计 Round 1 提取结果中 `source_para_ids` 覆盖的段落数 `covered_paras`
3. 计算覆盖率: `coverage = covered_paras / total_paras`

**判定规则**:

| 覆盖率 | 动作 |
|--------|------|
| ≥ 70% | ✅ 通过，继续 Round 2 |
| 50% ~ 70% | ⚠️ 警告，记录日志，继续 Round 2 但标记该章节为"低覆盖" |
| < 50% | ❌ 不通过，重试 Round 1（最多 1 次），重试后仍 < 50% 则标记为"需人工检查" |

> **设计动机**: Round 1 是后续两轮的基础——如果实体提取遗漏严重，Round 2 的关系提取和 Round 3 的细节提取都会在错误基础上构建。此 gate 是零成本的程序化检查（无 LLM 调用），可在早期发现质量问题，避免浪费后续 2 轮的 LLM 调用。
### 6.3 Round 2: 关系提取

- **目标**: 找出实体之间的所有关系
- **输入**: 章节原文 + Round 1 实体列表 + 已审核章节的实体列表
- **输出**: `list[ExtractedRelationship]`（Pydantic 约束）
- **关键规则**:
  - 实体名称必须与 Round 1 输出一致
  - evidence 必须是原文直接引用
  - 已审核章节的实体可作为关系目标（跨章关系）

### 6.4 Round 3: 细节提取

- **目标**: 提取非实体信息（案例、数据、引言、论点、建议）
- **输入**: 章节原文 + Round 1 实体列表
- **输出**: `ChapterDetails`（Pydantic 约束）
- **关键规则**:
  - 案例保留完整叙事（背景→过程→结果→启示）
  - 数据保留数值、上下文、来源
  - 引言保留原文措辞

### 6.5 短章节 vs 长章节

| 条件 | 策略 | 调用次数 |
|------|------|---------|
| < 20K tokens | 直接 3 轮提取 | 3 次 |
| ≥ 20K tokens | 分段滑窗 + 跨段桥接 | 3N + 1 次（N=段数） |

长章节处理详见 [§7 长章节处理策略](#7-长章节处理策略)。

### 6.6 结构化输出保障

使用 LangChain `with_structured_output()` 通过 tool calling 强制输出 Pydantic schema：

- `ChatTongyi`（DashScope 适配器）原生支持 `with_structured_output()`
- 底层通过 `bind_tools()` 实现，qwen-turbo/plus/max 均支持 tool calling
- 输出自动解析为 Pydantic 实例，格式错误率趋近于零
- 降级方案（三层降级，`json_repair>=0.58.7` 已确认在 `pyproject.toml` 依赖中）:
  - **L1**: tool calling 正常 → Pydantic 自动解析（主路径，成功率 ≥ 98%）
  - **L2**: tool calling 失败 → 退化为 JSON prompt + `json_repair.loads()` + Pydantic 验证
  - **L3**: JSON 修复后 Pydantic 验证仍失败 → 正则提取关键字段（name、type、description）构造最低可用实体，标记 `confidence: "low"`，在审核 MD 中高亮提示审核者重点检查

## 7. 长章节处理策略

### 7.1 分段滑窗

当章节超过 20K tokens 时，按段落边界分段，相邻段之间保留重叠窗口：

| 参数 | 值 | 说明 |
|------|-----|------|
| `LONG_CHAPTER_THRESHOLD` | 20,000 tokens | 低于此值走直接提取 |
| `SEGMENT_TARGET_SIZE` | 12,000 tokens | 每段目标大小 |
| `OVERLAP_PARAGRAPHS` | `max(3 段落, 300 tokens)`（按段落边界对齐） | 相邻段重叠，确保跨段实体不被切断。取段落数和 token 数的较大值：纯段落数在段落极短时可能不足（如 3 段仅 150 字），增加 token 下限兜底 |
| `MAX_SEGMENTS` | 8 | 单章最多分 8 段（~100K tokens 上限） |

### 7.2 分段提取流程

```
长章节原文 (30K-80K tokens)
  │
  ├── Round 1: 各段并行实体提取 → 合并去重（name+type 为 key）
  │
  ├── Round 2: 两轮
  │   ├── Pass 2a: 各段并行，提取段内关系
  │   └── Pass 2b: 跨段桥接（1 次调用）
  │       输入: 合并实体列表 + 各段摘要 + 段内关系摘要
  │       输出: 跨段关系
  │
  └── Round 3: 各段并行细节提取 → 合并去重（标题/指标/原文为 key）
```

### 7.3 重叠段落去重

重叠段落中的信息可能被两个 segment 都提取到。去重策略：

| 信息类型 | 去重 key | 合并策略 |
|---------|---------|---------|
| 实体 | `name + entity_type` | description 保留更长版本，source_para_ids 取并集 |
| 关系 | `source + target + relation_type` | evidence 保留更长版本，source_para_ids 取并集 |
| 案例 | `title` | 保留第一个 |
| 数据 | `metric + value` | 保留第一个 |
| 引言 | `text[:50]` | 保留第一个 |

### 7.4 跨段桥接

跨段桥接的输入不是完整章节原文（太长），而是：
1. 各段的**结构化摘要**（每段用 Round 1+2 已产出的实体列表 + 关系列表作为摘要，而非简单截取段首文字）
2. 合并后的**完整实体列表**（标注每个实体首次出现的段号）
3. 已发现的**段内关系汇总**（按段号分组）

> **设计决策**: 用实体+关系列表作为段落"摘要"，而非段首 200 字截取。原因：段落的叙事顺序不固定（如先结论后论证），截取首部可能丢失关键信息；结构化摘要精确反映每段提取了什么，更适合跨段关联推理。

LLM 从这些信息中推断跨段关系，如"段 1 提到的 BDNF 与段 3 提到的神经可塑性之间有 AFFECTS 关系"。

### 7.5 成本影响

以 50K token 的超长章节（分 4 段）为例：

| 步骤 | 调用次数 | 输入 tokens | 输出 tokens |
|------|---------|------------|------------|
| Round 1: 实体提取 | 4（并行） | ~60K | ~16K |
| Round 2a: 段内关系 | 4（并行） | ~68K | ~16K |
| Round 2b: 跨段桥接 | 1 | ~10K | ~4K |
| Round 3: 细节提取 | 4（并行） | ~60K | ~20K |
| **合计** | **13** | **~198K** | **~56K** |

## 8. Phase 2: 逐章审核 + 增量入图

### 8.1 审核 MD 生成

从章节提取结果反向生成审核用 MD。关键设计：**区分"新实体"和"已有实体"**。

审核 MD 结构：

```markdown
# 第 N 章: {chapter_title} — 提取审核

> 本章提取了 {n} 个实体、{m} 条关系。段落覆盖率: {coverage}%

## 新增实体（图中不存在）

### BDNF（脑源性神经营养因子）
**类型**: Mechanism
**描述**: 一种蛋白质，被称为"大脑的肥料"...
**来源**: P3, P5, P7

## 已有实体（图中已存在，本章新增关系）

### 有氧运动 [已在第 1 章提取]
**本章新增关系**: 有氧运动 → CAUSES → BDNF 分泌增加 (P5)

## 关系
| 起点 | 关系 | 终点 | 证据 | 来源 |
|------|------|------|------|------|

## 案例与故事
...

## 数据与事实
...

## 段落覆盖详情
- P1: ✅ (实体: 运动)
- P2: ✅ (实体: 神经可塑性)
- P4: ⚠️ 部分覆盖
...
```

### 8.2 前端兼容性

现有 `DraftEditorPage` 通过正则匹配 `## 类型` + `### 实体名` 解析实体列表。D2G 的审核 MD 保持同样的 `##` → `###` 结构，**MD 解析逻辑无需改动**。

审核 MD 中"新实体"用 `### 实体名` 标记，"已有实体"用 `### 实体名 [已在第 X 章提取]` 标记。前端解析时两种都能匹配。

> ⚠️ **前端需要的改动**: D2G 将实体类型从 6 种扩展至 15 种（详见 §4.1）。前端 `DraftEditorPage.tsx` 和 `useDraftEditor.ts` 中的 `ENTITY_TYPES` 数组和 `TYPE_LABELS` 映射需同步更新，新增对应类型的图标和标签。改动量约 20 行，不影响核心解析逻辑。

### 8.3 审核操作

审核者可以：
1. **删除** 实体/关系/案例（误提取的）
2. **编辑** 实体描述/关系类型（不准确的）
3. **新增** 遗漏的实体/关系
4. **合并** 两个实体（消歧未发现的重复）
5. **批准** （全部通过）

### 8.4 增量实体消歧

审核通过后，将新实体合入主图时做消歧。消歧分为两个层级：

#### 8.4.1 增量消歧（主路径，逐章触发）

每章审核通过后立即执行，确保后续章节能引用已消歧的实体：

```
新实体列表（本章提取 + 审核编辑后的版本）
  │
  ▼
embedding 粗筛 ──→ 与主图中已有实体计算 cosine similarity
  │                 阈值: 初始 0.85，PoC 阶段校准（见 §4.5.2）
  ▼
相似度 ≥ 阈值 ──→ LLM 精判是否同一实体（prompt 见 §4.5.1）
  │                 输出 same: true/false + reason
  ▼
same=true ──→ 合并（description 合并策略见 §4.4，union para_ids）
same=false ──→ 作为新实体加入主图
  │
  ▼
embedding 预缓存 ──→ 合并/新增的实体立即计算 embedding 并缓存，
                     供下一章的粗筛使用（避免重复计算）
```

embedding 模型: 复用现有 DashScope `text-embedding-v4`（已通过 `EmbeddingFactory` 集成）。

#### 8.4.2 全量消歧（全书入库前校验）

全书所有章节审核完毕后、入库 Neo4j 前执行一次全量消歧，作为增量消歧的补充校验：

- **目的**: 捕获增量消歧中因"后验信息"导致的遗漏（如第 3 章的实体 A 和第 15 章的实体 B 在逐章消歧时各自独立，但全书视角下明显是同一概念）
- **方法**: 对全图所有实体做一次 pairwise embedding 粗筛，对命中对调用 LLM 精判
- **触发条件**: 仅当全书实体数 ≤ 500 时执行（超过则跳过，依赖增量消歧结果）
- **位置**: 在 Phase 3 质量检查通过后、Phase 4 入库前

> **增量 vs 全量的关系**: 增量消歧是主路径，覆盖 95% 以上的合并需求；全量消歧是安全网，处理跨章节远距离的同义实体。两者使用相同的阈值和 prompt（§4.5）。

### 8.5 主图持久化

每章审核通过后，将 NetworkX 图序列化为 JSON 存入 Redis：

- Key: `master_graph:{book_id}`
- 序列化: `nx.node_link_data(G)` → JSON → Redis SET
- 反序列化: Redis GET → JSON → `nx.node_link_graph(data)`
- ⚠️ NetworkX 3.x 中 `node_link_data` 默认返回 `edges="links"` 格式，需显式传入 `edges="links"` 保持兼容；或锁定 `networkx>=3.0,<4.0` 版本范围
- 全书入库 Neo4j 后删除 Redis 临时数据
- 大图降级: 若 Redis value 超过 512MB（极端情况），改用本地 JSON 文件暂存
- **并发安全**: 多人审核同一本书的不同章节时，使用 Redis `WATCH/MULTI` 乐观锁：
  1. 读取当前图数据时记录版本号（Redis key 的 `objectid` 或自增版本字段）
  2. 修改后写入时用 `WATCH` + `MULTI` 检查版本未变
  3. 若版本冲突（其他审核者同时修改），重新读取最新版本并合并修改后重试
  4. 最大重试 3 次，仍冲突则提示审核者刷新页面

### 8.6 审核后处理

审核者的操作会改变提取结果，后续处理逻辑如下：

```
审核操作          →  后续处理
────────────────────────────────────────────
删除实体          →  同时删除该实体的所有关系，跳过消歧
删除关系          →  直接从图中移除
编辑实体描述      →  保留编辑后版本，消歧时用编辑后的 description 做 embedding
编辑关系类型      →  直接更新图中的关系类型
新增实体          →  走正常消歧流程（embedding 粗筛 + LLM 精判）
新增关系          →  校验 source/target 均存在于图中，否则提示错误
合并两个实体      →  保留目标实体，将源实体的 relations/para_ids 迁移至目标（description 合并策略见 §4.4），删除源实体
批准（全部通过）  →  触发 §8.4 消歧 + §8.5 持久化
```

> **关键约束**: 审核编辑后的结果必须重新经过消歧流程（§8.4），而非直接跳过。因为编辑可能改变实体语义，导致与主图中已有实体产生新的匹配。

## 9. Phase 3: 全书图质量检查

**纯程序化，零 LLM 调用。**

### 9.1 质量指标

| 指标 | 计算方式 | 阈值 | 低于阈值的动作 |
|------|---------|------|--------------|
| `orphan_rate` | 无任何关系的实体数 / 总实体数 | < 15% | 标记孤立实体供人工检查 |
| `connected_components` | 连通分量数（NetworkX） | ≤ 3 | 标记可能遗漏的跨段关联 |
| `largest_component_ratio` | 最大连通分量 / 总实体数 | > 70% | 低于说明图太碎片化 |
| `avg_degree` | 2 × 边数 / 节点数 | ≥ 1.5 | 低于说明关系不够丰富 |
| `chapter_coverage` | 每章被引用段落 / 总段落 | ≥ 80% | 低于的章节标记需重新提取 |
| `overall_para_coverage` | 全书被引用段落 / 全书总段落 | ≥ 75% | 低于说明提取不够全面 |

> **按书类型校准阈值**: 上述阈值适用于典型育儿/教育类书籍。对于其他类型的书（如理论性强的学术著作、案例集、工具书），孤立实体率和覆盖率的合理范围不同。PoC 阶段应收集 3 本不同类型书籍的实际指标分布，按 P25/P75 设置动态阈值，写入 `d2g_config.yaml`。

> **结构段落过滤**: 计算 `chapter_coverage` 时，应排除纯结构段落（如"下一章我们将讨论…"、目录页、参考文献列表）。判定规则：段落 token 数 < 30 且不含任何实体候选词的视为结构段落。

### 9.2 异常处理

质量检查不通过时的处理流程：

1. **孤立实体率过高** → 列出孤立实体清单，审核者决定是否补充关系或删除
2. **连通分量过多** → 列出各分量的实体，审核者判断是否有遗漏的跨段关联
3. **章节覆盖率低** → 该章节标记为"需重新提取"，重新执行 Phase 1

## 10. Phase 4: 入库 Neo4j

### 10.1 Cypher 生成

从内存图生成 MERGE 语句，复用现有 `schema.py` 的节点/关系类型：

- 实体节点: `MERGE (n:{EntityType} {name_normalized, book_id}) SET n.name, n.description, n.source_chapter`
- **名称规范化**: 入库前对 `name` 做程序化规范化——`name_normalized = name.strip().lower()`，`name` 字段保留原始大小写用于展示。避免"BDNF" vs "bdnf"、"有氧运动 " vs "有氧运动"导致的重复节点
- Book/Chapter 节点: 复用现有逻辑
- 关系: `MERGE (a)-[r:{RelType}]->(b) SET r.evidence`
- 跨书关系: `cross_relation.py` 需要两阶段升级：
  - **D2G 阶段**（本方案）: 入口处增加适配层，将 D2G 的 `ExtractedEntity` Pydantic 模型转换为 `cross_relation.py` 期望的 `Entity` dataclass 格式（字段映射: `name→name`, `entity_type→entity_type`, `description→description`, `source_para_ids→chunk_ids`）
  - **多书扩展阶段**（§08-5）: 查询逻辑从只查 `AutoEntity` 改为查所有 D2G 的 15 种类型（`WHERE any(label IN labels(n) WHERE label IN $d2g_labels)`），并重构为只对 Phase 5 建立的 `SAME_AS` 实体对检测跨书关系类型（CONSENSUS/COMPLEMENTS/CONFLICTS）

### 10.2 安全执行

- dry_run 模式预检（打印 Cypher 但不执行）
- 校验所有必填参数（name, book_id 非空）
- 事务执行（全部成功或全部回滚）

### 10.3 社区检测与跨章关联

> **设计动机**: §2 中提到 GraphRAG 的核心洞察是"跨章关联通过图社区结构内生解决"。D2G 的 Phase 0（全书背景）+ Phase 2（增量消歧）已覆盖大部分跨章关联，但仍需社区检测来发现隐式聚类。

**算法选择**: NetworkX 内置的 Louvain 社区检测（`community.louvain_communities`），无需额外依赖。

**执行时机**: 入库 Neo4j 之前（Phase 3 质量检查之后），作为 Phase 4 的可选前置步骤。

**流程**:
1. 对主图运行 Louvain 社区检测，得到社区列表
2. 每个社区生成 `AutoCommunity` 节点，包含：
   - `community_id`: 自增 ID
   - `members`: 社区内实体名称列表
   - `summary`: 社区内实体的 description 拼接（用于检索）
3. 社区内实体通过 `CONTAINS_ENTITY` 关系连接到 `AutoCommunity` 节点
4. 社区摘要可作为 RAG 检索的额外入口（用户问"运动对大脑有什么好处"时，匹配到"运动-神经可塑性"社区，返回社区内所有实体和关系）

**阈值与调参**:
- `resolution` 参数默认 1.0，值越大社区越小越细
- 若社区数量 > 实体数 × 0.3，说明 resolution 太大，需降低
- 若社区数量 < 3，说明 resolution 太小，需提高

**与 Phase 3 的关系**: 社区检测结果可补充 Phase 3 的 `connected_components` 指标——若 Louvain 社区与连通分量高度不一致，说明图中存在"桥接薄弱"区域，需人工检查。

## 16. 数据迁移与灰度切换

### 16.1 现有数据处理

| 场景 | 策略 |
|------|------|
| Neo4j 中已有 v1/v2 生成的图谱 | 保留不动。D2G 新书用新流水线，旧书按需重跑 |
| 新旧实体类型冲突 | D2G 新增的 6 种类型（CognitiveProcess 等）以新节点标签入库，不修改旧数据的标签 |
| 同一本书新旧共存 | **Staging 模式入库**（避免中途失败导致数据丢失）：
1. D2G 节点先写入临时 label（`:D2G_Staging`），带 `book_id` 和 `extraction_version: "d2g"` 标签
2. 全部写入成功后，在同一事务中：删除旧节点 + 将 staging 节点的 label 从 `:D2G_Staging` 改为正式 label
3. 若中途失败，staging 节点保留但不影响旧数据，可手动清理或重试
4. 回滚时按 `extraction_version: "d2g"` 或 `:D2G_Staging` label 删除 |

### 16.2 灰度切换方案

```
Step 1: PoC 验证（1 本书）
  - 选一本中等复杂度的书（~15 章，~50K tokens/章）
  - D2G 全流程跑通，人工审核提取质量
  - 对比 v2 同书结果，量化提升

Step 2: 并行运行（3 本书）
  - 新书同时用 v2 和 D2G 处理
  - 对比图质量指标（孤立率、连通度、覆盖率）
  - 收集审核者反馈

Step 3: 切换默认
  - D2G 设为默认流水线
  - v2 代码标记 deprecated 但保留 1 个版本周期
  - `generate_draft.py` 入口通过配置开关切换

Step 4: 清理
  - 确认稳定后删除 v2 代码（md_generator.py, md_parser.py 等）
```

### 16.3 回滚方案

- **配置开关**: `book_pipeline.py` 中通过 `pipeline_version: "v2" | "d2g"` 配置项切换，回滚 = 改配置
- **数据回滚**: D2G 入库的节点带 `extraction_version: "d2g"` 标签，回滚时可按标签删除
- **Redis 快照**: 每章审核通过后 Redis 中的主图数据保留至全书入库成功，中途失败可从 Redis 恢复

- **提取质量趋势**: 每本书的实体数、关系数、覆盖率随时间变化

### 17.3 告警规则

| 指标 | 阈值 | 动作 |
|------|------|------|
| tool calling 连续格式错误 | ≥ 3 次 | 暂停该章提取，触发 L3 降级（§6.6），通知运维 |
| tool calling 限流错误 | ≥ 5 次（指数退避重试后） | 暂停全书提取，等待限流恢复后自动续跑 |
| 单章提取耗时 | > `chapter_tokens / 5000` min（动态阈值） | 记录慢日志。短章节 < 3min 也需检查 |
| 消歧 embedding 相似度命中率 | > 30%（粗筛命中数 / 主图实体数） | 告警，阈值可能过低导致大量 LLM 精判调用 |
| 消歧 LLM 调用数 | > 10 次/章 | 告警，检查 embedding 阈值和主图实体膨胀 |
| Redis 序列化失败 | 任何 | 告警，降级为本地 JSON 文件暂存（§8.5） |
| Phase 0 自校验术语重叠率 | < 40% | 告警，Phase 0 全书阅读质量可能严重偏差，建议重跑 |
| 全量消歧误合并 | 审核者手动拆分 ≥ 3 次 | 告警，embedding 阈值需上调（§4.5.2 校准流程） |
