## 2. 🔴 P0 — 阻断性问题

### P0-1: 第二层搜索（Section 节点）搜索逻辑重复浪费

**现状**：
- `_run_section_node`（[base.py:688-793](backend/src/core/knowledge_qa/nodes/base.py#L688-L793)）在每个 Section 生成时都独立调用 `_direct_search` 搜索知识库
- `plan_outline_node`（[plan_outline.py:29-226](backend/src/core/knowledge_qa/nodes/plan_outline.py#L29-L226)）也独立搜索
- `plan_expand_parallel_node`（[plan_expand_parallel.py:295-384](backend/src/core/knowledge_qa/nodes/plan_expand_parallel.py#L295-L384)）为每个运动分组再独立搜索
- `generate_s4_citations_node`（[generate_s4_citations.py:57-215](backend/src/core/knowledge_qa/nodes/generate_s4_citations.py#L57-L215)）再次单独搜索

**问题**：
1. 同一个 `question` + `matched_book_ids` 组合被搜索 **6-8 次**（S1, S2, S3, S4-outline, S4-expand × N 组, S4-citations, S5），每次都是独立的 HTTP 调用 `GET /rag/search`
2. 虽然有 `state.search_cache` 缓存命中机制，但 `plan_expand_parallel` 的专项搜索（`{ex_name} 动作要领 执行要点`）不走缓存，因为 query 不同
3. `generate_s4_citations` 再次搜索（`_direct_search(search_terms, ...)`），search_terms 是从 structured_data 提取的运动名称

**根因**：搜索逻辑分散在多个节点中，缺乏全局搜索协调。`prefetch_context` 的 LazyGraphRAG 遍历提供了 `knowledge_context`，但 Section 节点仍独立搜索，没有复用这个上下文。

**影响**：
- S1-S5 共 5 节 + S4 大纲 + S4 展开 × N 组 + S4 引用，**最少 8 次，最多 20+ 次** 知识库搜索
- 大量重复 HTTP 调用 + Chroma 查询，每次 2-10 秒 = 总耗时 30-120 秒
- 用户在第二层搜索阶段等待时间过长

**建议方向**：将知识检索统一在 `prefetch_context` 或 `query_neo4j_graph` 之后做一次全量搜索，后续节点只消费已检索的上下文，不再独立搜索。S4 展开分组如果需要更细粒度的搜索，改为本地文本匹配而非重新调用检索 API。

### P0-2: 参考文献 book_title 没有保证来自知识库已有书籍

**现状**：
- `_format_search_context`（[base.py:447-512](backend/src/core/knowledge_qa/nodes/base.py#L447-L512)）在搜索结果末尾追加提示：
  ```
  本次检索结果来自以下书籍：{book_list_str}。
  请尽量从不同书籍中选取引用，确保引用来源多样化。
  citations 中每条必须包含 book_title, chapter, excerpt, relevance 字段。
  book_title 使用上方已规范化的书名（不含文件扩展名），chapter 使用上方的章节名。
  excerpt 必须从上方结果中的原文逐字复制，不允许改写或概括。
  ```
- 但 LLM 生成 citation 的 `book_title` 字段时，**不受任何结构化约束**
- `Section5Response` / `SectionOutput` 中 `citations` 是 `List[Dict[str, Any]]`，没有任何 Pydantic validator 校验 `book_title` 是否来自实际搜索到的书籍
- `verify_citations_node`（[verify_citations.py:111-286](backend/src/core/knowledge_qa/nodes/verify_citations.py#L111-L286)）**只校验 excerpt 非空、chapter 非空、citation_id 格式**，**不校验 book_title 的合法性**

**根因**：
1. Citation 的 Pydantic 模型没有 `book_title` 字段的枚举校验（因为搜索结果是动态的）
2. LLM 在对话历史较长时产生幻觉，编造不存在的书名
3. 验证节点只做结构完整性校验，不做内容真实性校验

**影响**：
- 用户看到的引用 `book_title` 可能是 LLM 编造的，与知识库中的实际书籍不符
- 破坏了知识问答系统的可信度——用户可能基于虚假引用做决策
- 前端展示引用时无法关联到原始书籍

**建议方向**：
1. 在 citation 生成后的后处理中，用搜索结果的 `source_book` 集合做白名单校验
2. `book_title` 如果不匹配任何已知书籍，自动替换为最相似的搜索结果 `source_book` 或标记为"无法验证"
3. `verify_citations_node` 增加 `book_title` 模糊匹配校验（用 `_normalize_book_title` 规范化后与搜索结果的 source_book 做匹配）

### P0-3: 空搜索守卫过早触发——知识库有数据时被误判为空

**现状**：
- `_run_section_node`（[base.py:725-728](backend/src/core/knowledge_qa/nodes/base.py#L725-L728)）中：
  ```python
  if not search_results:
      logger.warning(f"第{section_index}节知识库无搜索结果，跳过 LLM 调用")
      return await _build_empty_search_fallback(state, section_index, section_label)
  ```

**问题**：
- `_direct_search` 可能因为网络波动、RAG 服务暂时不可用等原因返回空列表
- 此时直接跳过 LLM 生成，"无引用空节"返回给用户
- 没有降级机制：当搜索结果为空时，**应该尝试让 LLM 从 `knowledge_context`（prefetch_context 预取的知识上下文）中提取信息**，而非直接放弃
- `_direct_search` 中已有降级逻辑（超时/失败时返回空列表），但 `_run_section_node` 的空搜索守卫没有区分"搜索失败"和"确实无匹配"

**影响**：
- 偶发的网络波动导致整节内容丢失
- 用户看到"知识库中未找到与此节相关的专业依据"提示，但实际数据存在

**建议方向**：
1. 搜索结果为空时，先检查 `state.knowledge_context` 是否有内容——如果有，降级用 `knowledge_context` 作为搜索上下文传给 LLM
2. 区分"搜索服务不可用"（保留错误信息）和"确实无匹配"（直接跳过）

### P0-4: `match_books` → `prefetch_context` 的搜索 book_ids 范围扩得太大

**现状**：
- `match_books_node`（[match_books.py:523-659](backend/src/core/knowledge_qa/nodes/match_books.py#L523-L659)）中：
  ```python
  # Step 5: 构建 search_book_ids — 包含所有候选书籍的 file_hash
  # 后续 RAG 检索不再做 LLM 级别的书籍过滤，而是让向量相似度自然排序
  # 这样所有已索引的书籍内容都能被搜索到，只是更匹配的内容排在前列
  search_book_ids: list[str] = []
  for c in candidates:
      ...
      if fh not in search_book_ids:
          search_book_ids.append(fh)
  ```
- 注释说明这是**有意为之**——所有候选书籍都传入，不做过滤
- 但 `matched_book_ids` 返回的是所有候选书籍的 `file_hash`，可能包含 **10-20 本不太相关的书**

**问题**：
- `prefetch_context` 对所有候选书籍做 LazyGraphRAG 遍历（[prefetch_context.py:52-138](backend/src/core/knowledge_qa/nodes/prefetch_context.py#L52-L138)）——每本书独立遍历社区树，可能消耗大量时间
- 后续 `_direct_search` 传入所有 `book_ids`——Chroma 查询范围变得非常大
- 大量不相关书籍的噪声数据进入 `knowledge_context`，稀释了真正相关的内容

**根因**："不做书籍级过滤"的意图是好的（避免过早过滤），但缺乏**中间阶段的相关性收缩**——应该在 prefetch_context 之后根据搜索结果的实际命中情况，动态缩减 `matched_book_ids` 范围。

**影响**：
- 知识检索的 precision 降低
- LazyGraphRAG 遍历耗时与 books 数量成正比
- knowledge_context 包含过多不相关内容

**建议方向**：
1. 在 `prefetch_context` 之后增加一个精简步骤：只保留实际命中 chunk 超过阈值（如 ≥3 条）的书籍
2. 后续节点的 `_direct_search` 使用精简后的 book_ids

## 3. 🟠 P1 — 严重问题

### P1-1: `prefetch_context` 的 LazyGraphRAG 遍历深且无时间限制

**现状**：
- `prefetch_context_node` 超时 10 秒（[prefetch_context.py:18](backend/src/core/knowledge_qa/nodes/prefetch_context.py#L18)）
- 遍历 `max_tokens=24000`（2× 默认值），[prefetch_context.py:84](backend/src/core/knowledge_qa/nodes/prefetch_context.py#L84)
- 每本书独立遍历：`for book_id in ready_ids` 循环内对每个 root 做 `explore_community_tree`
- 全局 root 再遍历一次

**问题**：
1. 10 秒超时对于 5+ 本书的社区树遍历来说太短——实际可能 2-3 秒就超时
2. 超时后返回空的 `knowledge_context`，所有后续节点失去最重要的知识来源
3. `max_tokens=24000` 很大，但没考虑 context window——过长会挤压 LLM 的有效 token 配额
4. 每本书独立遍历，没有按相关性做排序或截断

**影响**：`prefetch_context` 是知识问答的**核心知识来源**，其频繁超时导致系统退化到"每节独立搜索"模式，丧失了全局知识感知能力。

**建议方向**：
1. 按书籍相关性排序（`match_books` 已有 `matched_books_detail`），只对 top-3 做遍历
2. 全局 root 的遍历结果缓存（跨请求复用）
3. 超时时间应动态调整：`max(10, ready_books_count * 5)`

### P1-2: `plan_outline` S4 大纲 LLM 调用 2 次 + 重试最多 4 次，极易超时

**现状**：
- `plan_outline_node` 分两阶段生成：Phase 1 和 Phase 2 各一次 `_invoke_llm_json`（每次 120s 超时）
- 如果 phases 为空，触发 `_retry_outline_phases`（再次 60s）
- 如果 retry 也失败，触发 `_try_build_phases_from_content`（降级，无 LLM）
- 然后还有 3 个后处理函数：`_normalize_day_indices`、`_ensure_min_phases`、`_ensure_full_weeks`、`_enforce_rest_days`

**问题**：
1. Phase 1 + Phase 2 两次独立的 LLM 调用，每次 120s 超时 = 最长 240s
2. 如果再加上重试和降级，S4 大纲生成可能花费 **3-5 分钟**
3. `_invoke_llm_json` 走纯文本 JSON 路径（绕过 tool calling），但嵌套 phases JSON 对 27B 模型挑战大，经常产出残缺 JSON
4. 后处理函数链过长：`_normalize_day_indices` → `_ensure_min_phases` → `_ensure_full_weeks` → `_enforce_rest_days`，共 4 层修补

**影响**：S4 是整个流水线最慢的节点，经常导致整个请求超时或用户长时间等待。

**建议方向**：
1. 将 Phase 1 + Phase 2 合并为一次 LLM 调用（如果模型 context window 够），或改用更快的模型
2. 减少 S4 大纲的复杂度——是否真的需要 2 阶段 × 2 周 × 5 天 × 2 运动 = 40 个 slot？
3. 考虑预生成运动方案模板，LLM 只做填空而非全量生成

### P1-3: `plan_expand_parallel` 每组运动都独立搜索知识库

**现状**：
- `plan_expand_parallel_node`（[plan_expand_parallel.py:316-340](backend/src/core/knowledge_qa/nodes/plan_expand_parallel.py#L316-L340)）中：
  ```python
  # 共享搜索上下文（所有组共用）
  search_results = await _direct_search(state.question, ...)
  base_search_context = _format_search_context(search_results)

  # 每组再预取运动专项搜索
  for group_idx, group_slots in enumerate(groups):
      ex_query = f"{ex_names} 动作要领 执行要点 家长指导"
      ex_results = await _direct_search(ex_query, ...)
  ```

**问题**：
1. 40 个运动 slot，按每组 4 个分组 = 10 组
2. 每组一次共享搜索 + 一次专项搜索 = **20 次 HTTP 搜索调用**
3. `_direct_search` 每次 2-8 秒 → 总计 40-160 秒
4. 每组 6 并发（`MAX_PARALLEL=6`），但搜索调用本身是串行等待

**影响**：S4 展开阶段成为仅次于 S4 大纲的第二大耗时节点。

**建议方向**：
1. 搜索结果应全部来自 `prefetch_context` 预取的 `knowledge_context`，不做独立搜索
2. 运动专项搜索可以改为在本地 knowledge_context 中做关键词匹配提取相关段落
3. 如果确实需要额外搜索，应做批量搜索（一次请求多个 query）

### P1-4: `_direct_search` 多书补充搜索机制效率低

**现状**：
- `_direct_search`（[base.py:389-422](backend/src/core/knowledge_qa/nodes/base.py#L389-L422)）中：
  ```python
  if book_ids and len(book_ids) > 1 and all_results:
      books_in_results: set[str] = set()
      ...
      if len(books_in_results) < 2:
          for bid in book_ids:
              # 每本缺失书籍单独搜索一次！
              params = {"query": main_query, "limit": 8, "book_ids": bid}
              resp = await client.get("/rag/search", params=params)
  ```

**问题**：
1. 当主搜索返回的结果集中于 1 本书时，对**每本缺失书籍分别发起搜索**——如果 5 本书只命中 1 本，则额外 4 次 HTTP 调用
2. 每次补充搜索 `limit=8`，但总补充结果可能仍然少
3. 这个逻辑被每个 Section 节点调用——乘以 5-8 节 = 额外 20-40 次搜索

**影响**：大量不必要的 HTTP 调用，搜索阶段耗时翻倍。

**建议方向**：
1. 改为一次批量请求 `book_ids=缺失书籍列表`，而非逐本搜索
2. 将此逻辑移出 `_direct_search`，在 prefetch 阶段统一处理书籍多样性

### P1-5: `generate_s4_citations` 引用生成与正文生成分离导致 citation 与正文不符

**现状**：
- `generate_s4_citations_node` 从 S4 正文中提取引用标记 `[C001]`，然后独立搜索 + LLM 生成 citations
- LLM 需要为每个标记匹配搜索结果中的原文 excerpt

**问题**：
1. S4 正文由 `plan_outline` + `plan_expand_parallel` 生成，citations 由独立节点生成——**两个 LLM 调用的上下文不一致**
2. LLM 可能为 `C001` 生成一个在搜索结果中存在的 excerpt，但该 excerpt 与正文中 `C001` 所在位置的内容**不匹配**
3. 虽然要求"excerpt 逐字复制"，但没有校验 citation 内容与正文的语义一致性
4. `verify_citations_node` 只检查 excerpt 长度 ≥ 10 和 chapter 非空，不检查语义匹配

**影响**：用户看到的引用看起来合法（有 book_title, chapter, excerpt），但引用内容与正文论述不一致。

**建议方向**：
1. 如果条件允许，S4 正文生成时同步生成引用（而非分离）
2. 或至少在 `verify_citations_node` 中增加语义一致性校验（citation excerpt 与正文中引用位置附近内容的相似度）
3. 15 方案 Phase 3 L3 溯源校验覆盖了 excerpt 匹配，但语义一致性校验需额外补充——**方案待 15 设计文档补充**。

## 4. 🟡 P2 — 中等问题

### P2-1: `_format_search_context` 限制严格可能导致关键信息丢失

**现状**：
- `_format_search_context`（[base.py:447-512](backend/src/core/knowledge_qa/nodes/base.py#L447-L512)）：
  - `MAX_PER_BOOK = 5`（每本书最多 5 条）
  - `MAX_CHARS = 10000`（总字符限制）
  - 单条内容截断到 300 字符

**问题**：
1. `MAX_CHARS=10000` 大约等于 ~3000 tokens——对于 LLM context window 来说合理，但**对于 5 本书、每本 5 条的情况，单条平均只有 400 字符**
2. 内容截断到 300 字符可能丢失关键上下文——LLM 看到的只是片断
3. 问题不在于截断本身，而在于截断后的内容**过于碎片化**

**建议方向**：
1. 按问题相关性排序取 top-N 条完整内容，而非所有书均匀取样后再截断
2. 对于高相关性结果，保留更长的原文片段（如 600 字符）

### P2-2: Section 节点没有使用 Neo4j 查询的知识

**现状**：
- v2 图（[_assembly_v2.py](backend/src/core/knowledge_qa/_assembly_v2.py)）中 `query_neo4j_graph` 节点正确放置
- v2 节点（`analyze_child_v2`, `identify_problems_v2` 等）应使用 `neo4j_knowledge`
- 但 `_run_section_node` 的 `_build_full_user_message` **只注入 `custom_knowledge_context` 和 `knowledge_context`，不注入 `neo4j_knowledge`**

**问题**：
1. `neo4j_knowledge` 被注入 state 后，Section 节点并没有显式使用它
2. v2 节点是否真的读取了 `neo4j_knowledge` 需要逐节点验证
3. 如果 Neo4j 有数据但 Section 节点不消费，三层架构（Layer 1 知识图谱）形同虚设

**建议方向**：
1. 在 `_build_full_user_message` 中增加 `neo4j_knowledge` 参数
2. 对 v2 节点做逐节点检查，确认每个节点确实消费了 neo4j_knowledge

### P2-3: `contradiction_audit` / `knowledge_synthesis_v2` 缺乏实际跨书数据

**现状**：
- v1 图（[_assembly.py](backend/src/core/knowledge_qa/_assembly.py)）中 `contradiction_audit_node` 在 `generate_s4_citations` 之后
- v2 图（[_assembly_v2.py](backend/src/core/knowledge_qa/_assembly_v2.py)）中用 `knowledge_synthesis_v2` 替代
- 但这个节点的输入是 LLM 从各节内容中推断的差异——**不是从 Neo4j 跨书关系中查询的**

**问题**：
1. 如果 Neo4j 中有跨书关系但未被利用，节点只能靠 LLM"猜测"跨书矛盾
2. LLM 猜测的准确率远低于 Neo4j 中已审核确认的跨书关系

**建议方向**：
1. `knowledge_synthesis_v2_node` 应先从 Neo4j 查询跨书关系，再补充 LLM 推断
2. 降级逻辑（Neo4j 不可用时全 LLM）已设计但未验证

### P2-4: S4 后处理函数链过深且互相依赖

**现状**：
- `plan_outline_node` 末尾：`_normalize_day_indices` → `_ensure_min_phases` → `_ensure_full_weeks` → `_enforce_rest_days`
- 四个函数按顺序修改 `phases` 数据，后一个依赖前一个的输出

**问题**：
1. 函数链式调用形成"数据变形管道"——每个函数在修补 LLM 输出的缺陷
2. 如果 LLM 输出质量改进，部分修补可能产生**过度修补**（如 `_ensure_full_weeks` 在数据已正确时仍补全休息日）
3. `_enforce_rest_days` 的均匀分布逻辑可能打乱 LLM 精心安排的训练节奏

**建议方向**：
1. 合并后处理步骤，减少中间态数据变异
2. 记录每个修补操作，在审核阶段展示，让审核者知道哪些是 LLM 原始输出、哪些是后处理修补

## 5. ⚪ P3 — 轻微问题

### P3-1: `match_books` 中 LLM 查询分析 + 规则提取并行但 LLM 结果优先

**现状**：
- `_analyze_and_search_books`（[match_books.py:300-317](backend/src/core/knowledge_qa/nodes/match_books.py#L300-L317)）：
  ```python
  analysis_task = _analyze_query(question)  # LLM
  profile = _extract_child_profile(question)  # 规则
  # 并行执行
  analysis = await asyncio.wait_for(analysis_task, timeout=20)
  # 合并：LLM 结果为主，规则提取为补充
  behavior = analysis.behavior_traits or profile["behavior"]
  ```

**问题**：
- 规则提取是零延迟的，但 LLM 需要 2-5 秒
- 实际体验中，规则提取的结果通常足够准确（正则匹配年龄、关键词匹配特征）
- LLM 的价值在于"意图分类"和"查询改写"，而非实体提取

**建议方向**：
- 实体提取完全用规则（零延迟），LLM 只做意图分类 + 查询改写
- 减少 LLM 的 token 输出（不需要输出 behavior_traits 等可由规则确定的字段）

---

### P3-2: Schema 类型定义三套不一致

**现状**：
- `schema.py` 定义 8 种实体类型
- `md_generator.py` prompt 中定义 11 种
- 前端 `ENTITY_TYPES` 定义 6 种
- D2G 方案定义了 15 种

**问题**：同一个实体类型的名称和数量在三个地方不一致，导致前后端对不齐。

**建议方向**：统一为 D2G 的 15 种类型，`schema.py` 为单一真相源，前端从前端常量映射。

---

### P3-3: `_direct_search` HTTP URL 硬编码 `127.0.0.1`

**现状**：
- `_direct_search`（[base.py:344-348](backend/src/core/knowledge_qa/nodes/base.py#L344-L348)）和 `_analyze_and_search_books`（[match_books.py:296-298](backend/src/core/knowledge_qa/nodes/match_books.py#L296-L298)）中：
  ```python
  host = getattr(settings, "app_host", "127.0.0.1")
  port = getattr(settings, "app_port", 8000)
  if host == "0.0.0.0":
      host = "127.0.0.1"
  ```

**问题**：
1. 同一段代码在 `match_books.py` 和 `base.py` 中重复
2. 微服务部署（知识库独立部署）时，`http://127.0.0.1:8000/rag/search` 可能不可达——应该调用知识库服务的独立 URL

**建议方向**：
1. 提取为共用函数 `_get_rag_service_url()`
2. 通过配置支持独立的 RAG 服务 URL（而非依赖 app_host/app_port）
