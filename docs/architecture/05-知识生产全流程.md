### 1.1 硬约束: 知识库上传 → 绑定 → 策管

> **核心原则**: 知识库上传是策管的**唯一前置**。所有书籍必须先获得 `kb_book_id`，不存在"直接上传到策管"的路径。

```
Step 1 (必须)          Step 2 (必须)           Step 3 (自动)
────────────          ────────────           ────────────
知识库上传 EPUB        绑定页选定               AI 生成 → 审核
/knowledge-base       /admin/curation         → Neo4j 入库
→ 分块 → Chroma       → 按 kb_book_id 绑定    → KG 可视化
→ 分配 kb_book_id     → 绑定（重新读 EPUB）
```

**三条铁律**:

| # | 规则 |
|---|------|
| 1 | 书籍必须先存在于知识库中，拥有 `kb_book_id` |
| 2 | `kb_book_id` 仅作登记凭据。策管绑定后重新读取原始 EPUB，独立解析章节，**不使用知识库的 chunks** |
| 3 | 非 EPUB 格式不可策管（绑定页会拒绝 PDF 等格式）

## 2. 阶段 A: 知识库上传与绑定

> **前置**: 用户已在知识库 `/knowledge-base` 完成 EPUB 上传，获得了 `kb_book_id`。

### 2.1 用户操作

用户在策管入口页（`/admin/curation`）看到知识库中已上传、但尚未绑定的 EPUB 列表。选中一本书 → 点击「选定并绑定」。

### 2.2 系统行为

```
1. 根据 kb_book_id 定位原始 EPUB 文件路径

2. 策管独立重新读取 EPUB:
   - EPUBChapterParser.parse(epub_path) → 完整章节列表
   - 每章获得完整文本（非 chunks 碎片）

3. 在策管 DB 中创建书籍记录:
   - 记录 kb_book_id 作为关联凭据
   curation_book_id = uuid()
   kb_book_id = "kb_001"
   status = "draft"
   chapters = [...]
```

### 4.3 审核操作的交互细节

| 操作 | 触发方式 | 系统行为 |
|------|---------|---------|
| **编辑实体** | 点击左侧实体名 → 右侧 MD 滚动到对应位置 → 直接编辑 YAML | 实时保存到草稿 |
| **新增实体** | 左侧「+ 新增」按钮 → 弹出 YAML 模板 → 填写 | 追加到 MD 对应段落 |
| **删除实体** | 左侧实体右侧「×」按钮 → 确认弹窗 | 从 MD 中移除对应段落 |
| **解决矛盾** | 右侧面板「章间矛盾」→ 点击「查看」→ 并排对照两个描述 → 选择保留哪个或手动合并 | 更新 MD，同一实体只保留一个描述 |
| **重生成单章** | 左侧失败章节 → 点击「重新生成」 | 触发单章 ChapterGenerator |
| **确认实体** | 左侧实体左侧「✓」勾选框 | 标记为「已确认」（视觉上从橙色变为绿色） |
| **标记为已审核** | 顶部按钮「标记为已审核」 | 状态流转 draft → reviewed，记录审核人和时间 |
| **入库 Neo4j** | 顶部按钮「入库 Neo4j」 | 见阶段 D |

### 4.4 为什么要用 MD 作为中间格式

| 理由 | 说明 |
|------|------|
| **人类可读首选** | 审核者不需要了解 Cypher，直接阅读 Markdown + YAML |
| **Git diff 友好** | 审阅修改可版本控制 |
| **LLM 原生格式** | 生成和理解都是 Markdown |
| **双向可转换** | MD ↔ Cypher MERGE 确定性地互相转换，不存在信息丢失 |
| **断点恢复** | 草稿以文件/DB 存储，审核中断后可继续 |

## 5. 阶段 D: 入库 Neo4j——第一本书

### 5.1 用户操作

在审核页面点击「入库 Neo4j」。

### 5.2 系统行为

```
1. MD 状态检查: status == "reviewed" 才允许入库
2. MDParser.parse(md_text) → ParsedDocument
3. MDParser.to_cypher(doc) → list[CypherStatement]
4. Neo4j 事务: 逐条执行 MERGE（幂等）
5. 更新 MD status = "published"
6. 返回入库结果给前端
```

### 7.1 与第一本书的差异

### 8.2 跨书关系确认操作

| 跨书关系类型 | MD 中标注 | 用户可执行操作 |

```yaml
    custom_value: null

    relation_type: "CONSENSUS"

```

## 9. 阶段 H: 增量入库——第二本书

### 9.1 与第一本书入库的差异

第二本书入库使用 **MERGE 幂等操作**：

| 场景 | Cypher 行为 | 示例 |
|------|-----------|------|
| 新实体（Neo4j 中不存在） | `MERGE` 创建新节点 | 新书独有的「社交焦虑」→ 新建 |
| 已有实体（同名同类型） | `MERGE` 匹配已有节点 → 仅更新属性 → 不创建重复节点 | 「前额叶皮层」已存在 → 仅追加新书引用 |
| 跨书关系（已确认） | `MERGE` 创建 `CROSS_BOOK_*` 边 | 「有氧运动」→ `CROSS_BOOK_CONSENSUS` → 「运动改变大脑」的「有氧运动」 |
