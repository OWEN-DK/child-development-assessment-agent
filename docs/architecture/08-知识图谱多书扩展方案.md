# 知识图谱多书扩展方案 — 第二本书入库时的图谱变更设计

> **版本**: v1.3
> **日期**: 2026-05-31（v1.3 跨文档一致性审核修复）
> **状态**: ✅ 已审核（v1.3 修复跨文档一致性问题）
> **依赖**: [07-知识图谱直提方案-D2G.md](07-知识图谱直提方案-D2G.md)（D2G v1.4）
> **目的**: 补充 D2G 方案在"第二本书入库"场景下的完整链路设计——跨书实体消歧、审核阶段跨书感知、全局图重建策略

## 1. 问题背景

D2G 方案（§07）的 Phase 0→4 覆盖了**单本书**从 EPUB 到 Neo4j 知识图谱的完整链路。但在实际使用中，系统会持续导入新书。**第二本书入库时**，以下问题未被 D2G 覆盖：

| # | 问题 | D2G 现状 | 影响 |
|---|------|---------|------|
| 1 | 跨书实体消歧 | §8.4 仅做书内消歧 | 书2的"有氧运动"不会与书1的"Exercise_A"合并，图中出现重复节点 |
| 2 | 跨书实体合并后的关系迁移 | 未设计 | 合并节点后，两本书各自的关系边需要重新指向合并后的节点 |
| 3 | `cross_relation.py` 不兼容 D2G 实体类型 | §13.3 标注"不需要改动"（v1.3 已修正为"需要修改"） | 现有代码只查 `AutoEntity`，D2G 的 15 种类型全部漏掉 |
| 4 | 审核阶段无跨书感知 | 审核 MD 仅展示书内已有实体 | 审核者不知道哪些实体已在其他书中提取过，可能重复提取 |
| 5 | 全局图重建触发时机 | 未设计 | `global_rebuild.py` 目前是定时全量，D2G 入库后何时触发不明确 |

### 1.1 现有多书链路（v1/v2）

```
书1 → extract → persist(Entity/Relation) → book-level graph + community tree
书2 → extract → persist(Entity/Relation) → book-level graph + community tree
     ↓ 定时/手动
global_rebuild.py → 跨书同名合并(纯字符串) → 全局图 → 全局社区树
     ↓ 查询时
traversal.py → 社区树遍历 → 命中块 → 知识上下文
```

### 1.2 D2G 多书链路（本方案）

```
书1 → D2G Phase 0-4 → Neo4j 单书图谱
书2 → D2G Phase 0-4 → Neo4j 单书图谱
  │   └── Phase 2 增强: 审核 MD 展示跨书匹配，审核者可决策
  ▼
Phase 5: 跨书实体消歧（三层策略）
  ├── 高相似(>0.9): 合并为同一节点 + 关系迁移
  ├── 中相似(0.7-0.9): 创建 SAME_AS 边
  └── 低相似(<0.7): 不处理
  │
  ▼
跨书关系检测（更新后的 cross_relation.py）
  │
  ▼
全局图重建 → 全局社区树
```

## 2. 跨书实体消歧策略

### 2.1 三种策略对比

| 维度 | 方案 A: 合并 | 方案 B: 独立+SAME_AS | 方案 C: 分层处理 ✅ |
|------|------------|-------------------|-----------------|
| 图简洁度 | ⭐⭐⭐⭐⭐ | ⭐⭐ | ⭐⭐⭐⭐ |
| 查询准确性 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐ |
| 数据安全 | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ |
| 审核复杂度 | 中 | 低 | 高 |
| 回退难度 | 高 | 低 | 中 |

**选定方案 C（分层处理）**：按 embedding 相似度分三档，兼顾简洁性和安全性。

> **时序说明**: 跨书消歧分两步执行——(1) **Phase 2 审核前**：embedding 粗筛提前执行（§3.2），将跨书匹配结果展示在审核 MD 中，审核者可标记决策（合并/独立/跳过）；(2) **Phase 5**：全书审核通过后，执行实际的节点合并/建边，优先执行审核者决策（§2.5），无决策的按自动阈值处理。两步分离的原因是：审核者可能删除/编辑实体（D2G §8.6），Phase 5 必须基于最终审核结果执行。

### 2.2 分层阈值

| 相似度范围 | 判定 | 执行动作 | 示例 |
|-----------|------|---------|------|
| > 0.9 | 高度相似（同一概念） | **合并**为同一节点 | "BDNF" ↔ "脑源性神经营养因子" |
| 0.7 ~ 0.9 | 中度相似（可能同一概念） | 创建 **SAME_AS** 边 | "注意力训练" ↔ "专注力练习" |
| < 0.7 | 低相似度 | **不处理** | "有氧运动" ↔ "冥想" |

> **阈值校准**：初始值基于 DashScope `text-embedding-v4` 的中文语义经验。PoC 阶段（§11.1 Step 1）需对第一本书和第二本书的重叠实体跑 benchmark，按 F1 最优调整阈值，写入 `d2g_config.yaml`。

> **按领域配置阈值**：不同领域的书籍，实体名称的语义距离分布不同（如医学术语精确度高、教育概念模糊度高）。`d2g_config.yaml` 支持按书籍领域设置不同阈值：

```yaml
# d2g_config.yaml
disambiguation:
  default:
    high_similarity: 0.9    # 合并阈值
    mid_similarity: 0.7     # SAME_AS 阈值
  domains:
    medical:
      high_similarity: 0.85  # 医学术语精确度高，可适当降低
      mid_similarity: 0.65
    education:
      high_similarity: 0.92  # 教育概念模糊度高，需提高
      mid_similarity: 0.75
```

领域通过书籍元数据中的 `domain` 字段确定。未配置的领域使用 `default` 阈值。

### 2.3 合并流程（高相似度 > 0.9）

在 Neo4j 事务内执行，确保原子性。采用**双字段方案**（与 §9.3 一致）：`book_id` 保留 string 不变，新增 `book_ids: list[string]` 存储所有来源书籍。

```cypher
// ========== Step 0: 查找待合并节点 ==========
// 通过 name_normalized 精确匹配
// 注意：用 book_ids 列表匹配而非 book_id 单值，因为已被合并的节点
// 的 book_id 保留的是第一个入库的书籍 ID，但 book_ids 包含所有来源书籍。
// 例如：书2的实体合并到书1后，book_id="book1"，但 book_ids=["book1","book2"]。
// 书3入库时需要通过 book_ids 才能找到这个已合并的节点。
MATCH (old {name_normalized: $old_name_norm})
WHERE $old_book_id IN coalesce(old.book_ids, [old.book_id])
MATCH (new {name_normalized: $new_name_norm})
WHERE $new_book_id IN coalesce(new.book_ids, [new.book_id])
WITH old, new

// ========== Step 1: 记录合并来源（用于回滚，见 §11.2） ==========
// 使用独立 MergeLog 节点而非节点属性，避免 merged_from 列表无限膨胀
CREATE (log:MergeLog {
    target_entity: old.name_normalized,
    source_entity: new.name_normalized,
    source_book_id: new.book_id,
    original_description: new.description,
    original_book_ids: coalesce(new.book_ids, [new.book_id]),
    merged_at: datetime(),
    merge_id: randomUUID()
})
CREATE (old)-[:MERGED_FROM]->(log)

// ========== Step 2: 合并节点属性 ==========
// description 合并策略沿用 D2G §4.4
SET old.description = CASE
    WHEN size(old.description) > 1.5 * size(new.description) THEN old.description
    WHEN size(new.description) > 1.5 * size(old.description) THEN new.description
    ELSE old.description + '---' + new.description
END
SET old.source_chapters = old.source_chapters + new.source_chapters
// 双字段方案：book_id 不变，book_ids 追加
SET old.book_ids = coalesce(old.book_ids, [old.book_id]) + coalesce(new.book_ids, [new.book_id])
// name_normalized 保持 old 的值不变（两者应相同，否则不应触发合并）

// ========== Step 3: 迁移普通关系 ==========
// 入边：CREATE 而非 MERGE，避免与已有关系冲突导致关系丢失
FOREACH (ignore IN CASE WHEN true THEN [1] ELSE [] END |
    WITH old, new
    MATCH (src)-[r]->(new)
    WHERE src <> old AND type(r) <> 'SAME_AS'
    CREATE (src)-[r2]->(old)
    SET r2 = properties(r)
    DELETE r
)

// 出边
FOREACH (ignore IN CASE WHEN true THEN [1] ELSE [] END |
    WITH old, new
    MATCH (new)-[r]->(dst)
    WHERE dst <> old AND type(r) <> 'SAME_AS'
    CREATE (old)-[r2]->(dst)
    SET r2 = properties(r)
    DELETE r
)

// ========== Step 4: 迁移 SAME_AS 边 ==========
// 入边 SAME_AS：其他节点 → new → 改指向 old
MATCH (src)-[r:SAME_AS]->(new)
WHERE src <> old
CREATE (src)-[r2:SAME_AS]->(old)
SET r2 = properties(r)
DELETE r

// 出边 SAME_AS：new → 其他节点 → 改从 old 出发
MATCH (new)-[r:SAME_AS]->(dst)
WHERE dst <> old
CREATE (old)-[r2:SAME_AS]->(dst)
SET r2 = properties(r)
DELETE r

// ========== Step 5: 删除新节点 ==========
DETACH DELETE new
```

> **`book_id` 双字段方案**：`book_id`（string）保持不变，存第一个入库的书籍 ID；`book_ids`（list[string]]）存储所有来源书籍 ID。现有查询（`WHERE book_id = $id`）不需要改动，跨书查询用 `WHERE $id IN book_ids`。详见 §9.3。

> **`name_normalized` 一致性**：合并前校验 `old.name_normalized == new.name_normalized`，不一致时拒绝合并（说明 embedding 粗筛误命中）。Phase 4 入库时已通过 `name.strip().lower()` 计算 `name_normalized`（D2G v1.4 §10.1）。

### 2.4 SAME_AS 边策略（中相似度 0.7~0.9）

```cypher
MATCH (a {name_normalized: $name_a_norm, book_id: $book1_id})
MATCH (b {name_normalized: $name_b_norm, book_id: $book2_id})
MERGE (a)-[r:SAME_AS]->(b)
SET r.confidence = $similarity,
    r.created_by = 'd2g_phase5',
    r.llm_reason = $reason,
    r.created_at = datetime()
```

**查询时展开 SAME_AS**：

```cypher
// 查找某实体及其所有跨书同义实体
MATCH (n {name: $entity_name})
OPTIONAL MATCH (n)-[:SAME_AS]-(related)
RETURN n, collect(related) AS same_as_entities
```

### 2.5 审核者决策覆盖

Phase 2 审核时，审核者对每个跨书匹配标记了决策（合并/独立/跳过）。Phase 5 优先执行审核者决策。

> **实现机制**: Phase 2 生成审核 MD 时，先执行跨书 embedding 粗筛（§3.2），将匹配结果写入审核 MD 的"跨书匹配"章节。审核者在审核 MD 中对每个匹配标记决策。这些决策被序列化到 Redis（`d2g:cross_decisions:{book_id}`），Phase 5 执行时优先读取。详见 §3 和 §4.2 Step 2。

| 审核者决策 | Phase 5 执行 | 说明 |
|-----------|-------------|------|
| **合并** | 无论相似度，执行合并（§2.3） | 审核者确认是同一概念 |
| **独立** | 无论相似度，不合并不建边 | 审核者确认是不同概念 |
| **跳过** | 按自动阈值处理（§2.2 分层） | 审核者不确定，交给算法 |

### 2.6 消歧失败兜底

| 失败场景 | 处理策略 |
|---------|---------|
| 合并事务失败（Neo4j 超时/锁冲突） | 回滚事务，标记该实体对为"待人工处理"，在日志中记录 |
| SAME_AS 边创建失败 | 跳过该对，记录警告日志，不影响其他实体对 |
| embedding 计算超时 | 降级为名称精确匹配 + 括号内别名匹配 |
| LLM 精判超时 | 按 same=false 处理（保守策略），在日志中标记 |

### 2.7 SAME_AS 边生命周期管理

SAME_AS 边创建后，需要支持以下生命周期操作：

#### 2.7.1 事后修正（审核者/运维操作）

| 操作 | 触发场景 | 实现方式 |
|------|---------|---------|
| **撤销 SAME_AS** | 审核者事后判定两个实体不应关联 | 按 `merge_id` 软删除（标记 `revoked=true`） |
| **升级为合并** | 多本书验证后确认 SAME_AS 对是同一概念 | 执行 §2.3 合并流程，自动删除 SAME_AS 边 |
| **降级为独立** | 发现误判，需拆分已合并的节点 | 按 `MergeLog` 节点中的 `original_description` 和 `original_book_ids` 拆分（§11.2） |

**API 设计**：

```python
async def revoke_same_as(merge_id: str, reason: str, neo4j_session):
    """撤销指定的 SAME_AS 边（软删除，保留审计 trail）。"""
    neo4j_session.run("""
        MATCH ()-[r:SAME_AS {merge_id: $merge_id}]->()
        SET r.revoked = true, r.revoked_at = datetime(), r.revoke_reason = $reason
    """, merge_id=merge_id, reason=reason)

async def list_active_same_as(entity_name: str, neo4j_session):
    """查询某实体的所有活跃 SAME_AS 关联（过滤已撤销）。"""
    return neo4j_session.run("""
        MATCH (n {name: $name})-[r:SAME_AS]-(related)
        WHERE NOT coalesce(r.revoked, false)
        RETURN related.name AS name, related.book_id AS book_id
    """, name=entity_name).data()
```

#### 2.7.2 SAME_AS 边属性

每条 SAME_AS 边包含以下属性，支持完整的生命周期管理：

| 属性 | 类型 | 说明 |
|------|------|------|
| `confidence` | float | embedding 相似度 |
| `created_by` | string | `"d2g_phase5"` 或 `"reviewer"` |
| `created_at` | datetime | 创建时间 |
| `merge_id` | string | UUID，用于精确引用和撤销 |
| `llm_reason` | string? | LLM 判断理由 |
| `reviewer_decision` | string? | 审核者覆盖决策 |
| `revoked` | bool | 是否已撤销（默认 false） |
| `revoked_at` | datetime? | 撤销时间 |
| `revoke_reason` | string? | 撤销原因 |

#### 2.7.3 SAME_AS 边清理策略

| 场景 | 策略 |
|------|------|
| 全局图重建时 | `revoked=true` 的边不参与社区检测和查询展开 |
| 定期清理 | 每 50 本书后，删除 `revoked=true` 且 `revoked_at` > 30 天的边 |
| 合并后自动清理 | 两个实体被合并后，它们之间的 SAME_AS 边自动删除（§2.3 Step 4） |

## 3. Phase 2 增强：审核 MD 跨书匹配展示

### 3.1 触发条件

当 Neo4j 中已有其他书的实体时（即不是第一本书入库），Phase 2 生成审核 MD 时额外查询跨书匹配。

### 3.2 查询流程

```
本章提取的实体列表
  │
  ▼
从 Neo4j 加载其他书的所有实体
  │ WHERE book_id <> current_book_id
  │ 仅查 D2G 的 15 种类型节点
  ▼
embedding 粗筛 → cosine similarity
  │ 复用 Phase 2 消歧时的 embedding 缓存
  ▼
过滤 similarity >= 0.7 的候选
  │
  ▼
LLM 精判（Top 3 候选/实体）
  │ prompt: "判断两个实体是否指代同一概念"
  ▼
写入审核 MD 的"跨书匹配"章节
```

### 3.3 审核 MD 新增章节

在现有"新增实体"和"已有实体"之后，新增：

```markdown
## 跨书匹配（与已入库书籍的相似实体）

### BDNF（脑源性神经营养因子）
**本章描述**: 一种蛋白质，被称为"大脑的肥料"...

**匹配到**:
| # | 书名 | 实体名 | 相似度 | LLM判断 | 审核者决策 |
|---|------|--------|--------|---------|-----------|
| 1 | 《运动改造大脑》 | BDNF | 0.92 | 同一概念 | ○合并 ○独立 ○跳过 |
| 2 | 《儿童大脑发育》 | 脑源性神经营养因子 | 0.85 | 同一概念 | ○合并 ○独立 ○跳过 |

### 注意力训练
**本章描述**: 通过特定练习提升儿童注意力持续时间的方法...

**匹配到**:
| # | 书名 | 实体名 | 相似度 | LLM判断 | 审核者决策 |
|---|------|--------|--------|---------|-----------|
| 1 | 《专注力训练法》 | 注意力训练法 | 0.78 | 可能相关 | ○合并 ○独立 ○跳过 |

> **默认值**: 审核者决策列默认选中"跳过"。审核者不操作时视为"跳过"，Phase 5 按自动阈值处理。
```

### 3.4 审核者决策的存储

审核者在前端标记的决策**同时写入两个位置**：

1. **审核 MD 文件**（主存储）：保存回审核 MD 的表格中（修改"审核者决策"列的值），与现有审核流程一致
2. **Redis**（备份存储）：每次审核操作同步写入 Redis（key: `d2g:reviewer_decisions:{book_id}`，hash 结构，field = 实体名，value = decision JSON）

> **为什么需要 Redis 备份？** 审核者可能手动编辑 MD 文件导致格式损坏（删除表格行、改了列名等），Phase 5 解析 MD 失败时可从 Redis 读取备份。Redis 数据在全书入库成功后删除。

### 3.5 前端改动

`DraftEditorPage.tsx` 需要：
1. 解析 `## 跨书匹配` 章节
2. 为每个匹配项渲染单选按钮（合并/独立/跳过），默认选中"跳过"
3. 审核者决策保存到审核 MD 的表格中
4. 改动量约 50-80 行，不影响核心解析逻辑

### 3.6 性能优化

- **embedding 复用**：计算复用 Phase 2 消歧时的缓存，不额外调用 embedding API
- **LLM 精判范围**：仅对 `similarity >= 0.7` 的候选执行（通常每章 0-5 个），不增加显著成本
- **Neo4j 查询优化**：其他书实体总数 < 500 时直接全量加载比较；≥ 500 时按实体类型分组加载 + 按本章实体类型预过滤（只加载与本章实体类型相同的其他书实体），将比较空间从 N 降至 N × 同类型比例
- **embedding 索引缓存**：Phase 5 首次执行时将其他书实体的 embedding 向量缓存到 Redis（key: `d2g:cross_emb:{book_id}`），后续章节审核时直接从 Redis 加载，避免重复调用 embedding API 和 Neo4j 查询
- **跨书匹配结果缓存**：同一本书的跨书匹配结果缓存在 Redis（key: `d2g:cross_match:{book_id}`），审核不同章节时不重复查询

## 4. Phase 5：跨书实体消歧与全局图更新

### 4.1 执行时机

Phase 5 在以下条件**全部满足**时触发：

1. **全书所有章节审核完成** — 所有章节的审核 MD 状态均为"已批准"
2. **Phase 4 全部入库成功** — Neo4j 中已存在该书的所有实体和关系节点
3. **不是第一本书** — Neo4j 中已有其他书的实体（否则跳过 Phase 5）

> **为什么不能在 Phase 4 中途触发？** 审核者可能删除/编辑实体（D2G §8.6），Phase 5 必须基于最终审核结果执行。如果中途触发，合并决策可能基于被后续编辑删除的实体。

> **章节驳回场景**：如果某个章节被驳回需重新提取（D2G §9.2），Phase 5 不触发，直到该章节重新通过审核。

### 4.2 完整流程

```
Phase 5 输入: 新书已入库 Neo4j（Phase 4 完成）
  │
  ├── Step 0: 前置条件校验
  │   ├── 检查所有章节审核状态是否均为"已批准"
  │   ├── 检查 Neo4j 中是否存在其他书的实体
  │   └── 任一条件不满足 → 跳过 Phase 5
  │
  ├── Step 1: 加载数据
  │   ├── 从 Neo4j 加载新书所有实体（WHERE book_id = new_book_id）
  │   └── 从 Neo4j 加载其他书所有实体（WHERE book_id <> new_book_id，15 种类型）
  │
  ├── Step 2: 加载审核者决策
  │   └── 解析所有章节审核 MD 中的"跨书匹配"表格，提取 {entity, decision} 对
  │
  ├── Step 3: embedding 粗筛
  │   ├── 对新书实体计算 embedding（复用缓存）
  │   └── 与已有实体计算 cosine similarity，按阈值分三档
  │
  ├── Step 4: LLM 精判
  │   └── 对 embedding 命中对（similarity >= 0.7）调用 LLM 判断是否同一概念
  │
  ├── Step 5: 执行合并/建边
  │   ├── 有审核者决策 → 按决策执行
  │   └── 无审核者决策 → 按自动阈值执行
  │       ├── same=true + similarity > 0.9 → 合并（§2.3）
  │       ├── same=true + similarity 0.7-0.9 → SAME_AS 边（§2.4）
  │       └── same=false → 不处理
  │
  ├── Step 6: 跨书关系检测
  │   └── 调用更新后的 cross_relation.py，检测 CONSENSUS/COMPLEMENTS/CONFLICTS
  │
  └── Step 7: 触发全局图重建
      └── 调用 global_rebuild.py（全量或增量，取决于配置）
```

### 4.3 持久化设计

| 数据 | 存储位置 | Key 格式 | 用途 |
|------|---------|---------|------|
| 跨书消歧结果 | Redis | `d2g:cross_disambig:{book_id}` | 记录每对实体的消歧决策，支持审计 |
| SAME_AS 边 | Neo4j | — | 查询时展开跨书同义实体 |

## 5. `cross_relation.py` 兼容 D2G 实体类型

### 5.1 当前问题

`cross_relation.py` 的 `detect_cross_book_relations()` 只查询 `AutoEntity` 节点：

```python
existing = neo4j_session.run("""
    MATCH (ae:AutoEntity)
    WHERE ae.book_id <> $book_id
    RETURN ae.name AS name, ae.entity_type AS type, ...
""", book_id=new_book_id)
```

D2G 的 15 种类型（Problem, Solution, BrainRegion 等）全部被忽略。

### 5.2 修复方案

> **注意**：§5.3 已说明 `cross_relation.py` 不需要查询所有实体——Phase 5 已完成相似实体发现，`cross_relation.py` 只需对 SAME_AS 实体对检测关系类型。以下方案保留作为**通用查询模式**，供其他需要遍历所有 D2G 实体类型的场景使用。

查询所有 D2G 实体类型标签（不改入库逻辑，只改查询）。使用 Cypher 的 `labels()` 函数避免 14 次独立查询：

```python
# 单次查询获取所有 D2G 类型的实体
D2G_LABELS = [
    "Problem", "Solution", "BrainRegion", "Risk", "Exercise",
    "RootCause", "Prescription", "ChildProfile",
    "CognitiveProcess", "Theory", "Mechanism",
    "DevelopmentalStage", "Strategy", "KeyInsight", "ResearchFinding",
]

existing = neo4j_session.run("""
    MATCH (n)
    WHERE any(label IN labels(n) WHERE label IN $d2g_labels)
      AND n.book_id <> $book_id
    RETURN n.name AS name, labels(n) AS types,
           n.description AS desc, n.book_id AS book_id
""", d2g_labels=D2G_LABELS, book_id=new_book_id).data()
```

### 5.3 名称匹配策略

`cross_relation.py` 的任务是检测**跨书关系**（CONSENSUS/COMPLEMENTS/CONFLICTS），不是实体去重（实体去重由 Phase 5 处理）。因此名称匹配策略分两层：

1. **Phase 5 已处理的实体对**：如果两个实体已被 Phase 5 合并或建立了 SAME_AS 边，`cross_relation.py` 直接跳过（无需重复检测）
2. **Phase 5 未处理的实体对**（similarity < 0.7）：这些实体已经被判定为"不同概念"，不需要检测跨书关系
3. **剩余候选**：Phase 5 建立了 SAME_AS 边的实体对（similarity 0.7-0.9），这些是最可能有跨书关系的候选

因此 `cross_relation.py` 的名称匹配保持现有的简单策略即可，**不需要升级为 embedding 相似度**。Phase 5 已经完成了"找到相似实体"的工作，`cross_relation.py` 只需对 SAME_AS 实体对检测关系类型。

```python
async def detect_cross_book_relations_for_same_as(
    neo4j_session,
    llm_client: LLMClient,
) -> list[CrossBookRelation]:
    """检测已有 SAME_AS 边的实体对之间的跨书关系类型。"""
    pairs = neo4j_session.run("""
        MATCH (a)-[r:SAME_AS]->(b)
        WHERE a.book_id <> b.book_id
        RETURN a.name AS name_a, a.description AS desc_a, a.book_id AS book_a,
               b.name AS name_b, b.description AS desc_b, b.book_id AS book_b,
               r.confidence AS similarity
    """).data()

    relations = []
    for pair in pairs:
        relation = await _llm_judge_relation_type(pair, llm_client)
        if relation:
            relations.append(relation)
    return relations
```

### 5.4 `book_id` 类型变更影响

合并后 `book_id` 从 `string` 改为 `list[string]`，以下查询需要适配：

| 文件 | 查询模式 | 适配方式 |
|------|---------|---------|
| `cross_relation.py` | `WHERE book_id <> $id` | `WHERE NOT $id IN book_id` |
| `query_dispatcher.py` | `WHERE book_id IN $ids` | `WHERE ANY(id IN $ids WHERE id IN book_id)` |
| `global_rebuild.py` | `e.book_id = ""` | `e.book_id = []` |
| `builder.py` | `G.nodes[n].get("book_id")` | 需处理 list 类型 |

> **兼容方案**：为了减少改动量，可以在合并时不修改 `book_id` 类型，而是新增 `book_ids: list[string]` 字段存储所有来源书籍。原始 `book_id` 保留第一个入库的书籍 ID 作为"主书"。这样现有查询不需要改动，跨书查询用 `book_ids` 字段。

## 6. 全局图重建策略

### 6.1 阶段一：全量重建（2-3 本书）

每本书 D2G 入库 + Phase 5 完成后，自动触发 `global_rebuild.py`：

1. 加载所有书的实体和关系
2. 跨书同名实体合并（升级为 embedding 相似度匹配，替代纯字符串匹配）
3. 全局图构建 + Louvain 社区检测
4. 全局社区树存储到 MySQL

**触发时机**：Phase 5 Step 7 自动触发（`book_pipeline.py` 编排）。

> **与 D2G §10.3 的关系**：D2G §10.3 的社区检测是**单书级别**（book-level community tree），在 Phase 4 入库前执行，用于单本书内部的社区聚类。本方案 §6.1 是**全局级别**（global community tree），在 Phase 5 完成后执行，用于跨书的社区聚类。两者不冲突：单书社区树服务于单书内的检索，全局社区树服务于跨书检索。全局重建时会重新计算所有书的社区结构，覆盖 book-level 结果。

**与 Phase 5 的分工**：

- **Phase 5** 已完成跨书实体合并（高相似度合并 + 中相似度 SAME_AS 边）
- **全局重建**在 Phase 5 之后执行，**不需要重复 embedding 合并**，职责为：
  1. 加载所有书的实体（此时已包含 Phase 5 的合并结果）
  2. 构建全局 NetworkX 图
  3. Louvain 社区检测
  4. 全局社区树存储到 MySQL

`global_rebuild.py` 的 `_merge_entities_by_name()` 保留现有简单名称匹配作为兜底（处理 Phase 5 阈值调整后可能遗漏的边界情况），不需要升级为 embedding 合并。

### 6.2 阶段二：增量更新（≥5 本书）

当书量增长到全量重建耗时不可接受时（>30s），切换为增量模式：

1. 仅加载新书的实体和关系
2. 与全局图中已有实体做消歧（复用 Phase 5 的 embedding + LLM 流程）
3. 增量合并新实体到全局图
4. 局部重新运行 Louvain 社区检测（仅受影响的社区）
5. 更新全局社区树

**切换条件**：通过配置项 `global_rebuild_mode: "full" | "incremental"` 控制。

### 6.3 跨书关系与全局社区树

跨书关系（CONSENSUS/COMPLEMENTS/CONFLICTS）存入 Neo4j 后，全局社区检测会自然发现这些跨书连接——它们作为"桥接边"将不同书的实体拉入同一社区。这是 GraphRAG 的核心优势：**不需要手动管理跨书关联，图结构自动内生**。

## 11. 灰度与回滚

### 11.1 灰度方案

```
Step 1: 第二本书 PoC
  - 选一本与第一本书有大量重叠实体的书
  - D2G Phase 0-4 + Phase 5 全流程跑通
  - 验证合并/SAME_AS/跨书关系的正确性

Step 2: 审核者验证
  - 审核者检查跨书匹配结果
  - 确认审核者决策能正确覆盖自动阈值
  - 收集阈值校准数据

Step 3: 多书验证
  - 3 本书的完整入库 + 跨书消歧
  - 验证全局图重建和社区检测
  - 验证查询端 traversal.py 的跨书检索效果
```

### 11.2 回滚方案

- **配置开关**：`book_pipeline.py` 中 `enable_phase5: true/false`，回滚 = 设为 false
- **SAME_AS 边**：带 `created_by: "d2g_phase5"` 标签，回滚时按标签删除
- **合并节点**：合并时创建独立 `MergeLog` 节点（通过 `MERGED_FROM` 关系连接），回滚时按 `MergeLog` 中的 `original_description` 和 `original_book_ids` 拆分节点。`MergeLog` 节点不随实体节点膨胀，查询时 `MATCH (n)-[:MERGED_FROM]->(log)` 即可获取合并历史
- **全局图**：`global_rebuild.py` 可随时重跑，不受 Phase 5 影响
