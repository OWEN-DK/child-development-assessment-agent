# 最终目的

> 本文档定义 RAG 平台化改造的**根本目标和不可妥协的设计约束**。
> 所有架构决策、技术选型、优先级排序均以本文档为最高依据。
> 最后更新：2026-05-13

## 〇、战略决策：专攻 RAG Platform，弃用旧 Backend

**2026-05-13 决定：**

- **`rag-platform/` 是唯一的开发目标**。所有资源集中于此。
- **`backend/` 已弃用**，不再投入任何开发。其全部能力（除报告生成外）完整继承到 `rag-platform/`。
- **继承原则**：原 `backend/` 是一套经过验证的完整系统。`rag-platform/` 不是从零搭建，而是继承 backend 的全部基础设施和业务能力，仅剥离报告生成（WeasyPrint PDF），其余全部保留并通用化。

**完整继承清单**（从 `backend/` → `rag-platform/backend/`）：

| 类别 | 继承项 |
|------|--------|
| **基础设施配置** | HTTP 端口 51002、分解式 DB 字段、数据库连接池、Redis 全套（密码/连接池/缓存/PubSub/锁/Session）、JWT 认证、CORS、Prometheus、健康检查、Docker 资源限制 |
| **代码模块** | `api/json_response.py`（统一 JSON 响应）、`core/tracing/`（全链路追踪）、`middleware/`（异常/响应/追踪中间件）、`core/llm/adapters/`（LLM 适配器） |
| **Service 层** | `monitoring_service.py`、`alert_service.py`、`config_validation_engine.py`、`config_conflict_detector.py`、`config_health_service.py`、`trace_service.py`、`task_state_service.py`、`task_sse_publisher.py`、`test_run_task_adapter.py`、`export_notification.py` |
| **明确不继承** | 报告生成（WeasyPrint PDF） |

**不可妥协**：
- `rag-platform/` 必须能独立运行，不依赖 `backend/` 的任何代码或服务
- `backend/` 代码保留在仓库中作为参考，但不再维护、不再部署、不再集成
- 继承的模块需去业务化（如提示词模板、配置键中的儿童发展领域概念需移除或通用化）

## 一、多业务域聚合：通过搜索强化实现跨域知识融合

**为什么**：真实场景中，一个查询往往跨越多个知识领域。"高血压合并糖尿病如何用药"涉及心血管内科、内分泌科、药学三个领域的信息。传统单路 RAG 只能从单一知识库检索，无法跨域聚合。不同客户有不同的业务域组合——医疗客户有 6 个科室域，法律客户有 4 个法律分支域。

**目标**：

> 一个查询进入平台后，自动分析涉及哪些业务域，**并行分发到多个域管道**——每个域有自己的知识库、术语体系、检索策略和安全规则——各域独立检索后**跨域聚合**，检测矛盾、去重、统一合成为一份完整答案。
>
> 搜索强化发生在两个层面：**域内**（改写、扩展、BM25/向量检索选择、重排序、安全过滤）和**跨域**（多域并行分发、加权融合、冲突检测、统一合成）。

```
用户查询: "高血压合并糖尿病老年患者如何用药"
              │
              ▼
    ┌─────────────────┐
    │  查询分析 & 域路由  │  ← 识别涉及的业务域，拆解子查询
    └──┬──────┬──────┬──┘
       │      │      │
       ▼      ▼      ▼
   ┌──────┐┌──────┐┌──────┐
   │心血管域││内分泌域││ 药学域 │  ← 每个域独立的管道配置 + 知识库 + 检索策略
   │管道   ││管道   ││管道   │
   └──┬───┘└──┬───┘└──┬───┘
      │       │       │
      └───┬───┴───┬───┘
          ▼       ▼
    ┌─────────────────┐
    │  跨域融合 & 冲突检测 │  ← 加权 RRF 融合、跨域去重、矛盾检测
    └────────┬────────┘
             ▼
    ┌─────────────────┐
    │   统一答案合成     │  ← 标注各段来源域，标注检测到的冲突
    └─────────────────┘
```

**不可妥协**：
- 平台代码不知道任何具体业务域——"心血管""药学"是客户通过 UI 创建和配置出来的
- 新增一个业务域不需要修改任何平台代码：创建知识库 + 配置域管道 + 加入聚合管道即可
- 域管道是可折叠的独立单元：每个域有自己的节点链，域之间互不干扰
- 聚合层节点（查询分析、域分发、跨域融合、冲突检测、统一答案合成）工作在跨域层面
- **权限注入点**：域分发时，根据用户角色裁剪不可见的域管道——无权限的域不被激活
- **单域快捷路径**：查询分析节点检测到只涉及一个域时，直接短路：`查询分析 → 域管道 → 答案合成`，跳过域分发、跨域融合、跨域去重、冲突检测四个聚合节点

## 二、多知识库管理：创建多个独立知识库，通过搜索链接

**为什么**：不同业务域的知识必须分开存储——心血管指南和药学禁忌不能混在同一个向量库中，否则检索时会互相污染。不同角色能看到的库也不同——普通医生不应看到正在内部审核的指南库。用户需要一个平台管理多个独立知识库，在搜索管道中按需链接，同时受权限约束。

**目标**：

> 用户可在平台上创建任意数量的独立知识库——每个知识库有自己的文档集合、分块策略、向量索引。知识库之间物理隔离。
>
> **搜索是链接知识库的方式**：在管道编辑器中配置跨域搜索时，每个业务域绑定一个知识库。一个聚合管道可同时检索 3 个、5 个、10 个知识库，将分散在各库中的信息聚合为完整答案。
>
> **权限控制知识库的可见性**：每个知识库有 `visibility` 属性——公开（租户内全员）、角色可见（指定角色列表）、或私有（仅创建者）。域分发时自动裁剪用户无权限的知识库。
>
> 一个知识库可被多个管道复用（多对多关系）。

```
知识库（独立存在，各有权限）   搜索管道（链接方式，受权限约束）

kb_cardiology [公开] ──────┐
                          │
kb_endocrinology [公开] ──┤
                          ├──→ 跨学科综合问诊管道 → 统一答案
kb_pharmacology [角色:药师]─┤     （普通医生调用时自动跳过药学域）
                          │
kb_geriatrics [私有] ─────┘     （非创建者不可见）

kb_contract_law ────┐
                    ├──→ 法律尽调查询管道 → 统一答案
kb_company_law ─────┘
```

**知识库权限模型**：

| 属性 | 类型 | 说明 |
|------|------|------|
| `visibility` | enum | `public`（租户内所有角色可见）/ `role_scoped`（指定角色列表可见）/ `private`（仅创建者可见） |
| `visible_roles` | list[str] | 当 visibility=role_scoped 时，指定可见的角色列表 |
| `owner_id` | str | 创建者 ID |

**向量存储后端（每个知识库独立选择）**：

不同部署规模需要不同的向量存储。知识库创建时选择后端，可后续迁移。

| 后端 | 适用场景 | 特点 |
|------|---------|------|
| **Chroma**（默认） | 开发/小规模部署 | 轻量、零依赖、本地持久化。适合 < 10 万文档的单机场景 |
| **Elasticsearch** | 中等规模、生产环境 | 内置 BM25 + 向量检索、分布式、全文搜索能力强。选 ES 的知识库**不再需要独立的 BM25 索引** |
| **Milvus** | 大规模、高并发 | 专用向量数据库、十亿级向量、GPU 加速索引。适合 > 100 万文档或高 QPS 场景 |

向量后端选择对管道配置的影响：
- **Chroma**：BM25 检索节点需独立维护关键词索引（当前方案）
- **Elasticsearch**：BM25 检索和向量检索可统一走 ES，管道中的 BM25 节点直接调 ES 的 `match` 查询，向量节点调 ES 的 `knn` 查询
- **Milvus**：向量检索走 Milvus，BM25 仍需独立索引

```
知识库 A（医疗指南）  →  Milvus（千万级文档，高并发）
知识库 B（法律文书）  →  Elasticsearch（需要强大的全文检索 + 向量混合）
知识库 C（内部文档）  →  Chroma（千级文档，轻量部署）
```

**不可妥协**：
- 每个知识库物理独立（独立 collection/index），互不污染
- 每个知识库可独立选择**向量存储后端**（Chroma / Elasticsearch / Milvus），创建后支持迁移
- 每个知识库可独立配置**分块策略**（固定大小/语义/按段落/按标题层级，chunk_size、overlap 等参数可调）
- 每个知识库可独立选择 **Embedding 模型**（DashScope/OpenAI/自定义）、向量维度、相似度度量（cosine/euclidean/dot_product）
- 修改分块、Embedding 配置或向量后端迁移后自动触发全量索引重建
- 管道节点自动适配向量后端：BM25 检索节点检测到 ES 后端时直接用 ES 内置 BM25，否则用独立索引
- 知识库在管道编辑器中通过域绑定的方式引用，即插即用
- **用户看不到无权访问的知识库**：知识库列表、管道编辑器域配置下拉、搜索结果全部受权限裁剪

## 三、双层权限控制：库级别 × 文档级别，全局强制

**为什么**：同一家公司内部，管理员看全部数据，普通医生只看已发布指南库，实习生只看指定教材库；不同公司的数据绝不对彼此可见。不做权限隔离，RAG 检索会因语义相似度把 A 公司的机密文档返回给 B 公司的查询，或在同一公司内把未审核的内部文档返回给普通用户。

权限必须在检索全流程的两个层级注入——仅在一个层级过滤不够：

| 层级 | 过滤对象 | 执行时机 | 失效后果 |
|------|---------|---------|---------|
| **库级别** | 知识库 → 域管道 | 域分发前 | 不该激活的域被激活，浪费计算且暴露知识库存在 |
| **文档级别** | 域管道内的候选文档 | 检索执行时（向量/BM25 的过滤条件） | 检索出无权限文档，信息泄漏 |

**目标**：

> **客户间（租户级）**：共享部署实例，逻辑隔离——共享数据库通过 `tenant_id` 行级过滤隔离，向量库通过命名约定（`{tenant_id}_{kb_id}`）隔离，文件存储通过目录（`storage/{slug}/`）隔离，缓存通过 Key 前缀隔离。一期采用逻辑隔离方案；二期按需支持物理隔离升级路径（独立 DB 实例 / 独立向量库实例）。
>
> **客户内（角色级）**：基于 JWT + RBAC 的双层权限过滤。
>
> **第一层——库级别**：域分发前，根据用户角色裁剪域激活计划。无权限的知识库对应的域管道不被激活。用户甚至不知道不可见知识库的存在。
>
> **第二层——文档级别**：检索执行时，在向量存储的 metadata/字段层面注入 `doc_acl` 过滤条件（Chroma `where` / ES `filter` / Milvus `expr`），确保即使在同一知识库内，不同角色也只能检索到自己有权看到的文档子集。
>
> 两层皆是 **Pre-filter**（查询/检索前注入过滤条件），而非 Post-filter（检索后再丢弃——已泄漏）。

```
请求进入（含 JWT → user_id, tenant_id, roles）
         │
         ▼
  ┌──────────────┐
  │  库级别过滤     │  域分发前：裁剪不可见知识库 → 裁剪域激活计划
  │  (Domain裁剪) │  例：用户无"药学"角色 → 药学域不被激活
  └──────┬───────┘
         │
         ▼
  ┌──────────────┐
  │  域管道执行     │  每个域的检索节点
  │  (并行)       │
  │              │
  │  ┌──────────┐ │  检索时：注入 doc_acl 过滤条件
  │  │ 文档级过滤  │ │  Chroma→where / ES→filter / Milvus→expr
  │  └──────────┘ │
  └──────┬───────┘
         │
         ▼
    跨域融合 → 统一答案
```

**文档 ACL 模型**：

| 属性 | 类型 | 说明 |
|------|------|------|
| `doc_acl` | list[str] | 可访问此文档的角色列表。存储在向量存储的 metadata 中（Chroma metadata / ES fields / Milvus scalar fields） |
| `owner_id` | str | 文档上传者 ID |
| `access_level` | enum | `inherit`（继承知识库可见性，默认）/ `restricted`（独立收紧权限） |

**权限继承规则**：

- 文档上传后默认 `access_level = inherit`，自动获得所属知识库的 `visible_roles` 作为 `doc_acl`
- 仅当文档需要**比知识库更严格的权限**时，设置为 `restricted` 并手动指定 `doc_acl`
- **禁止**文档的权限比知识库更宽松：`restricted` 的 `doc_acl` 必须是知识库 `visible_roles` 的子集
- 知识库 `visible_roles` 变更时，级联更新所有 `inherit` 文档的 `doc_acl`；`restricted` 文档不受影响

**权限变更的副作用**：

- 修改角色权限 → 该租户下所有活跃的语义缓存立即失效
- 修改知识库 `visible_roles` → 该知识库的语义缓存失效，触发其 `inherit` 文档的 metadata 批量更新（不重建索引，metadata 是动态的）
- 修改文档 `access_level` → 仅该文档的 metadata 更新

**不可妥协**：
- 双层权限检查都在检索排名之前执行，不在排名之后（Pre-filter，非 Post-filter）
- 库级别裁剪在域分发时完成，文档级别过滤在向量存储查询条件中完成
- 权限过滤是**全局行为**，所有搜索 API（发布 URL 和通用端点）强制启用，不可绕过
- 同一管道对不同角色返回不同结果——这是设计意图，不是 bug
- 知识库、管道、评估数据集、发布 URL 均按租户隔离
- 权限变更后，相关缓存立即失效
- 行级过滤的结构约束：所有数据访问必须通过 Repository 基类（自动注入 `tenant_id`），禁止裸 SQL 绕过；CI 静态扫描强制检查；后台任务必须显式传入 `tenant_id`

## 四、管道编辑与发布：可视化构建 + 配置输出 URL

### 4.1 可视化管道编辑器

**为什么**：不同客户对搜索精度、安全合规、响应速度的诉求不同。A 客户需要"禁用词过滤 + BM25 检索 + 重排序 + 引用验证"，B 客户需要"同义词扩展 + 向量检索 + 语义缓存"。不能每接一家客户就为它改代码。

**目标**：

> 提供一个**可视化管道编辑器**（基于 React Flow），用户像搭积木一样在画布上拖拽节点构建搜索管道。每个业务域的管道由用户自由选择节点组合——没有任何节点是必选的。不需要的模块（如禁用词过滤、敏感词过滤）直接不拖入管道，完全跳过。
>
> 管道保存为 JSON 配置，后端引擎读取 JSON 编译执行。

**节点体系（22 种域内节点 + 6 种聚合节点，全部可选）**：

**域内节点** —— 每个域管道从中自由选取：

| 类别 | 节点 | 说明 |
|------|------|------|
| 查询理解 | 查询改写、同义词扩展、查询分解、术语标准化、意图分类、**禁用词过滤**、查询扩展 | 禁用词列表可自定义，可不启用 |
| 检索策略 | **BM25 检索**、**向量检索**、**混合检索**、多模态检索、结果融合 | 每种检索方式独立选配，所有参数可调 |
| 安全合规 | 敏感词过滤、PII 脱敏、内容审核 | 全部可选 |
| 质量增强 | 重排序、去重、幻觉检测、引用验证 | 全部可选 |
| 性能优化 | **语义缓存**、**速率限制** | 跨阶段节点，可插入管道任意位置 |
| 答案合成 | **结构化输出** | 将最终答案格式化为 JSON/表格/指定 schema |

**检索节点可配置参数（每一个都必须在 UI 属性面板中可调）**：

| 节点 | 可配置参数 |
|------|-----------|
| **BM25 检索** | `top_k`（返回数量）、`k1`（词频饱和度，默认 1.5）、`b`（文档长度归一化，默认 0.75）、字段权重（标题/正文分别加权）、`score_threshold`（最低分数阈值） |
| **向量检索** | `embedding_model`（模型选择）、`top_k`（返回数量）、`similarity_threshold`（相似度阈值）、`similarity_metric`（cosine/euclidean/dot_product）、`collection_name`（检索目标集合） |
| **混合检索** | `vector_weight`（向量权重 0-1）、`keyword_weight`（关键词权重 0-1）、`top_k`、`fusion_method`（RRF/加权求和/线性组合）、`rrf_k`（RRF 常数，默认 60） |
| **多模态检索** | 各模态 `weight`（文本/图片/表格权重分配）、各模态 `top_k`、`fusion_method` |
| **结果融合** | `fusion_method`（RRF/加权求和/线性组合）、各分支 `weight`、融合后 `final_top_k` |

**安全合规节点可配置参数（全部可选，不拖入即跳过）**：

| 节点 | 可配置参数 |
|------|-----------|
| **敏感词过滤** | `word_list`（敏感词列表，支持在线编辑/导入/正则表达式）、`filter_mode`（删除该文档/脱敏替换为 `***`/仅标记不删除）、`apply_to`（过滤查询文本/过滤检索结果/两者都过滤） |
| **PII 脱敏** | `target_types`（脱敏目标：手机号/身份证/姓名/邮箱/地址/银行卡号，多选）、`mask_char`（替换字符，默认 `*`）、`preserve_pattern`（保留格式的正则，如保留手机号前三位后四位） |
| **内容审核** | `model`（审核 LLM 模型，可设为 `none` 走纯规则模式）、`audit_rules`（审核规则集，可多选：色情/暴力/政治/违法/歧视/广告）、`action`（命中后行为：过滤文档/标记警告/直接拒绝查询）、`threshold`（审核敏感度 0-1） |

**质量增强节点可配置参数**：

| 节点 | 可配置参数 |
|------|-----------|
| **重排序** | `model`（重排序模型，如 rerank-v3）、`initial_k`（送入重排序的候选数）、`final_k`（输出保留数） |
| **去重** | `method`（MinHash/embedding）、`threshold`（相似度阈值，默认 0.85）、`scope`（域内去重/跨文档去重/两者） |
| **幻觉检测** | `model`（检测 LLM 模型）、`threshold`（检测阈值 0-1）、`action`（过滤/标记/两者） |
| **引用验证** | `mode`（strict 严格验证每句/lax 仅验证关键声明）、`model`（验证 LLM 模型） |

**查询理解节点可配置参数**：

| 节点 | 可配置参数 |
|------|-----------|
| **查询改写** | `model`（LLM 模型）、`prompt_template`（改写提示词模板）、`max_retries`（最大重试次数） |
| **同义词扩展** | `synonym_source`（同义词库来源：内置通用词库/域专用词库/自定义上传）、`max_synonyms`（每个词最大扩展数）、`expansion_mode`（全量扩展/仅名词扩展/仅关键术语扩展） |
| **查询分解** | `model`（LLM 模型）、`max_subqueries`（最大子查询数）、`decomposition_strategy`（按并列关系分解/按层级关系分解/自动判断） |
| **术语标准化** | `terminology_source`（术语映射表来源：域内置/自定义上传）、`normalize_mode`（精确匹配/LLM 动态标准化/两者）、`model`（LLM 动态标准化时的模型） |
| **意图分类** | `model`（LLM 模型）、`categories`（分类体系定义，可自定义增删分类）、`routing_rules`（各分类对应的路由规则，如"法规检索类→激活法律域"） |
| **禁用词过滤** | `stop_words`（禁用词列表，支持在线编辑/导入/正则）、`enabled`（是否启用）、`case_sensitive`（是否区分大小写） |
| **查询扩展** | `model`（LLM 模型）、`expansion_count`（生成扩展查询数）、`expansion_method`（改写/加限定条件/换角度提问，可多选） |

**性能优化节点可配置参数**：

| 节点 | 可配置参数 |
|------|-----------|
| **语义缓存** | `cache_backend`（Redis/内存）、`similarity_threshold`（命中阈值 0-1）、`ttl`（缓存过期时间）、`cache_key_strategy`（精确匹配/语义相似匹配）、`max_cache_size`（最大缓存条目数）、`cache_key_scope`（缓存键包含角色信息，防止不同权限用户互相污染缓存） |
| **速率限制** | `max_qps`（每秒最大请求数）、`algorithm`（滑动窗口/令牌桶/漏桶）、`scope`（按域限制/按管道限制/按用户限制）、`action_on_limit`（排队等待/直接拒绝/降级返回缓存） |

**答案合成节点可配置参数**：

| 节点 | 可配置参数 |
|------|-----------|
| **结构化输出** | `output_format`（JSON/Table/Markdown/自定义 Schema）、`schema_definition`（自定义输出结构定义，JSON Schema 格式）、`model`（LLM 模型）、`strict_mode`（严格校验输出格式/宽松容错） |

> **结构化输出与统一答案合成的关系**：结构化输出是**域内节点**——在单个域管道内，将检索到的候选文档格式化为特定结构（如提取药物名称和剂量为 JSON）。统一答案合成是**聚合层节点**——跨域融合完成后，综合多域信息生成最终自然语言答案。两者不冲突：域内结构化输出为聚合层提供结构化中间数据，聚合层在此基础上合成最终答案。

**聚合层节点** —— 跨域协调，其参数同样可配置：

| 节点 | 功能 | 可配置参数 |
|------|------|-----------|
| 查询分析 | LLM 识别查询涉及的领域，拆解子查询 | `model`（LLM 模型）、`max_domains`（最大激活域数）、`min_confidence`（域激活阈值）、`domain_keywords`（各域触发关键词，可自定义） |
| 域分发 | 将子查询并行分发到各域管道（**权限注入点：裁剪不可见域**） | `parallel`（是否并行）、`timeout_ms`（单域超时）、`max_concurrency`（最大并发域数） |
| 跨域融合 | 多域结果加权 RRF 融合 | `fusion_method`（weighted_rrf/weighted_sum/priority_ordered）、各域 `weight`、`rrf_k`、融合后 `final_top_k` |
| 跨域去重 | 移除多域重复文档 | `dedup_threshold`（相似度阈值，默认 0.85）、`dedup_method`（MinHash/embedding） |
| 冲突检测 | 检测跨域矛盾表述 | `model`（LLM 模型）、`enabled`（是否启用）、`conflict_threshold`（矛盾检测敏感度） |
| 统一答案合成 | 综合多域结果生成连贯答案 | `model`（LLM 模型）、`temperature`、`max_tokens`、`include_citations`（是否标注来源域）、`citation_format`（引用格式） |

**不可妥协**：
- 所有节点是可选的——用户按需拖入，不拖入即跳过
- 新增节点类型是平台发版动作（需后端实现新节点类 + 注册）
- 已有节点的参数配置客户可自助完成（UI 属性面板），**所有参数均可调，无硬编码默认值限制**
- 管道编辑器不要求客户写代码
- 域配置中绑定知识库时，下拉列表自动过滤用户无权访问的库
- **管道版本管理**：每次保存自动递增版本号（用户可附加变更说明）；支持回滚到历史版本；管道对比时列出两个版本的节点/参数差异；发布 URL 绑定的版本可切换（不修改 URL）
- **聚合层节点顺序可自由调整**：聚合层 6 个节点的连接顺序由用户在画布上拖拽连线决定，不受固定顺序约束。如用户可选择"先冲突检测再跨域融合"或"先融合再冲突检测"

### 4.1.1 条件路由（条件边）

管道不仅支持线性串联和并行分支，还支持**条件边**——根据上游节点的输出决定走哪条下游分支。条件边在画布上以虚线显示，不同于普通数据流边。

**两类条件边**：

| 类型 | 触发条件 | 典型用法 |
|------|---------|---------|
| **命中 / 未命中** | 语义缓存命中 → 跳过检索链，直接走答案合成；未命中 → 走完整检索 | 语义缓存节点出两条条件边 |
| **分类路由** | 意图分类结果 → 不同意图走不同检索策略 | 意图分类节点出 N 条条件边，每条对应一个分类 |

**不可妥协**：
- 条件判断逻辑在节点内部完成，管道编辑器只配置分支目标（不要求客户写判断代码）
- 条件分支的汇聚节点需明确标注（多条条件边指向同一节点时，编辑器自动检测是否合法）
- 一个节点最多出 1 条普通数据流边 + N 条条件边

### 4.1.2 节点降级路径

生产环境中节点可能失败——LLM 超时、向量库暂时不可用、重排序模型返回空。用户可为**任意节点**配置一条降级边（画布上以橙色虚线显示），定义主路径失败时的备选行为。

**可配置的降级策略**：

| 策略 | 行为 |
|------|------|
| **跳过该节点** | 将上游输出直传给下游，跳过失败节点 |
| **走备选节点** | 将数据路由到另一个同类型节点（如主重排序模型失败 → 走备选重排序模型） |
| **降级返回缓存** | 从语义缓存中取最近一次该管道的成功结果返回 |
| **中止并报错** | 不做降级，直接返回错误（默认行为） |

**不可妥协**：
- 降级边是全局能力——任意节点支持，不限于特定节点类型
- 降级发生时记录告警日志，写入执行追踪
- 降级触发频率超过阈值时自动告警（如"BM25 检索节点连续 10 次降级"）
- 编辑器在节点属性面板的"降级"选项卡中配置，不要求客户写降级逻辑代码

### 4.1.3 可复用节点组（复合节点）

用户常将固定的节点组合反复使用（如"术语标准化 → 混合检索 → 重排序"）。将常用组合保存为**复合节点**——拖一次等于部署一组节点。

```
复合节点: "标准医学检索组"
┌──────────────────────────┐
│  术语标准化 → 混合检索 → 重排序  │  ← 内部包含 3 个节点，参数已预设
└──────────────────────────┘

拖入管道后：
  → 展开态：显示内部的 3 个节点，可独立调整参数
  → 折叠态：显示为一个节点块，标注"标准医学检索组 │ 3 节点"
```

**不可妥协**：
- 用户可从任意节点组合创建复合节点（选中多个节点 → 右键 →"保存为复合节点"）
- 复合节点保存到用户个人的节点库，跨管道复用
- 修改复合节点的内部配置 → 不影响已部署的实例（实例是独立副本）
- 复合节点可在用户间共享（导出/导入 JSON）

### 4.2 管道发布：配置输出 URL

**为什么**：管道配置完成后，外部业务系统需要调用它。不能让每个调用方都记住管道 ID 和内部参数。

**目标**：

> 每条管道可**发布为一个自定义 URL 端点**，如 `POST /search/medical-consultation`。外部系统只需向这个 URL 发送查询文本，无需知道管道内部结构（有多少个域、用 BM25 还是向量检索、权重如何分配）。
>
> 管道 URL 可独立启用/停用、配置认证要求、速率限制、参数白名单。

```
管道编辑器（配置）              发布后的 URL（使用）
─────────────────              ─────────────────────
跨学科综合问诊管道 v3    →     POST /search/medical-consultation
法律尽调查询管道 v1      →     POST /search/legal-due-diligence
金融合规审查管道 v2      →     POST /search/finance-compliance
```

**不可妥协**：
- 调用方只通过 URL 调用，不感知管道内部结构
- 每个 URL 可独立配置认证、限流、启停
- 管道修改后发布 URL 保持不变（版本在内部切换）
- **权限过滤全局强制**：同一 URL 被不同角色用户调用时，返回结果受该用户权限约束（域裁剪 + 文档过滤）。调用方不能绕过权限系统
- URL 认证要求是额外的访问控制层（API Key / JWT），与角色权限是叠加关系（AND 逻辑）

## 五、RAG 评估：测试搜索管道效果

**为什么**：管道配置完成后，用户需要知道"这个配置的搜索效果到底好不好"。不能等到上线后发现 Hit Rate 低、答案不准。需要一个内建的评估机制，让用户在平台上就能测试和优化搜索管道。

**目标**：

> 提供内建的 RAG 评估模块。用户上传测试数据集（QA 对 + 相关文档标注），选择管道版本，运行评估。平台自动计算 Hit Rate、MRR、NDCG 等指标，结果按域、按查询类型分组展示。评估结果直接指向管道中的具体节点，指导参数调优。
>
> 形成"**配置 → 评估 → 调优 → 再评估**"的闭环。

```
配置管道 → [运行评估] → Hit Rate 低 → 增大 BM25 top_k
                │                          │
                └── 再次评估 ←── 调整参数 ←──┘
```

**评估指标**：Hit Rate、MRR、NDCG@K、答案准确率、域激活准确率、跨域覆盖率、冲突检测率、端到端延迟。

**权限在评估中的作用**：

- 评估数据集按租户隔离，按角色控制可见性（同知识库权限模型）
- 用户运行评估时，只能选择自己有权限的知识库和管道
- **评估结果按角色呈现差异**：同一管道用"管理员"身份和"普通医生"身份运行，指标可能不同——因为后者看到的知识库子集和文档子集更小。这不是 bug，是权限生效的证明
- 管道对比功能限制在同一角色视域内进行（苹果比苹果）

**不可妥协**：
- 评估必须在平台内完成，不依赖外部工具
- 评估结果必须指向具体节点和参数（"BM25 检索节点 top_k=10 时 Hit Rate 仅 0.65"）
- 支持管道对比：同一数据集上对比两个版本的指标差异
- 评估范围受评估者权限约束，不可绕过

## 六、搜索 API（对外统一接口）

**为什么**：管道配置完成并发布后，外部业务系统需要调用它。平台必须提供标准化的搜索 API，支持同步和流式两种响应模式，所有调用方无需感知管道内部结构。

**三种调用方式**：

| 方式 | URL 格式 | 适用场景 |
|------|---------|---------|
| **发布 URL** | `POST /search/{custom-path}` | 生产环境对外暴露，URL 简洁，隐藏内部细节 |
| **通用端点** | `POST /api/v1/search` | 测试、内部调用、需要动态切换管道 ID |
| **SSE 流式** | `POST /api/v1/search/stream` | 大模型生成答案时实时推送，用户不用等待完整响应 |

**不可妥协**：
- 三种方式均强制启用双层权限过滤
- SSE 流式搜索推送的内容与同步搜索结构一致，仅传输方式不同
- 响应中可包含 `filtered_domains` 字段，标注因权限被跳过的域（不暴露域的具体内容，仅说明"N 个域因权限未激活"）
- 调用方不直接操作 RAG 内部（不直接调向量库、不直接做分块），只通过 REST API

---

## 七、模块化改造范围：仅限 RAG 模块，调用方不限制技术

**为什么**：需要平台化改造的只是 RAG 相关的几个模块。这些模块是**管道型任务**，天然适合配置化为 DAG，适合做成通用平台。

**目标**：

> **RAG 平台**（`rag-platform/`）：独立部署系统，含后端 API + 前端管理界面。提供标准 REST API。
> **调用方**：不限制技术，HTTP 客户端即可。

**不可妥协**：
- RAG 平台是独立部署系统，`docker compose up` 一键启动
- 调用方不直接操作 RAG 内部（不直接调向量库、不直接做分块），只通过 REST API
- RAG 平台不限制调用方使用特定技术栈

---

## 八、技术选型：最低延迟 + 最佳体验

**为什么**：RAG 平台的核心竞争力是搜索延迟和用户体验。技术选型应以"最低延迟 + 最佳体验"为第一原则，不因语言偏好而限制性能上限。

**目标**：

> **选型原则**：Python / Java / Rust 均可使用，按场景选择最优方案。不做语言绑定，做性能绑定。
>
> **PipelineCompiler（编排引擎）**：Python 主体 + Rust 热点混合架构（见 [ADR-001](./adr/001-pipeline-compiler-orchestration-backend.md)）。编排框架和 23 个 I/O 密集型节点用 Python；5 个 CPU 密集型热点（MinHash 去重、RRF 融合、BM25 评分、PII 脱敏、文档分块）渐进式用 Rust + PyO3 重写。
>
> **节点执行器**：按节点特性选择语言——I/O 密集型节点（LLM 调用、向量检索）用 Python（生态优势）；CPU 密集型节点可用 Rust（PyO3 进程内调用，零跨语言开销）。
>
> **热路径优化**：先用纯 Python 跑通全部 28 个节点，Phase 8 后 profiling 识别热点再决定 Rust 重写范围。渐进式优化，不一次性重写。

**不可妥协**：
- 不引入 Kafka/RabbitMQ/服务网格等重型基础设施
- 新增组件必须有"不用它就无法解决的明确问题"作为理由
- 跨语言调用必须是进程内调用（PyO3 / JNI），禁止跨进程 RPC 增加延迟
- 技术选型必须有性能基准数据支撑，不凭感觉选型

## 优先级总则

1. **先通闭环，再做深度**：单域管道可运行 → 多域并行聚合可运行（含库级别权限过滤） → 知识库管理 → 评估调优 → 文档级别权限落地
2. **能力先继承再优化**：从 `backend/` 继承全部基础设施，确保可独立部署后，再逐步去业务化和优化
3. **权限内建于检索，不后加**：库级别和文档级别的权限过滤从第一天就嵌入检索流程，不是事后叠加层
4. **所有增强节点可选**：禁用词、敏感词、PII 脱敏等节点均按需使用，不拖入管道即跳过
5. **管道 = 产品**：管道编辑器不是开发工具，是客户管理员的生产工具——配置 → 评估 → 发布 → 监控，全流程在 UI 内完成
