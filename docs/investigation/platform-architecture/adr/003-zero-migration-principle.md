# ADR-003：零迁移原则

> 日期：2026-05-14
> 状态：已决定

## 背景

项目尚未上线，不存在历史生产数据或外部用户依赖。传统软件工程中的迁移策略（Alembic 迁移脚本、API 版本号、向后兼容层）在本项目中无适用场景。

## 决策

**零迁移原则**：所有变更直接覆盖旧实现，禁止保留向后兼容层、废弃标记、迁移脚本。

具体规则：

| 场景 | 行为 |
|------|------|
| 数据库表结构变更 | **直接修改 DDL**（`.ai/full_init_script_mysql57.sql`），不编写 Alembic 迁移脚本 |
| API 端点变更 | **直接替换**路由/参数/响应格式，不保留旧端点或版本号 |
| 前端路由/组件变更 | **直接替换**，不保留旧路由重定向 |
| 配置/提示词变更 | **直接覆盖**，不保留旧字段或降级逻辑 |
| 类/模块重构 | **直接删除**旧代码，不标记 `@deprecated` |
| 需求文档变更 | **直接覆盖**，冲突的旧文档删除（如 `search-enhancement-pipeline-design.md`） |

## 理由

1. **项目未上线**：数据库中的数据是开发测试数据，无迁移负担。
2. **减少复杂度**：每次变更都保留旧代码会导致代码库快速膨胀，且新旧逻辑交织增加 bug 密度。
3. **加速迭代**：去掉迁移脚本编写和维护成本，缩短变更周期。
4. **降低认知负荷**：开发者只需理解当前代码，不需要理解"这个字段为什么叫 v2"、"那条路由为什么跳转到新页面"。

## 例外

唯一例外：第三方 API 契约变更需确认外部依赖方已同步更新。例如，若前端发布 URL 的响应格式变更影响到已部署的外部调用方，需先协调升级。

## 后果

- DDL 变更后，需手动清理开发数据库中的旧表/旧列（`DROP TABLE IF EXISTS old_table`）
- CI/CD 不包含迁移脚本执行步骤
- 代码 review 中禁止出现 `@deprecated`、`v2` 后缀、`_legacy` 函数名
- 删除功能时需同时删除其测试、文档引用、API 端点注册
