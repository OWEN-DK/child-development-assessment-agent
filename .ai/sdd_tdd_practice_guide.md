# SDD+TDD 融合实践指南

> **文档定位**：本文档深入解析 SDD+TDD 融合实践的核心概念、全流程落地标准及避坑指南。基础工作流请参阅 `.ai/sdd_tdd_workflow.md`。

---

## 1. 核心理念

### 1.1 为什么需要 SDD + TDD 融合？

| 维度 | SDD（规范驱动开发） | TDD（测试驱动开发） | 融合价值 |
|------|-------------------|-------------------|---------|
| **核心目标** | 明确"做什么" | 验证"做对了" | 目标清晰 + 结果可验证 |
| **产出物** | 机器可读的规范文档 | 自动化测试用例 | 规范即测试，测试即文档 |
| **适用场景** | 复杂业务逻辑、多模块协作 | 单元功能、边界条件 | 全链路质量保障 |
| **人类角色** | 定义业务规则与验收标准 | 审查测试逻辑合理性 | 主导方向，AI 负责执行 |

### 1.2 第一性原则

1. **规范是唯一真理源**：所有代码、测试、文档必须与规范保持一致
2. **测试是规范的 executable 版本**：验收标准必须能直接转化为测试断言
3. **代码是最小实现**：只写让测试通过的代码，不添加规范外的逻辑

## 2. 全流程落地标准

### 2.1 阶段一：SDD 规范定义

**目标**：产出机器可读的结构化规范文档（`specs/xxx.md`）

**规范模板结构**：
```markdown
# [功能名称] 规范

## 1. 数据结构
- 字段名、类型、必填项、约束规则

## 2. 接口契约
- 请求/响应格式、错误码、边界条件

## 3. 业务规则
- 正常流程、异常场景、状态流转

## 4. 验收标准（AC）
- AC1: [可量化的验收条件]
- AC2: [可直接转化为测试断言]
```

**自查清单**：
- [ ] 数据结构定义清晰（类型、必填项、约束规则）
- [ ] 组件 Props/Events/接口契约明确
- [ ] 业务规则覆盖正常流程与异常场景
- [ ] 验收标准可量化、可直接转化为测试断言
- [ ] 禁止模糊描述（如"体验好"、"加载快"）
- [ ] 文档格式为机器可读的 Markdown + YAML/JSON

### 2.2 阶段二：TDD 测试先行（红阶段）

**目标**：基于规范生成测试，确认全部失败，建立验证基准

**执行步骤**：
1. 向 AI 输入完整规范，要求：仅生成测试文件，不生成业务实现
2. 人工校验测试逻辑，确认真实反映规范意图
3. 运行测试，**成功标志**：测试全部失败

**避坑指南**：
- ❌ 不要在测试中 mock 尚未实现的内部逻辑
- ❌ 不要跳过异常场景的测试覆盖
- ✅ 测试命名要清晰表达意图（如 `test_should_reject_invalid_email`）
- ✅ 使用参数化测试覆盖边界条件

### 2.3 阶段三：Coding 精准实现（绿阶段）

**目标**：编写最小代码集让测试通过

**执行步骤**：
1. 输入规范 + 失败测试，要求：仅实现最小逻辑
2. 运行测试，**成功标志**：测试全部通过
3. 重构优化，确保重构后测试仍通过

**避坑指南**：
- ❌ 不要添加规范外的"以防万一"逻辑
- ❌ 不要为了"优雅"而过度设计
- ✅ 代码必须严格匹配规范定义
- ✅ 重构前后必须运行测试验证

### 2.4 阶段四：集成与持续迭代

**循环推进**：新增/修改需求 → SDD 更新 → TDD 红 → Code 绿

**集成要求**：
- 规范检查、测试运行集成到 CI 流水线
- 每次提交必须符合规范、测试全量通过

## 3. 协同 Prompt 模板

### 3.1 生成测试用例（红阶段）

```text
角色：资深测试工程师
任务：根据以下 SDD 规范中的【验收标准】，生成{语言/框架}测试用例。
输入：{粘贴 SDD 规范完整片段}
要求：
1. 只生成测试代码，不生成任何业务实现代码
2. 100% 覆盖规范中所有的验收标准
3. 确保测试在无业务实现的场景下必然执行失败（Red 阶段）
4. 遵循对应测试框架的最佳实践，不耦合内部实现细节
```

### 3.2 生成业务实现（绿阶段）

```text
角色：资深开发工程师
任务：编写业务代码，使所有测试用例通过，同时严格符合 SDD 规范要求。
输入：
1. SDD 规范文档：{粘贴规范完整内容}
2. 失败的测试文件：{粘贴测试代码完整内容}
要求：
1. 只编写让所有测试通过所需的最小代码集，不添加任何规范外的冗余逻辑
2. 遵循{开发语言/框架}的行业最佳实践
3. 补充必要的类型定义与代码注释（全中文）
4. 严格匹配规范中定义的所有规则与约束
```

## 4. 常见陷阱与应对

| 陷阱 | 表现 | 应对策略 |
|------|------|---------|
| **规范模糊** | 验收标准无法转化为测试断言 | 退回 SDD 阶段，量化指标 |
| **测试过紧** | 测试耦合内部实现，重构即失败 | 测试只验证行为，不验证实现 |
| **代码过胖** | 实现了规范外的"额外功能" | 严格对照 AC，删除冗余 |
| **跳过红阶段** | 直接写代码再补测试 | 强制先运行测试确认失败 |
| **规范与代码不同步** | 修改代码未更新规范 | 变更必须先改规范，再改测试，最后改代码 |

## 5. 实战检查清单

### 每次功能开发前
- [ ] 规范文档已定义完整数据结构和接口契约
- [ ] 验收标准可量化、可直接转化为测试
- [ ] 测试文件已生成且全部失败（红阶段确认）

### 每次代码提交前
- [ ] 所有测试通过（绿阶段确认）
- [ ] 代码严格匹配规范，无冗余逻辑
- [ ] 代码注释全中文，类型定义完整
- [ ] 规范文档与代码保持同步

### 每次重构前
- [ ] 现有测试全量通过（建立基线）
- [ ] 重构后测试仍全量通过
- [ ] 规范文档未改变（仅优化实现）
